## 2. 用户应看到的整体关系

“工作安排”将目标、执行与自动化关联，但不混成一种任务：

| 对象 | 负责什么 | 不能误读成什么 |
|---|---|---|
| 待办 | 要达成的目标、来源、关联工作和完成依据 | 新建、到期或记下来不等于交给Agent执行 |
| 执行任务 | 一次具体工作及其会话、计划、产物、检查和结果 | 退出/结束不等于整个目标技术完成，更不等于用户验收 |
| 自动化规则 | 在明确范围与策略内，说明何时触发什么工作 | 保存、启用、到点、启动及各次结果不是同一事实 |

仍能直接新建Agent任务，不强迫先建待办；一次执行也不被定义成一个进程、
一轮对话或新的Run层级。人工和获准Agent使用同一份业务对象与来源记录，
不是两套彼此不同步的“个人待办/Agent待办”。关联不产生跨项目读取权。

用户只需看清：要做什么、为何会执行、在等什么、当前按哪份依据工作、
哪些结果已核实、还缺哪些检查，以及哪些动作需要自己决定。
本阶段不决定正式首页替代Q11默认all-tasks，也不冻结产品命名或导航。

## 3. Q51–Q67已确认决定

以下是摘要；持续设计原文及其历史“另议”边界见§8。
后续问题只推进其负责的原则，不倒写先前当时尚未批准的机制。

| 决定 | 已确认原则 | 保留的边界 |
|---|---|---|
| Q51 对象分层 | 待办、执行、规则关联但各有职责；保留每次结果；直接Agent任务保留 | 创建不即执行，结束不即验收，不选生产schema/Run协议 |
| Q52 同一套对象 | 人工与获准Agent共用对象，追溯发起者、来源任务和修改 | 创建/修改不授执行权，不扩大可读/可管范围 |
| Q53 明确交办 | 默认记录；明确交办可执行；可另开有范围的自动接单 | 自动接单和Full Access独立，不默认启用未来任务 |
| Q54 规则授权 | 每条接单规则由用户明确确认执行策略，覆盖内免重复确认 | 规则Full Access另授，不继承某次任务；监督/新技能人工同意不取消 |
| Q55 两种控制 | 暂停新启动与请求停止本规则在途工作分开，保全历史/成果 | 已发请求不等于已停止，不承诺回滚外部副作用，恢复须明确 |
| Q56 按目标完成 | 满足整条目标必需检查及适用监督才技术完成；用户验收另记 | 不要求用户逐项重复签字，也不代替用户要求的亲验 |
| Q57 范围可看懂 | 明确筛选、启用前预览、单项排除；覆盖内合条件新增可自动接 | 预览/匹配不是运行或授权，Agent不改标签绕过排除 |
| Q58 存量不偷跑 | 首次启用默认不接已有积压；可主动批量纳入旧待办 | 不重开已完成/待验收项；原执行/副作用未知先核实 |
| Q59 变更有依据 | 差异/影响先确认，默认用于新启动；未启动也重核，在途不静默换模型/API/目标 | Stop/撤权/硬限制优先于旧版；变更不自动补旧项或恢复暂停 |
| Q60 定时同原则 | 触发不同，复用逐规则授权、变更与执行控制；覆盖内不每次重问 | 保存/到点不授执行权，不强制每次先造待办 |
| Q61 漏跑不追赶 | 已核实错过且未启动默认跳过；可逐规则开启恢复后补一次当前检查 | 不冒充历史各期完成；在途/未知不当漏跑重放，逐期处理另议 |
| Q62 同规则不重叠 | 繁忙触发默认跳过；另可开结束后合并补一次，原占用安全收束后重核 | 不从Q61继承；手动/恢复不绕约束，不无限排队或恢复暂停 |
| Q63 冲突局部协调 | 不同入口的实际共享冲突轮流负责；安全独立工作并行 | 不抢占/强杀/删锁；未知先核实，不自动建worktree/克隆 |
| Q64 等待后重核 | 已有交办且允许等待，条件满足覆盖内自动继续；变化局部对齐 | 不盲套补丁/全项目重做，不复活跳过/暂停或新增重试权 |
| Q65 资源共用 | 用户明确可配置护栏；局部不绕项目/总额，委派/监督/重试等纳入且不重复算 | 预估/报告/未知分开；缺失不报零/精确账单，必需硬限不可执行如实受阻 |
| Q66 到限分类 | 并发/尝试用尽只挡新准入；在途执行边界到限挡扩张并请求安全收束 | 不打断最后一次合规尝试，不无限收尾/自扩额；未核实不报已停或监督通过 |
| Q67 补额≠续行 | 到限收束后默认等明确继续；可事先开范围自动续行或明确补额并继续 | 普通等待仍按Q64；不清零独立时长/重试，不重放未知操作或恢复用户Stop |

Q67还区分旧执行续行与未暂停规则的合法新触发：前者须有继续意图并核实
原执行/副作用，后者仍按原准入重核，不因旧执行到限一律冻结。
资源恢复只恢复该资源适用范围和周期的条件，不承诺外部CLI原地续跑、
无损检查点、恰好一次、瞬停或零超额。

## 4. 与既有监督、权限和原生边界衔接

- Q33技术核验与用户最终验收分开；Q34先核实原执行/副作用，保全成果，
  不盲重放；Q38只调整受影响工作与依赖，不默认重做整个项目。
- 启用U01时沿用阶段反思与独立治理，不为每条待办另加全套监督进程。
  主Agent、反思、治理可用不同API/模型，不因换角色漏算消耗或静默换在途配置。
  依赖接口待核对时不推进其联调，安全独立文档等仍可继续。
  本快照不改其既定职责、消息/升级规则或批准真实监督进程。
- Full Access只免有效覆盖内重复权限询问，不代替自动接单/定时启用，
  不改目标/审批/验收，不越过Stop、撤权、显式禁令、资源及宿主硬限制。
  模型想安装使用新技能仍须人工同意；样例选择不是真实安装许可。
- 真实共享业务owner仍在Rust core/host，SwiftUI只能经客户端API操作；
  样例内存owner只是虚构演示，不成为生产写入者或调度/权限引擎。
- SwiftUI＋苹果原生Liquid Glass、系统选择态、NativeSelection、语义色和
  辅助偏好不变；glass/classic、interactionMode、权限彼此独立。
- OMP原始交互PTY/TUI、managed-home及原生历史根边界不扩，
  不恢复rpc-ui，不读用户`~/.omp`；其他家族/自定义Agent身份不被简化。

## 6. Q68批准的阶段交付

先交本设计快照和独立执行MD；首批只规划**现有macOS App target内的
可交互离线原生审阅样例**。不是另建App/网页，不替换正式首页或主导航。

样例用可重置虚构内存演示五类关系：

1. 待办、执行、规则与来源；创建/运行/技术完成/用户验收分离。
2. 明确交办、范围/预览/排除/旧项批量纳入及规则执行策略。
3. 暂停/停止、未知事实与规则变更/在途依据。
4. 漏跑、繁忙跳过及两个独立“补一次”设置，用有限场景事件而非真实时钟。
5. 局部资源等待/独立工作、到限分类、计量完整性与补额后是否继续。

所有授权、运行、停止、补额、计量和检查结果始终标“离线示例”，不读写真实
项目/历史/待办/规则/账本/权限/凭据/配置/managed-home，不连接真实
Agent/API/MCP/PTY/host/反思治理或服务，不安装技能。
只允许有限fixture转换，不实施真实调度、权限、预算、恢复、持久化或生产DTO。

**不创建VM，也不以测试需要为由申请替代VM。** 本次仅文档交付；
后续经独立开工可实施与做已审查的无窗口检查。App、Preview、真实交互/
材质/键盘/AX运行验收仍NOT RUN/DEFERRED，不以编译或离屏装配冒充。
未来若另议真实UI，必须新的明确授权和政策审查，并仍遵守不创建VM要求。

## 7. 未决机制与监工拒绝线

以下未决定，不得为做样例顺手补全：

- 生产对象ID/状态、执行/会话/重试身份、存储schema、API/MCP工具schema、
  来源证据、防循环、去重/幂等与生产单写协议。
- 筛选语法、来源/后来纳入规则、存量/新增边界、预览时点、规则版本及
  在途配置/凭据分发、撤权传播、收束判据/期限和崩溃恢复。
- 时区/夏令时、时钟变化、休眠/后台驻留、恢复/漏跑判据、逐期补处理、
  公平性、等待期限/优先级、跨进程锁/租约/原子准入和四家族强制能力。
- 具体额度/默认周期、预留、计费归属、未知用量处理、控制资源、恢复期限、
  自动续行设置层级及无损恢复保证。
- 正式首页/工作安排导航、最终名称/布局、iOS业务接线和双商店适配。

监工应拒绝：用演示权限当真实授权、把用户Stop被动清掉、借补额无限重试、
把缺计量写成零、把缺监督写成通过、模拟已停止掩盖未知、以测试为由新建VM、
恢复UI或运行真实Agent、越白名单接生产服务/数据，以及用旧测试报告验收新代码。
