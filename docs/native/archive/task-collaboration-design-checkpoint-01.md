## 2. 用户想得到的协作体验

用户布置“做一个软件”等任务后，主Agent承担协调责任，把适合拆开的
编码、研究、验证等工作交给协作者，汇总真实成果、依赖与问题。
用户不必先管理一家AI公司，也不必亲自转发每段上下文或处理每次技术冲突。

核心不是“多开几个窗口”，而是能说明：

1. 谁在负责哪项工作，依据什么目标与版本，允许做什么。
2. 哪些工作可并行，哪些依赖未满足，哪里正在交接写入责任。
3. 哪些只是成员自报完成，哪些已有适用证据、可作为后续依据。
4. 出错后保留了什么、原执行是否真的停止、恢复影响哪些工作。

这是任务驱动的产品方向，不证明已有自动拆分器、完整依赖图、
强制权限边界、可靠消息或自动故障接管。

| Q32 | 独立工作并行；同一工作副本的同一文件/共享修改点同一时刻有一个明确写入负责人；主Agent协调交接、技术冲突、整合与验证 | 整个项目串行、不同文件必然独立、强制采用分支/worktree/锁 |

| Q34 | 保全成果、核实原执行与副作用后在原授权和预算内局部恢复；安全交接前不启动重叠替代写入；无关安全工作继续，覆盖内常规恢复不逐次询问 | 沉默等于已停止、盲目重放外部操作、无限重试、自动回滚项目/撤销副作用 |

## 4. 一条协作工作线怎样衔接

以下顺序解释产品语义，**不是已批准的状态机或调度协议**。

### 4.1 组织工作与交接上下文

主Agent根据已知要求起草工作包；用户可查看修订，不要求每次从空表手填。
关键依据标明版本/修订，必要资料在获准范围内按需展开，不倾倒全部会话、
项目资料或凭据。缺标准、权限、依赖等条件时明示缺口，不能自创验收要求。

工作包是有边界的交接约定，不是新增权限；写了“禁写”不证明系统已隔离。
收到工作包、回复同意、投递ACK或终端已创建，都不证明允许启动、
完整上下文已被模型消费或成员已产出正确成果。

### 4.2 授权配置与实际权限

用户要求的Full Access不能只是改名后继续逐项询问：
**已覆盖的任务操作和委派免掉相同的App逐次人工权限确认**，
不能把同一问题转移到每个协作者身上。
默认作用域是当前任务，不自动影响其他任务；这不决定恢复后保留行为、
更广的默认值或高影响动作的具体覆盖集。

协作者继承的是人工确认策略，实际能力仍为工作包所需且不超委派方有效授权。
不会默认复制主Agent全部权限/密钥；U01监督角色仍只读获准证据。
尚未确定如何表示、交付、强制这些能力，也未证明四类执行器均支持免提示执行。

Q33已确认：免人工确认不免成果核验或适用U01监督，不等于最终验收。
其余Full Access整体边界仍需细化，例如具体动作覆盖、真实系统能力、
显式禁令、硬额度、Stop/撤回与在途影响；不能把讨论建议一并记成批准，
也不能从缺少机制设计推出已经获得额外权限。

### 4.3 并行与共享修改点

主Agent在有效授权内协调常规交接、技术冲突和整合，不把每个冲突都交用户。
独立工作可以并行；同一副本的共享修改点有当期写入负责人。
不同路径若依赖同一接口、配置或测试资源，仍需核对实际依赖和影响。

没有决定使用锁、租约、独立副本还是其他方案；不强制每名成员建分支/
worktree，副本也不是权限沙箱。声明负责人不证明旧写入已经被强制隔离。

### 4.4 交付、核验与依赖放行

成员交具体产物/版本、差异、实际检查及未运行/受阻项。
主Agent对照工作包核对真实成果，不能只转述成员总结。
已有充分且适用的证据不必无差别重跑；缺必需证据或检查失败仍待核验/修正。
需整合时核对整合后版本，不能用旧版或孤立副本的结果冒充当前证据。

满足既定要求及适用监督门槛后，才作为已核验的依赖输入。
技术核验不是用户最终验收，不要求用户逐项点击“批准完成”。
执行进程退出、工作项核验与整个任务最终验收也不是同一个状态。

### 4.5 故障与局部恢复

保留已交付/部分成果、证据和失败事实，先核对哪些仍适用。
区分已确认失败、受阻与执行状态未知；无消息或超时不证明进程、
后台子进程或外部调用已经停止，不伪报已取消/已恢复。

主Agent在原授权与预算内组织有限重试、拆分或接手。涉及同一共享修改点，
先确认原写入已停止或被可靠隔离，并安全交接，再启动替代写入。
更新调度记录不能单独充当停止证据。

外部操作结果须核实：已完成或结果不明时不盲目重放。
恢复文件/任务记录不等于撤销数据库、网络等副作用。
只约束受影响工作包和依赖，安全独立工作继续；
Full Access覆盖内的常规恢复不重复询问。
缺授权/凭据或需改目标/验收、超出现有资源边界时明确受阻，
不靠无限重试或擅改权限绕过。

故障检测、重试数值与强制交接机制仍未定，本文不保证自动failover。

## 5. 与U01三角色监督的关系

协作成员不固定成主执行/反思/治理三人。
主Agent的协调身份不把治理者变成默认项目经理，
也不为每名协作者强制新增一整套监督进程。

启用U01时，继续执行其既定规则：

- 主执行者在授权内写入/执行；反思与治理只读获准证据并提出意见。
  角色可使用不同API/模型；这不是本轮已验证的兼容结论。
- 每编码阶段经反思及既定验证后关闭，待核对/整改只约束受影响依赖，
  安全独立工作继续。治理须及时、独立进程复审。
- 普通阶段满足Q21后，不因治理单独待审新增逐阶段签字；
  工具候选启用仍须必要治理评审与受保护验证，待审不算通过。
- 实质争议按Q24举证复审/升级用户；迟到漏检按Q25留史、局部重开并复核
  实际受影响依赖。协调核验不能替代这套监督。
- 监督API故障不算通过，不静默换模型或用主执行者自审替代。
  工具版本回退不是项目回滚或外部副作用撤销。

这些规则见 `task-evolution-design-checkpoint-01.md` 版本0.2；
真实引擎仍未获批。`task-evolution-review-stage-01.md` 版本1.0只覆盖
Q26独立离线样例，本快照不增加其文件、场景或验收要求，
也不代表本线程已审查通过外部执行者的产品改动。

## 6. 可用于审查设计的场景

下列用于核对原则是否表达正确，**不是已执行测试**；
Q35样例的具体场景与验收以独立执行包为准，不将本表当作完整执行协议。

| 场景 | 应体现的原则 |
|---|---|
| 用户要求开发软件 | 无须先建公司；主Agent协调，按需组合编码/研究/验证成员 |
| 登录接口尚待核验 | 不推进依赖接口的联调；不依赖它且无冲突的文档工作可继续 |
| 两成员都要改同一接口 | 同副本共享修改点有明确当期写入负责人，协调安全交接；不全项目停摆 |
| 成员称测试通过但未给适用证据 | 保持待核验，核对实际产物/版本和必需证据，而非直接完成依赖 |
| Full Access覆盖内委派和常规恢复 | 不向用户重复同一权限确认；仍核验交付、保留适用监督 |
| 成员无消息，进程状态未知 | 不直接判停或启动重叠替代写入；核实原执行并保留成果 |
| 发起外部写操作后结果未知 | 不当作未发生而重放；恢复记录不宣称副作用已撤销 |
