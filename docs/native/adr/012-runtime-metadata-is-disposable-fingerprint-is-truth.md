# ADR-012：`runtime.json` 是可丢弃状态；跨 writer 的真相是内容指纹，不是计数器

- 状态：**accepted（用户在 P2-02 门禁第三轮 Q17/Q19/Q23 拍板，2026-09-22）**
- 日期：2026-09-22
- 关联：ADR-010、ADR-011、`core/crates/aeroric-core/src/storage/runtime.rs`、`MIGRATION_PLAN.md` INV-03、Task P2-03/P2-04/P2-05/P3-06（实现落点）、`docs/native/baseline.md`（数据目录文件清单，本 ADR 要求新增）

## 背景：revision 很容易被赋予它给不出的保证

`runtime.json` 记 `schema/epoch/revision`，`bump_revision` 让计数器单调上升。但计数器只在**参与它的 writer 之间**有意义：P2-05 之前产品的主写入者仍是旧客户端，它既不取 lease 也不碰 revision；人工把 `projects.json` 换回旧内容同样不会让计数器后退。于是"revision 更高"并不等价于"数据更新"。同时 `runtime.json` 是新增文件，旧客户端从未读过它（已 grep 确认），因此它的丢失或不存在**不能**让数据变得不可读写。

## 决策

1. **`runtime.json` 是核心独占、可丢弃状态（Q23）**：缺失即以 `revision: 0` 重建，不影响任何用户数据；它只描述"谁在写、写到哪一步"。配套两件事：
   - `docs/native/baseline.md` 新增一张**数据目录文件清单**，逐文件标注「共享（旧客户端读写）/ 核心独占 / 外部只读」——今天这张表根本不存在，而 `rollback.md` 已经要求移交前备份真实 `~/.aeroric`。
   - 门禁 case 断言 `src-tauri` 里不出现 `runtime.json` 的读取，把"旧客户端忽略它"从假设变成实测。
2. **跨 writer 的检测靠内容指纹，不靠计数器（Q19）**：每个受管文件在 `runtime.json` 里记 `(sha256, size)`；写入前发现磁盘上的内容不是"我上次写下的那一份"，即返回 `REVISION_CONFLICT`，**绝不静默覆盖**。因此：
   - revision 的职责被明确为"检测同一目录内的并发覆盖"，不承担"数据新旧"的判断。
   - 旧客户端仍持写入权的那段迁移窗口里，core 侧 writer 常常会被判为冲突——**这是想要的效果而不是噪声**：那正是"两个 writer 在动同一个目录"的信号，也是 Action 5"不得并行启用两套 writer"第一次拥有机械执行。
   - 指纹字段与实现同批进入 P2-03/P2-04，并同步 bump `RUNTIME_SCHEMA_VERSION`（`deny_unknown_fields` 的代价正是为此准备的：未知键说明有别的写者，不说明可以猜）。
3. **机制与语义分开记账（Q17）**：P2-02 对自己拥有的部分负责（路径、注入、锁、原子写、恢复），可以 accepted；"revision 语义生效"作为**显式阻塞项**下传 P2-03/P2-04，且两者的验收原文各自要求一条反例（两个 writer 争同一目录被拒、落后写入被拒且不静默覆盖）。INV-03 在 P2-05 移交完成前不得宣布全局成立。

## 后果

- 任何"`runtime.json` 不在就说不出话"的设计都是错的：它可以被安全删除。写代码的人必须知道这一点，否则会把计数器当成真相。
- 指纹要覆盖的文件集合必须与「共享」清单一致，否则漏一个文件等于给那个文件开了静默覆盖的后门——这条清单本身应由门禁比对，而不是靠注释。
- 人工恢复（旧内容写回）会被指纹判为冲突，要求调用方重读再改写。这是有意的：恢复动作发生在核心之外，核心只有先看见它，才可能不在它之上继续写。
