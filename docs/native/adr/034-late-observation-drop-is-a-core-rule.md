# ADR-034：迟到观察丢弃是 core 的一条规则，不是宿主发射点的局部习惯

- 状态：已接受（Task P2-05 门禁，Q63 —— 用户拍板，采纳推荐）。
- 日期：2026-09-24
- 相关：ADR-023（core 唯一发射者）、ADR-033（移交面实测 28 处、一次性全交）、ADR-025（存活代寻址）、ADR-018（被截断的运行要先确认才能续跑）

## 背景

`is_task_active` 这道抑制今天只覆盖 28 个发射点中的 **3 处**，全部来自转录观察器：

| 位置 | 所在函数 | 发射的状态 |
| --- | --- | --- |
| `session.rs:517` | `sync_waiting_for_user()`（codex 转录观察） | `input_required` |
| `session.rs:650` | `process_claude_session_line()`（claude 转录观察） | `input_required` |
| `session.rs:668` | `process_claude_session_line()` | `running` |

它挡的是这一类事故：观察器线程比任务生命周期活得更久（codex/claude 的 watcher 有各自的轮询与
lazy-attach 期限），进程已经退出、卡片已经落成 `done`/`failed` 之后，一条迟到的转录行仍会想把状态
改回 `running`/`input_required` —— 用户看到的就是"一张已经关掉的卡片又开始转"。

其余 25 处（启动、退出、取消、手动完成、SSH/WSL/DSH 的状态机）今天**无条件发射**。所以
"哪些事件被抑制"不是一条事件级策略，而是 3 个调用点上的局部习惯。

ADR-033 决定这 28 处一次性全交 core。那时这道抑制必须有归属，三种可能里：

- **留在宿主**（sink 之前过滤）：逐字节等价、改动最小，但"该不该让用户看到这条状态"这个决定权
  仍在宿主。ADR-023 就只做到"只剩一个 `.emit` 调用点"，而不是"只剩一个做决定的人"；Swift 客户端
  将来要自己把这道判断重做一遍，两个宿主各持一半语义。
- **取消抑制**：最总括，但那 3 处会出现今天没有的状态复活，属于在"移交发射面"这一次改动里
  夹带用户可见的行为变更。
- **进 core 观察通道**：唯一同时做到"行为逐处不变"和"决定权真的收口"的选项。

## 决策

1. **抑制成为 core 运行时观察通道上的一条规则**，语义定形为：
   **来自运行时观察（转录 watcher / hook / 退出边）的状态变更，若该任务在本进程已无存活代，
   则丢弃，不改记录也不发事件。**
   落点是 `TaskRuntimeObserver` → `TaskService::observe` 这一侧，用 core 已有的
   `is_run_live(task_id, generation)` 判定，结果以已有的 `EventOutcome::Dropped(&'static str)`
   回报——**不新增端口方法，也不新增状态词**（九值词表 v1 冻结）。
2. **规则的边界就是上面那三处的来源类型**：转录与 hook 观察。启动/退出/取消/手动完成/DSH 状态机
   这些"宿主主动告知的变化"不在其列，它们今天无条件发射，移交后仍然无条件。
   任何扩大这条规则覆盖面的改动，都需要新的 ADR 和一处用户可见行为的论证，不能顺手加。
3. **可见性判断从宿主消失，但 `is_task_active` 本身不能删**。实测它有 4 个读取点，只有
   `session.rs:70` 是"要不要让用户看到这条"；另外 3 个是生命周期用途——`session.rs:322` 与
   `:603` 是两个观察器线程的循环继续条件，`:2217` 是一条流程守卫。删的只是第 70 行那一处的
   **语义角色**（连同它下面那 3 个发射点），函数保留给循环与守卫使用。
   把它一并删掉是一个看起来合理但会改坏观察器退出的错，所以这里写明。
4. **可核对**：这条规则要有一条 core 侧用例直接构造"任务已无存活代 + 来一条迟到观察"，断言
   `Dropped` 且记录与事件都没动；再有一条反向用例断言"仍有存活代时同样的观察必须生效"，
   否则规则可以在什么都不拦的情况下全绿。

## 后果

- 28 处移交完成后，`task-status` 与 `task-session` 的 `emitters` 都等于 1，且**唯一做决定的地方是 core**。
- 迟到观察的保护强度**不降反升**：今天它只管 codex/claude 的 3 个点，规则化以后所有走观察通道的
  来源（含 DSH、hook、退出边）都自动受同一道保护，而它们的可见性判定不会各写一遍。
- 前提是 ADR-033 里那条 DSH 观察通道：DSH 的状态必须先变成"观察"，这条规则才罩得到它。
- 一个已知的实现风险要留给实现步：`generation` 粒度。今天 `is_task_active` 问的是"这个 id 有没有
  任意存活代"（`has_live_run`），不是"这一代还活着吗"。规则若按代判定，同任务双开时迟到的老代
  观察会被丢，而今天它照样会发——**必须按"任意存活代"判定才能与现状等价**（ADR-025 的存活判断
  本来就是这个口径）。

## 落实（2026-09-24，与本 ADR 同批提交）

规则落在 `TaskService::observe` 里，位置是**算出待发状态之后、折叠与写表之前**：

```
若  incoming 状态非终态  且  当前行的状态是终态  →  EventOutcome::Dropped("task already settled")
```

三点必须写下来，因为它们都不是显然的：

1. **原有的陈旧代检查覆盖不到这个场景**。`observe` 开头已有
   `seen < current && !is_run_live(..)` 的丢弃，但迟到的转录行带的正是**刚结算那一代**的
   `generation`（`seen == current`），前半条件直接为假，所以放行。这一点是先写测试、
   看它**红**了才确认的（`Applied { status: InputRequired, changed: true }` 把已 `done`
   的行改回活），不是读代码读出来的。
2. **没有放进 `should_ignore_transition`**。那张表与客户端 `applyTaskStatusTransition` 逐字对齐
   （parity 门禁在管），而客户端**没有**这条规则——因为它从来收不到这些事件，抑制发生在宿主。
   把规则塞进转移表会制造一处"与旧客户端有意分歧"，而这条分歧的正确落点是观察准入，不是转移语义。
3. **一处命名的不等价**（不是悄悄改）：宿主当年问的是"这个任务还有没有活着的代"，
   本规则问的是"这一行是不是已经终态"。二者在**取消窗口**里不同：行已 `cancelled` 而进程尚未死透时，
   旧行为会让迟到的 `running` 通过并把卡片重新点亮，本规则把它丢弃。方向是更严格，
   且那个闪动不是功能；但因为它确实不等价，所以写在这里而不是只写在代码注释里。

配套：`tasks-status-machine-rust` 的地板 27 → **28**，新用例一正一反（活着的运行必须生效、
已结算的运行必须丢弃）+ 两条"未写盘"断言（`changed == false` 与指纹逐字节不变），
防止规则在什么都不拦的情况下全绿。可失败性用 `if false` 变异验证：关掉规则立即红，
按 sha256 逐字节还原。

## 更正（2026-09-24，ADR-035 决策 6 —— 本 ADR 的落实 §3 作废）

落实时把判据写成"这一行是不是终态"，覆盖面比本 ADR 决策 2 允许的范围宽（决策 2 明写规则的边界是
"转录与 hook 观察"，启动/退出/取消/手动完成/DSH 不在其列）。判据改回**本 ADR 后果最后一条本来就要的口径**：
`live_for(task_id)` 为空（这个任务在本进程已无任何存活代）才丢弃。

三点后果，都是往等价方向走：

1. 事故仍然挡住——进程退出后 claim 已结算，迟到的转录行到达时无存活代，照旧 `Dropped`。
2. **落实 §3 那条"已声明的取消窗口不等价"自动消失**——取消时 claim 还开着，存活代非空，
   迟到的 `running` 通过，与今天一致。不再需要"更严格方向"的豁免。
3. 启动时那条 `running` 不会被自己的规则挡掉——`start`/`resume` 先占 claim 再拉起进程，
   存活代非空。这一条是判据必须按"任意存活代"而不是"这一行是否终态"的真正原因：
   后者会让"在一张已 `done` 的卡片上再跑一次"这条正常路径变成静默不发。
