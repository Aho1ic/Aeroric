# ADR-025：只带 taskId 的请求——资源跟最新一代，取消打全部在飞代

- 状态：已接受（Task P2-05 门禁，Q52）
- 日期：2026-09-23
- 相关：ADR-017（同任务允许多代在飞）、ADR-020（运行身份唯一化为 core 的 per-task generation）、ADR-018（截断运行需确认）

## 背景

ADR-020 把 `TaskManager` 的容器改成 `(task_id, generation)` 键之后，留下一个必须先回答的问题：**旧客户端的所有入口都只有 `taskId`**。事实核对结果：

- v1 契约 `contracts/native/v1/methods.schema.json` 钉的是**方法名、别名、服务归属**，方法条目里**没有参数形状**（`$defs.method.properties` 为空）。所以技术上可以给命令加 `generation` 参数而不违反 ADR-009 的严格版本相等——但旧 React 客户端**没有任何"选代"的界面**，加参数等于让它传一个它无法选择的值。
- `remote/events_bridge.rs:13` 只转发事件名，远程客户端同样只认 taskId。

也就是说"哪一代"这个问题必须由宿主回答，不能推给调用方。

## 决策

按操作的性质分两条规则，**两条都要能机械断言**：

1. **资源型操作**（向进程写输入、resize pty、会话挂接/收养、启动输入信号的投递）寻址**该任务已注册的最大 generation**，即"最新一代"。
2. **意图型操作**（`cancel`、手动完成）作用于**该任务全部在飞代**。

## 理由与被否方案

- "一律只寻址最大代"（含取消）被否：那会让用户点完取消后仍有一代在跑，与 ADR-017 "另有代在飞就不落终态"的意图正面冲突，且没有任何界面能解释"还有一代活着"。
- "多代在飞时直接拒绝 task_id-only 请求"被否：歧义确实显式化了，但旧 GUI 会突然冒出按不动的按钮，而它本来就选不了代。
- "给契约加 generation 参数"被否，理由见背景。

## 后果

- "最新一代"需要一个可断言的定义：**已注册**的最大 generation，不是"core 账本里的计数器当前值"。两者在没有运行时会相等，但在"上一代刚退出、下一代还没起"的窗口里不等——用它做寻址会指向一个不存在的运行。
- 老一代在旧 GUI 里**继续跑但不再被寻址**：它的终端输出仍走 `OutputSink::Channel` 旁路，只是不再有输入通道。这是旧客户端的能力边界，不是 core 的状态错误；新宿主（P4/P5）按 generation 寻址，不受此限。
- 取消打全部在飞代意味着 `cancel` 必须能枚举某任务的所有代句柄——这条能力反过来约束 ADR-020 的容器形态：只存"当前代"的写法（单值 map）不满足它，必须能按任务聚合。
