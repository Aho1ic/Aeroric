# ADR-019：配置切换与所有写路径都不是"乐观写"，失败即无副作用

- 状态：已接受（Task P2-04 门禁，实现期自证 —— 反例 M7 与切换测试各抓一次）
- 日期：2026-09-23
- 相关：ADR-015（写入基线）、ADR-017（重试身份）、P2-04 Action 2（"配置切换失败回滚"）

## 背景

`src/state/app/taskSwitch.ts:405-435` 的写法是：先 `setTasks(committed)` 并排入保存队列，`await flush` 失败后再 `setTasks(rollbackTaskMutation(...))`。这是**乐观写**：内存里先当它成功了，落盘失败再撤。撤的时候必须逐字段判断"这个字段是不是我改的、现在还是不是我改的那个值"，否则会把期间迟到 hook 写进来的东西抹掉——那段字段级回滚逻辑（`rollbackTaskMutation`）就是为此存在。

core 的模型不是这样：每次变更都是 `load → 改 → commit`，commit 要么整份写下去、要么因基线不符而**根本没写**。于是"失败要回滚什么"这个问题在 core 里为空：磁盘上从未出现需要撤销的中间态。

## 决策

1. **core 不做乐观写**。`switch_config`（以及 `start`/`resume`）的失败路径只做三件事：释放认领、把运行号还给计数器、把错误交回调用者；不写任务文件、不起进程、不推进 revision。
2. `reducer::rollback_mutation` 与 `reducer::merge_changed_session_fields` 仍然移植并有 parity/单测覆盖，但**它们的用户是宿主**：旧客户端与新前端各自持有一份乐观列表，撤销发生在它们那一侧。P2-05 的 adapter 要按 ADR-015 的基线把"宿主视图 vs 权威快照"对账，而不是等 core 代替它回滚。
3. 远程通道限制（附件、worktree）从提交处理器移进服务层：`taskLifecycle.ts:283-296` 现在仍在 UI 里挡，但那只挡住表单；core 的 `start` 若收到装不下的载荷，必须在任何副作用之前拒绝。

## 后果

- "配置切换失败回滚"这条验收以**更强的形状**成立：不是"失败后能回滚"，而是"失败时不曾发生"。反例测试断言三件事同时成立——被拒的切换不写 revision、不起进程、把别人的旁路写留在原处。
- 宿主侧仍需字段级回滚，因此这两个端口都要在 P2-05 被真正接到：core 的权威快照 + `expected_revision`，宿主的乐观视图 + `rollback_mutation`。缺任何一半都会退化成"谁最后写谁赢"。
- 释放认领时把运行号一并退回，是为了守住"事件属于哪一代"的判断力：跳号会让一个从未发生过的运行看起来可能发生过。
