# ADR-010：数据目录的「可写入资格」分级——网络卷拒绝当 writer，云同步根允许但必须可见

- 状态：**accepted（用户在 P2-02 门禁第三轮 Q14～Q16/Q21/Q24～Q26 拍板，2026-09-22）**
- 日期：2026-09-22
- 关联：`MIGRATION_PLAN.md` INV-03（一个数据目录一个业务 writer）、`core/crates/aeroric-core/src/storage_lock.rs`、`paths.rs`（`--data-dir` 见 P3-07）、ADR-009（能力由 host 声明，不由环境推断）、ADR-011（拒绝对外长什么样）、ADR-008（detail 白名单闭合）

## 背景：锁只在它真正被支持的文件系统上才是锁

`DataDirectoryLease` 用 `File::try_lock`（POSIX 记录锁 / Windows 区域锁）把"谁在写这个目录"交给 OS，本机 APFS 上已用**两个独立进程**实测过互斥与死持有者自动释放。但同一段代码放到别的文件系统上语义就变了：

- **NFS / SMB / FUSE**：`flock`/记录锁是客户端相关实现，可能由 `lockd` 代理、可能因挂载参数被静默降级成"永远成功"。锁失败静默变成功，正是 INV-03 最坏的失效模式——两个 writer 都以为自己独占。
- **iCloud Drive / OneDrive / Dropbox 这类同步根**：文件**确实在本地盘**上，`statfs` 看就是本地卷，锁也真的有效；风险不在本机双写，而在**跨机合并**——同一目录在两台机器上各自被写，同步引擎自己决定谁赢。锁管不到，也不该假装管得到。
- 事实核对：旧客户端**没有任何**这类检测（`src-tauri` 里的 OneDrive/Dropbox 只是 opendal 存储后端，与数据目录无关），所以它今天在任何文件系统上都照样写。本 ADR 不是"恢复旧行为"，是给新核心定资格。
- 默认目录在用户 Home 下（`~/.aeroric`），而 P3-07 的 `--data-dir` 允许用户把它搬到任何路径，所以这条边界必须按"目录所在位置"判定，而不是按默认路径假设。

## 决策

1. **分级，不一刀切**：
   - 数据目录位于**非本地卷**（NFS/SMB/FUSE 等记录锁语义不保证的挂载）→ **拒绝取得 writer 权限**，返回专用错误（`LeaseError::UnsupportedLocation`），宿主/CLI 必须停下来报错。
   - 位于**已知云同步根**（本地卷 + 后台同步，如 iCloud Drive 的 `Library/Mobile Documents`、OneDrive 目录）→ **允许写**，但把这一事实记进 `runtime.json`（`volumeKind`）并要求宿主发出一次可见告警。
2. **不提供绕过开关**。理由：一个"我确认锁不可靠但仍要写"的选项等于把这条规则变成建议；真需要搬到网络盘的用户，正确做法是把 `--data-dir` 指回本地盘，而不是让产品在他不知情时丢数据。这与 ADR-008 关白名单是同一条纪律：拒绝的路径不留逃生门，否则拒绝不成立。
3. **判定手段下沉为端口，实现在 adapter（Q15）**：core 只拥有 `VolumeKind{Local, CloudSyncedRoot, NonLocal, Unknown}`、分级判定函数与云同步根前缀表（可注入）；真实 `statvfs`/`getmntinfo`/`GetDriveType` 由 adapter 用它**已有**的 `libc`/`windows-sys` 实现（`src-tauri/Cargo.toml:41,122`）。这样 core 保持零平台 FFI 依赖（P2-02 至今的 5 依赖不变），而"探针没接线"变成一个可被门禁看见的缺失，不是一份复制两遍的规则。
4. **`Unknown` 等于不可写（Q16，fail-closed）**：探针未接、OS 不支持、卷信息读不到，一律按资格不足拒绝。不允许"看起来不像网络盘所以放行"这种沉默推断——那正是本 ADR 要消除的失效模式。
5. **私有权限是资格的一部分（Q21）**：unix 侧 core 自己保证（新建即 0600、目录 0700，已实测）；Windows 侧由 adapter 回执（复刻 `src-tauri/src/storage.rs:284-288 / 743-745` 的继承 ACE 与显式 ACE 语义）后才能当 writer。**没有回执 = 不可写**，因为漏接线的后果是"agent token 与会话转录在别人也能读的目录里"，那是静默的隐私回归。
6. **资格检查是 `acquire` 的前置，不是移交任务的事（Q24）**：本 ADR accepted 的那一刻起，"任何文件系统都能拿到 writer"的实现就不允许存在。真实探针由 P2-05/P3-06 接，但它们的验收第一条就是"探针与权限回执已实现且有反例"——接不上那个任务自己就是红的。
7. **持有不等于一直持有（Q25）**：`acquire` 记下锁文件的 `(dev, ino)`（unix 由 std 元数据取得）；每次写入事务前重验——文件消失或 inode 变化即**停止写入并报错**，不自动重拿、不默默覆盖（此刻可能已有别人写过）。Windows 无稳定的 std 等价 API，因此该端**降级为只查存在**，并且这一差异必须写进代码注释、本 ADR 与门禁说明，**不得假装两端一致**。
8. **清理遗留临时文件的权力跟着 lease 走（Q26）**：只有刚取得 lease 的 writer 允许扫一次 `.<name>.<pid>-<ns>.tmp`（阈值 24h），并把删除清单返回给调用方（进事件/日志）。非 writer 永不扫描——删文件是丢数据最短的路径，它必须和"我是这个目录唯一的写者"绑在一起。

## 备选与被否决的理由

- **一律拒绝（含云同步根）**：最保守，但会硬挡真实用户（企业 Linux 的 NFS Home、把 Home 重定向到 OneDrive 的 Windows 机器），而他们真正需要的是"别把管理目录放这儿"的提示，不是不可用；且路径前缀启发式必然误伤。
- **只记文档不改行为**：与今天的旧客户端一致、零回归风险，但那样 INV-03 就成了"在本地盘上成立"的空话，而新核心是唯一承诺这条不变量的组件——写了不强制，等于没写。

## 后果

- `LeaseError` 变宽（新变体），`CoreContext::acquire` 的失败分支从"锁被占"扩展到"这里不该当 writer"，UI/CLI 文案要区分这两类（前者是"关掉另一个 Aeroric"，后者是"把数据目录搬回本地盘"）。
- 需要在门禁里给出**可判定**的边界：网络卷检测在 CI 上无法真跑，所以判定函数必须能被注入/伪卷名单测（同 ADR-006/007 的做法：规则进工件或进断言，不靠评审者眼力）。
- 回滚不需要动用户数据：本决策只影响"能不能开始写"，不改任何已存在文件的格式。
- `acquire` 的签名变宽（要接受探针结果与权限回执），因此 core 侧每个 writer 构造点都必须显式表态；测试用 fake 注入，包括 `NonLocal` 与 `Unknown` 两个反例——**没有 fake 就编译不过**，这是"漏接线"的机械下限。
- 身份重验与清理都需要新的反例：伪造一次"锁文件被删后重建"必须让写入停下；非 writer 调用清理必须被拒（或根本不存在入口）。CI 上真跑不了 NFS，所以判定函数必须以注入的卷清单单测，而不是靠评审者眼力（同 ADR-006/007 的做法）。
- 本 ADR 的 fail-closed 与 P2-02 Action 5"不能提前禁用旧保存路径导致 GUI 丢写"不冲突：旧客户端今天不取 lease、不读 `runtime.json`、也不经过 core 的资格检查，它照旧写它的；被关掉的是"新核心在不该写的地方开始写"。
