# ADR-026：core 拒绝写入时分两类——元数据重放一次，状态 op 一律报错

- 状态：已接受（Task P2-05 门禁，Q53）
- 日期：2026-09-23
- 相关：ADR-011（存储拒绝映射到冻结错误码，`StaleWrite → REVISION_CONFLICT`）、ADR-015（覆盖基线）、ADR-017（重试身份＝operation key）、ADR-019（core 不做乐观写）、ADR-022（队列只排队意图）

## 背景

移交 writer 之前，这条路径在旧客户端**不存在**：`save_project_tasks` 是全量覆盖，"谁最后写谁赢"，所以永远不会"被拒"。移交之后会出现一种旧 GUI 从未处理过的返回：core 依据 ADR-015 判定"我要覆盖的字节已经不是 core 上次发布的那份"，于是**拒绝写入**并回 `REVISION_CONFLICT`。

宿主持有一份乐观列表（ADR-019 决策 2），因此"被拒之后界面显示什么"不是理论问题：不处理就会让界面停在一个磁盘上从未存在过的状态。

## 决策

按 op 是否可能产生进程副作用分两类：

1. **元数据类**（重命名、pin、star、归档/取消归档等不产生进程副作用的意图）：冲突时**自动重放一次**——重新载入权威快照，把同一条意图再应用一次并提交；仍失败才报错。
2. **状态机类**（`start`、`resume`、`complete`、`cancel`、`switch_config` 等可能起进程或改变运行状态的意图）：冲突时**不自动重放**，直接报错并刷新权威快照。

## 与被否方案的关系

- 全类自动重放一次（我原本的推荐）被否：operation key 确实能保证"重放不会多起一个进程"（ADR-017），但用户明确选择**对起进程的操作永不自动再来一次**，把决定权留在人。代价是多一条失败路径，而不是正确性。
- 全类只报错不重放也被否：那会让"把某任务标成已归档"这种毫无歧义的意图因为一次无关的旁路写而丢失，用户要重做一遍。
- 这条分类与 ADR-025 的资源/意图二分**不是同一刀**：ADR-025 分的是"寻址哪一代"，本 ADR 分的是"能不能自动重试"。归档在 ADR-025 里是意图型（打全部在飞代无关，它根本不开代），在本 ADR 里是元数据型（可重放）。

## 后果

- "重放一次"必须真的只有一次：重放出来的第二次失败不得再触发重放，否则一次持续冲突会变成无限循环，并且每次循环都会重新拉权威快照、把用户的乐观编辑反复抹掉。
- 两类都需要把权威快照装回宿主视图，所以 `REVISION_CONFLICT` 在 adapter 里不是"一个错误字符串"，而是要携带"请重新加载"的语义。这与 ADR-011 的错误码映射对得上：码不变，宿主的处置不同。
- 报错文案不能沿用 `toast.saveTasksFailed` 那种"把 error 字符串塞进提示"的形状：`REVISION_CONFLICT` 对用户的意思是"有别人也改了这份数据"，不是"磁盘写入失败"。
