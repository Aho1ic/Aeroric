# ADR-022：保存队列只排队"意图"，读-改-写归 core

- 状态：已接受（Task P2-05 门禁，Q49）
- 日期：2026-09-23
- 相关：ADR-015（覆盖基线＝core 上次发布的字节）、ADR-016（generation 权威在 core 独占账本）、ADR-017（重试身份＝调用方的 operation key）、ADR-019（core 不做乐观写）、INV-03（一份数据目录一个业务 writer）

## 背景

`src/taskPersistence.ts` 的合并单位是**整个项目的任务数组快照**：

```
state.latestSnapshot = { tasks: allTasks.filter(t => t.projectId === projectId), options }
```

350ms 防抖后发给 `save_project_tasks`，而那个命令（`src-tauri/src/storage.rs:397-410`）是**全量覆盖**，数组为空时还会删掉文件。也就是说：宿主内存里那份列表一旦陈旧，下一次防抖到期就会把别人（另一个客户端、或 core 自己）写进去的行整片抹掉。这不是理论风险——它是 ADR-015 的覆盖基线要防的那件事，但防的位置选错了就会没用：如果宿主仍然发快照，core 只能在"已经决定要覆盖谁"之后再拒绝。

core 侧 P2-03/P2-04 已经有逐 op 的服务（`rename`/`toggle_star`/`archive`/`start`/`complete`/`switch_config`…）和指纹基线，`load → 改 → commit` 是它的默认形状。

## 决策

1. **队列只决定"何时把一次变更交给 core"，交的内容是意图**：`op + 载荷 + operation key`。宿主不再发整表快照，`save_project_tasks` 的全量覆盖语义在移交后不再被这条路径使用。
2. **读-改-写归 core**：每次变更由 `TaskService` 在权威快照上完成，并按 ADR-015 校验覆盖基线；因此"陈旧快照覆盖别人的行"在结构上不可能发生，而不是靠对账得赢。
3. **防抖保留，但合并的对象变了**：从"合并两份快照"变成"合并同一 operation key 的重复提交"——这正是 ADR-017 已经定好的机制，不新造概念。`flush`/`flushAll` 与退出前的双队列保留：它们现在是"催交意图"，不是"催发快照"。
4. **宿主的乐观视图仍然由宿主自己回滚**（ADR-019 决策 2）：`rollback_mutation`/`merge_changed_session_fields` 留在宿主侧，配合 core 返回的权威快照与 revision 对账。

## 后果

- 被否掉的两个方案：② 继续发快照、冲突时把本地未落盘编辑**字段级重放**到权威快照上——这需要新写一套任务记录的三方合并，而 core 的设计目标恰恰是让它不必要；③ 状态变迁走 op、纯元数据走快照的混合方案——它让"这个字段谁能写"变成逐字段记账的长期负担，最容易在迁移期产生"一半新一半旧"的 bug。
- 这条决策把"移交 writer"这件事的实际内容定义清楚了：不是"换个文件写"，而是**宿主放弃"我代表完整状态"这个假设**。P2-05 验收里"只发生一次存储写入序列和一次 spawn""没有双事件/事件回环"都以此为前提。
- `taskPersistence.ts` 的现有测试（防抖、单飞、失败后不立即重试同一快照、退出时排空新快照）要按新单位重写而不是删掉：那些性质关于"队列的行为"，与交的是快照还是意图无关。
