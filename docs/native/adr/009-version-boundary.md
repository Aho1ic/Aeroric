# ADR-009：本地主版本严格相等；远程 relay 是独立版本空间

- 状态：**accepted（用户在 P2-01 门禁第二轮拍板，2026-09-22）**
- 日期：2026-09-22
- 关联：`MIGRATION_PLAN.md` §2.3（每帧 `v`、握手协商）、ADR-003（能力由 host 声明）、ADR-008、P3-06（握手实现）、P4-02（Swift 客户端握手）、P8-03（远程/mobile 桥接）

## 背景：§2.3 写了"协商交集"，但没写怎么协

事实核对：本地每帧带 `v: 1`，`HostCapabilities { protocolVersion, buildVersion, dataFormat }` 在握手时报出；`packages/remote-contracts` 里**没有任何版本常量**（远程 relay 与本地协议今天无映射关系）。§2.3 那句"握手协商版本交集"如果被照字面实现，就要在只有一个版本的今天，为不存在的 v2 先写区间协商与降级路径——那部分代码永远测不到，只能靠假版本号自测。

## 决策

1. **本地主版本必须严格相等**：`handshake_allows_peer(version) == (version == PROTOCOL_VERSION)`，Rust/TS/Swift 各一份实现，`envelope.schema.json` 的 `versionPolicy.acceptsSameMajor` / `rejectsAnyOtherVersion` 由该函数**算出来**再写进工件（不是手抄的 true）。不等就在握手期拒绝并给原因，不降级成半条连接。
2. **v1 内部的兼容性一律由具名能力承载，绝不由版本号推断**。这与 P7-02/ADR-003 已定的"客户端不得用自己所在的 OS 去推 host 能力"是同一条纪律的两侧：既不拿环境猜能力，也不拿版本猜能力。
3. **引入 v2 需要先写 ADR**：方法名、topic 名、枚举拼法会被"替代 v1 的那个东西"冻结（ADR-002/006/007 的代价已经证明改名即协议变更），所以升版是设计决定而不是实现细节。
4. **远程 relay 与本地协议是两个独立版本空间**：桥接层（P8-03）必须**显式声明它映射了哪几对**，不得假设两者同步演进；今天 `packages/remote-contracts` 无版本常量，所以"映射关系"这件事本身是 P8-03 必须新增的工件，而不是既成事实。

## 备选与被否决的理由

- **现在就实现区间协商**：为不存在的第二版写代码，且无法用真数据验证；一旦协商逻辑本身有 bug，最先受害的是唯一真实存在的路径（v1↔v1）。
- **只拒绝不等、不写远程映射**：把"远程怎么对齐"留给后面偷偷决定，届时改的正是协议本身。

## 后果

- 握手（P3-06）与客户端（P4-02）各自调用同一份判定；`docs/native/reviews/protocol.md` 记录 Q13 的来路。
- P8-03 的验收里多一项可机械检查的东西：桥接必须公布它映射的版本对，未映射的组合必须显式拒绝而不是"看起来连上了"。
