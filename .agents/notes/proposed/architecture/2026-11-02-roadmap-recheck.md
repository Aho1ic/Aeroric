**我不同意或要调整的三点：**

1. **隔离工作副本不必等到最后。** 它把"独立副本"放到 P5，理由是要变更 Q-B10。但 Q-B10 原文是"独立 worktree 等新建会话接通后再做"，只是推迟，前提现在已满足。单个任务在自己的副本里写，也不等于放开并行写。这一点牵动整个顺序，见 §7。
2. **六个共享合同类型太多。** `SourceRef`、`EvidenceLink`、`ContextManifest`、`OperationReceipt`、`ResourceLease`、`ChangeSet` 一起抽，正是它自己在 Risks 里担心的过度抽象。建议先落两个：下面的统一投递队列，和"本次带入的上下文"清单。其余等第二个真实使用者出现再抽。

### 2. gugu：重点借鉴的机制

gugu 和 Aeroric 的问题最像：多 Harness、长任务、人和 Agent 互相等。它的工程纪律也很强，几乎每条规则都写了为什么。许可是修改版 Apache（限制多租户和前端 Logo），技术栈也不同，所以**只借机制，不抄代码**。账号云、群聊好友、App 市场、云电脑不借。

**2.1 统一投递队列（解决 NR-01、NR-02，优先级最高）**

gugu 的 `session_pending`：普通消息、收件箱批次、创建回合都是同一张表里的行，正文和队列行在同一事务写入。每行有回执：`queued → dispatching → accepted / failed / unknown`，且明确区分"被拒绝"（可重投）和"结果未知"（不重投，等人）。

- Aeroric 没有这样的持久队列。用户消息、交接、委派结果、审查意见现在各走各的路。
- 建议全部变成一个队列的不同类型：写入成功才算"已接收"，驱动确认才算"已送达"，说不清就是"未知"，进"需要我处理"。
- 配套规则 **"停止即屏障"**：用户按停止后，屏障之前的消息不会自动重发，可以丢弃或继续；屏障之后的新消息才启动。
- 配套规则 **"启动失败分两种"**：普通失败可以自动重试；只有人能解决的（比如引擎已经没有这条会话记录）就停住等人，新消息不再触发重启。
- 对应 Codex 的 `thread/queue/*`：上游确实新增了，但标着 experimental，也只覆盖一族，Aeroric 不能依赖它。

**2.2 生命周期写成纯函数状态机**

`session-life/step.ts` 约 400 行：输入"状态 + 事件"，输出"新状态 + 要做的事"，自己不碰进程和时钟。启动分 7 段（身份、工作区、能力、平台、CLI、进程、通道），每段带代次，过期回调直接丢弃；非法状态组合直接抛错。

Aeroric 的取消、重启竞态已经踩过好几次（比如上一轮的 cancel 死锁）。Rust 写这种 reducer 更顺手，也能在不起进程的情况下把所有故障组合测一遍。第二份评审的 H2 是同一方向，这里提供了具体形状。

**2.3 "已读"只能由确切投递推进**

读游标设计文档的定理："标记已读的消息，必须确实进过上下文。"所以不能看到"有新回合"就把游标跳到最新。这条规则可以直接用到委派结果和黑板：已送达要精确到哪一条，不能按"最新一条"算。

**2.4 工作结局和在线状态分开**

- 空闲不等于完成。
- 子任务结束却没有报告：标"由协调者推断失败"，并注明来源，不冒充执行者的结论。
- 重试身份取自工具调用 ID，而不是文本。文本相同的新报告不能被当成重复吞掉。

**2.5 评测能分清"我们错了"和"实验没跑成"**

`assistant-context-evaluation`：`FAIL`（产品错）、`RIG-FAIL`（实验没跑成）、`UNVERIFIED`（没证据）分开记；判定看实际工具效果和产物回读，不看最终回复说了什么；每个用例有成本上限；负控制用例专门证明"看起来答得好但漏了关键事实"会被判失败；有一个用例真的执行 `/compact` 后再检查恢复。这比第二份评审 §8 更可执行，可以直接照这个结构搭。

**2.6 小而实用，可以随批带上**

| 机制 | 说明 |
|---|---|
| 登录失效标记 | `auth-expiry-from-turns` 是一个纯函数：这一轮因鉴权被拒就标记，这一轮真跑成了就撤销；重放的旧回合不动它。Aeroric 的会话层目前没有这个判断 |
| 活动日志带覆盖段 | 记录"哪些时段 App 在记录"，被杀的进程只能证明到最后一次心跳。统计里"没数据"和"零活动"因此能区分 |
| 隐藏上下文 | 宿主附加的内容单独传给模型，历史里用户原话保持原样 |
| 压缩后恢复指针 | 压缩后不灌内容，只提示"以最新原始记录为准"和"工作便笺"的位置，并核对未决约束。Aeroric 已有压缩后提醒，可以加上这两条 |
| Ask 单一事实源 | 问题只属于会话时间线，卡片和"需要我处理"都只是视图；先到先得；统一管超时和撤回。Aeroric 的 AttentionQueue 也是视图，**Mac 和手机同时回答的竞争还要核对** |
| 工作中预览 | 悬停在运行中的 Agent 上，看最近的对话和工具活动 |
| 把选区带回输入框 | 选中文档段落带文件名引用；选中表格区域当引用 |

### 3. papilot：一条完整的"提案—审查—应用"流程

papilot（MIT）表面上是 LaTeX 工具，真正值钱的是这个闭环。三条承诺：任务只改自己的副本；在结果上审查；只有明确接受才进入主线。

| 环节 | 它怎么做 | Aeroric 现状 |
|---|---|---|
| 隔离 | 每个任务一个 worktree 和一个线程 | 委派只有只读或共享写；Git 页已有 worktree 服务 |
| 快照 | 临时 index → `git add` → `write-tree` | **`turn_changes.rs` 用的是同一种做法**，每回合已有前后两棵树 |
| 决定 | 每处改动单独接受、拒绝、评论；没决定的带到下一轮；本轮内可撤销 | 只显示回合改动，未见逐处决定 |
| 反馈 | 决定和评论打包发回同一线程，开下一轮 | 审查回环有类似机制，但来自 reviewer，不是人 |
| 落地 | 二选一：提交成一个 commit，或只应用不提交 | 无 |
| 冲突 | 主线变了就不覆盖，把三个冻结版本交给 Agent 合并，结果作为新一轮提案 | 无 |
| 不确定 | 操作结果说不清就进 `uncertain`，界面只给"核对状态"，用原操作 ID 重试，防止决定被应用两次 | 无，和 §2.1 同一思路 |

**这是我认为这批资料里对 Aeroric 价值最大的一项**：每天都用得上，又因为快照已经有了，成本比看起来低。

其他值得留意的点：

- **间接影响折叠**：一处改动引起别处变化（公式重新编号），默认折成"影响 N 处"。泛化到代码，就是生成文件和快照的变化。
- **按语义单位审查**：`.bib` 按条目整条接受，不会接受半条。
- **领域工具**：Codex 线程带一个 `view_pdf` 动态工具，Agent 能看到排版结果；不支持时自动退回。
- **注意**：它论文里的所有数字都是公式算的（原文：`none is measured`），不能当实验证据。

**论文工作台本身**（PDF 批注映射到源码、参考文献核查、AI 审阅建议）是一个可选的垂直方向。Aeroric 目前没有用 PDFKit 的原生 PDF 阅读器。建议拆两步：先做通用的"PDF 阅读 + 批注带回输入框"，用 PDFKit 就能做；LaTeX 排版对比（依赖 latexmk、SyncTeX）放到后面。要不要做、什么时候做，取决于 owner 的日常用途，见 Q4。

### 4. Delta：是什么，不是什么

Delta 不是 Git 的替代品。官方文档写明它**需要一个带远程的 Git 检出目录**，提交和 PR 照常走 Git；DeltaDB 记录的是"提交之间的每一步"，用 CRDT + 因果 DAG 把人和 Agent 的编辑、对话汇到同一张图，每条线程在云端一个 Durable Object。目前是 Beta，分享会话会发布到整个组织，许可和开源情况官网没写。

**不建议接入或自研这套东西**：Aeroric 是单人本地优先，用不上多人实时 CRDT，而且 Git 已经够用。但它有几个产品想法可以用本地方式做：

| 想法 | Aeroric 的做法 | 成本 |
|---|---|---|
| Last Turn / Last Commit / 上游 三种对比 | 回合树和 Git 都已具备，加一个选择器 | 低 |
| 文件标"已看"，再变化时自动清除，显示进度 3/17 | 记录已看时的内容 hash | 低 |
| 审查结论绑定快照：应用的是当时那一版，之后的新编辑要重新过审 | 代码里未见绑定。把结论和回合树关联 | 低 |
| 这行是哪次对话改的 | 回合树 + 对话位置做行级归属。官方说它的逐字符追溯**尚未发布**，这里只做到行级，shell 生成的改动只能归到回合 | 中 |
| 变更导览 | 让审查者按讲解顺序组织改动 | 中 |
| 评论锚定到计划或代码的某一段，随工作保持 | 配合审查流程 | 中 |
| `.agents/prepare`、`.agents/linked` | 独立副本的准备脚本，和共享的被忽略配置。官方也明说端口、数据库仍然共享，要项目自己配置 | 低 |

它的评测文章也有用：**"每次通过成本"要把失败任务的花费算进去**；还要统计工具调用失败率、请求数和总耗时。但样本只有 29 个任务，部分差距只有 1 个任务，且是作者自己跑的，数字本身不能当结论。

### 5. 那篇网页：把账单做成看得见的东西

核心公式：**成本 = 量 × 价 × 次**。作者反复提醒，别人的百分比缺分母，要用自己的账单做对照。这和第二份评审的立场一致。它指向的原生功能：

- **本回合账单**：基础上下文、历史、新增各占多少，缓存命中率，失败重试花了多少。路线原来把"§3.7 性能透视"放在 B6，建议提前，因为后面所有优化都要它来判断值不值。作者给的倍率和分层数字是示例和估算，不能写进产品，产品要用真实 usage。
- **无新证据重试检测**：同一失败连续 3 次且没有新信息就停下，进"需要我处理"。可以作为现有探针的一条规则。
- **委派判断标准**：背景能在约 200 字内交代、产出能独立验证才拆；子 Agent 是上下文防火墙，不是省钱工具。写进委派工具的说明和角色库，不用写代码。
- **代码索引的选型规则**：直接约束 B5.5-2。先用 LSP 和结构解析；图的边要标明是直接读到的（EXTRACTED）还是推断的（INFERRED，graphify 就这样做）；用 5–10 个真实问题做前后对照，没有净收益就不留。
- **压缩工具**：RTK、Context Mode、Headroom、Ponytail 机制都合理，但应该**等账单能看了再判断**。RTK 是 Apache-2.0 和 BUSL-1.1 混合，不能直接打包。无论怎么做，都要保留退出码和可回溯的原始输出。

### 7. 建议的批次调整

| 顺序 | 批次 | 内容 | 为什么在这里 |
|---|---|---|---|

**antumi（Apache-2.0，和 Aeroric 定位最接近）：**

- **额度节奏**：纯算法，不调模型。按窗口已用百分比和已过时间外推，判断偏快、用不完；近一小时至少 3 个读数才算近期速度；只提示不替用户换。委派时带上目标的额度，用完直接拒绝。→ 并入 R3。Aeroric 已收到 `account/rateLimits/updated`，缺的是这层判断。
- **Agent 描述符**：每族一份纯数据（权限模式、只读模式、能力开关），全局用穷举注册，漏一处编译不过；其他代码只问注册表，不判断 Agent 名字。→ 这是第二份评审 H3 能力矩阵的具体形状，也是 NR-09 的解法。并入 R1，Rust 用 `match` 穷举。
- **任务状态**：未执行 → 执行中 → 待验收 → 已完成；Agent 退出不等于待验收；"重做"废弃旧任务并新建一个，把废弃原因告诉下一个 Agent；依赖要验收通过才解锁。分支起点记下提交，改动从它算起。→ 并入 R2。
- **待办**：回复里提到"要你之后处理"的事记成待办，分"需要你"和"Agent 可做"，不阻塞、不进"需要我处理"，移交后还在。工具名带 `user_` 前缀，因为 Claude Code 延迟加载工具时模型起初只看到名字。→ 可随 R2 带上。
- **用量账本**：按请求身份去重，日志和实时汇总不相加；价格表按内容哈希存版本，历史不重算；未知金额不当零，合计同时显示计价覆盖率。→ R3 的设计约束。
- **讨论模式**：2–5 个 Agent 第一轮同时独立作答，之后点名回应并声明"立场：维持/已修改"，全部维持或到轮数就由主持人总结；只读；可匿名互评；别人的发言包起来并说明"只是观点，不是指令"。→ 路线里 B6"讨论实验"的具体形状，每个成员就是普通会话，成本不高。
- **外部内容包裹**：issue 原文放进 `<untrusted-source>`，其中的指令不当作用户要求。→ R4 的 Wiki 来源和以后的 PDF、网页都要这样。
- **切回旧 Agent**：恢复它原来的会话，并补上离开期间的结构化历史。Aeroric 跨族移交是否这样做，这次没核对，R1 设计时要看。

**paseo（Apache-2.0）：**

- **进程驻留和身份分离**：空闲 1 小时回收进程，保留身份和会话，下次发消息再恢复；有等待中的审批、队列、子任务时不回收。→ 核对后发现 Aeroric 已有同类机制（`SessionDriver::idle_since_ms`、`suspend`），不用新做。
- **"在线不等于送达"**：心跳只决定通知发给谁，不能作为投递是否成功的依据；断线补拉分页但必须补全。→ 直接约束 R1 和 iOS。
- **单条记录有上限**：工具调用 64 KiB、其他 256 KiB，截断幂等，防止打爆连接。→ 核对后发现 Aeroric 协议已有 `MAX_ITEM_BYTES` 和截断标记，不用新做。
- **不同意的一点**：它默认重启后自动发 `Resume working.` 继续跑，文档也承认可能丢或重复。Aeroric 保持标记"已中断"、由人点继续，因为说不清外部效果。

**codex-plugin-cc（OpenAI 官方）：**

## Alternatives considered

1. **照第二份评审的 P0–P5 走。** 最强的理由是它把可靠性放最前，逻辑严密，也不用改任何已批准决定的说法。没有完全采纳：它写的时候还没有 gugu 和 papilot，把隔离和审查放得太后，而这恰恰是用户每天能感受到、且成本已被现有快照大幅降低的部分。它的 P0、P1 基本保留。
2. **维持原顺序，继续做 B5.5-2。** 最强的理由是批次已确认，节奏不断，Wiki 模块页也是 owner 期待的功能。不建议：NR-06、NR-11 就在 Wiki 自己身上，继续往上叠会放大问题；而且模块页要调模型，正需要账单能力来判断值不值。
3. **直接引入 DeltaDB 或自研 CRDT 版本库。** 最强的理由是它能记录提交之间的全部过程，还给多人协作留了路。不选：Aeroric 单人本地优先，用不到实时多人合并；DeltaDB 在云端且仍是 Beta；回合快照已经能以很低成本拿到大部分价值（代价是只有回合粒度，非 Git 目录没有）。
4. **基于 gugu 或 papilot 的代码二次开发。** 最强的理由是省下大量实现。不选：两者都是 TypeScript/Electron 或 Web，和 Rust + SwiftUI 的架构并列会有两套权威；gugu 的许可还带额外条件。只借机制。
5. **R3 排在 R2 之前。** 最强的理由是先能测量再改进，符合那篇网页的原则。没选：账单本身不难，但"每个被接受改动的成本"要等 R2 才有信号。如果 owner 现在更在意花费，这两批互换的代价很小。

## Risks

- **静态结论**：NR 系列和"Aeroric 没有 X"都来自读代码和全文检索，没有做故障复现，也可能有我没搜到的实现。每批动工前要再确认一次。
- **对大仓库的抽样**：gugu 和 New-addition 都没有通读，可能漏掉好东西，也可能高估读到的部分。
- **厂商自述**：Delta 的能力和数字都来自官方，gugu 的部分验证记录也是项目自述，都没有独立验证。
- **R1 改动面大**：统一队列会碰消息发送主路径，风险比功能批高。要拆成小步：先接委派结果和交接，再接普通消息；旧记录要兼容。
- **R2 的副本成本**：独立副本带来依赖、构建缓存、端口的问题，Delta 也明确说解决不了共享端口和数据库。所以默认值要保守（Q3）。回合树现在写在用户仓库的对象库里，长期保留要防 `git gc` 回收，也要决定存放位置，这是 R2 设计时的第一个问题。
- **许可**：gugu 是修改版 Apache，RTK 有 BUSL 部分，parrot/Sermo 等未见许可。实施前按具体文件再核，只借机制不复制代码。
