# Agent Note: 207 项目调研落地总纲：先让状态可信，再闭合已有能力，最后开新入口

Status: proposed

## Problem

owner 让其他 Agent 调研了 207 个热门开源项目，并统计了它们的 issue 和 PR，产出放在仓库外的 `/Users/macbook/Documents/Aeroric-research/2026-11-11-frontier-review/`（总报告、19 篇专题、逐项目报告、两轮审计）。目的有两个：防止 Aeroric 闭门造车，功能越做越偏；把别人做得好的地方变成 Aeroric 的原生功能。

这批调研不能直接照着做，原因有三个：

1. **调研全部是静态阅读。** 程序、测试、GUI、VM 都没有运行，它自己也要求实施前按真实入口复核。
2. **它推荐的"第一批共用基础"大半已经做完。** 调研基线是 `main@8d4391c3`，而 [路线文档](../../../../docs/frontier-roadmap.md) 里的 R1（统一投递队列、停止屏障、能力表、故障注入）、R2（回合撤销、隔离副本）、R3（账单与配额）、R5（回合分级、换模型重跑）、B4（委派与验收）、B5（记忆）、讨论模式都已落地。照搬会重做一遍。
3. **新入口最显眼，也最容易带偏。** GitHub、浏览器、手机跟随、多 Agent 协作都依赖"动作有回执、完成有验收"。回执还有缺口时先做新入口，只会把同一类假状态复制到更多地方。

## Proposal

一句话：**调研的方向对，起点要改。** 起点从"建六类事实的共用基础"改成"修掉当前源码里已经能指到行号的假状态"，然后闭合已有子系统，最后才开新入口。

### 4. 交给实现模型的方式

**一次会话只做一片。** 每片的说明都是自足的：能独立验收，改动范围尽量落在一条纵向链上。

实现模型每片按这个固定流程走：

1. **读规则。** `AGENTS.md`、`docs/architecture.md`，以及该片说明里点名的子系统文档和已落地笔记。
2. **复核锚点。** 该片说明里的文件和行号是 `8d4391c3` 上的位置。先 `git rev-parse HEAD`，再打开这些位置确认现状没变；变了就按实际代码调整，并在笔记里写明。
3. **写笔记。** 按 `write-notes-like-deepseek` 给这一片单独写一篇 `proposed` 笔记（或原地更新已持有该决定的老笔记），写完跑 `pnpm verify-notes`。
4. **按链路改。** Rust 协议类型 → `export-schema` → `contracts/native/v1/**` → Swift 类型与客户端 → store 或 read model → SwiftUI。业务判断只写在 core 和 host。
5. **写测试。** 隔离数据根加假 Agent；故障场景加进已有的故障注入假驱动。不碰真实 Agent 目录、凭据和生产数据。
6. **跑验证。** `cargo test --manifest-path core/Cargo.toml --workspace`、`cd core && cargo fmt --check`、`swift test --package-path macos/AeroricKit`，该片涉及的 `pnpm native:check <module>`。真实窗口 UI 自动化和测试 VM 目前暂停，记为 NOT RUN。
7. **收尾。** 笔记转 `implemented`；`docs/` 里对应的现行事实同步；把需要目检的界面行为记进路线文档 §8 的待目检清单。不 commit、不 push，等 owner 说"目检通过，提交"。

**每片都要守的线：**

- 不新建"事实总管"或跨业务的大表。新字段加在现有对象上（投递记录、委派卡、检查点、回合记录、能力表）。
- 协议只加不改：新字段给默认值，旧客户端能照常解码。
- "不知道"是一等状态。超时、断线、读不到，都落 `Unknown` 并给出核对入口，不折算成成功或失败。
- 用户看到的文字先说结果，再给可做的动作；协议细节放详情里。
- 不自动批准任何权限请求。

### 5. 统一的验证输入

调研给了一张故障表。它不单独成片，而是每片挑相关的行加进测试。批次笔记里用括号里的短名引用。

| 短名 | 场景 |
|---|---|
| 接收后断线 | 对方已收下，回执在路上时连接断开 |
| 落盘失败 | 状态写盘返回错误 |
| 启动中停止 | 任务还在启动阶段，用户按了停止 |
| 过期事件 | 上一代运行的事件在新一代开始后才到 |
| 子任务迟到 | 父任务停止后，子任务才返回结果 |
| 选了没发出 | 用户点了批准，回应没能发给 Agent |
| 做了没回执 | 外部动作已经发生，回执丢了 |
| 同名替换 | 检查通过后，同名文件被换了内容 |
| 来源消失 | 引用的文件被删除或读不了 |
| 整理中遗忘 | 后台整理进行到一半，用户遗忘了其中一条 |
| 目标更新 | 审查进行中，PR 的 head 变了 |
| 分页不全 | 列表只取到一部分 |
| 用户接管 | Agent 操作途中用户亲自动手 |
| 设备撤销 | 手机在线时被撤销配对 |

指标沿用调研的口径，等 B 批完成后在换模型重跑的基础上做对照：验收通过率、假完成率、每个验收通过结果的总耗时和已知成本、重复外部效果数、遗漏要求数、恢复成功率、状态不明的持续时间、引用有效率、遗忘后复现率、用户纠正和接管次数。

## Alternatives considered

**照调研的第一批做：先建六类事实的共用基础，再往上接业务。** 它最强的理由是契约统一：投递、审批、验收、产物都用同一套身份和回执类型，后面的 GitHub、浏览器直接接上去。没选它，因为这套基础的大部分已经以各自的对象存在（投递记录、提交回执、操作账本、检查点义务），再抽一层只会多出一套要同步的类型。第二份评审提过六个共享类型，路线复核当时就以"过度抽象"为由只落了两个，后来的实现证明够用。

**先做新入口（GitHub 审查或浏览器），用真实需求倒逼基础。** 它最强的理由是用户马上能看到新功能，而且真实入口最能暴露基础缺什么。没选它，因为 A 批的缺口已经能指到行号，不需要新入口来暴露；而新入口会把"先标已发送再发送"这类问题带到写远端的场景里，那里的假状态代价更高。

**写成一篇大笔记。** 它最强的理由是一处看全。没选它，因为实现模型一次只做一片，一篇两千行的笔记每次都要整篇载入；拆成总纲加四篇批次笔记后，每次只读总纲的规则和一篇批次笔记里的一节。

## Risks

- **行号会漂。** 说明里的位置是 `8d4391c3` 上的。任何一片落地都会让别的片的行号变化，所以流程第 2 步要求每次复核。
- **静态核实不等于复现。** 表里的结论都没有用故障注入跑出来过。个别可能在运行时被别处的逻辑兜住，实现模型应先写出失败的测试再改。
- **A 批会碰很多已目检过的界面。** 委派卡、审批卡、撤销预览的文字和状态都会变，需要重新目检，待目检清单会变长。
- **粗估偏乐观。** 跨 Rust、schema、Swift 三层的片，实际耗时常是单层估算的两到三倍。
- **调研本身的覆盖有限。** 207 个项目里社区讨论读全的只有 26 个；需求归纳可能偏向文档写得好的项目。D 批开工前应由 owner 用自己的使用感受再筛一次。
