# Agent Note: 调研落地批次 D：新入口（GitHub、浏览器、手机、有限协作）

Status: proposed

## Problem

[落地总纲](../architecture/2026-11-15-research-adoption-roadmap.md) 把新入口排在最后。调研统计的 207 个项目里，用户请求最多的方向是：在 PR 上做审查、让 Agent 操作浏览器、在手机上跟进和审批、多个 Agent 分工。这些 Aeroric 目前都没有，或只有一部分。

排在最后有两个原因：

- **新入口会放大状态问题。** 浏览器动作、GitHub 评论、手机审批都是发出去就收不回的操作。批次 A 修的那类问题（显示已发送而实际没到）在这些入口上代价更高。
- **新入口依赖前面的对象。** GitHub 审查要绑定固定版本并产出有依据的结论（B3、B6）；手机审批要用审批回执（A2）和能力清单（C8）。

所以这一批的每一片都写了前置条件。前置没完成就开工，会重新造一遍前面的东西。

本篇 6 片。D1 最小、前置最少，建议第一个做（总纲决策 6）。D3 和 D6 开工前有必须先做的实验。工期估计来自调研，按一个实现者连续工作计。

这一批的位置信息比前几批少，因为多数是新代码。每片写明了要复用的现有模块。

## Proposal

### D1 GitHub 只读：把一个 PR 固定成快照来审

2026-11-21 第一步已实现，见 [D1 第一步笔记](../../implemented/feature/2026-11-21-d1-pull-snapshots.md)：做法第 1、2、6 条和方法的前两个（`github.pullSnapshot`、`github.snapshots`，另加 `github.snapshot`）。2026-11-21 第二步已实现，见 [D1 第二步笔记](../../implemented/feature/2026-11-21-d1-read-only-review.md)：第 3–5 条和 `github.reviewStart`、`github.review`（另加 `github.reviews`）；没有用隔离副本，PR 的 head 在 `.aeroric/pr-reviews/` 下分离检出。2026-11-21 第三步已实现，见 [D1 第三步笔记](../../implemented/feature/2026-11-21-d1-pull-review-section.md)：Git 侧栏的“PR 审查”一段。D1 完成，真实 GitHub 上的全程 NOT RUN。

**前置：** 无硬性前置。有 B3 更好（结论带依据）。

**用户会看到：** 在项目的 Git 页粘贴一个 PR 链接或从列表里选一个。Aeroric 显示它的标题、分支、变更文件、检查状态和已有评论，顶部写着"快照于某时刻，对应提交 abc1234"。点"让 Agent 审查"后，审查任务读的是这份快照。PR 之后有新提交时，页面提示"PR 已更新，当前结论针对的是旧版本"。审查结论保存为草稿，**这一片不向 GitHub 写任何东西**。

**复用：**

- Git 页和它的写操作（[Git 页写操作](../../implemented/feature/2026-10-30-git-page-writes.md)）。
- 审查循环的审查者角色和提示词（[审查循环](../../implemented/feature/2026-10-30-review-loop.md)）。
- 改动审阅的逐块视图（[逐块审阅](../../implemented/feature/2026-11-04-hunk-review.md)）。
- 凭据：用本机 `gh` 的登录状态或用户在设置里填的令牌；Aeroric 只保存凭据引用。先读 `core/crates/aeroric-core/src/git/` 看现有的远端访问方式。

**新对象（协议）：**

- `RepoRef`：`host`、`owner`、`name`、`repo_id`（GitHub 的数字 id，防止仓库改名后认错）。
- `PullSnapshot`：`repo`、`number`、`title`、`author`、`head_sha`、`base_sha`、`merge_base`、`fetched_ms`、`files`（路径、状态、增删行数）、`checks`（名称、结论、链接）、`comments`（作者、正文、锚点）、`truncated`（文件或评论超过上限时为真）。
- `CommentAnchor`：`path`、`side`、`line`、`commit_sha`。评论所在的提交不是 `head_sha` 时标"针对旧版本"。
- `ReviewRun`：`snapshot_id`、`task_id`、`state`、`findings`（位置、严重程度、正文、依据）。

**做法：**

1. core 新模块 `github/`：只读客户端，取 PR 元数据、文件列表、检查、评论。分页取全或在达到上限时置 `truncated`（分页不全）。
2. 快照持久化。同一个 PR 可以有多份快照，按 `head_sha` 区分。
3. 取代码：把 `head_sha` 和 `base_sha` 抓到本地仓库的一个专用引用下（`refs/aeroric/pr/<number>/<sha>`），不动用户的分支和工作区。审查任务在隔离副本里检出（[隔离副本](../../implemented/feature/2026-11-05-isolated-copy.md)）。
4. 审查任务以只读角色启动（A4 落地后用 `StrictReadOnly` 判断）。提示词里给出快照的文件列表、检查结果和已有评论。
5. 审查结论解析成 `findings`，每条绑定 `path`、`line`、`head_sha`。
6. 刷新：重新取 `head_sha`。变了就生成新快照，旧的 `ReviewRun` 标"针对旧版本"（目标更新）。
7. 方法：`github.pull_snapshot(url)`、`github.snapshots(projectId)`、`github.review_start(snapshotId, …)`、`github.review(runId)`。
8. Swift：Git 页加 PR 入口、快照视图、审查结论视图。

**验证输入：** 假 GitHub 服务（本地 HTTP）。PR 有 300 个文件（超上限）；审查进行中 PR 被强推；仓库改名；令牌无权限（返回明确原因，不返回空列表）；网络中断后重试不产生重复快照；评论锚点指向已不存在的行。

**完成条件：** 用户能完成"选 PR → 固定版本 → 读变更和检查 → 独立审查 → 打开每条结论的位置 → 保存草稿"全程；全程对 GitHub 只有读请求（由假服务断言）。

**估计：** 7–12 天。

**不做：** 不做 GitLab、Gitea；不做 Issue 列表和通知收件箱；不做合并。

### D2 GitHub 写：草稿和带回执的发布

2026-11-21 第一步已实现，见 [D2 第一步笔记](../../implemented/feature/2026-11-21-d2-publish-core.md)：做法第 2、4、5、6 条在 core 里，草稿、标记、逐条结果和重启后的“结果不明”；没有用 `OperationLedger`，每条的状态存盘加 GitHub 上的标记代替它。2026-11-21 第二步已实现，见 [D2 第二步笔记](../../implemented/feature/2026-11-21-d2-publish-methods.md)：宿主方法，只给 App。2026-11-21 第三步已实现，见 [D2 第三步笔记](../../implemented/feature/2026-11-21-d2-publish-draft-shown.md)：快照窗里的发布草稿。D2 完成，真实 GitHub 上的发布 NOT RUN。

**前置：** D1；A1 的投递回执模式；B3。

**用户会看到：** 审查结论可以逐条编辑、勾选，然后点"发布到 GitHub"。发布前显示将要发出的全部内容和目标（哪个 PR、哪个提交）。发布后每条评论有状态：已发布（带链接）、失败（带原因）、结果不明（带"去 GitHub 核对"）。PR 在此期间有新提交时，发布被拦下，要求用户确认或重新审查。

**新对象：**

- `GitHubWriteIntent`：`id`、`run_id`、`target`（`repo`、`number`、`head_sha`）、`items`（评论正文与锚点，或一次整体审查）、`state`（草稿、待确认、发送中、已完成、部分完成、失败、不明）、`operation_key`。
- 每个 `item` 有自己的结果：远端评论 id 和链接，或失败原因。

**做法：**

1. 发布是用户动作，**Agent 不能触发**。Context 工具里不提供发布方法。
2. 发布前重新取 `head_sha`。与意图里的不同则状态转为"目标已更新"，不发送（目标更新）。
3. 发送使用现有的操作台账（`OperationLedger`）：同一个 `operation_key` 只发一次。
4. 请求发出后没有收到响应时记为不明。恢复时先查询 PR 上是否已有带相同标记的评论（在正文末尾加一个不可见的标记注释），有则补记为已发布，没有才允许用户重发。**不自动重发。**
5. 部分成功如实显示，可以只重发失败的条目。
6. 这一片只支持：发布审查评论、发布一条总评。不支持批准、请求修改、合并、关闭。

**验证输入：** 假服务在收到请求后断开连接（做了没回执）；发布 5 条时第 3 条返回 422；发布前 PR 被强推；连点两次发布；宿主在发送中重启。

**完成条件：** 任何情况下不会向同一位置发出两条相同评论；每条评论的最终状态都能在界面上看到。

**估计：** 在 D1 之上再加 10–15 天。

### D3 浏览器：受控会话和动作回执

**前置：** A1、A2；C8 的结构化工具结果；**以及下面的焦点实验通过**。

**开工前必须先做的实验：** 证明 Aeroric 能在不抢用户键盘焦点和鼠标的情况下驱动一个浏览器实例。候选方式是通过调试协议驱动一个独立的、使用单独用户数据目录的浏览器进程。实验要回答：窗口能否保持在后台、输入是否完全不经过系统事件、用户同时在用自己的浏览器时互不影响。结论写成笔记。**实验不通过，这一片不开工**（总纲决策 7）。项目已有"不抢鼠标和焦点"的硬约束。

**用户会看到：** 任务可以附带一个浏览器会话。界面里有它的实时画面（只读）和动作列表。每个动作有状态：没送到、送到了但不确定是否生效、已送达未验证、已验证。用户可以随时点"我来接手"，之后 Agent 的动作被暂停，直到用户交还。

**新对象：**

- `BrowserTarget`：`connection_id`、`context_id`、`tab_id`、`frame_id`、`document_epoch`。页面导航或刷新后 `document_epoch` 加一。
- `BrowserAction`：`id`、`target`、`kind`（导航、点击、输入、读取、截图）、`args`、`state`、`evidence`（动作后的页面状态摘要或截图引用）、`operation_key`。
- `BrowserLease`：谁在控制（Agent 或用户）、从何时起。

**做法：**

1. 每个动作带上它所针对的 `BrowserTarget`。执行前比较 `document_epoch`：页面已经变了，动作被拒绝并返回"页面已变化，请重新读取"（过期事件）。这是这一片最重要的一条规则，防止点到错误的页面上。
2. 动作状态四级。"已验证"需要动作后的一次读取确认预期变化发生；没有预期条件的动作最高到"已送达未验证"。
3. 用户接管（用户接管）：租约转给用户，Agent 的在途动作标为取消，新动作被拒绝。
4. 有副作用的动作（提交表单、点击标有发送、支付、删除字样的控件）走审批，复用现有的审批通道。**不提供全局自动批准。**
5. 凭据：Agent 不能读取密码字段的值；登录由用户在接管状态下完成。
6. 浏览器进程由宿主管理生命周期，任务结束时关闭。
7. 以 MCP 工具的形式提供给 Agent（`browser_navigate`、`browser_read`、`browser_click`、`browser_type`、`browser_screenshot`），进入 C8 的工具清单。

**验证输入：** 假页面服务。点击发出后页面跳转；动作发出后浏览器进程崩溃（做了没回执）；用户接管期间 Agent 发动作；同一 `operation_key` 的动作重发；标签页被用户关闭。

**完成条件：** 没有任何动作会在页面已变化的情况下执行；每个动作的状态与实际一致。

**估计：** 17–27 天（不含实验）。

**不做：** 不驱动用户日常使用的浏览器实例；不做验证码处理；不做跨站的自动登录。

### D4 手机：先只读跟随，再做带回执的审批

2026-11-21 第一步已实现，见 [D4 第一步笔记](../../implemented/feature/2026-11-21-d4-command-identity.md)：做法第 1、2、5 条的宿主一侧，`commandId` 去重、`hostEpoch` 判旧（第 2 条里 `task_id`、`generation`、修订号的判旧还没做）、撤销设备清结果。2026-11-21 第二步已实现，见 [D4 第二步笔记](../../implemented/feature/2026-11-21-d4-phone-commands.md)：手机端的命令带上这两项，序号跳变、溢出、过期拒绝都要求重新同步（第 3 条）。2026-11-21 第三步已实现，见 [D4 第三步笔记](../../implemented/feature/2026-11-21-d4-approval-receipts.md)：第二阶段的审批回执（第 4 条）。真实连接上的收发、按 `generation` 和修订号判旧还没做。

**前置：** A1、A2、C8。

**现状：** iOS 伴随端已有加密通道、远程 RPC 编解码、快照存储和待审批列表、推送桥（见 `docs/subsystems/ios-companion.md`）。推送只是提示，不携带内容。调研指出的缺口：手机端对"我点的批准到底生效没有"没有确认；连接中断期间错过的事件靠事件缓冲补，缓冲溢出后状态可能不完整；手机发出的命令没有稳定的标识，重连后可能重发。

**用户会看到：**

第一阶段（只读跟随）：手机上的任务列表和会话内容与 Mac 一致。连接恢复后，如果错过的内容太多，显示"正在重新同步"，同步完成前不显示可能过期的状态。

第二阶段（审批回执）：在手机上批准或拒绝后，按钮变成"发送中"，直到 Mac 上的宿主确认。确认后显示"已生效"；超时显示"不确定是否生效，回到 Mac 上确认"；Mac 上已经处理过的显示"已在另一端处理"。

**做法：**

1. 每条来自手机的命令带稳定的 `command_id`（设备生成，重发不变）。宿主按 `command_id` 去重并保留结果一段时间，重复的命令返回第一次的结果。
2. 命令带上它所基于的状态：`host_epoch`（宿主启动标识）、`task_id`、`generation`、对象修订号。宿主发现基于的状态已过期时拒绝并返回当前状态（过期事件）。
3. 事件流带序号。手机发现序号不连续、或宿主告知缓冲已溢出时，丢弃本地状态，重新拉取完整快照。
4. 审批回执复用 A2：宿主只有在回应真正送达 Harness 后才回复手机"已生效"。
5. 设备被撤销后（设备撤销），它的在途命令全部拒绝，已保存的 `command_id` 结果清除。
6. 第一阶段不改变手机能做的事，只修同步的正确性。第二阶段只做审批，不增加发送消息、启动任务等新能力。

**验证输入：** `ios/AeroricCompanionKit` 的单元测试加：同一命令重发三次；宿主重启后手机带旧 `host_epoch` 发命令；事件序号跳变；审批发出后连接中断；Mac 和手机同时回答；设备撤销。

**完成条件：** 手机上显示"已生效"的审批，Harness 一定收到了；不存在重连后重复执行的命令。

**估计：** 25–37 天（两阶段合计）。

**不做：** 不在手机上运行 Agent；不做手机端的文件编辑；不做经由第三方服务器的中继（现有的通道方式不变）。

### D5 有限的多 Agent 分工

2026-11-21 第一步已实现，见 [D5 第一步笔记](../../implemented/feature/2026-11-21-d5-work-plan-rules.md)：新对象和做法第 1–6 条的判断，纯 core，不启动会话。宿主按调度结果开委派、跟着委派卡刷新、重启后恢复（第 7 条和“宿主重启后调度状态恢复”）是第二步；Agent 提议计划、用户确认和看板界面（第 8 条）是第三步。

**前置：** B1、B3、B6；A1。

**现状：** 委派是一对一的父子关系（[委派](../../implemented/feature/2026-10-31-delegation.md)），讨论模式是 2–5 个只读成员的圆桌（[讨论模式](../../implemented/feature/2026-11-12-discussion.md)）。没有"几个子任务之间有先后依赖"的表达。调研里这类功能需求很多，失败报告也很多：无界的 Agent 群、循环等待、多个 Agent 同时写同一批文件。

**用户会看到：** 在看板上把一个目标拆成几个工作单元，画出谁依赖谁。没有依赖的单元可以同时开始；有依赖的等前置通过验收后自动开始，并拿到前置的产物作为输入。任何时候都能看到每个单元为什么在等。

**新对象：**

- `WorkUnit`：`id`、`title`、`brief`、`role`、`depends_on`、`acceptance`、`state`（未开始、等待依赖、进行中、待验收、通过、失败、已取消）、`task_id`、`outputs`（B6 的产物引用）。
- `WorkPlan`：一组 `WorkUnit`，属于一个父任务。

**做法与约束：**

1. **数量上限**：一个计划最多 8 个单元，同时运行的最多 3 个。上限是常量，不做成设置。
2. **拒绝环**：保存计划时做拓扑检查，有环则拒绝并指出环上的单元。
3. **单写者不变**：同一工作目录同一时间只有一个会写文件的单元在运行（现有的 Q-B10 约束）。并行只适用于只读单元，或各自在隔离副本里工作的单元。
4. **依赖满足的定义**：前置单元的全部验收通过且没有过期项（B3）。前置失败时，下游保持"等待依赖"并写明原因，不自动跳过。
5. **输入传递**：下游的启动说明里列出前置的产物引用，下游用 `artifact_read` 读取。不把前置的整个对话塞给下游。
6. **子任务迟到**：下游已经开始后，前置的产物又有新版本时，下游的输入标为过期，由用户决定是否重做。
7. 每个单元就是一次现有的委派。这一片只增加计划、依赖和调度，不改委派本身。
8. 计划由用户创建或确认。Agent 可以通过工具**提议**一个计划，用户确认后才生效。

**验证输入：** 有环的计划；前置失败；前置通过后其产物被撤销；两个会写的单元同时就绪（只启动一个，另一个显示"等前一个写完"）；宿主重启后调度状态恢复。

**完成条件：** 任何时刻每个单元的状态都能用一句话解释；不会出现两个会写的单元同时在同一目录运行。

**估计：** 15–25 天。

**不做：** 不做 Agent 自行无限拆分；不做跨项目的计划；不做 Agent 之间的自由聊天通道。

### D6 Computer Use：推迟，写明重启条件

**结论：** 这一片现在不做。

**原因：** 通用的桌面操作目前无法满足项目的硬约束。实际使用中已经确认，现有的 Computer Use 执行方式会抢键盘焦点和鼠标。调研里这类功能的失败报告也集中在这里：误点、操作到错误的窗口、用户同时在用电脑时互相干扰。

**重启条件（全部满足才重新评估）：**

1. D3 的焦点实验通过，并且 D3 的动作回执模型在浏览器上运行了一段时间。
2. 存在针对单个应用、不经过全局输入事件的驱动方式（应用自己的脚本接口或辅助功能接口），并且能证明不影响前台应用。
3. 能为每个目标应用单独验证：窗口身份怎么确认、动作后怎么验证、失败怎么恢复。

**届时的形态：** 逐个应用接入，每个应用一份验证记录；复用 D3 的 `BrowserTarget` 思路（目标身份加文档版本）和四级动作状态。不做"能操作任意应用"的通用能力。

见 [暂缓的新增项](./2026-11-08-new-addition-deferred.md)。

## Alternatives considered

**先做浏览器，因为它是调研里请求最多的。** 它最强的理由是用户价值最大，也是和同类产品差距最明显的地方。没选它，因为它的前置最多、工期最长，而且有一个可能直接否决方案的实验。GitHub 只读审查工期短、不产生对外副作用，能先验证"固定版本 → 审查 → 有依据的结论"这条链路，这条链路浏览器和手机也要用。

**D1 和 D2 合成一片，直接做完整的 PR 审查。** 它最强的理由是只读审查的价值有限，用户最终要的是把评论发出去。没选它，因为读和写的风险完全不同。只读部分出错只是显示不对；写的部分出错会在公开的 PR 上留下错误或重复的评论。分开后 D1 可以先交付并积累对快照模型的信心。

**D4 通过云端中继让手机在任何网络下都能连上。** 它最强的理由是可用性，现在的方式要求手机能直接连到 Mac。没选它，因为这会引入一个需要运营的服务，并让会话内容经过第三方。现有通道的端到端加密和直连是有意的设计。

**D5 采用调研里某些项目的做法：让一个"主管"Agent 自行决定拆分和调度。** 它最强的理由是用户不必手工画依赖。没选它，因为调研里这类功能的问题报告最多：无界拆分、成本失控、循环。这里让 Agent 只能提议、由用户确认，并加数量上限。

**D6 现在就做一个受限版本，只在用户明确让出电脑时运行。** 它最强的理由是有些任务确实只能通过桌面操作完成。没选它，因为"用户让出电脑"无法可靠判断，而且没有动作回执模型时，出了错无法知道做到了哪一步。

## Acceptance criteria

- 每片开工前，它的前置条件在对应批次笔记里已转为 implemented。
- D1 完成时，假 GitHub 服务的请求日志里只有读请求。
- D2 完成时，重复发布、响应丢失、目标更新三种情形各有测试，且都不产生重复评论。
- D3 开工前，焦点实验的结论笔记已存在且结论为可行。
- D4 两个阶段分别验收；第一阶段不增加手机端的能力。
- D5 的数量上限、拒环、单写者三条各有测试。
- 所有对外写操作（D2 发布、D3 有副作用的动作）都经过用户确认，没有任何路径能由 Agent 单独完成。
- `cargo test --manifest-path core/Cargo.toml --workspace`、`swift test --package-path macos/AeroricKit`、`swift test --package-path ios/AeroricCompanionKit` 通过。真实 GitHub、真实浏览器、真机的验证记为 NOT RUN，并写明需要的条件。
- 界面变化记入路线文档 §8 待目检清单。

## Risks

- **GitHub 接口的限流和权限模型。** 细粒度令牌对检查和评论的权限各不相同。D1 要把"没权限"和"没有数据"分开显示，否则用户会以为 PR 没有检查。
- **D1 抓取 PR 引用会增大本地仓库。** 专用引用要有清理：快照被删除时删除对应引用。清理前按项目规则确认引用是 Aeroric 自己创建的。
- **D2 的"不可见标记"依赖 GitHub 保留 HTML 注释。** 实现前确认；如果不保留，改用评论正文的哈希加时间窗口匹配，并接受更高的"不明"比例。
- **D3 的实验可能不通过。** 那样浏览器这一片搁置，D6 也随之搁置。总纲已把这一点列为所有者决策。
- **D4 的工期最长，且真机验证目前暂停。** 单元测试只能覆盖协议和状态机；真实网络下的表现要等验证恢复。第一阶段风险较低，可以先做。
- **D5 的上限可能被认为太小。** 8 个单元、3 个并行是保守值。先用这个值积累使用情况，再决定是否调整；调大比调小容易。
- **这一批整体工期约 3–5 个月。** 期间前面批次的对象可能还在调整。每片开工时按总纲 §4 第 2 步重新核对它依赖的类型和位置。
