# Agent Note: 调研落地批次 C：闭合记忆、网关、技能与 Harness 能力清单

Status: proposed

## Problem

[落地总纲](../architecture/2026-11-15-research-adoption-roadmap.md) 的批次 C 处理四个已经存在、但各自还差最后一段的子系统。调研里把它们叫"接近闭环"：主体都在，缺的是让用户能核对、能撤回、能解释的那一段。

- **记忆。** 一条记忆的依据只有一段摘录和哈希，找不回原文在会话里的位置。用户删掉一条记忆后，由它派生出来的东西（搜索索引、技能候选、Wiki 贡献、正在进行的整理）不一定跟着消失。整理记录只有结束后的状态，看不到排队和进行中。
- **网关。** 用量按请求记一行。一次请求内部重试了三次，只看得到次数，看不到每次去了哪里、各花了多少。上游没返回用量时记成 0，和"真的是 0"分不开。缓存写入的 5 分钟档和 1 小时档合在一个数里，而两者价格不同。连接测试走的出口和真实推理走的出口可能不是同一条。
- **技能。** 内置技能、记忆沉淀出的技能、用户目录里的技能各有各的来源。一次会话到底挂载了哪些技能、各是哪个版本、为什么挂载，没有一处能查。
- **Harness 能力。** Aeroric 给 Claude 和 Codex 注入了 Context 工具，但 OMP 和 DSH 没有。会话启动时实际生效的工具有哪些，界面和 Agent 自己都说不清。工具调用的返回是一段文字，调用方分不出"成功""部分成功""需要重试"。

本篇拆成 9 片，分四组：C1–C3 记忆，C4–C6 网关，C7 技能，C8–C9 Harness 能力。组与组之间没有依赖；组内按编号顺序做。

位置都是 `main@8d4391c3` 上的。这一批里"动手前复核"的条目比 A、B 多，因为调研的不少结论来自静态阅读，这次没有逐行核对。

## Proposal

### C1 记忆的依据能定位到原文

**用户会看到：** 打开一条记忆的依据，能跳到来源会话里的那条消息，原话高亮。来源会话已被删除或内容已变时，写明"原文已不在"或"原文之后改过"，摘录仍然显示。

**现状：** `core/crates/aeroric-protocol/src/memory.rs:141` 的 `Evidence` 有 `task_id`、`harness`、`model`、`excerpt`、`hash`、`at_ms`。没有消息 id、角色和原文中的位置。

**改法：**

1. `Evidence` 加可选字段：`message_id`、`role`（用户、助手、工具）、`span`（在该消息文本里的起止字符位置）、`source_version`（来源会话历史在抽取时的版本标识，可用历史文件的长度加末尾哈希）。
2. 抽取（`core/crates/aeroric-core/src/memory/extract.rs`）要求模型在返回每条候选时附带它所依据的消息序号；core 把序号换成消息 id，并用摘录在消息里定位 `span`。定位不到时这三个字段留空，不猜。
3. 新方法 `memory.evidence_locate(itemId, index)`：返回当前能否定位、定位到的消息、原文是否与 `hash` 一致。
4. Swift：依据行加"在会话里查看"。
5. 旧记忆不回填；显示"这条记忆的来源位置没有记录"。

**验证输入：** 来源会话被压缩成 `.jsonl.zst`（见最近的提交 5e9be8a4）；来源会话被删除（来源消失）；来源消息被 Harness 的压缩改写。

**完成条件：** 新抽取的记忆里，至少有一条依据能定位到具体消息；定位不到的如实显示。

### C2 删掉一条记忆，派生的东西一起撤

**用户会看到：** 删除或归档一条记忆后，搜索不再命中它，由它促成的技能候选标为"依据已撤回"，Wiki 里引用它的贡献标为待核对。正在进行的整理不会把刚删掉的内容重新写回来。

**现状（调研给出，动手前逐项复核）：** 记忆库的状态变化（`memory/store.rs`）与派生数据之间没有统一的传播。可能的遗漏点：全文索引、`memory/skills.rs` 的技能候选依据、Wiki 贡献（`knowledge/`）、在途的抽取任务（`memory/run.rs`、`memory/barrier.rs`）。

**改法：**

1. 先写一张清单：记忆条目被哪些地方引用或复制。清单进笔记，逐项标注"已随状态变化更新"或"未更新"。
2. 记忆库加一个单调递增的 `epoch`。删除、归档、取代都使它加一。
3. 抽取开始时记下 `epoch`；写入结果前比较。期间有删除发生时，丢弃与被删条目文本哈希相同的候选，并在整理记录里写明丢弃了几条和原因（整理中遗忘）。
4. 技能候选和 Wiki 贡献保存它们所依据的记忆 id。记忆被删时，候选标"依据已撤回"，由用户决定保留还是丢弃；**不自动删除**用户已经采纳的技能。
5. 删除操作返回传播结果：影响了几处、哪几处没成功。没成功的进"需要我处理"。

**验证输入：** 抽取进行到一半时删除一条将被重新抽出的记忆；删除一条已促成技能候选的经验；传播到索引时注入写失败（落盘失败）。

**完成条件：** 清单里的每一处都有对应测试，证明删除后不再能通过那一处读到该记忆的内容。

### C3 整理过程看得见，写入结果逐条有交代

**用户会看到：** 整理记录里能看到排队中和进行中的整理，可以取消。结束后每条候选都有结果：写入了、与已有的合并了、被用户规则拦下了、写入失败。记忆被反复引用时，"用过几次"按独立的任务计数，同一个任务里引用十次算一次。

**现状：** `memory.rs:238` 的 `MemoryRunState` 只有 `Done`、`Partial`、`Failed`、`Skipped`，都是结束态。`MemoryRun` 有 `failed_writes` 计数但没有逐条结果。使用统计在 `MemoryStats`（动手前复核它的去重方式）。

**改法：**

1. `MemoryRunState` 新增 `Queued`、`Running`、`Canceled`。新增值只追加，旧客户端把不认识的值显示为"进行中"。
2. `MemoryRun` 加可选的 `outcomes`：每条候选的文本哈希、结果类别、失败原因、对应的记忆 id。
3. 新方法 `memory.run_cancel(runId)`。取消只影响尚未写入的候选；已写入的不回滚，并在记录里写明。
4. 失败重试只重试失败的候选，不重新调用模型（候选内容保存在运行记录里，设保留期）。
5. 使用反馈按 `(记忆 id, 任务 id)` 去重。
6. 索引损坏时提供"重建索引"，作为一种运行类型出现在整理记录里。

**验证输入：** 运行中取消；宿主在运行中重启（恢复为失败并可重试，不是静默消失）；同一任务对同一记忆多次反馈。

**完成条件：** 任意时刻整理记录与实际进行的整理一致；每条候选的去向都能查到。

### C4 网关按每次尝试记账，缺失的用量不算零

2026-11-19 第一步已实现，见 [C4 第一步笔记](../../implemented/feature/2026-11-19-c4-gateway-attempts.md)：每次尝试一行（`router_attempts`，被熔断跳过的也记），用量来源分"上游报告/未知"，缓存写入分两档，汇总单列"用量未知的请求数"，宿主新增 `gateway.requests` 读出记录。和下文的出入：未知时用量列仍存 0（列是 NOT NULL，改可空要重建表），由来源列排除；动手前发现这份记录此前没有任何地方读。第二步也已实现，见 [C4 第二步笔记](../../implemented/feature/2026-11-19-c4-usage-unknown-shown.md)：回合账单没记用量时写"用量未知"、卡片写"未记录"（账单仍读会话文件，不改读网关记录）；配额节奏读的是已用百分比，不涉及；"用量与成本"页加"网关请求"一节，点开看每次尝试。

**用户会看到：** 用量页里一次请求可以展开，看到每次尝试：去了哪个连接、用了哪个模型、状态、耗时、用量。用量来自上游报告、Aeroric 估算、还是未知，各有标记。缓存写入分 5 分钟和 1 小时两档。

**现状：** `core/crates/aeroric-core/src/local_router/usage.rs:32` 的 `RouterRequestRecord` 每个请求一行，有 `attempt_count`，但没有各次尝试的明细。`cache_creation_tokens` 是单个数（`:45`），表结构里默认值为 0（`:321`），解析在 `:663` 附近。上游不返回用量时与真实的 0 无法区分。

**改法：**

1. 新表 `router_attempts`：`request_id`、`attempt`（序号）、目标连接、出站模型、状态码、耗时、四项用量、错误摘要、是否被熔断器跳过。现有的请求行保留为汇总。
2. 用量加来源标记 `usage_source`：`reported`、`estimated`、`unknown`。请求行和尝试行都加。`unknown` 时用量列存空值，汇总时不计入并单独统计"有几次请求的用量未知"。旧数据标 `reported`（无法追溯）并在迁移说明里写明。
3. 缓存写入拆成 `cache_write_5m_tokens`、`cache_write_1h_tokens`，保留原列作为合计。上游只给合计时，两个新列为空，不按比例猜。
4. 账单（[回合账单](../../implemented/feature/2026-11-09-turn-bill.md)）和配额节奏（[配额节奏](../../implemented/feature/2026-11-10-quota-pace.md)）读新字段：未知用量的回合显示"用量未知"，不显示 0。
5. Swift 用量页加展开和来源标记。

**验证输入：** 第一次尝试 429、第二次换连接成功；流式响应中途断开且没有用量事件；上游返回分档的缓存写入；旧库升级。

**完成条件：** 一次有重试的请求，各次尝试的用量之和等于请求行的合计（未知的除外，且未知被明确标出）。

### C5 连接测试和真实请求走同一条出口

2026-11-19 第一步已实现，见 [C5 第一步笔记](../../implemented/bug-fix/2026-11-19-c5-gateway-honours-connection-proxy.md)：核对出网关一律直连、不看连接的"使用全局代理"，而测试和目录会走代理；现在四处共用 `connection_proxy` 和同一套代理规则，网关按连接的选择走代理，由假代理测试断言三条路径的目标、代理和密钥一致。第 3、4 条（测试结果带修订号、"需要重测"、写明费用）留到第二步。

**用户会看到：** 设置里"测试连接"通过后，真实会话不会因为走了另一条路而失败。测试结果写明测的是哪个端点、哪个凭据、配置的哪一版。配置改过之后，旧的测试结果标为"配置已变，需要重测"。

**现状（调研给出，动手前复核）：** 模型目录拉取、连接测试和推理请求各自构造出站请求，代理设置、请求头、凭据解析可能不一致。相关代码在 `core/crates/aeroric-core/src/local_router/`、`connections/`、`providers/`。

**改法：**

1. 找出三条路径各自构造 HTTP 客户端和凭据的位置，列进笔记。
2. 抽出一个共用的"出口描述"：provider、端点、凭据引用（不是凭据本身）、代理、配置修订号。三条路径都从它构造客户端。
3. 测试结果持久化时带上出口描述的摘要和配置修订号。读取时比较修订号。
4. 测试只发最小的真实请求（目录或一次极短的补全），并在界面上写明会产生的费用量级。

**验证输入：** 假上游只接受带特定请求头的请求；测试后修改代理设置；凭据引用被轮换。

**完成条件：** 三条路径对同一连接发出的请求，目标地址、代理和认证头一致（由测试断言）。

### C6 额度恢复后自动续跑（默认关闭）

**用户会看到：** 回合因额度用尽停下时，卡片上有"额度恢复后自动继续"的开关，默认关。打开后显示预计恢复时间；到时间后自动发出同一条输入，并写明"这是额度恢复后自动续跑的"。

**现状：** 配额读数和节奏提示已落地（[配额节奏](../../implemented/feature/2026-11-10-quota-pace.md)）。因额度停下的回合需要用户手动重试。

**改法：**

1. 只在回合的失败原因被明确识别为额度用尽、且配额读数给出了恢复时间时提供开关。
2. 续跑走投递队列：一条 `Waiting` 的投递，带"不早于某时间"的条件。队列目前没有定时条件，需要加一个可选字段。
3. 续跑用原回合的操作键派生新键，保证宿主重启后不会发两次。
4. 以下情况取消续跑并告知：用户在此期间发了新消息、任务被停止、恢复时间到了但读数仍显示用尽（顺延一次，再失败则放弃）。
5. 续跑**不改变权限模式，不代替用户批准任何东西**。

**验证输入：** 恢复时间前宿主重启；恢复时间到达时用户正在输入；读数接口不可用。

**完成条件：** 开关打开的回合恰好续跑一次，或以明确原因取消。

### C7 技能目录：每次会话挂了哪些技能、哪个版本、为什么

**用户会看到：** 设置里有一个技能目录，列出全部技能及其来源（内置、记忆沉淀、用户目录、插件）、当前版本、内容摘要。会话信息里列出这次会话挂载的技能，每个写明原因（默认挂载、角色要求、用户选的）。

**现状：**

- 内置技能在 `core/crates/aeroric-core/src/extensions/builtin_skills.rs`（[内置技能](../../implemented/feature/2026-10-30-builtin-skills.md)）。
- 记忆沉淀的技能在 `memory/skills.rs`，协议里有 `SkillVersion`、`SkillProposal`（[记忆技能](../../implemented/feature/2026-10-31-memory-skills.md)）。
- 用户目录和插件技能在 `extensions/skills.rs`、`extensions/plugins.rs`。
- 调研称科学类技能是构建时内嵌的，界面上看不到版本和来源；Skill Hub、MCP 管理、插件管理的界面与后端的接线不完整（动手前逐个复核，如实记录每个入口的真实状态）。

**改法：**

1. 协议新增 `SkillDefinition`：`id`、`name`、`source`、`version`（内容哈希加可读版本号）、`path` 或内嵌标记、`summary`。四种来源都投影成它；各自的存储不动。
2. 新方法 `skills.catalog()`。
3. 会话启动时记录 `MountedSkill`：`skill_id`、`version`、`reason`。存进任务的启动记录，B7 的输入清单从这里读技能版本。
4. 内嵌技能在目录里写明"随应用内置，版本同应用"。
5. 逐个检查 Skill Hub、MCP 管理、插件管理的入口：能用的保留；后端没接的，界面上要么接上，要么移除入口或标"尚未提供"。**不留点了没反应的按钮。**
6. Swift：设置里的技能目录页、会话信息里的挂载列表。

**验证输入：** 四种来源各一个假技能；同名技能来自两个来源（目录里两条都列，写明哪个生效）；会话中途技能被升级（已启动的会话仍显示启动时的版本）。

**完成条件：** 任意一次会话，能查到它启动时挂载的每个技能及版本。

### C8 Harness 有效能力清单

**用户会看到：** 会话信息里有"这次会话能用的工具"：Aeroric 注入了哪些、Harness 自带哪些已知的、哪些因为什么原因没注入。Agent 调用 Aeroric 的工具后，拿到的结果分得清成功、部分成功、需要重试、被拒绝。

**现状：**

- Context 工具只注入本机的 Claude 和 Codex（`core/crates/aeroric-core/src/sessions/live/context_server.rs`）。
- `core/crates/aeroric-cli/src/mcp_context.rs:306–352` 的 `call_tool` 把宿主返回压成一段文字，只有 `isError` 一个布尔值。
- `:368–373`：按行读标准输入，没有单行长度上限；解析失败的行被静默丢弃，调用方收不到任何回应。
- 能力表（[能力表与登录](../../implemented/feature/2026-11-03-capabilities-and-login.md)）描述的是 Harness 支持什么功能，不描述这次会话实际注入了什么工具。

**改法：**

分三步，每步可单独交付。

**第一步：清单。**

1. 会话启动时生成 `EffectiveToolCatalog`：每个工具的名称、所属（Aeroric 注入、Harness 自带）、作用范围（只读、会写、会对外发送）、是否已就绪及依据、未注入的原因。存进启动记录。
2. `session.capabilities` 的返回加可选的 `tools` 字段。
3. Swift：会话信息里显示。

**第二步：结构化结果。**

4. `call_tool` 的返回除文字外加 `structuredContent`：`status`（成功、部分、需要重试、被拒绝、不明）、`operation_id`（有副作用的调用）、`cursor`（还有更多）、`artifact_refs`（B6）。文字部分保留，旧 Harness 不受影响。
5. 标准输入读取加单行字节上限。超限时返回结构化错误：`limitKind`、`allowed`、`observed`、`retryable`。解析失败且能取到 `id` 时返回 JSON-RPC 错误，不再静默丢弃。
6. 有副作用的工具（`delegate`、`board_write`、`board_decide`、`memory_propose`）接受调用方提供的幂等键；重复调用返回第一次的结果。

**第三步：触发评测。**

7. 给每个工具写 3–5 条"应该触发"和"不应该触发"的提示，用假 Harness 跑通流程，真实 Harness 的评测记为 NOT RUN 并写明需要的条件。评测集放在仓库里，作为以后改工具描述时的回归输入。

**验证输入：** 超长单行；非法 JSON；同一幂等键调用两次；宿主在调用中途断开（做了没回执）；工具清单与实际注入不一致时的启动。

**完成条件：** 界面上的工具清单与启动参数里实际注入的一致（由测试比较两者）；任何一次工具调用都有回应。

### C9 OMP 和 DSH 接上 Context 工具，或如实写明没接

**用户会看到：** OMP、DSH 会话的工具清单里，Aeroric 工具要么可用，要么写着"这个 Harness 还不能接入 Aeroric 工具"和原因。委派、看板、记忆这些依赖工具的功能，在不可用的 Harness 上入口是灰的。

**现状：** 注入只覆盖本机 Claude 和 Codex。OMP 相关代码在 `core/crates/aeroric-core/src/agents/omp.rs` 和 `sessions/live/omp/`，DSH 在 `agents/dsh_host/`。两者是否支持 MCP 服务器配置需要实测（2026-11-16 更新：OMP 的这部分已在 [各 Harness 原生融合](../architecture/2026-11-16-harness-native-capabilities.md) §2 查清，上游支持，接线在那篇的 H2 做，本片不重复；本片只剩 DSH）。远端会话（[远端会话走本机网关](../../implemented/feature/2026-10-28-remote-sessions-through-local-gateway.md)）同样没有注入。

**改法：**

1. 先做事实核对：OMP 的 RPC 模式和 DSH 各自能否在启动时配置一个 stdio MCP 服务器。结论写进 `docs/subsystems/agent-capabilities.md`。
2. 能配置的：补注入，并为该族写一条用假进程的启动测试，断言启动参数里有 Context 服务器。
3. 不能配置的：C8 的清单里写明原因；能力表里 `DelegateChild`、`Reviewer` 等依赖项相应置为 `No`。
4. 远端会话：Context 服务器需要连回本机宿主。这一片只写明"远端未接入"；接入方案留给批次 D 的 D4，那里会处理跨设备的身份和回执。
5. 与 [ACP 方言](../../implemented/feature/2026-11-08-acp-dialects.md) 的关系：如果那一篇先落地，注入点改在 ACP 层；否则各族分别处理。

**验证输入：** 各族的启动参数快照；能力表快照。

**完成条件：** 不存在"界面上有入口、但这个 Harness 实际调不到工具"的功能。

## Alternatives considered

**C2 用调研建议的全局"事实管理器"，所有派生数据都登记依赖关系，删除时沿图传播。** 它最强的理由是一劳永逸，以后新增派生数据只需登记。没选它，因为现在的派生点是可以数清的几处，一张清单加逐处测试更容易验证；图结构本身会成为新的出错来源。总纲 §6 已把它列为明确不做。

**C4 不加尝试表，把各次尝试序列化进请求行的一个 JSON 列。** 它最强的理由是不需要新表和联表查询。没选它，因为按连接统计失败率、按尝试汇总用量都要查这些数据，JSON 列不能高效聚合。

**C6 额度恢复后默认自动续跑。** 它最强的理由是多数用户希望如此，开源项目里这是最常被请求的功能之一。没选它，因为自动续跑会在用户不在场时消耗额度并修改文件；默认关闭、逐回合打开，符合"不代替用户做决定"的原则。等使用数据显示多数人都打开再考虑改默认值。

**C8 不做结构化结果，只在文字里约定前缀（如"部分成功："）。** 它最强的理由是所有 Harness 都能读文字，零兼容风险。没选它，因为 MCP 规范已经有 `structuredContent`，约定前缀需要每个调用方自己解析，而且容易被模型改写。文字部分仍然保留，兼容性不受影响。

**C7 把四种技能来源合并成一个存储。** 它最强的理由是模型最干净。没选它，因为四种来源的生命周期不同（内嵌的随应用、记忆的有审批、用户目录的由用户管理），合并存储要迁移数据且没有用户可见的收益；统一投影已经能回答"挂了什么"。

## Acceptance criteria

- C2 的派生点清单写进笔记，每一处有测试。
- C4 的库迁移有升级测试：旧库升级后原有数据可读，新列为空或有明确的默认标记。
- C7 完成后，Skill Hub、MCP 管理、插件管理三个入口各有一句当前事实写进 `docs/subsystems/macos-app.md`。
- C8 第一步完成后，工具清单与启动参数的一致性由自动测试保证。
- C9 的事实核对结论写进 `docs/subsystems/agent-capabilities.md`。
- `cargo test --manifest-path core/Cargo.toml --workspace`、`cd core && cargo fmt --check`、`swift test --package-path macos/AeroricKit` 通过。
- 协议变化都是新增；`contracts/native/v1/**` 同步。
- 界面变化记入路线文档 §8 待目检清单。

## Risks

- **C1 依赖模型返回正确的消息序号。** 模型可能给错。core 必须用摘录在该消息里实际匹配，匹配不上就不记位置；不能相信模型给的序号。
- **C2 的清单可能不全。** 静态阅读可能漏掉某个缓存。补救是加一条端到端测试：删除后，通过所有对外的读取方法（搜索、召回、技能目录、Wiki 搜索、Context 工具）搜索该记忆的一段独特文本，都不应命中。
- **C4 会增加写入量。** 每次尝试一行。按现有的保留策略清理；实现前确认请求表的清理逻辑会连带清理尝试表。
- **C5 可能改变现有连接的行为。** 统一出口后，以前靠不一致"碰巧能用"的配置可能失效。上线时对每个已有连接重跑一次测试并提示结果。
- **C6 与"不在用户不知情时花钱"之间有张力。** 开关是逐回合的，续跑前的预计费用无法给出。卡片上要写明"续跑会继续消耗额度"。
- **C8 的结构化结果可能让某些 Harness 的旧版本报错。** 实现前在三个 Harness 上各确认一次对未知字段的容忍度；不容忍的族不发 `structuredContent`，并在工具清单里注明。
- **C9 可能得出"OMP、DSH 都接不了"的结论。** 那样这一片的产出就是如实置灰。这仍然是有价值的结果，但要在总纲的决策里告诉所有者，由其决定是否为这两族做别的接入方式。
