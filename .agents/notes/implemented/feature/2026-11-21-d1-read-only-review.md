# Agent Note: D1 第二步：在 PR 自己的检出里只读审查，结论存成草稿

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D1 做法第 3–5 条：

- 把 PR 的 head 和 base 取到本地仓库的专用引用下（`refs/aeroric/pr/<编号>/<提交>`），不动用户的分支和工作区；
- 审查任务在隔离副本里检出，用只读角色启动，提示词里给出快照的文件、检查和已有评论；
- 审查结论解析成条目，每条绑定路径、行号和 head 提交。

[第一步](2026-11-21-d1-pull-snapshots.md)已经能把 PR 固定成快照（`main@c7132258`）。动手前核对的事实：

- **[隔离副本](2026-11-05-isolated-copy.md)不适合 PR。**
  - 它为“在副本里改、再把改动逐块带回原目录”设计。起点是原目录现在的样子，包括未提交的改动，并且记着基线；
  - PR 审查的起点是一个别人推上去的提交，什么也不带回。
  - 能复用的只有两样：`.aeroric/` 目录写进 `info/exclude`，以及 `isolated_copy::check` 判断是不是有提交的 Git 仓库。
- **会话的工作目录来自任务记录的 `worktreePath`**（`launch_plan::working_directory`）。审查循环开审查者时，就是把写入者的 `worktree*` 字段抄过去。
- **只读的做法已有先例。** 讨论成员和只读委派用 `permission_mode: "plan"`，由 Harness 自己守住只读（A4 的 `StrictReadOnly`）。
- **PR 的提交在 GitHub 上的引用是 `refs/pull/<编号>/head`**，可以直接 fetch。

## Decision

**取代码**（`github::review::fetch`）：

- 把 `+refs/pull/<编号>/head` 取到 `refs/aeroric/pr/<编号>/<head 前 12 位>`。
- 取到的提交必须就是快照的 head。不是的话，说明 PR 在快照之后又推过，就删掉这个引用，报“PR 在快照之后又有了新提交（现在是 …），先刷新快照再审”。
- 引用已经指向这个 head 时，不再联网。
- base 提交在本地没有时，顺带取一次 base 分支；取不到不影响审查 head。
- **从哪里取**（`remote_for`）：用户已有的、指向这个仓库的远端优先（SSH 写法和 https 写法都认），这样用的是用户自己的凭据；没有就用 `https://<主机>/<所有者>/<仓库>.git`。

**检出**（`checkout`）：

- 在 `<仓库>/.aeroric/pr-reviews/<快照 id>` 用 `git worktree add --detach` 检出 head。已经检出在这个 head 上的直接复用。
- `.aeroric/` 照隔离副本的做法写进 `info/exclude`，不会出现在用户的未跟踪文件里。

**审查会话**（宿主 `github.reviewStart {projectId, snapshotId, agent?}`）：

- 新建一个任务：
  - Harness 默认 Claude，也可以指定 Codex；
  - `permission_mode: "plan"`；
  - `worktreePath` 指向检出的目录；
  - 标题是“审查 PR #编号：标题”。
- **提示词**（`prompt`）写明：
  - PR 编号、标题、仓库、作者，head 和目标分支；
  - 看改动用 `git diff <合并基>...HEAD`；
  - 只读，不改文件，不提交，不向 GitHub 发任何东西；
  - 变更文件最多列 120 个，其余写个数；
  - 检查结果；
  - 已有评论最多 20 条，标出针对旧版本的，并提醒别重复提；
  - 最后放一个 json 代码块：`{"findings": [{path, line, severity, body, basis}]}`。
- 快照已被同一个 PR 更新的快照取代时，拒绝审这份旧的。

**读结论**（`github.review {projectId, id}`、`github.reviews {projectId}`）：

- 审查会话还在跑时，原样返回。
- 跑完以后，取会话的最后一条回答，用 `findings` 解析：
  - 取最后一个 json 代码块；没有代码块时，取最后一个 `{"findings"…}`；
  - 路径必须是 PR 里的文件，前面的 `./` 或 `/` 去掉。快照的文件列表不完整时，检出里存在的文件也认；
  - 正文为空的丢掉；
  - 行号超出这个文件在 head 上的行数时，去掉行号，条目保留；
  - 严重程度只认 high、medium、low，别的按 medium；
  - 最多 50 条。
- **结果：**
  - 解析出来（包括空列表）就记成“完成”，存进 `<数据目录>/github/<项目>/reviews/<id>.json`；
  - 没有结论块就记成“失败”并写原因。之后再读时会重新解析，所以在会话里让审查者补上，就能变成“完成”。
- 快照被新的取代以后，这份审查标“针对旧版本”。

全程只向 GitHub 读：取代码是 git fetch，第一步的 HTTP 请求只有 GET。

## Alternatives considered

**照方案用隔离副本。** 最强的理由是方案写了，而且副本已经管好了目录、清理和带回改动。没选：

- 副本从原目录现在的样子开始，会把用户没提交的改动带进 PR 的审查；
- 它的“带回改动”在只读审查里用不上；
- 要从一个提交开始，就得给它加一种起点，改动比单独检出一个提交大。

**审查结论让 Agent 调一个工具交回来，不解析回答。** 最强的理由是结构可靠，不怕格式出错。没选，至少这一步不做：

- 现有的 Context 工具里没有“交 PR 审查结论”这一项。为一个入口加工具，要过 C8 的评测集和 H8 的三档；
- 读回答里的 json 块，也能在会话外补救：让审查者补上，再打开一次即可。

**会话一结束就由宿主主动解析并存盘。** 最强的理由是列表打开时不用等。没选：

- 要在回合结束的钩子里加一条分支；
- 读的时候解析，代价只是一次读会话记录，而且审查者后来补的结论也能被认到。

## Consequences

- **收益：**
  - 选定的快照能在它自己的检出里被只读审查，用户的分支、HEAD、未提交改动都不动；
  - 结论按 PR 的文件和 head 上的行核对过；
  - PR 更新后，旧结论标出“针对旧版本”。
- **代价：**
  - 每份快照在仓库里多一个 worktree 和一个引用，这一步还没有清理；
  - 每次读审查列表，都会重读一次还没完成的审查会话的记录。
- **局限：**
  - 没有界面；
  - 只认 GitHub 的 `refs/pull/<n>/head`；
  - 远端项目（SSH、WSL）不能审；
  - 结论靠回答里的 json 块，审查者没按格式写时要用户去会话里催；
  - 不能选模型和 Agent 配置，只能选 Harness。
- **验证：**
  - core 新增 5 个测试，测试用本地仓库充当 GitHub：
    - head 取进专用引用并分离检出：用户的 HEAD、分支、未提交改动都不变，检出不出现在 `git status` 里；再来一次复用，不联网；
    - 快照之后 PR 又推过：拒绝，并删掉取到的引用；
    - 已有的 SSH 写法远端被认出来，没有时用 https 地址；
    - 提示词各部分齐全；结论只留 PR 里的文件，超出行数的去掉行号，未知严重程度按 medium，没有块时返回空；
    - 审查草稿按项目存，快照被取代后标“针对旧版本”。
  - 宿主新增 1 个测试：
    - 没有快照、项目不是 Git 仓库都拒绝；
    - 用 git 的 `insteadOf` 把 GitHub 地址指到本地仓库后，开始审查：假 Claude 在检出目录里以 plan 权限启动，检出在 PR 的 head 上，用户的 HEAD 不变，列表里有这份审查。
- **NOT RUN：**
  - 对真实 GitHub 的 fetch；
  - 真实审查者能不能按格式交回结论。
