# Agent Note: 定时任务第二批：常用模板、上一次还在跑时结束后补一次、活跃时段

Status: implemented

## Problem

[定时任务第一批](2026-11-14-scheduled-tasks.md)只做了"到点开会话"的最小链路，有三处不便：

- **新建时从零写起**：backlog A12 列了一组例行的代码工作（审查、依赖更新、测试覆盖、TODO 清理、CI 排查、发布说明、安全审计、项目体检），用户每次都要自己写提示词和检查命令。
- **上一次还在跑就只能跳过**：每 2 小时一次的规则，碰上一次跑了 3 小时的会话，中间那次就丢了。backlog A12 写的是"会话忙时排队"，工作安排设计稿则是"默认跳过，可选结束后补一次，最多保留一个"。
- **没有活跃时段**：间隔型规则半夜也会开会话。backlog 把它记作 X23"活跃时段与忙时排队"。

用户 2026-11-14 说"全部按推荐"，定了 5 条：

1. 下一项做定时任务第二批。
2. 顺带修"选中坏的 claude"，见[另一篇](../bug-fix/2026-11-14-broken-cli-copy-on-path.md)。
3. 新建弹窗加 8 个"从模板开始"的胶囊，只预填，全都可以改；模板只放在 Swift 端。
4. 每条规则可选"上一次还在跑时：跳过（默认）/ 结束后补一次"，最多攒 1 次；补跑照样受每天上限、额度和前置检查约束。
5. 每条规则可选活跃时段，可以跨午夜；时段外到点的推迟到下一段开始时补一次，复用额度推迟那一套补跑机制；不做全局时段、写入系统日历和 cron。

## Decision

**协议**（`aeroric_protocol::schedule`）

- 规则新增两个设定：
  - `when_busy: WhenBusy`：`skip`（缺省，不写盘）或 `after`；
  - `active_hours: Option<ActiveHours { start_minute, end_minute }>`：本地时间，结束早于开始表示跨午夜。
- 规则新增两个状态，由宿主写，保存规则时清掉：
  - `hours_retry_ms`：时段外被推迟的那一次，在这个时间补跑；
  - `busy_pending`：有一次在等上一次的会话结束。
- 运行结果新增两种：
  - `Queued`："上一次还在跑，结束后补跑"；
  - `OutsideHours`：不在活跃时段而推迟，`retry_ms` 是补跑时间。

**调度**（core `schedule::tick` / `fire`）

- `fire` 的检查顺序：活跃时段（"立即运行"不查）→ 上一次还在跑 → 每天上限 → 额度 → 前置检查 → 开会话。
- **上一次还在跑**：
  - `skip`：照旧记为 `Busy`；
  - `after`：记为 `Queued`，并带上那个会话的 id，规则标上 `busy_pending`。
- **活跃时段外**：记为 `OutsideHours`，补跑时间是 `calendar::next_hours_start`，即下一段的开始。说明写"不在活跃时段 09:00–18:00，推迟到 11月17日 09:00 补跑"。
- **`tick` 把三种推迟一并处理**：额度（`quota_retry_ms`）、时段（`hours_retry_ms`）、等会话（`busy_pending` 并且上一次的会话仍在跑）。
  - 推迟期间到了新的正常时间，只把 `last_due_ms` 前移，不写记录，合进那一次补跑。
  - 推迟到期（或会话结束）后补跑一次，代表最近一个被推迟或被合并的时间。
  - 跑完按结果重设这三个状态。
  - 一次性规则只要被推迟，就保持开启，等补跑。
- **下次时间**：`list` 的 `next_ms` 依次取额度补跑时间、时段补跑时间，都没有才算正常的下一次；正常的下一次落在活跃时段外时，显示下一段的开始，因为到点时会被推迟到那里（2026-11-15 目检：时段 05:25–06:25 的规则原来写"下次 05:21"）。等会话的规则，下次时间要看会话什么时候结束，界面上直接写"结束后补跑"。
- **校验**：时段的开始和结束都要在一天之内，并且不能相同。
- **时间判断**（`calendar::in_hours` / `next_hours_start`）：按本地的时和分判断；夏令时跳过的时刻放行。

**界面**（Swift）

- **新建弹窗顶部**："从模板开始"一排胶囊（`ScheduleTemplate.all`，8 个）。点一个，填入名字、提示词、重复方式和时间、建议的检查命令：
  - 审查新提交：每天 09:00，有 24 小时内的提交才跑；
  - 检查依赖更新：每周一 10:00；
  - 补测试覆盖：每周三 14:00；
  - 清理 TODO：每周五 16:00，有 TODO 或 FIXME 才跑；
  - 排查 CI 失败：每 2 小时，最近一次 CI 失败才跑，需要 `gh`；
  - 写发布说明：每周五 17:00，7 天内有提交才跑；
  - 安全审计：每周一 11:00；
  - 项目体检：每周一 09:30。

  只读类的模板在提示词里写明"只读，不要改代码"。权限仍然是这个 Agent 的默认模式。只在新建时显示；"每 2 小时"从当下开始算。
- **编辑弹窗**多了两行：
  - "忙时"：胶囊滑块，"跳过 / 结束后补一次"；
  - "时段"：开关"只在这段时间运行"，打开后是两个时间选择。
- **列表行**：副标题加上"仅 09:00–18:00""忙时补跑"。下次时间这一栏，被时段推迟时写"不在活跃时段 · 时间 补跑"，等会话时写"上一次还在跑 · 结束后补跑"。
- **运行记录**：`queued` 写"上一次还在跑，结束后补跑"，`outsideHours` 写"不在活跃时段，推迟"。

## Alternatives considered

- **忙时一律排队**（backlog 原文"会话忙时排队"）：不用多一个选项。没有采用（第 4 题）：像"排查 CI 失败"这类规则，上一次还在跑时再来一次是多余的；默认跳过，和第一批的行为一致。
- **忙时排多次**：没有采用：会话跑了一整天的话，每小时的规则会攒下二十几次；最近一次就代表了"现在该做的事"，和"错过只补最近一次"同一个道理。
- **全局活跃时段**（设置里一处管所有规则）：只设一次。没有采用（第 5 题）：不同规则需要的时段不同，例如 CI 排查只在白天，夜间体检反而要在半夜；需要时以后可以加一个默认值。
- **时段外的直接丢掉，不补**：最简单。没有采用：每天 07:00 的规则配了 09:00–18:00 的时段，就永远不会跑；推迟到时段开始补一次，用户能在运行记录里看出时间设得不对。
- **模板放在宿主或 core**：iOS 等其他客户端也能用。没有采用（第 3 题）：模板只是预填，没有运行时语义；以后需要共享时再挪。
- **cron 表达式、写入系统日历**：backlog D16 和 A12 都提过。没有采用（第 5 题）：四种重复方式加上活跃时段，已经覆盖了这 8 个模板和常见的用法；cron 的编辑和解释成本高，日历要申请 EventKit 权限。

## Consequences

- 收益：
  - 常见的例行工作点一下就能建好；
  - 长会话不再吞掉下一次；
  - 间隔型规则不在半夜打扰；
  - 三种推迟（额度、时段、等会话）共用一套"推迟期间合并、到期补一次"的规则，行为一致。
- 代价：
  - 规则多了四个字段，其中两个是宿主写的状态；保存规则会清掉所有待补的那一次；
  - "结束后补跑"靠每 30 秒检查一次会话是否在跑，会话结束后最多晚 30 秒才补；
  - 时段按本地时和分判断，换时区之后跟着变；
  - 模板的检查命令依赖项目里有 git，CI 那个还依赖 `gh`；没有时检查失败，不唤醒模型，运行记录里写着退出码；
  - 模板只在 Mac 上有。
- 待目检（已记进路线图的待目检清单）：
  - 新建弹窗的模板胶囊和预填结果；
  - "忙时""时段"两行；
  - 列表行的副标题和下次时间；
  - 一条真实的规则在时段外推迟、会话忙时排队后补跑。

## Testing

- core `schedule` 新测试：
  - 每小时一次、选了"结束后补一次"：10:00 开出会话；11:00 会话还在跑，记 `Queued`；12:00 仍在跑，不写记录；会话结束后补跑一次，代表 12:00；之后不再重复。
  - 活跃时段 09:00–18:00：19:00 记 `OutsideHours` 并推迟到次日 09:00，下次时间就是它；夜里各个时间都不写记录；次日 09:00 开出会话；"立即运行"不受时段限制。跨午夜的 22:00–06:00 判断正确，下一段开始算对；开始和结束相同的规则拒绝保存。
- Swift `ScheduleTests`：
  - 忙时和时段能往返编码，`skip` 不回传；
  - 两种状态的下次时间文字、两种新结果的文字、时段文字；
  - 8 个模板齐全、id 不重复、各自有提示词。
