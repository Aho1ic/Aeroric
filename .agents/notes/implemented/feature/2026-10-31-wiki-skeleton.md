# Agent Note: 项目 Wiki 骨架（B5.5-1）：决策页、操作手册、索引，手改保护、修订、导出与 MCP

Status: implemented

## Problem

项目里的设计决定散落在 `.agents/notes/`，可复用的做法散落在 B5 的经验和技能里。用户要一份能浏览、能修改的项目知识，Agent 要能按需读到，并且按需读取时不要每次都塞进整堆原文。路线文档 §4 要求做成"编译型知识"：页面互相链接、每段都有来源、用户改过的部分不被覆盖、可以导出。owner 2026-10-31 定了 Q-W1–Q-W6，全部按推荐。第一批只做三种不需要调用模型的页面。

## Decision

**存储**（core 新的顶层模块 `knowledge/`；协议 `wiki.rs`）

- 每个项目一个 `<data>/knowledge/<项目>/wiki.db`，包括这些表：
  - `pages`：整页 JSON；
  - `revisions`：只追加；
  - `issues`；
  - `pages_fts`：全文索引，正文先经 cjk 分词；
  - `meta`：存来源指纹。
- 每次保存页面，同时写一份 `pages/<slug>.md`。这只是方便人看的投影，权威在数据库。
- 页面由段落组成，一个 `##` 小节就是一段。每段的 key 是稳定的：
  - 决策页：`note:<路径>#<小节>`；
  - 操作手册：`memory:<id>` 或 `skill:<name>`；
  - 索引页：`index:<分组>`。
- 每段记下来源（SourceRef）、`user_edited`，以及编译器上次产出这段时的 `compiled_hash`。

**编译**（`compile.rs`，确定性，不调用模型）

- 三种页面：
  - **决策页**：每篇笔记一页，slug 是 `decision-<去掉日期的文件名>`；标题、状态、分类和四个小节都来自笔记；
  - **操作手册**：本项目和全局的 active 经验按置信度、有用次数排序，后面接上已采纳的学会技能，并写出各 Harness 的调用方式；
  - **索引页**：最后生成，按页型分组，链接写成相对的 `.md`，导出后照样能点。
- 合并到现有页面：
  - 没被改过的段落：跟着来源更新；
  - 用户改过的段落：保留；如果编译出的 hash 和上次记的 `compiled_hash` 不一样，开一个 `sourceChanged` issue，附上新内容，再更新 `compiled_hash`，同一处变化只开一次 issue；
  - 来源消失时：改过且还有文字的段落保留，并开 `sourceRemoved` issue；其余段落删掉；
  - 用户自己加的段落（key 是 `user:<n>`）一直保留；
  - 整页的来源都没了：页上还有用户的文字就保留并开 issue，否则删页，修订记录留着。

**编辑与修订**

- `apply_edit` 把整页 Markdown 按 `##` 切开，按小节标题对回原来的段落：
  - 文字变了的标为用户改过；
  - 被删掉的小节保留为空的、用户改过的段落，这样下次编译不会把它加回来；
  - 新出现的小节成为 `user:` 段落。
- 每次编译、编辑、回到旧版、采纳 issue 建议，都会生成一个修订。"回到第 n 版"就是把第 n 版的 Markdown 当作一次编辑重新应用。
- 采纳 issue 建议：把建议内容写进那一段，并取消"用户改过"的标记。

**自动编译、导出、Agent 工具**

- 宿主每 2 分钟巡检一次，只看开启了记忆、或者已经有 Wiki 的项目。
- 指纹由三部分合成：笔记文件的路径、大小和修改时间，经验和技能的数量，以及它们最新的更新时间。指纹没变就不编译。
- 导出：
  - 目录必须是项目里的相对路径，不能含 `..`，不能在 `.git` 里，也不能是绝对路径（开头带 `/` 的在去掉斜杠之前就拒绝）；
  - 只写 `<目录>/<slug>.md`，不删除那里已有的任何文件；
  - App 先调用 `wiki.exportPlan`，列出会写哪些文件，用户确认后才真正写。
- Agent 工具：
  - `read_wiki`：不给 slug 时读索引页，slug 不存在时列出所有页面；
  - `search_wiki`：用 bm25 检索，查询词之间是 OR，最多返回 8 条，每条带片段；
  - `flag_wiki_issue`：issue 类型为 agent，作者记为会话 id；
  - 只在项目里有页面、并且用户为这个项目打开了"Agent 可读"时出现在工具列表里（`context.wikiAvailable`）。开关默认关闭，依据见 [R4-3 评测](../testing/2026-11-10-wiki-agent-eval.md)。CLI 把"问宿主一个是否问题"的逻辑抽成了 `host_says`。

**界面**

- 侧栏新增"Wiki"（`WorkspaceSection.wiki`），放在"记忆"下面。项目右键菜单加"项目 Wiki…"。
- 页面布局：
  - 页头：切换项目、重新编译、导出…、issue · N；
  - 左侧页面树：索引、操作手册，决策页按分类分组、可以折叠；有手改段落的页面带一个小圆点；
  - 右侧正文：每个小节用 `SelectableMarkdown` 渲染，下面有来源脚注胶囊，点开后打开笔记（App 的文件预览）或跳到记忆页。用户改过的小节左边有一条 2pt 的强调色竖线，带"你改过"字样，来源有更新时还会提示"见 issue"。
- 弹窗：
  - 编辑：等宽 TextEditor，不显示滚动条；
  - 修订：CapsulePicker 菜单，点一项回到那一版；
  - issue：采纳建议或关闭；
  - 导出：先预览要写的文件，再确认导出。

## Alternatives considered

- **第一批就做模块页**：要调用模型、还要建代码符号索引，按 Q-W1 留到 B5.5-2（后改名 R4，结构部分见 [模块页骨架](2026-11-10-wiki-module-pages.md)）。
- **以 Markdown 文件为权威，让用户在磁盘上直接改**：没法做到段落级的手改保护和修订历史，用户在磁盘上改了也没有入口回流。所以权威放在数据库，md 只是投影（路线文档 §7 也这样定）。
- **用户改过的段落直接被新编译覆盖、旧版留在修订里**：违背"编译器不能覆盖手改"。改为开 issue 由用户决定。
- **用文件系统监听来触发编译**：要跨平台维护监听器，还容易漏事件。改为每 2 分钟比较一次指纹，不调用模型，成本几乎为零。

## Consequences

- 段落按小节标题对位。用户如果改了某个小节的标题，下次编译时它会被当成"删掉一段、加了一段"处理：原段留空不再出现，新标题成为用户自己的段落。
- 操作手册里经验的统计（有用次数等）一变，页面就会更新。如果用户手改过这一段，就会开 issue。
- 测试：
  - core 5 个：笔记解析；编译三种页与检索；手改保护、issue、采纳、修订、回到旧版；删掉的小节不会被加回来、来源消失时的删页规则；导出路径、手动报告和指纹；
  - 宿主端到端 1 个（用 fixture 的真实项目目录）；
  - CLI 工具列表；
  - Swift 2 个。
- 2026-10-31 目检（computer-use `2026-10-31-1614-aeroric-wiki-skeleton`）：编译、手改保护、自动编译开 issue、采纳、修订回退、导出，以及真实 Codex 会话调用三个工具，都已通过。修了两处 P2：
  - **点来源后看不到文件预览**：Wiki 是全页，而中央的文件预览只在任务面渲染，所以文件其实已经打开，却被藏住了。现在先切到这个项目的任务面，再打开文件（`openProjectFile`）。画布卡片打开文件走的是同一条路径，有同样的问题，一并改了。
  - **导出目录被拒后，错误被弹窗挡住，内容还是原始协议对象**：现在 `exportPlan` 的错误写进 `exportError`，在导出弹窗里显示成一行可读的原因；改目录或取消时清掉。其他操作失败的提示也改成 `describe`，只给出宿主返回的 message。
  - 像素级目检（"你改过"竖线的颜色、截断等）因为截图工具异常没做成，仍等 owner 目检。
