# Agent Note: E12 第二步：输入框里用 @ 引用本项目的任务

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E12 的第二步：在输入框输入 `@`，选一个或几个本项目的任务，Agent 这一轮就能读它们。做法里写：`@任务` 作为这一轮明确授权的来源，写进消息的元数据；`read_session` 能读整个项目的会话，这一点不收紧，只是让“引用”成为显式的动作。

第一步（[E12 第一步笔记](2026-11-21-e12-latest-reply.md)）已经让 `read_session` 能只读另一个会话 Agent 的最后一条回复。

动手前（`main@48d59f2b`）核对的事实：

- `session.prompt` 的参数是 `{taskId, text, mode?}`，结构是 `deny_unknown_fields`。消息先进投递队列，轮到它时由 `send_user` 交给驱动。
- `send_user` 交出去之前，会在消息前面加两样东西：
  - 检查点的状态提醒，直接拼在文字前面；
  - H4 按这条消息找到的记忆，放在“Aeroric 附加的上下文”信封里（`opening::attach_because`）。
- App 的转写在用户消息开头认出这个信封，折叠成一行“Aeroric 附加的上下文”，气泡里只留用户打的字。
  - 这一行的摘要固定写“这个 Agent 没有系统层，开场内容随第一条消息发出”；
  - H4 的记忆块也用同一个信封，摘要同样这么写，其实不对。
- 会话页输入框已经有 `/` 命令和 `#角色` 两种提示列表，都是在输入框上方按草稿内容列出。
- 投递队列存的是交给 Agent 的全文：排队中的消息在页面上的回显，和“修改”取回到输入框的文字，用的都是它。

## Decision

**协议：** `session.prompt` 加 `references`，是任务 id 的列表，可省略；一条消息最多 5 个（`MAX_REFERENCES`）。

**宿主核对引用：** 下面任何一种情况都拒收整条消息并写明原因，不会丢掉引用照常发出：

- 引用了这个任务自己；
- 引用的任务找不到；
- 引用的任务不在同一个项目里；
- 超过 5 个。

重复的 id 只算一次。

**消息怎么带上引用：**

- 入队时，宿主把引用块放进“Aeroric 附加的上下文”信封，接在用户的话前面。引用块写明：用户这一轮用 @ 明确引用了这些任务，每个任务的标题和 taskId，以及怎么读——用 `read_session`，只要结论时加 `mode: latest_assistant`。
- 交出去时（`send_user`），先拆下这个信封：
  - 状态提醒照旧拼在用户的话前面；
  - 再把引用块和 H4 找到的记忆合进同一个信封。
  
  这样不会出现信封套信封，App 只认得外面一层，里面那层会原样露在气泡里。
- 检查点记录和记忆检索用的都是用户打的字，不含引用块。

**这就是方案说的“写进消息的元数据”：** 信封随消息进了转写，看转写就知道这一轮引用了哪些任务；不另外开一个字段。

**界面：**

- 会话页输入框里，在开头或空格、换行之后输入 `@`，上方列出本项目别的任务：最近改动的在前，不含已归档的，打字按标题或 id 开头筛选，最多 8 行。邮箱地址里的 `@` 不会触发。
- 选一个，草稿里的 `@…` 被拿掉，输入框上方多一个带 × 的胶囊；满 5 个后列表就不出现。
- 发送时把胶囊里的任务一起发出，然后清空；发送失败，草稿和胶囊都放回去。
- 占位文字改成“继续对话，输入 / 使用命令，@ 引用任务”。
- 转写里“Aeroric 附加的上下文”这一行的摘要，改为读信封开头写的原因：
  - 开场内容仍是原来那句；
  - 记忆显示“Aeroric 按这条消息自动找到的相关记忆和 Wiki”；
  - 引用显示“你这一轮用 @ 引用的任务”。
- 排队消息的回显和“修改”取回的文字，都去掉信封，只留用户打的字。

## Alternatives considered

**消息记录上另开一个 `references` 字段，宿主或驱动在交出去时再拼。** 最强的理由是数据干净，转写之外也查得到。没选：

- 投递队列、四个驱动的转写格式都要跟着改，存储也要迁移；
- Agent 最终看到的还是消息里的一段文字；
- 信封已经是 Aeroric 往会话里放东西的唯一格式，E5 定下的，App 也已经认得。

**直接把被引用任务的最后一条回复贴进消息。** 最强的理由是 Agent 不用再调一次工具。没选：

- 引用 5 个任务、每个 2 万字，一条消息就可能多出 10 万字，用户看不到这笔开销；
- 有时 Agent 要的是过程而不是结论，只给指针，让 Agent 按需选读法。

代价写在局限里。

**`@` 也出现在新建任务页的输入框里。** 没选：新任务还没有会话，也就没有“这一轮”。先只做会话页。

## Consequences

- **收益：** 用户能明确告诉 Agent“看那个任务”，不用复制粘贴；转写里留着这一轮引用了什么。
- **代价：** 引用块大约每个任务一行，加上开头一段说明。
- **局限：**
  - 只给指针：会话没有 Context 工具时（远端会话，C9 表里写“没有”），Agent 读不到被引用的任务；
  - 输入框的胶囊只在这个窗口里，草稿存到收件箱或切换页面后不保留；
  - 用户自己打的字如果恰好以“[Aeroric 附加的上下文]”开头，会被当成信封拆开；
  - 没有在真实 Agent 上看它会不会去读被引用的任务（NOT RUN），界面没有目检（UI 自动化暂停）。
- **验证：**
  - 宿主测试新增 1 个，宿主会话测试共 65 个全部通过：
    - 引用自己、找不到、超过 5 个，都被拒收并写明原因；
    - 引用一个任务（重复一次），Claude 收到的消息以信封开头、写明“你这一轮用 @ 引用的任务”、taskId 只出现一次、写了 `latest_assistant`，最后是用户的话。
  - core 新增 1 个：引用块的写法；标题里的结束标记被转义，关不上信封；信封体再包一次内容不变。
  - Swift 测试新增 5 个，相关的 `TaskMentionTests`、`AttachedContextTests`、`LiveSessionStoreTests` 共 25 个、`LiveSessionContractTests` 4 个，全部通过：
    - `@` 的识别、筛选、满额、去掉草稿里的 `@…`；
    - 候选只含同项目、未归档、不是自己的任务，最近的在前；
    - 信封的原因读取，以及去掉信封后的文字；
    - 仓库层把引用带给宿主；
    - 请求只在有引用时带 `references`。
- **待目检：** 已记进路线文档 §8 待目检清单。
