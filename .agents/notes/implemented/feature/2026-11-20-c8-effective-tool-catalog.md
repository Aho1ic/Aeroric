# Agent Note: C8 第一步：每次会话能用的工具清单

Status: implemented

## Problem

[批次 C 方案](../../proposed/feature/2026-11-15-adoption-c-memory-gateway-skills.md)第 C8 片要求：会话信息里有"这次会话能用的工具"，包括三部分：

- Aeroric 注入了哪些；
- Harness 自带哪些已知的；
- 哪些因为什么原因没注入。

完成条件是界面上的清单与启动参数里实际注入的一致，并由测试比较两者。

动手前（`main@6be6cd5d`）：

- **注入情况不留痕迹。** Aeroric 的 Context 工具由执行器在启动时交给会话（`give_context` → `set_context_server`）。只有本机的 Claude、Codex 和 ACP 会话会接受；OMP 用的是默认实现，返回不接受；远端会话不给。结果只用来决定要不要收回令牌，不留下记录。
- **工具分组的条件只在命令行进程里。** `aeroric-cli mcp-context` 在 `tools/list` 时问宿主四个问题，按回答决定提供哪几组工具：
  - 项目开没开记忆；
  - 有没有允许 Agent 读的 Wiki；
  - 有没有参考代码库；
  - 有没有设置专家模型。

  App 不知道某个会话到底拿到了哪几组。
- **能力表**（`session.capabilities`）描述的是 Harness 支持哪些功能，不是这次会话实际有什么。
- **C7 的一个漏洞**：技能挂载记录用 `runs_locally()` 判断要不要记。这个函数问的是"能不能起本机 Context 服务器"，对本机 OMP 也返回假，所以本机 OMP 会话的技能挂载没有记下来，而它的技能其实是挂了的。

## Decision

**一张共享的工具表**（`aeroric-protocol/src/tools.rs` 的 `AERORIC_TOOLS`）：

- 列出 Context 服务器能提供的每个工具：名字、所属组（基础、记忆、Wiki、参考库、专家），以及作用范围：
  - 只读；
  - 会写：改文件，或改 Aeroric 自己的看板、记忆、待办；
  - 会对外发送：`ask_expert` 把问题发给另一个模型。
- `aeroric-cli` 加了一个测试：`tools/list` 能列出的全部工具，与这张表的名字和分组完全一致。以后增删工具，两边不一致就会测试失败。

**每次启动记下清单**（核心 `sessions/live/tool_catalog.rs`）：

- 执行器在每次启动或恢复会话时判断注入情况，分四种：
  - 已注入；
  - 远端会话；
  - 这个 Harness 还不能在启动时接入（OMP，或驱动拒绝了）；
  - 宿主没准备服务器。

  再按与 `mcp-context` 相同的四个条件，算出这次每组工具是否提供，并写明依据，如"这个项目开启了记忆"或"还没有设置专家模型"。没注入时，每个 Aeroric 工具都写同一个原因。
- 附上 Harness 自带的已知工具，标为 Harness 所有，依据写"自带；是否能用由权限模式决定"。
  - Claude 列出 Read、Edit、Bash、WebFetch 等 10 个；
  - Codex 列出 shell、apply_patch 等 5 个；
  - OMP、DSH 没有可靠的清单，不列，不编。
- 记到 `<data>/tool-catalogs/<任务>.json`，每次启动一条，保留最近 20 条。读写与 C7 的技能记录共用 `storage/launch_log.rs`，C7 的 `MountLog` 也改用它。

**宿主和界面**：

- `session.capabilities` 的参数加可选的 `taskId`。带上时，返回里多一个 `tools`，是这个任务最近一次启动的清单；没有记录就不带。
- 会话信息里，"技能"下面加"工具"一行：
  - 已注入时写"Aeroric 工具 14/21 · Claude 自带 10 个"；
  - 没注入时用警示色写"没有 Aeroric 工具：原因"。
  - 点开后，先列提供的 Aeroric 工具（名字 · 只读 / 会写 / 会对外发送），再列没提供的（按原因归在一起），最后列 Harness 自带的。

**修正 C7**：`Route` 加了 `is_remote()`。技能记录改为只跳过远端会话，本机 OMP 会话的技能挂载会记下来。

## Alternatives considered

**由 `mcp-context` 进程在回答 `tools/list` 后把实际列出的工具报给宿主。** 最强的理由是记的就是 Agent 真正看到的列表，不是推算。没选：

- 这个进程在会话第一次列工具时才启动，有的 Harness 要到第一回合才列，启动时还拿不到；
- 宿主忙时，这个进程会在 3 秒后只给基础工具，再报回去又要一次往返。

执行器在启动时按相同条件计算，并有测试分别保证"条件相同"（共享表与 CLI 一致）和"注入相同"（执行器测试比对 `thread/start` 里的服务器）。

**Harness 自带工具从各 Harness 实时读取。** 最强的理由是准确。没选：Claude、Codex 都没有不启动会话就列出内置工具的接口。写死的清单标为"已知的，Aeroric 不控制"，不冒充完整。

**OMP 写成"可以接入，待实现"。** 没选：本步只说实际情况。OMP 是否能接入是 C9 和 H2 的事；在那之前，它就是"还不能在启动时接入"。

## Consequences

- **收益**：
  - 任意一次 C8 之后启动的会话，能看到它有哪些 Aeroric 工具、为什么少了哪几组，以及 Harness 自带了什么；
  - OMP 和远端会话没有 Aeroric 工具这件事，在界面上明确写出；
  - 工具增删时，命令行与清单不一致会被测试抓到。
- **代价**：每次启动多写一个小文件。
- **局限**：
  - 记录的是启动时的条件。会话中途打开项目记忆、加了 Wiki，要到下次启动才反映到清单里，与 `mcp-context` 的行为一致；
  - Harness 自带工具只是已知清单；
  - C8 第二步（结构化结果、单行上限、幂等键）和第三步（触发评测）还没做。
- **验证**：
  - 核心层新增 3 个测试（`tool_catalog_tests.rs`）：
    - 已注入时各组按条件提供，依据文字正确，Aeroric 工具数与共享表一致，Claude、Codex 自带工具在列；
    - 远端、不支持、没有服务器三种情况，每个 Aeroric 工具都写同一个原因，OMP 没有自带清单；
    - 记录与读取，没设目录时不写。
  - 执行器新增 1 个测试：没有服务器时，`thread/start` 里没有 `aeroric_context`，清单也说没注入；有服务器时两边都有，基础工具可用，记忆没开所以记忆工具不可用。还检查了 `is_remote` 和 `harness`。
  - CLI 新增 1 个测试：列出的工具与共享表完全一致。
  - 宿主集成测试新增 1 个：`session.capabilities` 不带任务、带没有记录的任务时都没有 `tools`，有记录时返回清单，字段用驼峰。
  - Swift 新增 1 个测试：清单解码；汇总文字（已注入、没注入、未记录、读取中）；没提供的按原因归组；作用范围的文字。
  - 界面待目检，记在路线文档 §8。
