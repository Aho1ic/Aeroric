# Agent Note: 配额感知调度：Codex 额度用完时，定时任务推迟到重置后补跑一次

Status: implemented

## Problem

[定时任务](2026-11-14-scheduled-tasks.md)到点就开会话，不看额度还剩多少。本机 Codex 订阅的 5 小时窗口或每周窗口用完时，开出来的会话第一轮就是"没跑成 · 额度"：白开一个会话，这个时间点也算处理过了，要等下一个正常时间才会再跑。

[额度节奏](2026-11-10-quota-pace.md)（R3-3b）已经每 10 分钟读一次订阅额度，两个窗口的已用百分比和重置时间都记在数据目录的 `quota-readings.jsonl` 里，但只用来显示，调度没有用到。[推迟提案](../../proposed/feature/2026-11-08-new-addition-deferred.md)第 24 项"配额感知调度、额度恢复后续跑"的触发信号是"A12 动工"，定时任务上线后这个信号出现了。

用户 2026-11-14 说"全部按推荐"，定了 5 条：

1. 下一项做第 24 项。
2. 只做调度这一侧：到点先看额度，用完就不开会话，等重置后补跑一次。"会话跑到一半额度用完，恢复后自动接着做"放到第二批。
3. 只对 Codex 这一族生效；5 小时或每周窗口任何一个用到 100% 就算用完；节奏"偏快"只提示，不拦。
4. 只认 15 分钟以内的读数，没有就当场读一次；读不到照常运行。
5. 运行记录里记一条"额度用完，推迟到 HH:MM 重置后"；重置后补跑一次，仍然先跑前置检查、受每天 24 次上限约束；推迟期间到了新的正常时间，合成一次；定时任务页显示"额度用完 · 重置后补"；不进"需要我处理"。

## Decision

**判定额度**（core `metrics::quota_pace::state`）

- 输入是读数、当前时间和新鲜度上限（协议 `schedule::QUOTA_FRESH_MS`，15 分钟）。每个窗口只看它最新的一条读数，这条超过 15 分钟就当没有。
- 结果分三种：
  - `Out { reset_at }`：某个窗口已用 100%，并且重置时间还没到。两个窗口都用完时，取较晚的重置时间。
  - `Fast { exhaust_at }`：没有用完，但按 `pace` 推算会在重置前用完。两个都偏快时，取较早的用完时间。
  - `Fine`：其余情况，包括没有足够新的读数。
- 一条重置前读到的 100%，过了重置时间不再算用完。所以补跑时，如果 15 分钟内的最新读数还是重置前那条，也不会被它再次推迟。

**谁受影响**（宿主 `session_live_services/schedule.rs` 的 `Env::quota`）

- 只有 `is_builtin(agent)`，并且 `session_family(agent) == Codex` 的 Agent 才看额度，现在只有内置的 `codex`。
- `claude_gpt55` 虽然用 codex 风格的参数启动，走的却是网关脚本；自定义 Codex 配置有自己的 home 或网关。它们都不花本机订阅的额度，照常运行。
- 先读 `quota-readings.jsonl`。没有 15 分钟内的读数时，产品宿主当场读一次订阅，用的是 `usage.*` 那个 `codex app-server` 槽（`HostWiring::codex_rpc`，现在也传进 `register_session_live_services`）。读完再判定。
- 测试宿主（`product == false`）不启动 `codex`，只看文件。

**推迟与补跑**（core `schedule::fire` / `Schedules::tick`）

- 检查顺序：上一次还在跑 → 每天上限 → 额度 → 前置检查 → 开会话。额度用完时不跑前置检查，等补跑时再跑。
- 到点额度用完：
  - 结果记为 `RunOutcome::QuotaOut`，`retry_ms` 是重置时间加 `QUOTA_RETRY_AFTER_MS`（1 分钟）；
  - 说明写"Codex 额度用完，推迟到 HH:MM 重置后补跑"，跨天时写成"11月18日 09:00"；
  - 规则记下 `quota_retry_ms`，`last_due_ms` 照常前移；
  - 一次性规则在补跑之前保持开启。
- 推迟期间：
  - `tick` 遇到新的正常时间，只把 `last_due_ms` 前移，不开会话，也不写运行记录，等补跑时合成一次。
  - `list` 返回的 `next_ms` 就是补跑时间。
- 到了 `quota_retry_ms`：
  - 补跑一次，代表最近一次被推迟或被合并的时间（`last_due_ms`），`catch_up` 为真；
  - 补跑同样经过"还在跑""每天上限""额度""前置检查"四道关；
  - 如果额度还是用完（比如每周窗口也到顶了），按新的重置时间再推迟。
- 手动"立即运行"：
  - 额度用完时同样不开会话，说明写"Codex 额度用完，HH:MM 重置；手动运行不自动补"，不安排补跑；
  - 手动运行开出了会话，就清掉这条规则待补的那一次。
- 保存规则（包括开关）会清掉 `quota_retry_ms`，和"保存即视为处理到现在"的规则一致。
- 节奏偏快：照常开会话，在运行记录的说明后面加一行"Codex 额度节奏偏快：照这个速度 HH:MM 用完"。

**界面**（Swift）

- `LiveScheduleRule.quotaRetryMs` 只读，保存时不回传。
- 定时任务页这一行原本显示"下次 …"，推迟时换成"额度用完 · 时间 后补跑"。
- 运行记录：
  - 到点推迟的写"Codex 额度用完，重置后补跑"；
  - 手动运行被拦的写"立即运行 · Codex 额度用完，没开会话"；
  - 补跑的那条带"补跑 ·"前缀。
- 不进"需要我处理"。

## Alternatives considered

- **一并做"额度恢复后续跑"**：会话跑到一半额度用完，恢复后自动接着做，正是第 24 项的后半句。这一批没做（第 2 题）：要在回合结束时识别额度错误，各个 Harness 的报错格式不同；还要在宿主重启之后记得哪些会话在等额度，量比较大。调度这一侧现在就能用上已有的读数。
- **节奏偏快也推迟**：可以省下额度给手动会话。没有采用（第 3 题）：偏快只是外推，近一小时的速度可能就是这条定时任务自己造成的；拦下来，可能让定时任务一直跑不起来。
- **用任何年龄的最新读数**：省掉当场读。没有采用（第 4 题）：读数太旧时，用户可能已经换了账号或升级了套餐。15 分钟比采样间隔（10 分钟）略长，正常运行时总有一条新鲜读数，不需要当场读。
- **对所有 Codex 族 Agent（包括自定义配置）都看额度**：配置简单。没有采用：自定义配置和 `claude_gpt55` 不花这台 Mac 的订阅额度，用订阅的读数拦它们是错的。
- **推迟期间每到一个正常时间都记一条"额度用完"**：记录更细。没有采用（第 5 题）：每 1 小时一次的规则，在 5 小时窗口里会堆出 4、5 条相同的记录，补跑时也说不清该补哪一次。

## Consequences

- 收益：
  - 内置 Codex 的定时任务不会在额度用完时白开会话，重置后自动补跑一次；
  - 推迟和补跑都在运行记录里写明；
  - 节奏偏快会在运行记录里提前提醒。
- 代价：
  - 只认内置 `codex`；Claude 等其他 Agent 没有额度读数，用完了照样会开出"没跑成 · 额度"的会话；
  - 判断依据是读数，不是真正发出一轮请求；读数和实际额度可能有几分钟的出入。重置时间之后还会多等 1 分钟；
  - 推迟期间不开任何会话，哪怕中间额度因为换账号恢复了；只能手动"立即运行"；
  - 保存规则会丢掉待补的那一次；
  - 第 24 项的后半句"额度恢复后续跑"不在这一批，同日由[无人值守自动重试](2026-11-14-unattended-auto-retry.md)实现，只管无人值守的会话。
- 待目检（已记进路线图的待目检清单）：
  - 额度真正用完时，定时任务页的"额度用完 · 时间 后补跑"、运行记录里的说明；
  - 重置后补跑出的会话；
  - 手动"立即运行"被拦时的提示。

## Testing

- core `metrics::quota_pace` 新测试：
  - 两个窗口都用完时等较晚的重置；
  - 超过 15 分钟的读数不算；
  - 重置前读到的 100% 在重置之后不算用完；
  - 偏快给出用完时间，正常为 `Fine`。
- core `schedule` 新测试，用每小时一次的规则：
  - 10:00 额度用完，推迟到 12:31；11:00 和 12:00 不开会话、不写记录；
  - 12:31 补跑一次，代表 12:00，带"偏快"说明；补完下次回到 13:00；
  - 手动运行被拦时写明跨天的重置时间，并且不补；手动开出会话后清掉待补；
  - 一次性规则推迟时保持开启，补跑后关闭。
- Swift `ScheduleTests`：
  - `quotaRetryMs` 能解析，保存时不回传；
  - 推迟时下次时间的文字，以及两种 `quotaOut` 运行记录的文字。
- 宿主侧（只认内置 `codex`、15 分钟内没有读数时当场读）没有集成测试：测试宿主的 `Families` 把所有 Agent 都当成非内置。这部分列进了待目检清单。
