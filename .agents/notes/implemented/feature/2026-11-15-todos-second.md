# Agent Note: 待办第二批：Agent 提议待办、验收检查、检查没过让 Agent 接着修

Status: implemented

## Problem

[工作安排第一批](2026-11-15-todos.md)把"用户写待办 → 手动交办 → 用户验收"这个闭环做通了，留下三件事给第二批：

1. 待办只能由用户自己写。Agent 做事时常会发现本轮范围以外、值得以后做的事，例如顺带看到的另一个 bug、该补的测试。现在这些只能写在回复里，过后就找不到了。
2. "待验收"时用户只能读 Agent 的说明，没有客观依据。Agent 说"测试都过了"，可能只跑了一部分。
3. 交办出去的会话没人看着。第一批里，这些会话被宿主重启打断、某一轮没跑成，都要等用户自己发现。

2026-11-15 用户说"继续做下一步"，我按推荐定了 5 条，用户回复"全部按推荐"：

1. 下一项做待办第二批。
2. Context MCP 加 `todo_propose`，所有会话都有，不设开关。提议的待办等用户"收下"或"不要"；一个会话最多 5 条待处理的提议；同一项目里已有同名的在办待办时拒绝。
3. 每个待办可选填一条"验收检查"命令。会话这一轮结束后，宿主在后台自动跑一次，结果记在这次交办上；会话里又跑了一轮就重新检查。检查通过也不自动验收。
4. 自动规则只做两条，都默认关：
   - 交办出去的待办会话算"无人值守"，和定时任务、委派共用"自动继续"开关；
   - 每个待办可以打开"检查没过时让 Agent 接着修"：在原会话里发一条消息附上检查输出，最多 2 次。

   不做新建待办时自动交办、按项目或标签设规则、按时间触发。
5. 这一批不替换审阅版，等 Codex 的集中目检结束后再一起构建。

## Decision

**协议**（`aeroric_protocol::todo`）

- `TodoState` 加 `proposed`：Agent 提议的，等用户收下（变成 `open`）或丢掉（删掉，不留记录）。
- `Decision` 加 `take`（收下）。只有 `proposed` 能收下。提议不能交办、不能重新打开、不能验收。
- `Todo` 新增三个字段：
  - `proposed_by`：提议它的会话；
  - `check`：验收检查命令；
  - `fix_on_fail`：检查没过时接着修，只在有 `check` 时生效。
- `Assignment` 新增两个字段：
  - `check: CheckRun`：这次交办的会话最近一次检查，含 `state`（`running` / `passed` / `failed`）、`output`、`at_ms`、`turn_ms`；
  - `fixes`：已经发回会话修了几次。
- 常量：
  - `PROPOSALS_PER_SESSION = 5`；
  - `FIX_ROUNDS = 2`；
  - `CHECK_TIMEOUT_MS = 600_000`。验收检查多半是一整套测试，所以给 10 分钟；定时任务的前置检查只给 30 秒。
- RPC：
  - `todo.check {id}`：重新检查，立即返回，检查在后台跑；
  - `context.todoPropose {token, title, notes?}`：Context MCP 的 `todo_propose` 调用它。

**一轮只检查一次**

- 检查绑定在"会话最后一轮的开始时间"（`turn_ms`）上。同一轮已有结果就不再跑；会话里又跑了一轮（用户接着聊，或者 Agent 在修），轮次变了，就再检查一次。
- 同一个待办同一时刻只跑一个检查：`begin_check` 在锁里把状态写成 `running`，已经在跑就返回 `false`。
- 检查跑完时，如果待办已经重新交办，或者宿主重启时把这次检查清掉了，结果就丢弃（`finish_check` 返回 `None`）。
- 宿主启动、注册待办服务时，先把遗留的 `running` 清掉（`reset_running`），这些检查会重新跑。这时还没有任何检查在跑，不会误清。

**core**（`aeroric_core::todos`）

- `propose` 用来查重的标题比较：去掉首尾空白，不分大小写。和 `proposed`、`open`、`assigned` 三种状态的待办比较。拒绝时的报错带上已有待办的 id，Agent 能看到是哪一条。
- `due_checks(env)`：找出满足以下条件的待办，它们需要检查：
  - 状态是 `assigned`，并且有检查命令；
  - 最新会话处在"待验收"（`Progress::Review`）；
  - 最后一轮还没有检查结果。

  会话记录在锁外读，因为可能慢。
- `check_for(id, env)`：手动重新检查用。会话必须真的结束过一轮，否则报"会话这一轮结束后才能检查"。
- `fix_due(todo)`：同时满足三条时，返回要发的第几次：打开了"接着修"、最新检查没过、`fixes` 还没到 2。
- `fix_prompt`：一条消息，写明这是第几次修、检查命令、检查输出，并要求 Agent 改到这条命令通过，再说明改了什么、怎么验证的。
- `prompt_for` 现在多两段：
  - 有验收检查时，告诉 Agent 命令是什么，这一轮结束后 Aeroric 会跑它；
  - 上一次交办检查没过时，附上那次的输出。

  这样重新交办给新会话时，新会话知道上次卡在哪。
- `SessionView` 加 `last_turn_ms`。宿主在会话没在跑时，从 `rerun::turns` 的最后一轮取。

**宿主**（`session_live_services/todo.rs`）

- 后台轮询每 `TICK_MS`（30 秒）一次，把到期的检查一个一个跑完。
  - 命令用 `schedule::check::run_tail` 在项目目录里跑，走登录 shell，PATH 和 Agent 用的一样（同一天目检后定时任务的检查也改成这样），限时 10 分钟。
  - 项目不在本机时，记为没过，并写明原因。
- 检查没过、`fix_due` 返回第 n 次时，把 `fix_prompt` 发进原会话，发送成功后才计数。会话不在内存里时，先安静地重新打开（`reopen_quiet`）再发。会话正在跑一轮时不发；等这一轮结束，会再检查一次。
- `todo.check` 用 `wiki::in_background`（改成了 `pub(super)`），拿到 `Arc<Live>` 后另起线程跑检查。调用立即返回状态为"检查中"的待办。
- `context.todoPropose` 用上下文令牌得到会话和项目。和 `memory_propose` 不同，它不要求项目开启记忆。
- `restart::unattended` 多一条：`todo::knows_task`，即这个会话是某个待办交办出去的。[宿主重启后续跑](2026-11-14-resume-after-restart.md)和[无人值守自动重试](2026-11-14-unattended-auto-retry.md)因此都对待办会话生效，仍由同一个开关控制，默认关。
- `schedule::check` 新增 `run_tail`：输出超过 2000 字时，保留"退出码"那一行和输出的最后 2000 字。测试失败的摘要通常在输出末尾。定时任务前置检查用的 `run` 行为不变，仍保留开头。

**Context MCP**（`aeroric-cli mcp_context`）

- 基础工具里加 `todo_propose {title, notes?}`。
- 说明里加一句"把本轮范围以外、值得以后做的事提议成用户的待办（todo_propose）"。
- 工具描述写明：
  - 只进待确认；
  - 不能用来代替把当前的事做完；
  - 不要提议这一轮马上就会做的事；
  - 每个会话最多 5 条，同名会被拒。

**界面**（Swift）

- 待办页：
  - 顶部有"Agent 提议（N）"区。每条显示标题、项目、说明，按钮有"收下"、"不要"（直接删掉）、"来自会话"（打开提议它的会话），还有编辑图标。
  - 下面是"在办"。
- 有验收检查的行，多一行：
  - 检查状态胶囊："检查中…""检查通过""检查没过"，悬停显示命令；
  - "已让 Agent 接着修 n/2 次"；
  - "看输出 / 收起输出"，展开后是等宽字体、可选中的输出。
  - 待验收时，按钮里还有"运行检查"或"重新检查"；检查正在跑时置灰。
- 有会话在跑或检查在跑时，页面每 5 秒刷新一次，否则每 30 秒一次。页面离开就停。
- 编辑弹窗：
  - 加"验收检查"输入框；
  - 加"检查没过时让 Agent 接着修（最多 2 次）"开关，没填命令时置灰；
  - 下面一段说明运行方式。
  - 提议在弹窗里叫"编辑提议"。
- 交办弹窗：预览的消息和宿主的 `prompt_for` 一致，包括检查命令和上次没过的输出；有检查时，说明文字会提到这一轮结束后会跑检查。
- "需要我处理"：
  - 那一行改成"待办：N 条待验收、M 条 Agent 提议"，下面的说明随两种数量变化；
  - 有提议时这一行也算进侧栏数字。
- 设置里"自动继续"开关的说明，写明交办出去的待办也在范围内。

## Alternatives considered

- **提议进记忆收件箱**：不用新建状态，复用现成的待确认流程。没有采用。记忆存的是事实和约定，待办是要去做的事，两者的去向不同：待办可以交办、可以验收，记忆不行。
- **只给开了记忆的项目提供 `todo_propose`**：和 `memory_propose` 一致。没有采用（第 2 题）。提议只是待确认，用户不收下就什么都不发生，没必要再加一道门；每个会话 5 条的上限已经防住刷屏。
- **检查通过就自动验收**：省一次点击。没有采用（第 3 题）。检查只证明"这条命令过了"，不证明"这件事做对了"。命令可能没覆盖到要改的地方，Agent 也可能为了让检查通过改了测试。第一批的原则"执行结束不等于目标完成"仍然成立。
- **检查没过就重新交办（开新会话）**：新会话上下文干净。没有采用（第 4 题）。原会话知道自己改了什么、为什么那样改，修起来更快；只把检查输出发给新会话，等于让它从头摸一遍。用户需要换会话时，手动"重新交办"，新会话的提示词里会带上上次的输出。
- **检查输出保留开头**：和定时任务前置检查一样，复用现成的 `run`。没有采用。测试套件的失败摘要通常在末尾；保留开头，2000 字往往全是"通过"的行。所以加了 `run_tail`，定时任务那边不受影响。
- **手动重新检查同步跑完再返回**：代码最简单。没有采用。一套测试可能跑几分钟，App 的调用会超时。所以改成立即返回"检查中"，页面在检查期间每 5 秒刷新一次。

## Consequences

- 收益：
  - Agent 发现的事有了去处，用户一点就能收下；
  - "待验收"有了客观依据：检查通过或没过，以及输出；
  - 打开"接着修"后，常见的"测试没过"能在没人看着时修到通过，最多两次，不会无限循环；
  - 交办出去的会话被重启打断、因为网络或额度没跑成，可以和定时任务一样自动接着做，前提是用户打开了开关。
- 代价：
  - 每 30 秒的后台轮询，要为每个有检查命令且已交办的待办读一次会话记录；没在跑的会话还要读转写。待办多的时候有开销，但只有填了检查命令的待办才会被读。
  - 检查一个一个跑，一套 10 分钟的测试会让后面的检查排队。
  - 检查命令以用户身份、在项目目录里运行，权限和定时任务前置检查一样，由用户自己写、自己负责。
  - "接着修"计数只在消息发出去之后才加。如果检查跑完时用户正好在原会话里跑一轮，这次修就不发；等那一轮结束，会再检查一次。
  - 提议没有过期机制：会话结束了，它的提议仍留在那里，直到用户处理。
- 第一批笔记里列为"没做"的几项，现在的状态：
  - 已做：Agent 提议、检查作为完成依据，以及接着修和无人值守这两条规则；
  - 仍没做：按规则自动交办、权限、繁忙、共享护栏。
- 待目检（已并入路线图待目检清单里的待办那一行）：
  - Agent 提议区的样子与收下、不要、来自会话；
  - 编辑弹窗的验收检查和"接着修"开关；
  - 行内的检查胶囊、看输出、重新检查，以及检查中的刷新；
  - "需要我处理"那一行的两种数量；
  - 一个真实待办从交办、检查没过、Agent 接着修、检查通过到验收的全过程；
  - 真实会话里 Agent 调用 `todo_propose` 的样子。

## Testing

- core `todos::second_batch_tests` 3 个：
  - 提议：去空白；查重不分大小写，和 `open`、`proposed` 都比，报错带已有 id；换项目可以；每个会话 5 条上限，别的会话不受影响；提议不能交办、重新打开、验收；收下后变成 `open`，重复收下被拒；收下后腾出名额；`knows_task` 只认交办，不认提议。
