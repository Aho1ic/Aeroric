# Agent Note: H4 第一步：回合改过的文件立刻给 Wiki 页标“可能过时”

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H4 的第 3 条：刚改过的模块，对应的 Wiki 页要当场标上“可能过期”，不等下次编译。

动手前（`main@07c92cf5`）核对的事实：

- 模块页的每段都记着它读过的代码文件和那一版的 blob（`SourceRef { kind: Code, target, version }`）。
- 只有编译时才拿当前文件比对，在说明段前写“可能过时”（`knowledge/explain.rs` 的 `sources_now`、`stale_lines`）。两次编译之间，页面一直显得是最新的。
- 每个改了文件的回合结束时，宿主都会做改动快照，写进回合账本（`TurnRecord.files`，路径相对仓库顶层），然后调用回合收束钩子（`TurnChangeTracker::set_hook`）。四族都走这条路。
- 模块页引用的路径相对项目文件夹，而项目可能在仓库顶层下面。

## Decision

**在回合收束钩子里标记**（`executor.rs`）：回合改过文件、项目有 Wiki 时，用账本里这个回合的文件调 `Wikis::mark_changed`。

- 用回合结束的快照，不从各家的工具事件里抠路径：快照能覆盖用 Shell 改的文件，四族也一样。
- 时机是“这一回合结束时”，不是“写下文件的那一刻”。对“下次编译才发现”来说，已经是当场。

**判断**（`knowledge/changed.rs`）：

- 一页引用的代码文件，和改过的文件相同，或改过的路径以“/引用路径”结尾（项目在仓库顶层下面时），就算命中。
- 命中的页记下文件、会话 id 和回合结束时间，同一文件只留最近一次。
- 存在项目 Wiki 库旁的 `changed-since-compile.json`。下次编译读过所有文件后整体清空，因为编译本身就会对照当前文件重写，或标出可能过时。

**显示**：

- `wiki.page` 多返回 `changed`。Swift 的 Wiki 页标题旁出一个“可能过时”标记，悬停写明是哪些文件，提示重新编译后更新。
- Agent 用 `read_wiki` 读这一页时，正文前多一行 `> 可能过时：这页生成后，… 在会话里改过，还没重新生成。`，和编译时那行“可能过时”是同一种说法。

H4 其余几条：

- 第 1 条（开场白）、第 4 条（原生子代理）已由 H3、H5 做完。
- 第 2 条（按消息召回，默认关闭）是第二步。
- 第 5 条（用 Harness 自己的 Hook 在回合中途改写上下文）眼下没有需要它的事，不做。

## Alternatives considered

**改完立刻重新编译这些页。** 最强的理由是页面马上就是对的。没选：

- 模块页的说明段要调模型（R4-2），每个回合都跑，成本和延迟都不可接受；
- 不调模型的部分重编，也要扫一遍项目代码。

标记只读页面和账本，几乎不花时间。

**从各家的工具事件里取被写的路径，写下的那一刻就标。** 最强的理由是更即时。没选：

- 四族的写文件事件形状各不相同；
- 用 Shell 改的文件根本没有这类事件；
- 快照已经是四族统一的事实来源。

**标记写进页面本身（`WikiPage` 加字段、走一次修订）。** 没选：标记是临时的，下次编译就失效；写进页面会多出一条修订，编辑和回退时还要处理它。

## Consequences

- **收益**：
  - 刚改过的模块，Wiki 页当场显示“可能过时”；
  - Agent 读到这页时也看得到提示，不会把旧说明当成现状。
- **局限**：
  - 只看代码文件的引用；笔记、记忆类来源的页不受影响（它们的来源不是会话改的代码）；
  - 改动被撤销后，标记仍留到下次编译（偏保守）；
  - 页面未目检，已记进路线图 §8 待目检清单。
- **验证**（在 Mac mini 上跑）：
  - 核心层：
    - 没有 Wiki 时什么都不标；
    - 编译后改 `core/b/src/main.rs`（带上仓库顶层前缀），引用它的两页都被标；
    - 没被引用的文件不标；
    - 同一文件再改一次只留最新的会话；
    - 提示行的文字正确；
    - 再编译一次，标记清空。
  - Swift：一个和多个文件时的提示文字。
