# Agent Note: H5 第二步：原生子代理和委派列在一起，黑板写入标明子代理

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) 的 H5 有四条。[第一步](2026-11-20-h5-roles-as-native-subagents.md)做了第 3、4 条（把角色投影成原生子代理、讲清 `delegate` 的用途）。这一步做剩下两条：

1. 原生子代理和 `delegate` 开的子会话列在一起，各自标明谁在管理；没有结构化打断方法的，不给打断按钮。
2. 子代理写到黑板上的内容，标明是哪个子代理写的。

动手前（`main@f6c71ca7`）核对的事实：

- **原生子代理已经有统一的更新**：`SessionUpdateKind::Subagent { id, title, status, detail }`。
  - Claude 的任务事件映射成它（`claude/map.rs`），后台命令也走这条路，标题带“后台命令：”前缀；
  - OMP 的子代理事件映射成它（`omp/map.rs`）；
  - Codex 没有：子线程的开始、结束只写成派发卡片上的进度行（`codex/driver.rs` 的 `child_notification`）。
- **界面**：`Subagent` 更新只在会话信息卡里列出（“子 Agent”“后台命令”两组）。进度页的“委派”一节（`DelegationPanelSection`）只列 `delegation.list` 的卡片，由应用层的 `TaskWorkspaceView` 读出后传入。
- **黑板**：`BoardEntry.author` 是 `"user"` 或写入会话的 task id。`context.boardWrite` 按 token 找到会话，记成这个会话写的。
- **Context 服务器分不出调用者**：每个会话一个 `aeroric-cli mcp-context` 进程、一个 token。Claude、Codex 的子代理继承父会话的 MCP 连接，OMP 的子代理经父连接代理（方案 H5 第 2 条）。`tools/call` 里只有工具名和参数。上游有没有带上能区分子代理的 `_meta`，静态读不出来。

## Decision

**列在一起**：

- 进度页的“委派”一节分两组：
  - 先列这个会话的原生子代理，组标题是“Harness 自己的子代理 · 由 Harness 管理，Aeroric 只能看”；
  - 后面是委派子会话，有原生子代理时组标题是“经 Aeroric 委派 · 由 Aeroric 管理”；
  - 没有原生子代理时，这一节和原来一样。
- 原生子代理行显示“标题 · 状态”，进行中的再加最近一步。行上没有任何按钮。三家都没有按子代理打断的结构化方法，打断整轮已经在会话页上。
- 数据直接用会话实时模型的 `subagents`，由应用层在组装面板时并入 `DelegationPanelModel.native`（`with(native:)`），后台命令滤掉。不经核心层的新接口：这份数据本来就随会话更新推到界面上。
- **Codex 也进列表**：驱动在子线程的回合开始和结束时各发一条 `Subagent` 更新。
  - 更新的 id 是子线程 id，标题与卡片上的一致（“子代理 worker”）；
  - 状态：`completed` 记为完成，`interrupted` 记为取消，其余都记为失败，与卡片上“只有明确的 completed 才算完成”一致；
  - Codex 进程退出时，还在跑的子线程记为已取消，不会一直停在“进行中”；
  - 卡片上的进度行照旧。

**黑板写入标明子代理**：服务器分不出调用者，按方案写好的退路，由子代理自报名字。

- `board_write` 加可选参数 `subagent`，说明是“你是被派出来的子代理时填自己的名字”。任何子代理都能看到这句，不只是 Aeroric 投影的角色。
- 投影出去的角色定义正文末尾写明该填的名字：Claude 插件里是 `aeroric:<id>`，受管目录里是 `aeroric-<id>`。
- 条目的 `author` 仍是会话。条目和变更记录各加一个 `subagent`：
  - 去掉首尾空白后为空的不记；
  - 最多 60 个字符；
  - 用户的写入不记。
- 改一条已有的条目时，条目保留原来写它的子代理，这次改动另外记在变更记录里。
- 黑板上这一行显示成“证据 · 子代理 X：……”，名字放在正文前面，行尾截断时不会被截掉。悬停说明是“会话 T 的子代理 X 写的”。

**只读角色可以写黑板**：Claude 的只读白名单加上 `mcp__aeroric_context__board_write`。

- 理由同 H2 放行 Aeroric 工具：黑板是 Aeroric 自己的记录，委派出去的只读子会话本来就被要求把发现写上黑板（`delegation/prompt.rs`）。
- `board_decide`、`delegate` 和其他写入类工具仍不在白名单里。
- OMP 的 MCP 工具由 OMP 自己附加，本来就能写。

## Alternatives considered

**在服务器侧自动认出子代理**：用 Claude 流里子代理消息带的 `parent_tool_use_id`，和收到的 `board_write` 调用按时间配对；或者假设 `tools/call` 的 `_meta` 带工具调用 id。最强的理由是不靠模型自觉，标得准。没选：

- 按时间配对，在两个子代理同时写、或主会话和子代理同时写时会配错；配错的标记比没有标记更误导人。
- `_meta` 有没有、叫什么，静态读不出来，按猜测写进协议会变成永远不生效的代码。

真实 Harness 跑通后，如果确有可用字段，再加服务器侧的认定，自报的名字退为补充。

**原生子代理在核心层并进 `delegation.list`。** 最强的理由是一个接口拿到全部子代理。没选：`delegation.list` 是持久化的委派卡片，带契约、验收和回报；原生子代理只是本会话的实时状态，并进去要给它造一份假契约，还要处理持久化和重启。界面层合并，两份数据各保持原样。

**原生子代理也给打断按钮，按下打断整轮。** 没选：用户以为只停一个子代理，实际停掉整轮，这正是方案说的“入口亮着、实际做不到”。

## Consequences

- **收益**：
  - 用户在一个地方看到这个会话的所有子工作，清楚哪些能接手（委派），哪些只能看（原生）；
  - Codex 的子代理和 Claude、OMP 一样出现在列表里；
  - 子代理写到黑板上的东西能看出是谁写的。
- **局限**：
  - 黑板上的子代理名是自报的，模型不填就没有标记，填错也认不出来；它只用来显示，不影响任何权限；
  - 原生子代理列表只反映会话活着时的实时状态，不持久化：重新打开应用后看到的，是会话重放里还在的那些；
  - 真实 Harness 里子代理会不会按说明填 `subagent`、Codex 子线程事件在真实会话里的顺序，NOT RUN；进度页的样子未目检，已记进路线图 §8 待目检清单。
- **验证**（在 Mac mini 上跑）：
  - 核心层：
    - 黑板测试：子代理写入记名字、作者仍是会话；改动保留原写者、变更记录各自记；用户写入不记；空白不记；长名字截到 60 字符。
    - Codex 驱动测试：子线程开始、完成各一条更新；未知结束状态记为失败；进程退出时还在跑的记为已取消。
    - 角色定义测试：只读白名单含 `board_write`，不含 `board_decide`、`delegate`；正文写明该填的名字。
  - Swift：面板模型滤掉后台命令；行文字和两组标题；黑板行和悬停说明带子代理名，从 JSON 解码出 `subagent`。
