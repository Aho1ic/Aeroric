# Agent Note: D5 第一步：工作计划的规则

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D5 要做的是：把一个目标拆成几个工作单元，画出谁依赖谁。没有依赖的可以同时开始；有依赖的，等前置通过验收后自动开始，并拿到前置的产物作为输入；任何时候都能看到每个单元为什么在等。

完成条件：

- 任何时刻，每个单元的状态都能用一句话解释；
- 不会出现两个会写文件的单元同时在同一目录运行。

方案也写了调研里最常见的失败：Agent 群无界扩张、循环等待、几个 Agent 同时写同一批文件。

动手前（`main@5f877356`）核对的事实：

- **委派只有一对一的父子关系**（`sessions/live/delegation/`），没有子任务之间的先后依赖。
- **委派卡（`DelegationCard`）有现成的东西可用：**
  - 状态：启动中、运行中、检查中、已回报、失败、已停止、超预算、被打断；
  - 验收结果（B3），每条有状态、依据，以及是否已过期（`stale`）；
  - 交付物引用（B6，`ArtifactRef`，`art-…@版本`）。
- **工作区三种：**
  - 只读；
  - 在父任务目录里写（`Shared`），同一时间只能有一个，即 Q-B10；
  - 在隔离副本里写（`Copy`）。

D5 估计 15–25 天，分三步：

- 第一步：规则，本篇；
- 第二步：宿主按规则开委派、跟着委派卡刷新、重启后恢复；
- 第三步：Agent 提议计划、用户确认，以及看板界面。

## Decision

**协议**（`aeroric-protocol/src/work_plan.rs`）：

- `WorkPlan`：id、父任务、标题、单元、是否已确认、建立时间。
- `WorkUnit`：
  - id、标题、说明、角色、工作区、依赖、验收条款；
  - 开始后的委派 id；
  - 开始时拿到的前置产物（`started_with`）。
- `UnitState`：未开始、等待依赖、进行中、待验收、通过、失败、已取消。
- `UnitStatus`：状态、一句原因、输入是否已过期。
- 上限是常量，不做成设置：`MAX_UNITS = 8`，`MAX_RUNNING = 3`。

**规则**（`sessions/live/delegation/plan.rs`），都是纯函数，不启动任何东西。

`validate`，计划能不能保存：

- 1 到 8 个单元；
- 编号不重复，标题不能空；
- 依赖必须是计划里的单元，不能依赖自己；
- 有环就拒绝，并按顺序点名环上的单元，例如“计划里有环：「A」 → 「B」 → 「C」 → 「A」”。

`unit_state`，已开始的单元从委派卡得出状态：

- 启动中、运行中、检查中 → 进行中；
- 已回报：
  - 有一条验收失败 → 失败；
  - 全部通过且没有过期 → 通过；没有验收条款时，回报即通过；
  - 否则（还有没定的，或已过期）→ 待验收；
- 失败、超预算、被打断 → 失败；
- 已停止 → 已取消。

`schedule`，每个单元现在是什么状态、为什么，以及现在开哪几个：

- 已开始的，状态由委派卡决定，原因写“在运行”“已回报，验收还没全部通过”“验收全部通过”“失败了，等你处理”“已停止”。
- 没开始的，先看前置：
  - 有前置失败或停止 → 等待依赖，“前置「X」失败或停止了，等你处理”。下游不自动跳过；
  - 有前置还没通过 → 等待依赖，“等「X」通过验收”；
  - 前置都通过了，按顺序再看：
    - 计划没确认 → “计划还没确认”；
    - 已经有 3 个在跑 → “同时最多运行 3 个，等前面的跑完”；
    - 自己要在父任务目录里写，而已有一个在写 → “等「Y」写完：同一个目录同时只能有一个单元写文件”；
    - 否则 → 进入这次要开的名单，写“现在开始”。
- 名单按计划顺序排。同一轮里先排上的写者，也会挡住后面的写者。只读的和在副本里写的不受写者限制。

`inputs`、`brief`，输入怎么传：

- 下游拿到的输入，是前置委派卡上现在的产物引用；
- 下游的说明是它自己的说明，加上一段“前置单元的产物（用 artifact_read 读）”，逐条写路径和 `art-…@版本`；
- 前置没有登记产物时，写明“前置单元 …… 没有登记产物”；
- 不把前置的对话塞给下游。

**输入过期：** 下游开始时记下拿到的产物（`started_with`）。之后，只要其中有一个不在前置现在的产物里，比如版本变了、被撤回，这个单元就标“输入已过期”，原因后面加“前置的产物在它开始后又变了，输入已过期”。重不重做，由用户决定。

**调度是计划加委派卡的纯函数：** 宿主重启后，只要读回计划和各委派卡，再算一次，得到的就是同样的结果。第二步的“重启后恢复”就靠这一点。

## Alternatives considered

**调度器自己存每个单元的状态，委派卡变了就推进。** 最强的理由是一般的状态机都这么做。没选：

- 委派卡已经是唯一的事实来源（A1、B3、B6），再存一份就会出现两份对不上；
- 纯函数在重启后不用迁移任何东西，测试也最直接。

**前置失败时下游自动跳过，计划继续往下走。** 最强的理由是不会卡住。没选：

- 方案明确不做自动跳过；
- 下游依赖前置的产物，跳过只会让它在错误的输入上做事。

写明“前置失败了，等你处理”，正好满足“每个单元的状态都能用一句话解释”。

**上限做成设置。** 没选：方案把它定为常量，目的就是防止“无界的 Agent 群”。要放宽，应该另写笔记。

**同一目录的写者靠委派自己的拒绝来挡（“同一时间只有一个可写的子任务”）。** 最强的理由是已有这条规则。没选，至少不只靠它：

- 被拒绝的单元会变成“失败”，而它其实只是要等；
- 在调度里先挡住，原因写成“等「Y」写完”，用户看到的就是实情。

## Consequences

- **收益：**
  - 计划的规则，包括上限、环、依赖满足、单写者、输入传递和过期，都在一处，而且每个结论都带一句原因；
  - 重启恢复不需要额外的状态。
- **代价：** 没有。这一步只加了纯函数和类型。
- **局限：**
  - 还不能用：没有宿主方法，不会真的开委派，也没有界面；
  - 依赖满足只看验收结果，不看产物是否齐全；
  - 不检查两个单元的工作区有没有重叠，比如两个副本最后都要合回同一个目录，那由用户带回时处理。
- **验证：** core 新增 5 个测试，全部通过：
  - 计划校验：空计划、9 个单元、重复编号、依赖自己、依赖不存在、有环（点名环上的三个单元，不点不在环上的）；
  - 没确认时不开任何单元，下游写“等「A」通过验收”；确认后开前 3 个，第 4 个写同时最多 3 个；
  - 两个写者只开第一个，第二个写“等「W1」写完…”，副本照开；先前开的写者在跑时，新的写者等；它通过后，下一个开；
  - 前置：通过才开下游；已过期是待验收；失败、停止时下游写“等你处理”，不跳过；没有验收条款时，回报即通过；超预算算失败，检查中算进行中；
  - 输入：下游说明列出前置产物；没有产物时写明；开始后前置的产物换了版本，标输入已过期。
