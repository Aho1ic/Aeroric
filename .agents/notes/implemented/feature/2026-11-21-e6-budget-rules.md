# Agent Note: E6 第一步：无人值守工作的用量上限规则

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E6 要做的是：

- 设置里可以按日和月、按金额或 token，给“无人值守的工作”设上限。无人值守的工作，指定时任务、不是人发起的委派和审查；
- 用到 80% 时用量页变色，到顶时只通知一次；
- 侧栏有一个“暂停所有 Agent”开关。

做法的约束：

- 只在开始新工作前检查，不在回合中途截断；
- 人自己发的消息照常执行；
- 被跳过的定时任务，在运行记录里只记一行；
- 暂停时停掉进行中的回合、拒收新消息，定时任务到点安静跳过。

来源是 OCR #409：一次失败的大 MR 审查烧掉了约 9000 万 token。

第 7 节第 3 问“用量上限是否默认只管无人值守的工作”没有标出答复。这里按推荐的“是”来做：人发起的工作从不被上限挡住。

动手前（`main@4529b8df`）核对的事实：

- **谁算无人值守。** 宿主已有一个判断（`restart::unattended`），用在重启续跑和自动重试上：委派出来的子会话、定时任务开的会话、交办出去的待办。审查会话另有 `REVIEW_OF` 标记。
- **用量数据的来源。** 回合账单已经从会话转写里读出了每个回合的 token、模型和估算成本（`sessions::transcript_stats::TurnStat`，`cost_usd` 按价目表估，表里没有的模型不估）。驱动发的 `Usage` 事件口径各家不同：Codex 有累计也有单次，OMP 不报 token。所以不靠它们。
- **本地日的起点**已有 `memory::run::day_start_ms`，按本地时区算。

E6 估计 3–5 天，分三步：

- 第一步：规则和设置，本篇；
- 第二步：宿主在开始无人值守的工作前读用量、检查、只通知一次，以及“暂停所有 Agent”的执行；
- 第三步：设置界面、用量页变色、侧栏开关。

## Decision

**协议**（`aeroric-protocol/src/budget.rs`）：

- `UsageCap`：周期（本地日或本地月）、token 上限、估算金额上限，两个上限至少填一个；
- `BudgetSettings`：上限的列表，加上“暂停所有 Agent”；
- `Spend`：一个周期内用了多少 token、多少钱；
- `Gate`：`Go`、`Near`（到了 80%）、`Stop`（到顶）、`Paused`；
- `BudgetStatus`：给设置页用。

**规则**（`aeroric-core/src/budget.rs`），都是纯函数：

- `spent_since`：把无人值守回合里，结束时间在周期起点之后的 token 和估算金额加起来。估不出金额的回合，只计 token。
- `gate`：
  - 打开了“暂停所有 Agent”→ `Paused`，优先于一切上限；
  - 任何一个上限到了 100% → `Stop`，原因写明是哪个周期、用了多少、上限多少，以及“定时任务和不是你发起的委派、审查先不开始”；
  - 否则，有到 80% 的 → `Near`，写占比最高的那一个，例如“今天无人值守的工作用了 850 / 1000 token（85%）”；
  - 否则 → `Go`。
- `notice_key`：到顶时给一个键，同一个周期里不变：日上限用当天零点，月上限用当月 1 号零点。宿主用它做到“每个周期只通知一次”。
- `month_start_ms`：本地当月 1 号零点。
- **设置**存在 `<数据目录>/budget.json`：
  - 上限必须大于 0，否则拒绝保存，旧设置不变；
  - 两项都空的上限丢掉；
  - 没有文件时，是没有上限、也没暂停。

**只算无人值守的回合**：交给 `spent_since` 的回合，由宿主只从无人值守的任务里取，规则本身不区分。

## Alternatives considered

**另记一本用量账：每个无人值守回合结束时写一行。** 最强的理由是检查时不用读会话转写，代价小。没选，这一步不做：

- 回合账单已经从转写里算好了每回合的用量和成本，再记一份就会出现两份对不上的数字；
- 检查只在开始无人值守的工作前做一次，不频繁。

真要省读取，第二步可以只读本月动过的无人值守任务。

**到上限时在回合中途停掉。** 没选：方案明确说只在开始新工作前检查，从不在回合中途截断。中途停掉会留下改了一半的文件，和 E5 的“对外动作感知的重启”同一个顾虑。

**人发起的工作也受上限约束。** 最强的理由是上限更严。没选：第 7 节第 3 问的推荐是只管无人值守。人在看着，自己会停；被上限挡住自己的消息，反而让人困惑。

## Consequences

- **收益：** 上限、80% 提示、到顶只通知一次、暂停优先，规则都在一处，并且有测试。
- **代价：** 没有。这一步只有纯函数、类型和一个设置文件。
- **局限：**
  - 还没有接到宿主，规则不会挡住任何工作；
  - 金额是按价目表估的，价目表里没有的模型不计金额，只计 token；
  - 周期按本地时区算，跨时区出差时会跟着本机时区变。
- **验证：** core 新增 5 个测试，全部通过：
  - 只算周期内的回合；估不出金额的回合只计 token；
  - 门：没上限放行；79.9% 放行；85% 提示，并写明用量和占比；到顶停，并写明原因；月金额到顶时，即使日 token 没到也停；两个都快到时，写占比高的那个；暂停优先；
  - 到顶的通知键同一天不变；没到顶没有键；月上限用当月 1 号；
  - 月起点是 1 号零点，并且不晚于当天零点；
  - 设置存取：空的上限丢掉；0、负数、NaN 都拒绝，旧设置不变。
