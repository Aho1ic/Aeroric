# Agent Note: E8 记忆页写明新会话带入多少、哪些没带上

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E8（并入 C1–C3）要求记忆页有加载用量，例如“本次会话带入 3.2k / 6k 字，另有 12 条没带上”。来源是 OMB 记忆，以及 agent-knowledge-mcp 有上限的基础上下文：注入时返回实际带入的条目和截断情况（`sources`、`truncated`）。

E8 的其余几条，动手前（`main@aae2e84d`）核对过，都已经有了：

| 要求 | 已由谁完成 |
|---|---|
| 关于“你”的条目带原话 | C1 |
| 改动可撤销、改动日志在 Agent 写不到的数据目录 | C2、C3、H7 |
| 召回内容放在消息里，不放进系统提示词 | H4 |

还缺的就是加载用量。核对的事实：

- 新会话开场带入的记忆，由 `memory/profile.rs` 的 `render` 生成：关于用户的在前，项目事实在后，钉住的优先，总长不超过 `PROFILE_BUDGET_CHARS`（1200 字）。超出的不列，文末写“还有 N 条未列出，可用 memory_recall 检索”。
- H7 会把少用的事实移出开场（`demoted`），这些也不会被带入。
- 宿主已经有 `memory.profile` 方法，只返回这段文字；App 没有调用它。
- 会话页的账单（H3）能看到单个会话带入了多少记忆，但记忆页看不到整体情况。

## Decision

**core 量一量开场带入的内容。**

- `profile::measure` 和 `render` 用同一套规则，同时记下：用了多少字、带了哪些条目、哪些因为超出上限没带上。`render` 改为调用它，行为不变。
- `Memory::profile_load(项目)` 返回四样：
  - 文字；
  - 字数；
  - 带入的条数；
  - 没带上的条目，分两类：超出上限的，以及被 H7 移出开场的事实。

**宿主的 `memory.profile` 多返回这些：** `usedChars`、`budgetChars`、`carried`，以及 `leftOut`。`leftOut` 的每一项写 id、种类、文字和原因（`budget` 或 `demoted`）。

**记忆页显示一行。** 在当前范围（全局或某个项目）的列表上方，例如“新会话会带入 840 / 1200 字（8 条），另有 12 条没带上”：

- 有没带上的时，这一行用警示色，旁边有“看没带上的”按钮；
- 点开后逐条列出，每条写明原因：“超出字数上限”或“已移出开场，只能检索到”；
- 悬停写明：没带上的，Agent 仍能用 memory_recall 找到。

## Alternatives considered

**按会话记下每次实际带入了什么，在记忆页列出各会话的加载。** 最强的理由是更贴近“本次会话”。没选：

- 单个会话带入了多少，H3 的账单已经能看；
- 记忆页要回答的是“我的记忆现在会怎样被带入”，这就是开场时那一次计算；
- 用同一个函数现算，不会和真正带入的内容对不上。

**把上限改成可调。** 没选：方案没有要求，上限和开场的总预算（H3）是一起定的。

## Consequences

- **收益：**
  - 用户能看到记忆有多少进了每个新会话；
  - 能看到哪些因为字数或 H7 的调整没进去，好决定钉住哪条、压缩画像，还是删掉一些。
- **代价：** 每次刷新记忆页，多算一次开场文字，在内存里完成。
- **局限：**
  - 显示的是现在新开会话会带入的，已经开着的会话以它启动时为准；
  - 交接简报等其他开场内容不在这一行里，它们在 H3 的账单里；
  - 界面没有目检。
- **验证：**
  - core 新增 1 个，画像相关的 2 个全部通过：
    - 61 条记忆时，字数等于文字长度、不超过上限；
    - 带入加没带上正好 61 条，没带上的条数和文末“还有 N 条未列出”一致，没带上的文字不在开场里；
    - 不用记忆的项目只带入关于用户的 1 条。
  - Swift 新增 1 个：解码、“新会话会带入 840 / 1200 字（8 条），另有 2 条没带上”的写法、两种原因的写法、旧宿主返回 nil、什么都不带时的写法。
- **待目检：** 已记进路线文档 §8 待目检清单。
