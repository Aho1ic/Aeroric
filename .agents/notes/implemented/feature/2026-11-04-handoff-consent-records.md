# Agent Note: 交接授权依据（R1-3b）：按规则记下用户对提交、推送、发布说过的话，只供接手的会话参考

Status: implemented

## Problem

换来源或委派之后，新会话看不到用户之前说过的“提交”“先别推送”这类话。它要么再问一遍，要么凭猜测行事。我们需要让继任者知道用户说过什么，但不能把过去的同意当成这一次的授权。

## Decision

- core `checkpoint/consent.rs` 用规则识别用户亲手输入的消息，不调模型。规则如下：
  - 先按标点拆成短句。
  - 关键词：提交/commit、推送/push、发布/上线/release/publish；英文必须是独立单词。
  - 否定：关键词前面出现“不要、别、先别、不用、暂不、不许、不、勿、don't、no”等，记为否定，不限句子长度。
  - 同意：同时满足这几条才算——不是问句（以问号或“吗、么、呢”结尾，或带“要不要、是否”等）；不带任何否定或含糊的字；去掉标点后不超过 12 个字；不带“前、后、的”这类描述性的字。
- 排除注入文本：Codex 的注入上下文、`[Aeroric …]` 标记、以“# 交接清单”开头的文本都不算。状态提醒先把前缀切掉，再看剩下的部分。
- `Checkpoint.consents` 存每条记录：类别、立场、原话（最多 60 字）、第几轮、seq、时间。
  - 每类只保留最近一次同意和它之后的否定；从没同意过的类别，最多保留 5 条否定。
  - 同一轮里原话相同的记录去重。发送方和会话回显都会报告同一条消息，所以不去重会记两次。
  - 回放时从历史消息补算，不做迁移。
- 交接清单在“约束”之后加一节“用户明确同意过（仅供参考，不代表本次授权）”，节末提醒新会话：执行前仍要按自己的规则向用户确认。状态提醒不带这一节。
- 右侧详情加一个只读的“授权记录”小节，内容和交接清单一致。

## Alternatives considered

- **让模型判断用户是否同意**：会多一次请求，结论也不稳定。用规则可以写成测试，误判时也容易解释。
- **识别到否定时自动加成约束**：约束是硬规则，规则误判会把一句随口的话变成硬约束。所以只记录；需要硬约束时，用户自己点“加一条约束”。
- **把同意当成可以直接执行的授权**：违背“过去的同意不代表这次授权”这一原则，不采用。

## Consequences

- 同意的规则偏严，较长的同意句会漏掉，比如“这些都没问题了可以提交到主分支”。这是有意为之：漏掉一次同意，代价只是新会话多问一句。
- 每类只留最近一次同意。更早的同意要用 read_session 去看原文。

## Verification

- core 单测：
  - 短句同意、描述句和问句不算、否定从宽，三类正反例都有覆盖；
  - 注入文本被排除；
  - 保留规则和去重；
  - 交接清单这一节的文字和位置；
  - 状态提醒不带这一节。
- Swift 单测：`consents` 能解码，坏行被丢弃；排序与交接清单一致；标签和时间的文字正确。
