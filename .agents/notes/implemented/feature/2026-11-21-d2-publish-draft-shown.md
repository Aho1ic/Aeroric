# Agent Note: D2 第三步：快照窗里的发布草稿

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D2 要用户看到这些：

- 审查结论可以逐条编辑、勾选，再点“发布到 GitHub”；
- 发布前显示要发的全部内容和目标，即哪个 PR、哪个提交；
- 发布后每条有状态：已发布（带链接）、失败（带原因）、结果不明（去 GitHub 核对）；
- PR 有新提交时拦下发布。

动手前（`main@b9e4e0b1`）：

- [第一步](2026-11-21-d2-publish-core.md)在 core 里做好了草稿、标记核对、逐条结果；
- [第二步](2026-11-21-d2-publish-methods.md)给 App 加了 `github.writeDraft`、`writes`、`writeEdit`、`publish`；
- [D1 第三步](2026-11-21-d1-pull-review-section.md)的快照窗已经按审查列出结论。

## Decision

**快照窗里每份有结论的审查下面：**

- 还没有草稿时，有一个“准备发布到 GitHub”按钮。悬停说明：先变成草稿，可以逐条改、勾选，确认后才发。
- 有草稿时，显示发布草稿（`PublishDraftView`）：
  - **状态一行**，按颜色区分：
    - 草稿：“草稿：改好、勾选后发布”；
    - 发布中；
    - 已全部发布；
    - “部分发布：失败的可以再发”；
    - 没有发出去；
    - “N 条结果不明：先去 GitHub 核对”；
    - 目标已更新：写宿主给的原因，例如“PR 在审查之后有了新提交（现在是 …），没有发布；重新审查后再发”。
  - **每条一行：**
    - 勾选框；
    - 位置：“总评”，或者 `src/a.rs:12`；
    - 正文：没发出的（草稿、失败）可以直接改，改了出现“保存”；已发出和结果不明的只读；
    - 状态：待发布、不发布、发送中、已发布、“失败：原因”、“结果不明：原因，去 GitHub 核对”；
    - 已发布的有“在 GitHub 上看”链接。
  - **按钮：**
    - “发布到 GitHub”：没有要发的、正在做别的、目标已更新时不可点；
    - 结果不明时另有两个：
      - “核对后再发”：照常发布。宿主会先按标记在 GitHub 上找，找到的记为已发布，找不到的仍是结果不明、不发；
      - “仍然重发结果不明的”：悬停说明只在核对过、GitHub 上确实没有时才用。

**确认框：**

- 标题：“发布 N 条评论到 所有者/仓库#编号？”，N 是这次真正会发的条数：勾选了、还没发出的，以及要求重发时结果不明的那几条。
- 正文：
  - 针对的提交；
  - “发布前会再确认 PR 没有新提交；已经在 GitHub 上的不会重复发。”；
  - 要求重发时加一句“结果不明的这几条在 GitHub 上没有找到，会再发一次”；
  - 然后逐条列出位置和正文开头 60 个字，换行压成空格。

**状态对象** `PullReviewBook` 加了四件事：

- `writes`：随列表一起读；
- `prepare`、`edit`、`publish`：都在做完后重读列表，出错时写“准备发布失败”“保存失败”“发布失败”；
- `write(for:)`：取某份审查的草稿。

文字在 `PublishText`，协议模型是 `LiveWriteIntent`、`LiveWriteItem`。

## Alternatives considered

**每条一个“发布”按钮，逐条发。** 最强的理由是用户对每一条的控制最细。没选：

- 方案要求发布前显示“将要发出的全部内容”，一次确认看全；
- 逐条发也挡不住“发了一半改主意”。勾选已经能做到只发其中几条，失败的还能单独再发。

**结果不明时只给“重发”。** 最强的理由是界面更简单。没选：

- 多数“结果不明”其实已经发成了，只是回答丢了；
- “核对后再发”不会重复发，应该是默认的那一步；
- “仍然重发”留给核对过、确实没有的情况，按钮上写明。

**正文用多行编辑器，另开一个窗来改。** 没选：快照窗已经是一个弹窗，再叠一层太深。正文直接用可以多行的输入框改，最多显示 6 行。

## Consequences

- **收益：** D2 在 App 里能走完：准备草稿 → 改、勾选 → 看着确认框发布 → 每条的结果和链接。发了一半、结果不明、PR 被推过，界面上都写明下一步该做什么。
- **代价：** 快照窗里的审查块变长了。
- **局限：**
  - 草稿不能删，也不能重新从结论生成；
  - 不能把一条行内评论改到别的行；
  - 链接用系统浏览器打开；
  - 没有“批准”“请求修改”，这一片不做。
- **验证：** Swift 新增 `PublishDraftTests` 2 个测试，D1 的 `PullReviewTests` 照旧通过：
  - 草稿按快照窗的样子读出：位置、每条状态的几种写法、哪些能改、总状态（结果不明、目标已更新、部分发布）、这次会发哪几条（要求重发时多出结果不明的那条）、确认框标题和正文（提交、承诺、每条一行）；
  - 状态对象：准备、改勾选、改正文、发布、要求重发，都按当前项目发给宿主，参数对；保存被拒时写明。
- **待目检：** 已记进路线文档 §8 待目检清单。
- **NOT RUN：** 在真实 GitHub 上发布。
