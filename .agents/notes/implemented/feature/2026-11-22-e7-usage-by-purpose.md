# Agent Note: E7 第一步：网关用量按用途分开，失败的尝试单独算

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E7（并入 C4）：用量页把花费按用途分开，失败或被替换的尝试单独列出，不被成功的那一次掩盖。

来源有两个：

- LinkSense 记忆成本事故：72% 的钱花在记忆上，却没人知道；
- OCR #409：外层只统计了最后成功的那一次。

做法里写：网关的每条用量记录加上 `purpose`；另外核对托管 Codex HOME 的 `features.memories`，Codex 的原生记忆默认应关闭。

动手前（`main@d04e81a7`）核对的事实：

- C4 已经让网关按每次尝试记账（`router_attempts`），用量页“网关请求”一节列出每个请求和它的尝试。但没有用途，也不知道请求是哪个任务发的。
- 每个经网关的请求都带着任务令牌：`task_tokens::lookup` 能查到任务 id。签发令牌的地方有 7 处。
- 任务记录能看出任务的种类，App 也是这么判断的：
  - `reviewOf`：审查者；
  - `delegateOf`：委派的子任务；
  - `discussionOf` 或 `discussion`：讨论；
  - `branchOf`：重跑分支；
  - 定时任务开出的会话，在 `schedules.json` 的运行记录里有它的任务 id。
- Aeroric 自己调模型的地方（记忆整理的分析模型）不经网关，整理记录里已经各自记了模型、token 和费用（Q-M13）。
- Codex 0.167 的协议快照里只定义了 `ThreadMemoryMode`，没有任何请求用到它；`features.memories` 这个配置项在这个版本里有没有，要真实二进制才能核对。

## Decision

**每条请求记下任务和用途。**

- 网关在鉴权时从请求头取出任务令牌对应的任务 id，记账时写进新列 `task_id`；
- 用途写进新列 `purpose`，取值有：answer（回答）、review、delegation、discussion、rerun、schedule、unattributed（没带任务令牌，例如用访问令牌直连的客户端）；
- 旧行的用途是空的，界面写“未记录用途”；
- 两列都用 C4 加列的同一套 `ensure_column` 迁移。

**用途由宿主判断。**

- core 只提供一个挂钩 `set_purpose_resolver`，宿主装上：
  - 从任务记录按上面的字段判断；
  - 都不是时，再看定时任务的运行记录里有没有这个任务；
  - 否则就是回答。
- 判断结果按任务缓存，任务不会换种类。只有“回答”只缓存一分钟：定时任务是在开出会话之后才保存运行记录的，会话的头几个请求可能先到。

**按用途汇总。**

- `gateway.requests` 多返回 `purposes`：近 30 天每种用途的请求数、失败数、输入输出 token、用量未知的次数；
- 另外单独算失败的尝试：没被熔断跳过、但状态码 ≥400 或没有回应或带错误的那些，包括次数和它们各自的 token。这样一次先失败、换连接后成功的请求，失败那次的花费不会被成功那次盖住。

**界面：** “用量与成本 → 网关请求”的汇总下面多一段“近 30 天按用途”，每种用途一行，例如“审查 · 12 次 · 输入 30K · 输出 4K · 失败的尝试 3 次（输入 9K · 输出 0）”。有失败尝试的行用警示色。

## Alternatives considered

**签发网关令牌时就带上用途。** 最强的理由是记账时不用再查任务。没选：

- 签发的地方有 7 处，每处都要知道任务的种类；
- 定时任务的会话在签发时还认不出来。

记账时由宿主统一判断，只有一处规则。

**把记忆整理、标题这些 Aeroric 自己的调用也并进这张表。** 方案里列了“记忆、标题和摘要”。这一步没做：

- 这些调用不经网关；
- 整理记录已经逐次记了模型和费用。

把两边并成一张“按用途”的总表，是下一步。

**这一步就关掉托管 Codex 的原生记忆。** 没做：0.167 的协议里没有能用的开关；`features.memories` 能不能放进 `thread/start` 的配置、放了会不会让启动报错，要真实二进制核对。先记 NOT RUN，不盲改启动配置。

## Consequences

- **收益：**
  - 用量页能看出钱花在回答、审查、委派、讨论、重跑、定时任务里各多少；
  - 失败或被替换的尝试单独计数、单独算 token。
- **代价：** 每条请求多存两个短字段。用途判断第一次要读一次任务记录（之后有缓存），定时任务要读一次 `schedules.json`。
- **局限：**
  - 只覆盖经网关的请求：Claude、Codex 用自己的登录、不经网关时没有这些记录；
  - Aeroric 自己调模型（记忆整理）的花费还在整理记录里，没有并进这张表；
  - 托管 Codex 的原生记忆没有关（NOT RUN，见上）；
  - 按用途的汇总固定看近 30 天，界面上不能改；
  - 没有在真实网关流量上看过（NOT RUN），界面没有目检。
- **验证：**
  - core 新增 2 个，网关相关的 195 个全部通过：
    - 四条请求按用途分组，每条前面那次 429 尝试算进“失败的尝试”和它的 token，时间窗外的不算，读回的记录带着任务和用途；
    - 没带任务的请求是 unattributed。
  - 宿主新增 1 个：任务记录到用途的规则，定时任务只在别的都不是时才算。
  - Swift 新增 1 个：`purposes` 的解码、每行的说法、旧行写“未记录用途”。
- **待目检：** 已记进路线文档 §8 待目检清单。
