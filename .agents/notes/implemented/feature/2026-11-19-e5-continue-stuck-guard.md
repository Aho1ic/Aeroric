# Agent Note: E5 第三步：无人值守自动继续的卡住守卫

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) 的 E5 第 3 项。

动手前核对了现状。没人看着时，Aeroric 会用三种方式让一个会话自己接着跑，每种都已经有次数上限：

| 方式 | 上限 |
|---|---|
| [无人值守自动重试](2026-11-14-unattended-auto-retry.md)：某一轮没跑成，过一会儿在原会话里重试 | 网络、服务错误 3 次，额度 1 次 |
| [宿主重启后自动继续](2026-11-14-resume-after-restart.md) | 每个会话 1 次 |
| 交办待办的验收检查没过，把输出发回会话让它接着修（[待办第二批](2026-11-15-todos-second.md)） | `FIX_ROUNDS` = 2 次 |

缺的是 OMB 那种"看结果"的判断。每种方式只数自己发了几次，不看发出去之后的那一轮做成了什么，也看不到别的方式发了几次。三种方式会叠加：比如一个交办的会话，重启后自动继续一轮、修复一轮、那一轮没跑成又自动重试……每种都没超上限，加起来却可能一直在原地打转，每一轮都只回一句"我做不到"、一个工具都没成功调用。

OMB 运行时契约第 6 节的两条守卫是：

- 连续两次续跑都没有成功的工具调用，就停下；
- 续跑中最后三次的错误文字完全相同，就停下。

## Decision

- **一个守卫，管三种方式**：
  - 守卫的状态记在会话记录上（`continueGuard`），由 core `sessions/continue_guard.rs` 判断；
  - 宿主的三个发送点（`retry::send_due`、`restart::resume_settled`、`todo::run_check`）发之前都先问它。
- **记账**：每次自动发出，就在 `sends` 里记一笔（时间和方式：`retry`、`restart`、`todoFix`），只保留最近 6 笔。
- **判断**（下一次自动发送之前）：
  - 用会话自己的转写，对每一笔找它之后开始的第一轮（容许 5 秒误差，因为记账是在发出之后才写的），同一轮只算一次，还在跑的一轮不算；
  - 每轮取三样证据：
    - 这一轮有没有跑（是不是"没跑成"）；
    - 成功返回的工具调用有几个；
    - 没跑成时的错误文字（状态码加说明）。
  - 两条规则：
    - 最近两轮都跑了，但没有一个工具调用成功 → 停下，原因写"连续 2 次自动继续都没有成功的工具调用，再续下去也不会有进展"；
    - 最近三轮的错误文字完全相同 → 停下，原因写"同一个错误在自动继续后连续出现 3 次：500 upstream overloaded"。
  - **没跑成的轮次不算"跑了没进展"**：网络断了不等于 Agent 原地打转。这样用户 11-14 定的"网络错误重试 3 次"不会被第一条规则砍成 2 次，没跑成的轮次只参与第二条规则（同一个错误）。
- **停下之后**：
  - 守卫记下 `stalled`（原因和时间）。之后三种方式都不再自动发送，直到有人介入；
  - **自动重试**：这条重试链直接记为放弃（`gaveUp`），`error` 写守卫的原因。"需要我处理"里原有的"没跑成"那一行会带上这个原因；
  - **重启后自动继续**：跳过，会话照旧停在"被中断"等人点继续。定时任务的运行记录写"被 Aeroric 重启打断；自动继续停下：……，等你点继续"；
  - **待办修复**：不再把检查输出发回会话。
- **有人介入就清零**：用户在会话里发消息（`session.prompt`），或手动点"继续"（`session.continueAfterRestart`），整个守卫记录删掉，从头记账。
- **App**："需要我处理"多一种行，标签"自动继续停下"，说明就是守卫写的原因。如果是守卫让自动重试放弃的，"没跑成"那一行已经写了原因，就不再重复列这一行。

## Alternatives considered

**照搬 OMB：没跑成的轮次也算"没有成功的工具调用"。** 最强的理由是口径最简单。没选：网络错误时连着两次没跑成很正常，这样算会把用户定的 3 次重试砍成 2 次。没跑成的原因已经由重试链按原因区分了，守卫只管"跑了却没进展"和"一直是同一个错误"。

**每种方式各自加一份守卫。** 没选：问题恰恰出在三种方式叠加。一份记在会话上的账，才看得到它们加在一起的效果。

**守卫停下后过一段时间自动解除。** 没选：没有新信息时，过一会儿再试多半还是一样；有人介入才是新信息，所以只在用户发消息或点继续时清零。

## Consequences

- **收益**：无人值守的会话不会在"重试、修复、续跑"之间原地打转；停下时写明原因，用户在"需要我处理"里能看到。
- **代价**：
  - 每次自动发送前读一遍会话转写；
  - 记录上多一个最多 6 笔的字段。
- **局限**：
  - "没有成功的工具调用"按工具调用算。一轮只写文字、不调工具的回答（例如汇报"做不到"）算没进展；真的只需要写字的续跑，第二次时也会被拦下。不过这三种续跑本来都是要它去动手的；
  - 错误文字要完全相同才算同一个错误，带时间戳或请求 id 的错误认不出来；
  - 单独一种方式很难触发第一条规则：待办修复只有 2 次，发第 2 次时只有 1 轮可看；重启后自动继续每个会话只有 1 次。守卫主要在几种方式叠加时起作用（例如重启续跑一轮、自动重试一轮、修复一轮），以及自动重试链放弃后又开新链的情况；
  - 委派子会话里由主会话发的退回重做、审查回环发的意见不在守卫范围内，它们各自有上限（重做只由用户点；审查最多 3 轮，并有 B5 的无进展判断）。
  - E5 剩下第 4 项（不变量测试）。
- **验证**：
  - `continue_guard.rs` 新增 3 个测试：
    - 连续两轮跑了但没有成功的工具调用就停，中间有进展就不停，还在跑的一轮不算；
    - 同一个错误三次就停，错误不同不停，两次没跑成不算"没进展"；
    - 记账只留最近 6 笔，停下后状态保持，JSON 字段名正确。
  - 宿主集成测试 `a_cut_turn_that_already_pushed_is_not_continued_on_its_own` 补充：一个守卫已停下的无人值守会话，在自动继续打开时没有被续跑。把守卫判断临时换成永远放行后，这条断言确实失败，说明测试有效。
  - Swift 新增 `testAStalledContinuingShowsOnce`。
  - 没有用真实 Agent 跑过多次续跑（NOT RUN）。界面待目检，记在路线文档 §8。
