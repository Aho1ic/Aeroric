# Agent Note: H7 第二步：事实按使用移出或移回开场白

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H7 第 2 条：

- 按被注入后的反馈和被检索的次数，把条目在“开场白”和“按需检索”之间移动；
- 开场白满了，先降最久没用上的；
- 整理频率按访问量定，不按固定周期。

完成条件是：一条注入多次但从未被标“有用”的开场白条目被降级，并有记录。

动手前（`main@d0d7bf6c`）核对的事实：

- 开场白里的记忆档案（`memory/profile.rs::render`）取启用中的画像和事实：
  - 画像在前，事实在后；
  - 置顶的在前，其余按更新时间新的在前；
  - 取到预算为止，放不下的写“还有 N 条未列出，可用 memory_recall 检索”。
- 每条记忆有四个计数（`MemoryStats`）：
  - `injected`：开场白带过，同一任务只算一次；
  - `retrieved`：被 `memory_recall` 找到；
  - `helpful`、`wrong`：用户或 Agent 的反馈。
- 后台整理（`dream_due_scopes`）只在打开了后台学习、会话空闲时，逐个范围跑；H7 第一步的原生记忆读取也在这里。

## Decision

**只移动事实，不动用户画像和置顶的条目**（`memory/placement.rs`）：

- 画像（语言、习惯这类）不常被检索、也很少被标“有用”，但每个会话都用得上，按计数挪会误伤；
- 置顶是用户的明确意思。

**移出开场白**（仍能被 `memory_recall` 找到），满足任一条：

- 开场白带了至少 8 次，从没被标过“有用”，也没被检索过；
- 带过至少 2 次，“不对”多于“有用”。

**移回开场白**：移出后被标“有用”，或比移出时多被检索 2 次。移出时的计数记在 `demoted` 表里，用来和之后比。

**记录**：每次移动写进 `placements` 表（条目、时间、移出还是移回、原因），`memory.placements` 按新到旧读最近 50 条。

**什么时候判断**：每次后台整理的每个范围都过一遍。判断只看计数，没有被用到的条目计数不变，就不会移动，所以移动快慢跟着访问量走，而不是按固定周期。整个过程不调模型。

**预算放不下时**：同为置顶、或同为非置顶的事实中，“有用 + 被检索”多的排前；数相同时，按原来的顺序（新的在前）。放不下的是最少用上的，它们照常写进“还有 N 条未列出”。

## Alternatives considered

**给记忆条目加一个“位置”字段（开场白 / 检索）。** 最强的理由是记忆页可以直接显示。没选：

- 要改协议里的 `MemoryItem`，以及 Swift 的解码和所有构造处；
- 位置是由使用推出来的状态，单独一张表就能表达，也不会把一次移动和条目的修订混在一起。

记忆页要显示它的时候，再从 `memory.placements` 读。

**按“最后一次被用到的时间”判断。** 最强的理由是更贴近“最久没用上”。没选：使用记录（`uses` 表）只记哪个任务用过、用的是哪一种，不记时间；而“带了很多次仍没人用”比“很久没用”更能说明它在开场白里没价值，一个很久没开会话的项目不该因此丢掉记忆。

**连画像一起按计数移动。** 没选，原因见上。

## Consequences

- **收益**：
  - 开场白里长期没人用的事实会自己退出，把位置留给用得上的；
  - 退出的仍能检索到，用上了还会回来；
  - 每次移动都写明原因。
- **局限**：
  - 门槛（8 次、2 次）是初值，要等 H8 的数据来调；
  - 只在后台学习打开时整理；
  - 记忆页还看不到移动记录，只有 `memory.placements` 接口；
  - 第 3 条（对照原文纠错）是第三步。
- **验证**（在 Mac mini 上跑）：
  - 一个项目里放五条：一条闲置的事实、一条被检索过的事实、一条置顶事实、一条画像、一条被标“不对”的事实；开场白带了 8 次之后：
    - 闲置的和被标“不对”的移出，原因分别写明“带了 8 次”和“不对”；
    - 开场白里没有这两条，其余三条都在；
    - 检索仍能找到移出的那条。
  - 移出后再被检索一次，不够移回；第二次之后移回，原因是“又被检索 2 次”，开场白里又有它。
  - 移动记录共 3 条，最新的在前。
