# Agent Note: E4 按文件类型的审查规则

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) 的 E4。[审查循环](2026-10-30-review-loop.md) 的审查者只拿到 diff、验收条款和约束，审什么全凭它自己想到：

- 改了 GitHub workflow，审查者不一定想到 `pull_request_target` 和命令注入；
- 改了 SQL 迁移，不一定想到回滚和锁表；
- 项目自己的约定（例如"金额一律用整数分"）没有地方写给审查者。

OCR 的经验是"按路径用模板匹配规则，比用自然语言引导更稳定"：70 多份规则文档，用 glob 对应到文件类型。它的用户还提了两点：

- 同一路径要能叠加多份规则（OCR #1177），OCR 自己是第一个匹配的生效；
- 规则要带严重度（OCR #96）。

## Decision

- **规则**（`review/rules.rs`）：每条有编号、路径 glob、级别和内容。
  - glob 从仓库根算起：`**` 任意层目录，`*`、`?` 不跨目录，`{a,b}` 任选其一；
  - 不含 `/` 的 glob 按文件名匹配，在任何目录下都算（`*.rs`）。
- **内置 10 条**：
  - `gha-untrusted-code`（阻断）、`gha-hygiene`（重要）：`.github/workflows/`、`.github/actions/` 下的 yml；
  - `sql-migration`（阻断）；
  - `rust`、`swift`、`ts-js`、`python`、`shell`、`dependencies`、`dockerfile`（重要）。
  - 每条只写几项最容易出事、审查者容易漏的检查，不照搬 OCR 的长文档。
- **项目规则文件** `.aeroric/review-rules.json`：
  ```json
  {"disable": ["shell"],
   "rules": [{"id": "money", "paths": ["src/billing/**"], "severity": "blocker", "text": "金额一律用整数分"}]}
  ```
  - `rules` 追加规则，级别不写时是 `major`；
  - 编号和内置规则相同时，替换那条内置规则；
  - `disable` 关掉内置规则；
  - 文件读不懂，或某条规则缺编号、路径、内容时，整个文件不用，只用内置规则，并写明原因。
- **叠加**：一个文件命中几条就适用几条，不是第一个匹配的生效。
- **按改动前的版本读**：规则文件优先从这一轮"改动前"的快照树里读（`git cat-file -p <before>:.aeroric/review-rules.json`），所以一个回合改不了审查它自己的规则。
  - 快照里没有（文件被忽略或没入库）时，读磁盘上的现状。
  - 这一轮改了规则文件时，提示词写明"本轮按改动前的规则审查，规则文件本身的改动请照常审查"。
- **注入**：提示词里加"审查规则（按文件匹配）"一节，只放命中了这一轮要审的文件的规则。
  - 每条写明级别和它适用于哪些文件（最多列 8 个，多的写"等 N 个"）；
  - 要求违反时按规则的级别报，并在意见里写 `rule`；
  - 规则内容合计超过 12000 字时，多出来的只列编号。
- **意见的 `rule`**：只保留这一轮提示词里给过的规则编号，审查者编的编号丢掉。App 展开意见时写"依据规则：money"。
- **App**：进度页审查一节多一行"审查规则 · 内置 9 条 · 项目 1 条（关了 1 条内置）"。
  - 点开列出每条规则（编号 · 级别 · 路径，项目规则标"项目"，关掉的标"已关闭"），悬停显示内容；
  - 上面一行说明规则文件的状态：没有文件、已读取、读不懂（警示色，带原因）、远程项目读不到。
  - 数据来自新方法 `review.rules {taskId}`，读的是磁盘上的现状。

## Alternatives considered

**照搬 OCR 的规则文档，按文件类型一份一份写全。** 最强的理由是覆盖面广。没选：长文档会挤占审查者的上下文，而且大多是审查者本来就会看的通用建议。内置规则只写容易漏、出了事代价大的几项；项目需要更多时自己加。

**规则存在 Aeroric 的数据目录里，在 App 里编辑。** 最强的理由是不用碰仓库，界面上就能改。没选：规则是项目的约定，放在仓库里可以和代码一起评审、一起改；而且按改动前的快照读，能防止写代码的会话改规则来放松自己的审查，存在数据目录里就做不到这一点。代价是这一版 App 里只能看、不能编辑。

**第一个匹配的规则生效（OCR 的做法）。** 没选：OCR #1177 的用户就是因为这个没法给同一路径叠加语言规则和项目规则。

## Consequences

- **收益**：
  - workflow、迁移这类高风险文件有固定的检查项；
  - 项目约定能写给审查者，而且只在相关文件上出现；
  - 写代码的会话改不了审查自己的规则。
- **代价**：
  - 每轮审查多读一次规则文件（一次 `git cat-file`，或一次磁盘读）；
  - 改了 Rust、Swift 这类常见文件时，提示词多几百字。
- **局限**：
  - 规则文件被 `.gitignore` 忽略或没入库时，快照里没有它，只能读磁盘上的现状；这时写代码的会话在同一回合改它，会影响这一轮的审查。Aeroric 自己的仓库就忽略了整个 `.aeroric/`。
  - App 里不能编辑规则，要在编辑器里改 `.aeroric/review-rules.json`；
  - 级别只是写给审查者的要求，宿主不强行改意见的级别。
  - 远程项目（SSH、WSL）的审查卡读不到规则列表，只显示内置规则。
- **验证**：
  - `rules.rs` 新增 3 个测试：
    - glob 按路径或按文件名匹配，包括 `**`、`{a,b}`、`./` 开头；
    - 项目文件追加、替换、关闭内置规则，同一个文件叠加两条规则，读不懂时只用内置规则；
    - 超出篇幅的规则只列编号。
  - `review/tests.rs` 新增 `project_rules_reach_the_reviewer_as_they_were_before_the_turn`：在真实 git 仓库里，回合清空了规则文件，审查者拿到的仍是改动前的 `money` 规则和内置的 `rust` 规则，不相关的规则没有出现；意见里编的规则编号被丢掉。
  - 宿主测试 `a_changed_turn_is_reviewed_by_another_family_and_answered` 加了 `review.rules` 的调用。
  - Swift 新增 `testThePanelListsTheReviewRulesInForce`。
  - 界面待目检，记在路线文档 §8。
