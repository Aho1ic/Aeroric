# Agent Note: H7 第三步：记忆和之后的会话原文对不上时，提议替换并附原文位置

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H7 第 3 条：整理时发现记忆和会话原文矛盾，提议替换并附原文位置，用 C1 做的定位。完成条件是：一条和录好的会话原文矛盾的记忆，产生一条带原文定位的替换提议。

动手前（`main@754df87d`）核对的事实：

- **抽取时已经能取代旧记忆。** 抽取一个会话时，模型能看到已有记忆，用 `supersedes` 指出被取代的那条（`extract.rs` 的规则第 3 条）。这条候选以待确认状态写入，用户确认时旧的那条变成“已被取代”（`store.rs` 的 `activate`）。
- **但抽取这条路有两个漏洞：**
  - 模型只能看到前 40 条已有记忆（`extract::prompt`），之外的看不到；
  - 每个会话只抽取一次。之后才写下的记忆，不会再拿去对照更早结束、但比它新的会话。
- **后台整理（`dream.rs`）只比记忆和记忆。** 它找字面相近的组，判断重复或冲突；冲突进整理建议，但不看会话原文，也不带原话位置。
- **C1 的工具都在。** `locate::find_span` 按“去空白、全角转半角、忽略大小写”找到原话在消息里的字符位置。`EvidenceLocation` 记下消息序号、角色、起止位置和消息哈希。宿主的 `source_messages` 能读回一个任务或导入会话的文本消息。

## Decision

**整理时，把记忆放在之后的会话原话旁边**（`memory/contradict.rs`）：

- **怎么配对，不调模型：**
  - 宿主给每次整理带上这个范围最近结束的 4 个会话，按完成或归档时间取。项目范围取这个项目的；全局范围（用户画像）取所有用了记忆的项目的。
  - 每条启用中的画像和事实，只看结束时间晚于它写下时间的会话里，用户说的话。
  - 和这条记忆至少共享 2 个字对（与整理分组同一种比较），挑共享最多的一句。
  - 以下几种情况跳过：
    - 记忆自己的依据就是这句话（按消息哈希判断）；
    - 这条记忆已经有一条待确认的替换在等；
    - 这一对之前问过了。“问过”按“记忆 id + 消息哈希”记在记忆库里，最多留 500 对。
  - 一次整理最多问 8 对，共享多的、会话新的优先。
- **怎么判断，调一次分析模型：**
  - 逐对问用户这句话是否推翻了这条记忆。改主意、纠正、说明它不对才算；只是相关或补充不算，拿不准也不算。
  - 推翻的给出四样：逐字摘出的原话、改正后的记忆、理由，以及对的序号。
- **core 核对模型的回答，以下几种整条丢掉并计数：**
  - 原话在那条消息里找不到，或者少于 2 个字；
  - 改正后的文字是空的、太长、像密钥，或者和原记忆一样；
  - 对的序号不存在，或者同一对给了两次。
- **写入：**
  - 每条改正写成一条待确认记忆，种类、分类、范围都和原记忆相同，`supersedes` 指向原记忆。
  - 依据是用户的原话，位置是那条消息的序号和原话的字符起止，消息哈希按全文算，所以 C1 的 `memory.evidenceLocate` 能直接找到它。
  - 整理期间原记忆被改过的，这次不写。
- **生效：** 用户确认前，原记忆照常生效；确认走普通的确认流程，原记忆变成“已被取代”。拒绝就是普通的拒绝，这句改正被记成遗忘，不会再提。
- **整理记录：** 改正算进这次的“待确认建议”数，原因里写“N 条记忆和之后的会话原文对不上，改正放在待确认的记忆里”。

**整理的触发不变。** 对照原文只在后台整理或“现在整理”时做，和分组判断、画像压缩共用当天的整理次数上限。

## Alternatives considered

**改正写成一种新的整理建议（`DreamRelation` 加一种）。** 最强的理由是“整理建议”列表本来就放整理得出的东西，用户在一处看完。没选：
- 新增一种关系，App 的解码、建议卡片、采纳和撤回都要跟着改；
- 而“一条取代旧记忆的待确认记忆”，抽取那条路早就有了，带依据位置的展示和“在会话里查看”也已经有了。
用同一条路，用户确认的东西和抽取时的改正长得一样。

**每次整理把会话原文整段交给模型，让它自己找矛盾。** 最强的理由是模型可能找到字面不相近、意思相反的话（“缩进”对“tab 宽度”）。没选：
- 4 个会话的原文动辄几万字，每次整理都要付这笔钱；
- 模型给出的原话还是要逐字核对。
先按字对配对，每次最多 8 对、每对几百字，花费可控。字面不相近的矛盾，这一步漏掉，列在局限里。

**发现矛盾就直接替换，像重复的经验那样自动合并。** 最强的理由是用户的原话已经说了新的做法。没选：
- 方案 §8 第 3 问定了，整理的产出一律走提议和确认；
- 模型判断“推翻”可能错，比如用户只是在一个特例里换了做法。

## Consequences

- **收益：**
  - 记忆被用户后来的话推翻时，会出现一条改正。改正附带原话，以及原话在哪个会话的哪条消息；
  - 抽取时看不到的记忆、更早抽取过的会话，也能在整理时对上。
- **代价：**
  - 每次整理多读最多 4 个会话的记录；
  - 有配对时多一次模型调用；
  - 记忆库的键值表里多一个“问过”的清单。
- **局限：**
  - 只看用户说的话，不看 Agent 的；
  - 字面不相近的矛盾找不到；
  - 一条记忆每次整理只和一句话配对；
  - 会话结束时间晚于记忆写下时间，不代表那句话一定说在记忆之后。只要那句话不是这条记忆自己的依据，就会拿去问，由模型判断是否推翻。
- **验证：** `contradict_tests.rs` 新增 5 个测试：
  - 记忆和之后会话里共享最多的那句用户原话配对，以下几种不配：更早结束的会话、Agent 的话、问过的对、已经有替换在等的记忆；
  - 记忆自己的依据那句话不拿来对照；
  - 模型的改正只留原话在那条消息里找得到的那条：原话找不到、对的序号不存在、改正和原文一样的都丢掉，位置对应原话的字符；
  - 一次整理把被推翻的记忆变成一条取代它的待确认记忆，依据带任务、原话和位置，C1 的核对结果是“原位还在”；确认前原记忆照常生效，确认后被取代；
  - 同一对第二次整理不再问模型。
  记忆测试共 69 个，全部通过。
- **NOT RUN：** 真实会话和真实分析模型下的效果，包括配对的召回、模型判断“推翻”的准确度，都没跑过。
