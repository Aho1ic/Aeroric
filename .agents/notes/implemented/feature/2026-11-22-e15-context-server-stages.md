# Agent Note: E15 第二步：Aeroric Context 工具没接上时，写明停在哪一步、各用了多久

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E15 要求：MCP 没起来时，写明是哪个服务、卡在哪一步（启动、`initialize`、`tools/list`、调用）、各用了多久。

[第一步](../../implemented/feature/2026-11-21-e15-mcp-startup.md)读的是 Codex 和 Claude 自己报的 MCP 状态。留下两个缺口：

- DSH 和 OMP 不报 MCP 状态，这两家的会话什么也看不到；
- 两家都不报卡在哪一步。

CU 2026-11-13 记过 DSH 等 `tools/list` 卡住整个回合，正是第二个缺口。

动手前（`main@3424a3c8`）核对的事实：

- Aeroric 自己的 Context 服务器是 `aeroric-cli --data-dir <数据目录> mcp-context`。令牌从环境变量 `AERORIC_CONTEXT_TOKEN` 读。执行器每次给会话配上它时，都签发一个新令牌（`ContextTokens::issue`）。
- 服务器答 `initialize` 时会先问宿主这个项目有没有记忆、Wiki 等（`memory_enabled`、`host_says`），所以 `initialize` 自己就可能卡在宿主那边。
- 驱动把每条更新交给执行器的 sink 链。宿主能往会话日志里直接加一条提示（`registry().log(task).push`，E6 的用量提示就是这样加的）。
- 四家都在开始第一轮之前就接上 MCP 服务器、要工具清单。

## Decision

**服务器记下自己走到了哪一步。** `aeroric-cli mcp-context` 把各步时间写进 `<数据目录>/context-stages/<sha256(令牌) 前 16 位>.json`。文件名从令牌推出来，但不含令牌本身。记录的有：

- 进程启动的时间、pid；
- `initialize` 到达的时间，以及客户端名（`clientInfo.name`）；
- `initialize` 答完的时间；
- 第一次答完 `tools/list` 的时间；
- 第一次 `tools/call` 的时间和工具名。

每一步只记第一次，整份文件原子地写（先写临时文件再改名）。服务器启动时，顺手删掉 7 天没动的文件。

**执行器在回合结束时读。** 新的 sink 层 `ContextStageWatch` 放在投递回执层下面。看到 `TurnEnded` 时：

- 取这个任务当前的令牌和签发时间，读对应的文件；
- 工具清单已经要过，这个令牌就算接上了，之后不用再查；
- 没有要过，就在会话里加一条警示提示，每个令牌只说一次。

提示的四种写法：

- 文件不存在，或者是签发之前的旧文件：“没有启动：给会话配上它 N 秒后，这一轮结束时 Agent 还没有启动 aeroric-cli mcp-context”；
- 进程起来了，没有 `initialize`：写进程在配上后几秒启动、已过多久；
- `initialize` 到了没答完：写“卡在向 Aeroric 宿主查询（已等 N 秒）”；
- `initialize` 答完了，Agent 没来要工具清单：写 `initialize` 用了多久答完、之后已过多久。

每种都写客户端名（有的话），以及这一轮用不了记忆、委派、黑板等 Aeroric 工具。

**写进会话日志不在驱动的推送里做**，而是另起一个线程，避免和驱动拿着日志锁时撞上。

## Alternatives considered

**服务器每走一步就调宿主的 RPC 报告。** 最强的理由是宿主立刻知道，不用等回合结束。没选：

- 要报告的恰恰是“连宿主都可能连不上”的情况；
- 服务器为了报告去连宿主，会多一处可能卡住的地方。

写本地文件不依赖宿主，宿主不在也能事后查。

**按时间判断：配上后 N 秒还没要工具清单就报。** 没选：

- 要一个计时器，还要决定 N 是多少；
- 回合结束是一个自然的检查点：这一轮已经过去了，没接上的工具这一轮确实没用上。

**也覆盖用户自己能力包里的 MCP 服务器。** 没选：那些是别人的程序，不会写这个文件。它们的启动状态，Codex 和 Claude 在第一步里已经报了。

## Consequences

- **收益：**
  - 四家 Harness 的会话里，Aeroric 工具没接上时都会说出来，并写明停在哪一步、各步用了多久；
  - `initialize` 卡在宿主查询的情况能和 Harness 没来要清单的情况分开。
- **代价：**
  - 每次会话启动多写一个几百字节的文件，7 天后清掉；
  - 每个会话第一次回合结束时多读一次文件。
- **局限：**
  - 要等回合结束才说，一直卡着不结束的回合不会提示；
  - Harness 如果是第一轮之后才要工具清单，第一轮结束时会误报一次；四家目前都在开轮之前就要；
  - 一个令牌只查一次：之后进程换了（空闲释放后再恢复）又没接上，不会再说；
  - 写进日志的提示只在实时更新里有，重开会话页后看不到（同第一步）；
  - 没有在真实 DSH、OMP 上制造一次没接上的情况来看（NOT RUN）。
- **验证：**
  - core 新增 3 个：
    - 文件名从令牌推出、不含令牌、写了能读回、新文件不会被清掉；
    - 四种提示的写法和用时；
    - 签发前的旧文件不算。
  - 命令行新增 1 个：喂给服务器 `initialize`、`notifications/initialized` 和两次 `tools/list`，文件里客户端名、各步时间依次不减，判定为已接上。
  - Mac mini 全量验证 4039 个全部通过：加了这一层之后，宿主和执行器已有的会话测试都没有受影响。
