# Agent Note: D2 第一步：审查结论发布到 GitHub，同一条不会发两次

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D2：

- 审查结论可以逐条编辑、勾选，再发布到 GitHub；
- 发布后每条有状态：已发布（带链接）、失败（带原因）、结果不明（去 GitHub 核对）；
- PR 有新提交时，拦下发布；
- 完成条件：任何情况下都不会向同一位置发出两条相同的评论，每条评论的最终状态都能看到。

动手前（`main@b1610906`）核对的事实：

- [D1](2026-11-21-d1-pull-review-section.md) 已经能把 PR 固定成快照、只读审查、结论存成草稿。它的 GitHub 客户端只发 GET。
- **方案要求的 `OperationLedger` 是任务的操作台账。** 它在 `task-operations.json`，按任务的世代和认领记账，为“启动、停止会话”这类操作设计，键是任务，不是一条评论。
- **GitHub 的两类评论都能在正文里藏一段 HTML 注释，显示时看不见：**
  - 行内评论：`POST /repos/{o}/{n}/pulls/{num}/comments`，带 `commit_id`、`path`、`line`、`side`；
  - 整个 PR 的评论：`POST /repos/{o}/{n}/issues/{num}/comments`。
- 方案第 1 条：发布是用户动作，Agent 不能触发，Context 工具里不提供。

## Decision

**协议**（`aeroric-protocol/src/github.rs`）：

- `WriteIntent`：
  - id、项目、对应的审查；
  - 仓库、PR 编号、审查时的 head 提交；
  - 条目、状态、原因、建立时间、发送时间。
- `WriteItem`：
  - id；
  - 路径和行号，没有就是总评；
  - 正文、是否勾选、状态；
  - GitHub 上的评论编号和链接、失败原因。
- 条目状态：草稿、发送中、已发布、失败、结果不明。
- 发布状态：草稿、发送中、完成、部分完成、失败、结果不明、目标已更新。

**草稿**（`github::publish::draft`）：

- 第一条是总评：“审查了提交 abc1234：N 条意见。”，没有行号的结论也列在里面；
- 每条有行号的结论一条行内评论：严重程度（严重、问题、建议）加正文，有依据时附在后面；
- 全部默认勾选；
- `edit` 可以改正文、改勾选，但只限还没发出、也不在发送中的条目，正文不能为空。

**发布**（`publish`）只有一个入口，由 App 在用户点击后调用。分三步：

1. **重读 PR 的 head。** 和审查时的不同，就记成“目标已更新”，写明现在的提交，一条都不发。
2. **查标记。** 每条发出去的正文末尾有 `<!-- aeroric:<发布 id>:<条目 id> -->`。发布前把 PR 的两类评论都翻一遍（每类最多 2000 条），找到本次发布的标记，就把那一条补记成已发布，带上编号和链接，不管这一侧原来记的是什么。
3. **逐条发送：**
   - 发送前先把这一条记成“发送中”并存盘；收到回答后再存一次。
   - 2xx 且有评论编号：已发布。
   - 4xx：失败，带 GitHub 的原话。401、403 写明是令牌或权限的问题。
   - 连不上：失败，写明没有发出去。
   - 发出后超时，或 5xx，或 2xx 但回答读不出来：结果不明。
   - 一条失败不影响后面的。

**哪些条目会发：**

- 草稿、失败的会发；
- 结果不明的只有用户明确要求“仍然重发”才发，而且是在第 2 步查过标记、GitHub 上确实没有之后；
- 已发布的不再发。

**结果：**

- 有结果不明的 → 结果不明；
- 勾选的全部已发布 → 完成；
- 有一部分已发布 → 部分完成；
- 一条都没发出 → 失败。

**防止连点和重启：**

- 发布状态是“发送中”时，再发布直接拒绝。宿主另外还要按发布 id 加锁，放在第二步。
- 宿主重启后读到“发送中”，用 `recover` 把那些条目记成“结果不明”，注明“发送时 Aeroric 停了”。下一次发布会先按标记核对。

**写客户端单独一个**（`publish::Writer`）。读客户端 `client::Client` 仍然只发 GET，所以“只读”的断言仍然成立，写操作只在这一个模块里。

**存储：** `<数据目录>/github/<项目>/writes/<id>.json`。

## Alternatives considered

**照方案用 `OperationLedger`，按 `operation_key` 只发一次。** 最强的理由是项目里已有一套“只做一次”的台账。没选：

- 那套台账的键和恢复流程都围着任务的世代转，用在一条评论上要扩一个新的种类；
- 更关键的是，它只能记住“这边发过没有”。请求发出后没收到回答时，它也说不清 GitHub 那边有没有这条。
- 标记能直接在 GitHub 上查到，这才是“发没发成”的事实。所以每条的状态存盘加标记核对，比台账多回答了一个问题。

**结果不明时自动核对后重发。** 最强的理由是用户少点一下。没选：

- 方案第 4 条写明不自动重发；
- 查标记有上限：评论超过 2000 条的 PR 可能查不全。这时自动重发就可能重复。

**用 GitHub 的“一次审查”接口（`POST /pulls/{n}/reviews`），一次发出所有行内评论。** 最强的理由是只有一个请求，要么全成，要么全不成。没选：

- 一条评论的行号不在改动里，整次审查就会被拒，用户看不到是哪一条的问题；
- 方案要求逐条显示状态，部分成功如实显示；
- 发成“审查”会带上批准或请求修改的语义，而这一片只发评论和总评。

## Consequences

- **收益：**
  - 同一条只会成为一条评论：没收到回答时靠标记补记，重启时记成结果不明、等用户决定；
  - 每条的去向都写明：链接、原因，或者“结果不明”。
- **代价：**
  - 每次发布前要读一遍 PR 的评论列表；
  - 每条评论多一段看不见的注释。
- **局限：**
  - 标记只在评论正文里，有人在 GitHub 上编辑评论、删掉了注释，就核对不到；
  - 查评论最多 2000 条；
  - 行内评论只发在右侧，也就是新代码一侧；
  - 还没有宿主方法和界面，这一步用户用不上。
- **验证：** core 新增 6 个测试，全部通过，测试对着本地的假 GitHub，它会记下收到的评论：
  - 草稿：总评在前，没有行号的结论并进总评；可以改、可以取消勾选，已发出的不能改；
  - 一次发完：行内评论发在审查的提交上，带标记；发送前存过“发送中”；再发一次，不多发一条；
  - 5 条里第 3 条返回 422：其余照发，结果是部分完成并写明 422；再发只发那一条，GitHub 上最终 5 条；
  - 发布前 PR 被强推：结果是目标已更新，一条都没发；
  - 假服务收下评论但回答太晚：记成结果不明，不重发；下次发布按标记补记为已发布，GitHub 上没有重复；
  - 发送中重启：再点发布被拒；重读后记成结果不明；GitHub 上没有的不会重发；用户要求重发后才发，最终完成。
- **NOT RUN：** 对真实 GitHub 的发布。
