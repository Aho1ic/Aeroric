# Agent Note: H8 第二步：自动行为分三档上线，一键退回

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H8 第 3 条：

- 新沉淀的技能和新的自动注入，先是“候选”，只记录本来会不会触发；
- 再是“只挂描述”，证据够了才“默认生效”；
- 任何一档都能一键退回。

完成条件里与这一步有关的一条：三档之间的切换各有一条测试。

动手前（`main@2f86964b`）核对的事实：

- **按消息召回（H4）已经有三种模式。** 模式是 `off`、`candidate`、`on`，存在 `<数据目录>/recall/mode.json`，默认 `candidate`。三种模式之间不记换过几次，也没有“退回”。
- **学到的技能（B5-3b）采纳后立即挂载。**
  - 用户采纳技能提议后，写进 `builtin-skills/learned/index.json`；
  - `learned_offers` 把它挂给所在项目的每个会话。
  - 能做的只有停用（`disable_skill`）和换版本，没有“先观察”这一档。
- **开场白的指路段**（`opening::pointers`）列 Wiki 页标题和委派角色，不列技能。
- 别的自动注入（开场白的各段、委派结果送回）是固定行为，方案没有要求给它们分档，这一步不动。

## Decision

**一个通用的档位表**（`sessions/live/rollout.rs`）：

- **档位：**
  - `off`：关；
  - `candidate`：候选；
  - `described`：只挂描述；
  - `default`：默认生效。
- **每个自动行为有一个 id**：
  - `recall`：按消息召回，默认候选，最低到关；
  - `skill:<名字>`：学到的技能，默认只挂描述，最低到候选。
- **换档：** `set` 把离开的档位和时间压进历史，最多留 20 次；换成同一档不算一次。
- **退回：** `revert` 回到上一次换档之前的档位，所以从“默认生效”一下跳到“关”，退回一次就回到“默认生效”。没有历史时降一档；已在最低一档时报错。
- **计数：** 每次判断记一次 `checked`，本来会触发的再记一次 `would`。设置页以后用它显示“本来会触发几成”。
- **存储：** 都在 `<数据目录>/rollout/state.json`；读写时持锁，原子写入。

**按消息召回按档位走：**

- `recall.mode` 的读写改为读写档位：`on` 对应默认生效，`described` 是新加的一档。
- **只挂描述：** 命中时附进信封的只是出处，即记忆 id 加前 16 个字、Wiki 页标题，写明用得上再用 `memory_recall` 或 `read_wiki` 取，不附原文。
- 每条不太短的消息记一次判断，命中算“会触发”。召回关着时不记。
- H4 的 `mode.json` 留在原处，没有代码读它。它是同一天加的，只在开发时用过，档位表里没有记录时按默认的候选处理。

**学到的技能按档位走：**

- **候选：** `learned_offers` 不挂载它。每条不太短的用户消息，拿它 SKILL.md 的描述和消息比关键词，与召回的取词方式相同；至少共有 2 个就算“会触发”。这一项不论召回开不开都记。
- **只挂描述：** 照常挂载，就是采纳后原来的样子。挂载的技能各家本来就只先看到名字和描述。
- **默认生效：** 照常挂载，并在开场白指路的第一行写“学到的技能（遇到相关问题先用）：名字…”。只列适用于这个会话目录的技能。
- 不能在这里关，要关用技能本身的停用。两处都能关，用户会分不清哪个算数。

**宿主接口：**

- `rollout.list {}`：列出召回、每个学到的技能，以及其他动过或计过数的；
- `rollout.set {id, tier}`；
- `rollout.revert {id}`。

这一步不做界面，设置页放在下一步。

## Alternatives considered

**新学到的技能一律从候选开始，按方案字面来。** 最强的理由是方案就是这么写的：先观察，证据够了再挂。没选：

- 学到的技能要用户在提议卡上点了“采纳”才会有。采纳就是一次人工把关，再降成候选，等于让用户的选择悄悄不生效；
- 现在也没有界面让用户再把它升上来。

所以采纳后默认是只挂描述，和原来一样；候选这一档留给用户或以后的评测主动降级。将来如果有了不经用户确认、自动沉淀的技能，它们应从候选开始。

**每种行为各管各的档位，召回留在 `recall/mode.json`，技能写在技能索引里。** 最强的理由是改动小。没选：

- 设置页要一处列出所有自动行为的档位和触发率；
- 退回和换档记录的规则也应只有一套。

**退回固定降一档，不看历史。** 最强的理由是规则更简单。没选：方案说的“一键退回”，是撤销刚才那次改动。用户把召回从“默认生效”直接关掉，退回应该回到“默认生效”，而不是“候选”。

## Consequences

- **收益：**
  - 召回多了一个折中档：只告诉 Agent 有什么，不占它的上下文；
  - 一个学到的技能可以先降到候选，看它“本来会触发”的比例，再决定挂不挂、要不要写进开场白；
  - 每次换档都能退回。
- **代价：**
  - 每条用户消息都会读写一次 `rollout/state.json`：召回一次，候选的技能每个一次；
  - 候选技能的判断要读一遍技能索引和各 SKILL.md。
- **局限：**
  - 候选技能的“会触发”只是关键词重合，不是模型判断，也不看这个技能是否适用于消息所在的项目；
  - 开场白、委派结果送回等别的自动注入还没有档位；
  - 计数只有总数，没有按 Harness 分。
- **验证：**
  - 档位表 5 个测试：召回逐档上升，再逐档退回到关，最低一档报错；跳档后退回一次回到原档；学到的技能不能在这里关，退回到候选为止；计数；候选的技能不挂载，退回后又挂载。
  - 执行器 1 个测试：
    - 召回在只挂描述时只附出处、不附原文，在默认生效时附原文；
    - 候选的技能在召回关着时也按消息计数，不相关的消息不算触发；
    - 默认生效的技能进开场白指路，退回后不进。
  - 开场白测试延伸：默认生效的技能列在指路第一行。
  - 宿主集成测试 1 个：经 RPC 列出、换档、退回，`recall.mode` 读到的是同一个档位；错误的档位、把技能关掉、缺 id 都被拒绝。
- **NOT RUN：**
  - 真实会话里只挂描述的召回 Agent 会不会去取；
  - 默认生效的技能是否更常被用上。
