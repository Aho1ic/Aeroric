# Agent Note: E7 第二步：Aeroric 自己调分析模型的花费也按用途列出

Status: implemented

## Problem

[E7 第一步](2026-11-22-e7-usage-by-purpose.md)让网关的用量按用途分开。方案列的用途里有“记忆”“摘要”这类，它们是 Aeroric 自己调的模型，不经网关，所以第一步的表里没有。LinkSense 那次事故恰恰是这一类：72% 的钱花在记忆上，却没人知道。

动手前（`main@a8dfb20d`）核对的事实：

- Aeroric 自己调模型只有一个入口，宿主的 `analysis_call`。它用记忆设置里选的连接和模型，直接请求那个连接的地址，不经网关。用到它的有两处：
  - 记忆整理：抽取、做梦、矛盾检查；
  - Wiki 的模块说明。
- 记忆整理每次都在整理记录里（`MemoryRun`）记了时间、状态、输入输出 token 和估算费用。
- Wiki 模块说明每次生成都记进 `explain_runs`：模型、token、时间、是否出错。
- 两边都只记在自己的页面上，用量页看不到。

## Decision

**`gateway.requests` 的 `purposes` 多两行，从这两份记录读出来：**

- “记忆整理”：近 30 天的整理记录。用过 token 的，或者失败了的，算一次调用；
- “Wiki 模块说明”：近 30 天、有 Wiki 页面的项目的生成记录。

**统计方式和网关的行一致：**

- 成功的调用算进输入、输出；
- 失败了但已经花了 token 的，算进“失败的尝试”，带着它的 token；
- 失败了、也没花 token 的，只算失败次数。

**标明是直连。** 这两行带 `direct: true`，界面写“记忆整理（直连分析模型）”，和经网关的行分开，也不会重复计算：它们本来就不经网关。合在一起后按次数从多到少排。

## Alternatives considered

**让分析模型改走网关，统一由网关记账。** 最强的理由是只有一个账本。没选：

- 分析模型的连接可能不在网关的路由里；
- 改走网关会改变它的鉴权和代理设置；
- 两份记录已经逐次记着用量，读出来就够了。

**也算进估算费用（整理记录里有 `cost_usd`）。** 没选：网关的行没有费用，这一段只比 token 和次数；费用单独看整理记录。

## Consequences

- **收益：** 用量页一处就能看出记忆整理、Wiki 说明花了多少 token，失败的也单独列出。
- **代价：** 每次打开用量页，多读一次整理记录（最多 2000 条），并为有 Wiki 页面的项目各读一次生成记录。
- **局限：**
  - 整理记录只读最近 2000 条：30 天里整理超过 2000 次时，更早的那些不计入；
  - 托管 Codex 的原生记忆仍然没关（第一步写的 NOT RUN）；
  - 界面没有目检。
- **验证：**
  - 宿主新增 1 个测试：一次成功、一次花了 token 后失败、一次没花 token 就失败，统计为 3 次、失败 2 次、成功的 token 900/80、失败的尝试 1 次 300 token；没有调用时这一行不出现。
  - Swift 新增 1 个测试：`direct` 的解码，以及“记忆整理（直连分析模型） · 4 次”的写法。
- **待目检：** 已记进路线文档 §8 待目检清单。
