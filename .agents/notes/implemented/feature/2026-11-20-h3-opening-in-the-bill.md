# Agent Note: H3 第二步：开场白按段计入回合账单

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H3 第 5 条要求：开场白的内容和长度计入[回合上下文账单](2026-11-09-turn-context-and-retry.md)的"记忆""说明"两类，让用户看得到它占了多少。

[H3 第一步](2026-11-20-h3-unified-opening.md)之后，开场白由三段组成：用途说明、记忆档案、指路，有交接简报时接在后面。开场白之前账单是这样算的：

- **Codex**（`transcript_stats.rs` 的 `codex_base_kind`）：开发者消息按开头判断类别，开头是 `# Aeroric 记忆` 的算"记忆"。开场白现在以用途说明开头，整段会算进"其他"，其中的记忆档案也被算成"其他"。
- **Claude**：`--append-system-prompt` 追加的内容在会话文件的系统提示快照（`prompt_snapshot`）里，整段算"系统提示"。

开场白在会话记录里是什么样子，按 Codex 源码（`fe8e540a`）核对过：

- `developerInstructions` 由 `DeveloperInstructions` 渲染；
- 不加任何包装标记，原文作为开发者消息里单独的一段（`input_text`）。

## Decision

**`opening::bill_parts(text)`：按标题拆分，各段的字数加起来等于原文。**

- 从 `---` 分隔处切开：前面是开场白，后面是交接简报，简报算"其他"。
- 开场白再按 `\n\n# ` 开头的标题分段：
  - `# Aeroric 记忆` 开头的段算"记忆"，这个前缀在 `memory/profile.rs` 定义成常量 `HEADER_PREFIX`；
  - 用途说明、指路都算"说明"；
  - 相邻的同类段合并。
- 分隔符计入前一段，所以各段字数之和等于原文字数。

**Codex。** 开发者消息里以用途说明标题开头的那一段，按 `bill_parts` 分段计入，来源写"Aeroric 开场白"。其他段照旧按开头判断类别。

**Claude。** 系统提示快照里，从用途说明的标题开始拆出：标题之前的仍算"系统提示"，从标题起按 `bill_parts` 分段计入。

**界面。** 不用改：账单卡本来就逐项列出类别和来源，"说明""记忆"两行的来源里会出现"Aeroric 开场白"。

## Alternatives considered

**给开场白加一个包装标记（比如 `<aeroric_opening>`），账单认标记。** 最强的理由是识别更可靠，不依赖标题文字。没选：模型读到的就是这段文字，加 XML 式的包装会多出一层模型要理解的结构。用途说明的标题本来就是唯一的，用它识别就够了。

**整段算"说明"，不拆出记忆。** 没选：方案明确要求分"记忆""说明"两类；记忆档案的长度是用户最想知道的（它有自己的上限，满了要压缩画像）。

## Consequences

- **收益**：
  - 用户能在账单里看到开场白各段各占多少；
  - Codex 的记忆档案不再因为排在用途说明后面，被算成"其他"。
- **局限**：
  - Claude 那部分只按代码推断：`--append-system-prompt` 的内容出现在系统提示快照的末尾，没有用真实的 Claude 会话文件核对过（NOT RUN），需要一份新近的会话文件；
  - DSH、OMP 的会话文件本来就不记基础部分，账单不拆这段，开场白也就不在里面。
- **验证**（在 Mac mini 上跑）：
  - `bill_parts` 一个单测：各段的类别按顺序是说明、记忆、说明、其他，字数合计等于原文；没有记忆档案时整段算说明。
  - 账单一个测试：
    - Codex 会话文件里，开发者消息的开场白段拆成说明、记忆、其他，数字与各段字数相同，来源是"Aeroric 开场白"；
    - Claude 的系统提示快照拆出同样几项，系统提示只剩开场白之前的部分。Claude 的账单另外还计了一点别的内容，折算有舍入，允许差 3。
