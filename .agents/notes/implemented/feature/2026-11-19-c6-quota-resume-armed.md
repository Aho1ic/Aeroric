# Agent Note: C6 额度恢复后自动续跑，由用户逐回合打开

Status: implemented

## Problem

[批次 C 方案](../../proposed/feature/2026-11-15-adoption-c-memory-gateway-skills.md)第 C6 片要求：回合因额度用尽停下时，给用户一个"额度恢复后自动继续"的开关，默认关；打开后到恢复时间自动续跑一次，或者以明确原因取消。

动手前核对现状，发现这件事一半已经有了：

- [无人值守自动重试](2026-11-14-unattended-auto-retry.md)已经能处理额度用完：宿主每 30 秒看一次会话，最后一轮因额度没跑成、且读数给出恢复时间时，在任务记录上存一条 `autoRetry` 链（等待 → 已发 / 放弃 / 取消），到点在会话里发一句"接着做"。
- 这条链只在全局开关"自动继续"打开时工作，面向的是没人看着的会话。
- 有人看着的会话（全局开关关着）停在额度上，只能等用户自己回来重发。没有"只为这一轮打开"的入口。

方案原本设想走投递队列，给投递加一个"不早于某时间"的条件，再用原回合的操作键派生新键防止重发。

## Decision

**沿用已有的重试链，不新建定时投递**（`core/crates/aeroric-core/src/sessions/auto_retry.rs`）：

- `AutoRetry` 加两个字段，缺省为假、为假时不写盘，旧记录照常读：
  - `armed`：这条链是用户为这一轮打开的；
  - `postponed`：已经因为额度仍用完顺延过一次。
- `arm` 决定能不能打开，只在以下条件都满足时给出一条等待中的链：
  - 最后一轮明确因额度没跑成，否则"上一轮不是因为额度用完没跑成"；
  - 这一轮还没在等，否则"这一轮已经在等额度恢复后自动继续"；
  - 读数给出了恢复时间，否则"读不到额度的恢复时间，没法定时继续"。
  
  到点时间是恢复时间后一分钟（恢复时间已过则从现在起一分钟），只发一次。
- `before_send` 在发出前再查一遍：
  - 会话已停止：取消，写"会话已经停止，不再自动继续"；
  - 这一轮之后有过新的回合（用户发过消息）：取消，写"期间你发过新消息，不再自动继续"；
  - 读数仍显示用完：第一次顺延到新的恢复时间后一分钟，第二次放弃，写"恢复时间到了额度仍用完"。
- 发出的话以"额度已恢复，这是你开的自动续跑。"开头，后面接原有的"先看看工作区现在的状态，再从中断处接着做"。

**宿主**（`core/crates/aeroric-host/src/session_live_services/retry.rs`）：

- `session.autoRetry.offer {taskId}` 返回能否打开以及预计时间 `{available, resetAt, dueMs}`，不能时返回 `{available:false, reason}`。
- `session.autoRetry.arm {taskId}` 存下这条链，在会话里记一条"你开了额度恢复后自动继续，HH:MM 继续"。会话不存在返回 NOT_FOUND，条件不满足返回 INVALID_ARGUMENT 并附原因。
- 打开的链立即交给 30 秒一次的巡检；宿主重启后，巡检照旧从记录里找回所有等待中的链。
- 全局开关关着时，未经用户打开的链照旧到点取消；用户打开的链不受全局开关影响，但要先过 `before_send`。
- 取消沿用原有的 `session.autoRetry.cancel`。

**App**：

- 会话页在最后一轮因额度没跑成、且没有等待中的链时，问宿主能否打开。能打开就在顶部显示一条提示："额度用完了，约 HH:mm 恢复"，旁边一个按钮"恢复后自动继续"。
- 悬停说明写明：恢复一分钟后发一句接着做；期间发了消息或停止会话就不发；不改权限；续跑会继续消耗额度。
- 打开后提示换成原有的自动重试横幅，文字为"额度恢复后自动继续：HH:mm 继续"，带"取消"。

## Alternatives considered

**按方案走投递队列，给投递加"不早于"条件。** 最强的理由是续跑和用户手动排队的消息走同一个队列，顺序和状态都在一处。没选，原因有两条。第一，重试链已经解决了同一类问题：到点发送、宿主重启后找回、发送失败记原因、横幅加取消。另起一套，就会有两套对"额度用完后怎么续"的判断。第二，投递队列里的条目是用户写好的原话，续跑发的是一句"接着做"，算不上用户的输入。原回合派生键要防的是发两次，这里由链的状态挡住：发出后链变成"已发"，重启后不会再发。

**到点重发原回合的那条输入。** 方案写的是"发出同一条输入"。最强的理由是用户不用解释，模型照原意重来。没选：额度用完的回合常常已经做了一半，原样重发会让模型从头再做一遍、改过的文件再改一遍。已有的续跑话术要求先看工作区，再从中断处接着做，更安全。

## Consequences

- **收益**：
  - 有人看着的会话停在额度上，可以一键约好恢复后接着做，不必盯着时间；
  - 用户中途写了消息或停了会话，续跑自动作废并写明原因，不会和用户抢着发。
- **代价与局限**：
  - 读数只来自内置 Codex 的配额读数，其他 Agent 读不到恢复时间，不提供开关；
  - 到点时读数接口不可用，按"已恢复"处理照发。如果其实仍用完，这一轮会再次因额度停下，链已用完，不会反复重试；
  - 到点时用户正在输入框里打字但还没发，宿主不知道，会照发；
  - 宿主没有"会话正在被看着"的判断，所以开关不区分有人和无人，只要用户按了就生效。
- **验证**：
  - `auto_retry` 新增 3 个测试：
    - 只有额度停下、恢复时间已知的回合能打开，不能重复打开，到点是恢复后一分钟；
    - 发出前遇到停止、新回合就取消，仍用完先顺延一次再放弃；
    - 两个新字段随记录读写，缺省不写盘。
  - 宿主集成测试 `session_live` 延伸：
    - 对正常结束的会话，offer 返回不可打开和原因，arm 返回 INVALID_ARGUMENT，记录上不写 `autoRetry`；
    - 对不存在的会话，arm 返回 NOT_FOUND。
    
    额度真用完、到点发出的完整路径需要内置 Codex 的配额读数，集成测试没有覆盖，靠核心层的纯函数测试和目检。
  - Swift `AutoRetryTests` 新增一个测试，检查用户打开的链的横幅文字和提示文字。
  - 界面待目检，记在路线文档 §8。
