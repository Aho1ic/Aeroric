# Agent Note: 定时任务第一批：到点在项目里开新会话，先跑检查命令决定要不要唤醒模型

Status: implemented

## Problem

backlog A12（工作安排）和路线图 §3.8（定时任务的前置检查）一直没有落地：

- 侧栏没有任何"到点做事"的入口。工作安排页（`WorkArrangementsReview`）只是 DEBUG 下的设计稿，里面是演示数据，没有接后端。
- 用户想要的典型用法是"每天早上看看昨晚有没有新提交""每周五写周报"。这类任务大多数时候没有事可做，每次都唤醒模型是白花钱。§3.8 的思路（来源 N 的 schedule gate）是先跑一条 shell 检查，检查不通过就不唤醒模型。

用户 2026-11-14 说"全部按推荐"，定了 5 条：

1. 下一项做 A12 定时任务第一批，含 §3.8 前置检查。
2. 重复方式只有一次、每天、每周、每隔 N 小时，不做 cron。到点在指定项目里，用指定的 Agent 开一个新会话，发出预设的提示词。错过的时间只补最近一次。上一次的会话还在跑，就跳过并记为"忙，跳过"。工作安排设计稿里的待办、交办、规则不在这一批。
3. 前置检查：每条规则可选一条 shell 命令，在项目目录里用用户的登录 shell 运行，超时 30 秒。退出码为 0 才开会话，输出的前 2KB 附在提示词末尾；不为 0 就记为"检查没过"，不唤醒模型。
4. 侧栏加一页"定时任务"，用胶囊样式：列表、新建和编辑弹窗、每条规则的运行记录，能点开那次开的会话。
5. 会话用这个 Agent 的默认权限模式，需要审批时进"需要我处理"；每条规则每天最多开 24 个会话；检查命令按用户身份运行，不另加沙箱。

## Decision

**规则与运行记录**（协议 `schedule.rs`，core `schedule/`）

- `ScheduleRule`：名字、项目、Agent、可选的模型、提示词、重复方式（`Repeat`）、可选的检查命令（`check`）、开关，以及"上一次处理到哪个时间"（`last_due_ms`）。
- `Repeat` 的四种取值：
  - `once {atMs}`；
  - `daily {minute}`：当地零点之后的分钟数；
  - `weekly {weekdays, minute}`：1 是周一，7 是周日；
  - `every {hours, fromMs}`：从 `fromMs` 起每隔几小时。
  - 字段在线上是 camelCase（`rename_all_fields`）。2026-11-15 目检前，`rename_all` 只改了取值名，字段仍是 `at_ms`、`from_ms`，App 保存"一次"和"间隔"规则时会被拒绝（"missing field `from_ms`"）；现在两种拼法都能读，写出来是 camelCase。
- 运行记录 `ScheduleRun` 的结果（`RunOutcome`）有五种：
  - `started`：开了会话，带会话 id；
  - `checkFailed`：检查没过，带输出；
  - `busy`：上一次的会话还在跑；
  - `limited`：到了每天的上限；
  - `failed`：开会话失败，带原因。
  另外两个标记：`catchUp` 表示比该运行的时间晚了 2 分钟以上，是补跑；`manual` 表示是"立即运行"。
- 存储：规则和运行记录都放在数据目录的 `schedules.json`，整份原子写入。每条规则最多保留 50 条运行记录。读写由一把锁串起来，定时触发和"立即运行"不会同时改这个文件。

**什么时候算"该运行了"**（`calendar.rs`）

- 按本地时区计算，传进来的是 `chrono::Local`，测试里固定成 UTC+8。
- `latest_due(规则, since, now)` 只返回 `(since, now]` 之间最近的一个时间点。宿主关着的几天里错过的多次，合并成一次补跑。
- 每天和每周：从今天往前最多看 8 天，找最近一个落在选中星期几的时间点。夏令时跳过的那个本地时间不存在，就跳过那一天。
- 保存规则时，把"已处理到"设成保存的那一刻。10:05 保存一条每天 10:00 的规则，要等明天 10:00，不会立刻补跑。

**一次运行的顺序**（`Schedules::tick`、`fire`）

宿主每 30 秒（`TICK_MS`）调一次 `tick`。每条开着的规则如果有该运行的时间点：

1. **忙**：这条规则上一次开的会话还在跑回合，或者状态是待处理、运行中、等你回答，就记为 `busy`，不开新会话。
2. **上限**：今天（当地零点起）已经开了 24 个会话（`DAILY_MAX`），记为 `limited`。
3. **检查**：
   - 项目不在本机，记为 `failed`："项目不在本机，没法运行前置检查"。
   - 否则用 `$SHELL -lc <命令>` 在项目目录里运行，30 秒超时；超时就杀掉进程，算没通过。
   - PATH 用 Agent 启动时用的那一份（`login_shell_path`，从交互式登录 shell 读一次）。`zsh -lc` 不读 `.zshrc`，很多人把 Homebrew 加进 PATH 的那一行就在那里；2026-11-15 目检时 `gh` 因此报 command not found。
   - stdout 和 stderr 分别在独立线程里读，避免一边写满管道卡住进程。
   - 退出码不为 0，记为 `checkFailed`，输出里带上"退出码 N：……"。
4. **开会话**：
   - 提示词是规则里写的那段；检查通过并且有输出时，在后面附上"前置检查 `<命令>` 的输出："，再加一个代码块，内容最多 2000 字（`CHECK_OUTPUT_CHARS`），超出的写"（已截断）"。
   - 宿主走和"新会话"按钮完全相同的 `task.run`（`services::task_run` 改为 `pub(crate)`）。不传权限模式，所以用宿主的默认值；开好之后把会话改名为"<规则名>（定时）"。
5. 无论结果是哪一种，这个时间点都记为已处理，规则不会越积越多。一次性的规则运行过后自动关掉。

**立即运行**（`run_now`）：不看时间，其余规则照旧：忙就跳过、受每天上限限制、照样先检查。手动验证一条规则不用等到点，结果标为"立即运行"。

**宿主 RPC**（`session_live_services/schedule.rs`）

- `schedule.list {}` → `{rules}`，每条带下次运行时间 `nextMs`；
- `schedule.save {rule}` → `{rule}`：`id` 为空是新建；项目不存在或规则不合法，返回 `INVALID_ARGUMENT`；
- `schedule.delete {id}` → `{deleted}`，运行记录一起删；没有这条返回 `NOT_FOUND`；
- `schedule.runNow {id}` → `{run}`；
- `schedule.runs {id}` → `{runs}`，从新到旧。

**规则校验**（`schedule::validate`）：

- 名字和提示词不能为空；
- 必须选了项目和 Agent；
- 时间不超过 23:59；
- 每周至少选一天，并且只能是 1–7；
- 间隔在 1 小时到 7 天之间。

**界面**（`SchedulePage`、`ScheduleEditorSheet`、`ScheduleStore`）

- 侧栏"工作"组新增"定时任务"，排在"需要我处理"后面。
- 列表每行：
  - 胶囊开关、名字；
  - "每天 09:00 · 项目 · Agent · 先检查"；
  - 下次运行的时间；
  - "立即运行"按钮；
  - ⋯ 菜单：编辑、运行记录、删除。删除前会确认。
- 运行记录在行内展开，最多显示 20 条：时间、结果（"补跑 · 上一次还在跑，跳过"这类说法）、检查输出；开了会话的有"打开会话"。
- 编辑弹窗：
  - 名字、项目、Agent 都用胶囊控件；
  - 重复方式用胶囊分段：一次、每天、每周、间隔；
  - 时间：一次是日期加时间；每天是时间；每周是七个星期几的胶囊加时间；间隔从 1、2、4、6、12 小时和 1 天里选；
  - 提示词是多行输入框；检查命令是带终端图标的胶囊输入框；
  - 下面一段说明：检查怎么运行、权限模式、每天上限、错过只补一次。
- Agent 的选项和新会话页一样，是四种 Harness（`agentChoices`）。

## Alternatives considered

- **往已有会话里发消息，而不是开新会话**：上下文能接着用。没有采用（第 2 题）：定时任务常常在无人看着的时候跑，往一个正在用的会话里插话会打乱它；新会话互不干扰，侧栏里也一眼能看出是哪次定时开的。
- **错过的每一次都补**：不漏掉任何一次。没有采用（backlog A12 原文就是只补最近一次）：宿主关了三天，回来连开三个"早报"会话，没有意义还花钱。
- **上一次还在跑就排队**：不丢掉这一次。没有采用：排队的那次真正开始时，它要看的东西多半已经被上一次看过了；记一行"忙，跳过"，用户能看到，也能手动立即运行。
- **支持 cron 表达式**：更灵活。没有采用（第 2 题）：四种重复方式覆盖了常见用法，cron 的界面和校验成本高，可以以后加。
- **检查命令放进沙箱**：更安全。没有采用（第 5 题）：命令是用户自己写的，和他在终端里敲的权限一样；加沙箱反而会让 `git fetch` 这类需要网络和凭据的检查失败。
- **直接把工作安排设计稿接上后端**：设计稿已经画好了待办、交办、规则、核验的整套流程。没有采用（第 2 题）：那套是"工作安排"，牵涉待办的来源、交办权限、完成核验，比"到点开会话"大一个量级；先把触发、检查、记录这条最小的链路跑通。
- **规则存进任务库或 SQLite**：可以查询。没有采用：规则只有几条到几十条，一个 JSON 文件整份读写最简单，坏了也好修。

## Consequences

- 收益：
  - 有了第一个真正的"到点做事"入口；配上检查命令，没新提交的早上一分钱不花；
  - 补跑、忙、上限、检查没过都会记一行，用户能看到每个时间点发生了什么；
  - 开会话和手动新建走同一条路径，会话本身没有任何特殊之处，审批、撤销、回合分级都照常可用。
- 代价：
  - 只有宿主开着才会触发：Mac 睡眠或关机期间不会运行，醒来后只补最近一次；最长延迟 30 秒；
  - "默认权限模式"是宿主 `task.run` 的默认值（询问），不读新会话页上次的选择；需要审批的定时会话会一直停着，等你去处理；
  - 检查命令按用户身份、用登录 shell 运行，登录脚本有输出时会混进检查输出；命令本身的安全由用户负责；
  - "忙"只看这条规则上一次开的会话，不看同一项目里的其他会话，两条规则可能同时在一个项目里写；
  - 远程项目、已移除的项目不能运行，记为失败；
  - 时区按宿主所在 Mac 的本地时间；改了时区，每天和每周的规则跟着变；
  - 工作安排设计稿里的待办、交办、核验、活跃时段、写入系统日历、7 个模板都还没做（活跃时段、常用模板和"忙时结束后补一次"已由[第二批](2026-11-14-scheduled-tasks-second.md)实现；待办和手动交办由[工作安排第一批](2026-11-15-todos.md)实现）；
  - 规则保存在本机的 `schedules.json`，不跟随项目，也不同步到其他设备。
- [推迟提案](../../proposed/feature/2026-11-08-new-addition-deferred.md)里有两项的触发信号这次出现了：第 16 项"宿主重启后续跑"（无人值守的定时任务上线）、第 24 项"配额感知调度"（A12 动工）。这一批没有做它们，已在那篇里注明；后来分别由[宿主重启后续跑](2026-11-14-resume-after-restart.md)和[配额感知调度](2026-11-14-quota-aware-scheduling.md)实现（后者只做了调度这一侧）。
- 待目检（已记进路线图的待目检清单）：侧栏"定时任务"页、新建和编辑弹窗的各种重复方式、开关、立即运行、运行记录与打开会话；一条真实规则到点开出会话、会话名带"（定时）"。

## Testing

- core `schedule::calendar` 2 个测试：
  - 每天和每周按当地时间触发；关了三天只补最近一次；保存之后的时间才算；
  - 一次性的和每隔几小时的按各自的起点计算；当地零点。
- core `schedule::check` 1 个测试：退出码 0 通过并带输出；非 0 带退出码和输出；超时被停止；超长输出被截断。
- core `schedule` 3 个测试（假宿主）：
  - 每天一次，处理过的不再触发，关了几天补跑一次，上一次还在跑记为忙，忙也算处理过；
  - 检查不通过不开会话；通过时输出附进提示词；一次性的运行后自动关掉；立即运行；删除时连运行记录一起删；
  - 每天 24 个会话的上限，第二天重新计数；开会话失败记下原因；项目不在本机；六种不合法的规则都被拒绝。
- 宿主集成测试 `a_schedule_with_a_failing_check_opens_no_session`：保存、列表带下次时间；立即运行时检查不通过，不开会话，记下退出码和输出；没有名字、项目不存在都被拒绝；重复删除返回 NOT_FOUND。2026-11-15 补上：按 App 的写法（`fromMs`、`atMs`，以及第二批的忙时和时段）保存"间隔"和"一次"规则，读回来字段不变。
- 协议单测 `repeat_fields_are_camel_case_and_old_files_still_read`：写出 `fromMs`；读 App 的 `atMs`；读旧文件里的 `from_ms`。
- 这个字段名的错，之前的测试都没发现：Swift 测试只在 Swift 里自己往返，宿主测试只用了"每天"（`minute` 不受影响）。
- Swift `ScheduleTests`：四种重复方式在线上来回不变；空的检查命令不发送；界面上"每天 09:00""每周一、三 18:30"和运行结果的说法；保存、停用、立即运行、删除都发到服务，被拒绝时保留原因。
- 2026-11-14 在 review 包里经宿主 RPC 走了一遍（没碰鼠标）：给本机项目保存一条停用的每周规则，检查命令是在 git 仓库里先 `git rev-parse` 再 `exit 1`；立即运行得到 `checkFailed`、"退出码 1：没有新提交"，没有开会话；运行记录里有这一条；删除后列表为空。
- 没有验证真实的"到点开出会话"：需要真实的 Agent 并且会花钱，列进了待目检清单。
