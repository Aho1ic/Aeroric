# Agent Note: C2 第一步：删除或归档一条记忆，记忆库里派生的东西一起撤

Status: implemented

## Problem

[批次 C 方案](../../proposed/feature/2026-11-15-adoption-c-memory-gateway-skills.md)第 C2 片要求：删除或归档一条记忆后，搜索不再命中它；由它促成的技能候选标"依据已撤回"；Wiki 里引用它的段落标为待核对；正在进行的整理不会把刚删掉的内容写回来。

方案的第一条是先列一张清单：一条记忆被哪些地方引用或复制，逐项标注删除或归档时有没有跟着更新。下表是逐处读代码后的结论（`main@9c73f060`）。

**记忆库内部**（`memory.db`）：

| # | 地方 | 动手前 | 本步之后 |
|---|---|---|---|
| 1 | 条目本身（`items`） | 永久遗忘删除，归档改状态 | 不变 |
| 2 | 依据（`evidence`） | 永久遗忘时一起删 | 不变 |
| 3 | 全文索引（`items_fts`） | 永久遗忘时删；搜索只取 `active` | 不变 |
| 4 | 语义向量（`vectors`） | 永久遗忘时删；近邻只取 `active` | 不变 |
| 5 | 被它取代的旧版本（`supersedes` 链） | 永久遗忘时一起删 | 不变 |
| 6 | 被整理合并进它的重复条目（只记了 `superseded_by`） | **没删**；撤销那次整理会让它重新生效 | 永久遗忘时一起删 |
| 7 | 遗忘签名（`barrier`） | 永久遗忘时记下，Agent 和抽取不能再提同样的话 | 不变 |
| 8 | 进行中的会话抽取 | 永久遗忘的话会被签名拦下；**归档或被取代的话会作为新候选写回** | 写入前对照撤回记录，丢掉期间撤回的 |
| 9 | 进行中的整理（dream） | 写入前对比开始时的快照，中途变了的条目退出这次整理 | 不变（已有测试） |
| 10 | 等待决定的整理建议 | **仍可决定**，内容涉及已删或已归档的条目 | 标为"已撤回" |
| 11 | 技能候选和已采纳的技能 | **不知道依据没了** | 标"依据已撤回"，不删；恢复时撤掉标记 |
| 12 | 整理记录（`runs`） | 只有计数、标题和原因，不含条目文字 | 无需更新 |
| 13 | 已整理标记（`extracted`） | 只有任务 id 和对话哈希 | 无需更新 |
| 14 | 代码版本链（`chain`） | 按会话和回合记改动，不含记忆文字 | 无需更新 |

**记忆库之外**（留给后续步骤，或如实说明）：

| # | 地方 | 现状 | 处理 |
|---|---|---|---|
| 15 | Wiki 页面里由经验编译出的段落（`memory:<id>`） | 只在重新编译时才去掉；在那之前，Wiki 搜索和 Agent 的 `context.wikiRead` / `wikiSearch` 仍能读到 | 第二步 |
| 16 | Wiki 修订历史 | 旧版本里的文字一直留着 | 第二步 |
| 17 | 已采纳技能的 `SKILL.md` 文件（会挂到会话里） | 文件里有经验的文字 | 按方案不自动删，第 11 项标记后由用户决定；第三步在界面上给出入口 |
| 18 | 用户导出的 Wiki 文件（项目目录里） | 是用户自己的文件 | 不动，第二步在结果里写明 |
| 19 | 已经开始的会话里注入的画像和召回结果 | 进程里已有，收不回来 | 无法撤回；新会话读到的是最新的 |

## Decision

**撤回记录**（`memory/store.rs`）：

- 新表 `withdrawn`，按序号记下撤回的话的签名（与遗忘签名同一把密钥的 HMAC，不存原文）。
- 以下五种情况都会写一行：
  - 永久遗忘；
  - 归档；
  - 编辑取代旧版本；
  - 采纳一条会取代旧条目的候选；
  - 整理合并掉重复项。
- 最新序号就是方案说的 `epoch`。直接用表的自增序号，不另存计数，删掉旧行后序号也不回退。
- 记录保留一周。一次抽取不会持续这么久。

**进行中的抽取**（`memory/run.rs`）：

- 调用模型前读下当前序号。
- 写入前，把候选和经验的文字（按同样的规范化方式）与这个序号之后撤回的签名比较，相同的丢掉。
- 整理记录写明"整理期间有 N 条相同的记忆被删除、归档或取代，没有写回"。
- 之后新开始的抽取不受影响：用户可能又说了一遍。

**永久遗忘的范围**：`chain` 除了沿 `supersedes` 往回找旧版本，也把 `superseded_by` 指向它的条目一起带上。这些是整理合并掉的重复项，说的是同一件事；不删的话，撤销那次整理会把用户已经要求遗忘的内容恢复回来。

**技能和整理建议**：

- `SkillProposal` 加 `sourceWithdrawnMs`：经验被归档或永久遗忘时记下时间，恢复时清空。不改状态，不删文件：已采纳的技能仍然生效，由用户决定。
- 等待决定的整理建议里，只要涉及的条目被归档或遗忘，就标为 `Withdrawn`（已撤回）。

**返回传播结果**：

- `Memory::forget` 和 `Memory::archive` 都返回 `Withdrawal`：
  - 撤了几条（遗忘时含旧版本和被合并的条目）；
  - 哪些技能被标了；
  - 撤回了几条整理建议。
- 宿主的 `memory.forget` 保留原来的 `removed` 计数，另加 `withdrawal`；`memory.archive` 在 `item` 之外加 `withdrawal`。
- 这些改动都在同一个记忆库里、同一把锁下完成，要么都成功要么报错，所以这一步还没有"部分没成功"的情况。方案第 5 条说的"没成功的进需要我处理"，留给第二步跨到 Wiki 时再做。

## Alternatives considered

**用一个计数字段记 epoch，抽取结束时只比较计数变没变。** 最强的理由是最简单。没选：只要期间删了任意一条记忆，整次抽取就都要作废或重来，而期间删掉的多半与这次会话无关。按签名逐条对照，只丢真正相同的那几条。

**撤回记录里存原文，或存不加密钥的哈希。** 最强的理由是排查时能直接看出撤回了什么。没选：永久遗忘的承诺是"不留原文"。不加密钥的哈希对短句可以穷举还原，所以沿用遗忘签名那把密钥。

**技能的依据撤回时直接停用技能。** 最强的理由是被遗忘的文字不再出现在会话里。没选：方案明确要求不自动删除用户已经采纳的技能。技能可能已经被用户改写，和原经验不是一回事。先标记，由用户决定。

## Consequences

- **收益**：
  - 归档或取代一条记忆后，正在跑的抽取不会把它作为新候选塞回待确认列表；
  - 永久遗忘不会再被撤销整理绕过；
  - 技能和整理建议能看出依据已经没了；
  - 调用方能拿到这次删除牵涉了哪些地方。
- **代价**：记忆库多一张小表，每次撤回写一行，一周后清掉。
- **未完成**：
  - 清单第 15、16、18 项（Wiki）在第二步做；
  - App 里显示"依据已撤回"和删除结果是第三步；
  - 方案验证输入里的"传播到索引时注入写失败"，第二步跨存储时再测。
- **验证**：
  - `withdraw_tests.rs` 新增 5 个测试：
    - 五种撤回方式都会记下，按规范化后的文字比较，记录之前的序号看不到；
    - 遗忘保留的条目，会连带删掉整理合并进它的条目，撤销整理也恢复不了；
    - 涉及已归档或已遗忘条目的整理建议变成"已撤回"，无关的不动；
    - 技能被标"依据已撤回"但仍是已采纳，恢复后撤掉标记，再遗忘时重新标上；
    - 遗忘后，列表、搜索、召回、待确认、画像都读不到那段文字。
  - `run.rs` 新增 1 个测试：模型调用期间用户归档了一条相同的记忆，这次抽取不写回，并写明原因；之后新开始的抽取照常提出。
  - 宿主集成测试延伸：`memory.archive` 和 `memory.forget` 返回 `withdrawal`，`removed` 不变。
  - 清单第 9 项由已有测试 `an_item_changed_during_the_call_drops_out_of_the_run` 覆盖。
