# Agent Note: E2 事实核查过滤：被 diff 直接驳倒的审查意见在发给写代码的会话前拦下（默认关）

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) 的 E2 还差最后一块：事实核查过滤。[E2 第一步](2026-11-19-e2-findings-snippet-locate-fold.md) 做了片段、按代码定位、合并重复，过滤留给 owner 拍板。2026-11-26 owner 定：开工，默认关。

审查者偶尔会提明显说错的意见：说“没有判空”，diff 里就有判空；说“这里改了签名”，引用的代码根本不在这次改动里。这类意见照样发给写代码的会话，对方要花一轮去驳回，审查循环可能因此多走一轮，甚至因为“阻断被驳回”交给用户。

OCR 的做法是用一个便宜模型核查每条意见，口径是“留下一条错的意见，只花审阅者几秒；删掉一条对的意见，是悄无声息地毁掉一个真问题”。所以过滤必须保守，而且要先评测误删率。

## Decision

**开关：每个会话的审查设置里加 `factCheck`，默认关**（`ReviewSettings.fact_check`）。
- `review.set {taskId, factCheck}` 打开；`review.get` 回读；进度页审查一节加一个开关，说明写清会用记忆的分析模型、只删两种意见、什么不删；
- 关着时不序列化这个字段，已有设置的样子不变。

**模型：用记忆“整理设置”里选的分析模型**（宿主 `analysis_call`），不新增配置。没选分析模型时核查不跑，卡片写原因，意见全部保留。

**什么时候核查：** 审查者这一轮结束、意见已定位和合并之后，只在这一轮有阻断意见（本来就要发给写代码的会话）时才核查。没有阻断的一轮本来就算通过，不花这次调用。
- 核查期间卡片仍是“审查中”，`factCheck.state = running`；
- 核查在审查循环自己的线程上跑，不占着锁；
- 结果回来时这一轮已经变了（被停止、宿主重启、换了一轮），结果丢掉。

**只有两种理由可以删，模型说了还要过确定性的关**（`review/fact_check.rs`）：
1. **`not_in_diff`：意见引用的代码不在这次改动里。** 要求意见带片段，并且压缩空白后，片段既不在改动后的文件里（E2 已标 `unlocated`），也不在 diff 的任何一行里。没有片段的意见不能这样删。
2. **`refuted`：diff 里有一行字面上直接驳倒它。** 模型必须照抄那一行；压缩空白后，这一行要真的出现在 diff 的新增行或上下文行里，并且至少 4 个字。抄不出来、对不上的，不删。

**这些一律不删：**
- 五类保护主题：内存安全、并发、声明一致性、行为或兼容性变化、未使用的参数。模型要给每条意见标主题；另外按意见文字里的关键词（并发、竞态、死锁、锁、线程、内存、越界、溢出、unsafe、兼容、breaking、签名、声明、未使用的参数……）确定性地再认一遍，任一边认出就保护；
- 类别是 `security` 的意见；
- 上一轮也提过、写代码的会话没改好的意见（E3 的 `repeats`）：它已经被人看过一次，不该被模型悄悄拿掉。

**删掉的意见不消失：** 卡片 `factCheck.filtered` 列出每条被删的意见、理由和依据（照抄的那一行，或“引用的代码不在这次改动里”）；App 写“已过滤 N 条被 diff 直接驳倒的意见”，点开逐条看。被删的不发给写代码的会话，也不算阻断。删完没有阻断了，这一轮算通过。

**核查失败不影响审查：** 调用失败、回答读不出，意见全部保留，卡片写“核查没跑成：…，意见全部保留”。

**评测**（`review/fact_check_eval.rs`）：一组固定用例，每条是“diff + 意见 + 应该留还是删”，其中故意包含：
- 被 diff 驳倒的错意见（应删）；
- 说对了的真问题（应留）；
- 保护主题里看起来像被驳倒的（应留）；
- 模型容易乱抄依据的（应留）。

宿主 `review.factCheckEval {}` 用当前的分析模型跑一遍，回报每条的结果、误删条数（`wronglyRemoved`）和该删没删的条数（`missed`）。单元测试用三个假模型跑同一组用例：照标准答案回答的，误删和漏删都是 0（用例和护栏一致）；把每条都判“驳倒”、依据是编的，一条都删不掉；把每条都判“驳倒”、依据抄 diff 里真有的一行，保护主题的用例仍然一条都删不掉。

## Alternatives considered

**不用模型，只做确定性过滤（片段不在 diff 里就删）。** 最强的理由是结果可复现、不花钱。没选：`unlocated` 的意见常常只是审查者抄片段时改了几个字，意见本身是对的；只凭“找不到片段”删，误删会很多。确定性检查只做模型判断的护栏。

**默认打开。** OCR 的基准显示精度更高。没选（owner 定）：误删一个真问题的代价比多留一条错意见大得多；先用评测证明误删率低，再考虑默认打开。

**被删的意见仍然发给写代码的会话，只是标“可能有误”。** 最强的理由是什么都不会丢。没选：这样写代码的会话还是要花一轮去答复，过滤就没有意义了。被删的意见留在卡片上给用户看，已经足够追溯。

**核查交给审查者自己（提示词里要求它自查）。** 没选：审查者就是犯错的那一方，同一个上下文里自查效果有限；而且自查没有“照抄依据、再由程序核对”这道关。

**全局开关而不是每个会话一个。** 最强的理由是设一次就行。没选：评测阶段先在个别会话上打开、对照效果更合适；审查设置本来就是按会话存的，加一个字段改动最小。

## Consequences

- **收益：**
  - 明显说错的阻断意见不再耗掉写代码的会话一轮，审查循环更少因为“驳回”交给用户；
  - 被删的每条都有依据，用户能核对；
  - 有一组固定用例，换分析模型时能马上看到误删率。
- **代价：** 打开后，每个有阻断意见的审查轮多一次分析模型调用，发给写代码的会话会晚几秒。
- **局限：**
  - 只看 diff，不看完整文件和项目其他地方；需要上下文才能驳倒的意见不会被删（这是有意的保守）；
  - 主题关键词是固定的一张表，认不出的保护主题只能靠模型标；
  - 评测用例是手写的一小组，覆盖不了所有语言和写法。
- **验证：**
  - Rust：
    - `fact_check_tests.rs`：两种理由各自的护栏、保护主题（模型标的和文字里的）、`security`、`repeats`、回答读不出，以及上面三个假模型跑评测用例；
    - `review/tests.rs`：打开核查后，被驳倒的阻断意见不发给写代码的会话、这一轮算通过；保护主题被模型判删时照样发出（`guarded` 记 1）；调用失败时意见全部发出；没打开时不调用；
    - 宿主 `session_live.rs`：`review.set` 的 `factCheck` 回读，没选分析模型时 `review.factCheckEval` 说明原因；
  - Swift：卡片解码 `factCheck`，`已过滤 N 条` 的说法；
  - 真实分析模型的误删率：`review.factCheckEval` NOT RUN，等目检时用 Magpie 的模型跑一次。
