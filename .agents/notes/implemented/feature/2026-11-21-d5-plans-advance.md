# Agent Note: D5 第二步：计划确认后按规则开委派，卡片一变就推进

Status: implemented

## Problem

[D5 第一步](2026-11-21-d5-work-plan-rules.md)把工作计划的规则写成了纯函数（`main@1d7e05ab`）：上限、环、依赖满足、单写者、输入、过期，以及每个单元的一句原因。但它不启动任何东西。

方案第 7 条要求“每个单元就是一次现有的委派”，只增加计划、依赖和调度，不改委派本身。验证输入里还有“宿主重启后调度状态恢复”。

核对的事实：

- `Delegations::start(parent, contract, origin, actor)` 建一张委派卡，交给宿主开子会话，返回这张卡。
- 卡片的每一次变化都经过 `Delegations::publish`：开始、运行、回报、失败、停止，以及验收重算（B3 的 `refresh_acceptance`）。卡片存在 `<委派目录>/tasks/<父任务>.json`。
- 宿主重启后，读回的“运行中”的委派记为“被打断”（现有行为）。
- 委派自己也会拒绝第二个在父任务目录里写的子任务。

## Decision

**存储：** 计划存在 `<委派目录>/plans/<父任务>/<计划 id>.json`。

**三个操作**，写在 `delegation/plans.rs` 里，作为 `Delegations` 的方法：

- `save_plan`：保存草稿。
  - 没有 id 时生成一个（`plan-…`）；
  - 已确认的计划不能再改；
  - 保存时清掉单元上的委派号、开始时的输入和开不起来的原因，不能由提交的人自己写这些；
  - 先按第一步的规则校验，不合规就拒绝。
- `confirm_plan`：用户确认。确认后马上推进一次。
- `plans`：列出这个父任务的计划，每个单元带状态和原因。只读，不开任何东西。

**推进**（`advance_plans`）：

- 对父任务每个已确认的计划：
  1. 从委派卡读出各单元的现状；
  2. 用第一步的 `schedule` 算出该开哪几个；
  3. 逐个开一次普通委派，约定按单元填：
     - 说明：单元的说明，加上前置产物的清单；
     - 角色、工作区；
     - 验收条款：单元的每一条；
     - 来源：用户，因为是用户确认的计划；
     - 发起者：`plan:<计划 id>`，审计里看得出来；
  4. 开成了，就把委派号和开始时拿到的输入写回计划；开不起来，就把原因记在单元上（`start_error`）。之后这个单元显示“开不起来：原因”，算失败，下游等你处理，也不会反复再试。
- **何时推进：**
  - 父任务的任何一张委派卡变了，`publish` 结束前推进一次。没有计划的父任务只多检查一次目录是否存在；
  - 读计划时（`delegation.plans`）也推进一次。
- **防重入：** 开委派本身也会让卡片变，又会要求推进。所以每个父任务同时只有一轮推进，其间到来的要求记一个“再来一轮”，这一轮做完再从盘上读计划，重算一次。同一个单元不会被开两次。

**重启：** 不另存调度状态。宿主重启后，计划和委派卡就是全部事实，再算一次就是现在的样子。重启前在跑的单元，它的委派被读成“被打断”，于是单元显示“失败了，等你处理”。下一次读计划时，该开的照常开。

**宿主方法**（`session_live_services/delegation.rs`），都要求父任务存在：

- `delegation.plans {taskId}`：先重算验收、推进，再列出；
- `delegation.planSave {plan}`；
- `delegation.planConfirm {taskId, planId}`。

## Alternatives considered

**宿主起一个定时器，定期推进。** 最强的理由是简单，不怕漏掉某种卡片变化。没选：

- 委派卡的所有变化都经过 `publish`，挂在这里不会漏；
- 定时器在没有计划时也在空转；
- 读计划时再推进一次，正好兜住启动后还没有任何卡片变化的情况。

**推进时不开委派，交给宿主另一个线程去开。** 最强的理由是 `publish` 里不做重活。没选：

- `start` 本身就是轻量的：建卡片，交给宿主异步开子会话；
- 放到另一个线程，又要处理两个线程同时推进的问题，现在的“每个父任务一轮、其间的要求并入下一轮”已经解决了它。

**开不起来的单元下一轮自动重试。** 没选：开不起来通常是本机没有那个 Harness、权限不允许这类原因，自动重试只会反复失败。记下原因，由用户处理，和方案“前置失败时不自动跳过”同一个思路。

## Consequences

- **收益：**
  - 用户确认计划后，单元按依赖、上限和单写者自动开下去，每一步都能在委派卡上看到；
  - 宿主重启不会丢掉计划，也不会把同一个单元开两次。
- **代价：**
  - 每次委派卡变化，多一次“这个父任务有没有计划”的目录检查；
  - 有计划时，还要读一遍计划文件。
- **局限：**
  - 没有界面；
  - Agent 还不能提议计划（第三步）；
  - 不能改已确认的计划，也不能单独重开某个单元；输入过期后要不要重做，界面上也还没有入口；
  - 重启前在跑的单元，会显示为失败，要用户在委派那边重做。
- **验证：**
  - core：委派测试里新增 1 个，委派模块共 44 个全部通过。
    - 有环的计划保存不了；
    - 保存后没确认，什么都不开；
    - 确认后开没有依赖的两个，第三个写“等「单元a」通过验收”；确认过的计划不能再保存；
    - a 回报后，b 自动开起来，说明以 b 自己的说明开头；
    - 再推进一次，不会多开；
    - 换一个委派实例读回同一目录（模拟重启）：a 是通过，b 是“失败了，等你处理”。
  - 宿主：1 个测试。
    - 经 RPC 保存草稿，拿到 `plan-…` 的 id，没确认；
    - 列出时写“计划还没确认”“等「单元a」通过验收”，委派列表是空的；
    - 有环的被拒，未知的任务被拒。
- **NOT RUN：** 真实 Harness 上跑一个多单元的计划。
