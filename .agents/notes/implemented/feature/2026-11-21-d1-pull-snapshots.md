# Agent Note: D1 第一步：GitHub PR 只读地固定成快照

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D1 的目标是一条完整流程：

1. 选一个 PR，固定在一个版本上；
2. 读它的变更和检查；
3. 让 Agent 独立审查；
4. 打开每条结论的位置；
5. 把结论存成草稿。

全程对 GitHub 只发读请求。总纲（§7 第 6 问）定了 D 批先做 D1。

动手前（`main@3424afb8`）核对的事实：

- **Aeroric 不和 GitHub 的接口打交道。**
  - `core/src/git/` 只做本地 Git 和 `git` 命令的远端操作（推送、拉取）；
  - 不读 PR、检查和评论，没有 GitHub 的 HTTP 客户端，也没有 PR 的数据结构。
- **core 已经有网络出口。** core 依赖 `reqwest`（DSH 客户端、用量查询、模型探测都在用），也有 `axum`，测试可以起一个本地的假服务。
- **凭据。** 方案要求“用本机 `gh` 的登录状态或用户在设置里填的令牌，Aeroric 只保存凭据引用”。设置里没有 GitHub 令牌这一项。

D1 估计 7–12 天，分三步：

- 第一步：只读客户端和快照，本篇；
- 第二步：把代码取到专用引用下，在隔离副本里用只读角色审查，结论解析成带位置的条目；
- 第三步：Git 页的入口、快照视图和结论视图。

## Decision

**协议**（`aeroric-protocol/src/github.rs`）：

- `RepoRef`：主机、所有者、名字、GitHub 的仓库编号。
- `PullSnapshot`：
  - id，项目；
  - 仓库、编号、标题、作者、状态（是否已合并）、链接；
  - head 和 base 的分支名、提交，以及合并基；
  - 抓取时间；
  - 文件（路径、状态、增删行数、改名前的路径）；
  - 检查（名字、状态、结论、链接）；
  - 评论（作者、正文、锚点、是否针对旧版本、时间）；
  - `truncated`；
  - `superseded`。
- `CommentAnchor`：路径、哪一侧、行号、所在的提交。

**链接**（`github::target`）认这几种：

- `https://github.com/<所有者>/<仓库>/pull/<编号>`，带或不带协议，编号后面的部分忽略；
- `<所有者>/<仓库>#<编号>`；
- GitHub Enterprise 的链接，接口根是 `https://<主机>/api/v3`。

所有者和仓库名只允许字母、数字、`-`、`_`、`.`，不能是 `.` 或 `..`。看不懂的链接直接拒绝，给出例子。

**客户端**（`github::client::Client`），只发 GET：

1. **先读仓库。** 改了名的仓库 GitHub 会重定向，跟过去后记下现在的名字和仓库编号，后面的请求都用现在的名字。
2. **再读 PR**：标题、作者、状态、head 和 base；然后用 compare 取合并基。
3. **列表分页取：**
   - 文件最多 200 个，检查最多 100 个，评论最多 200 条（整个 PR 的评论加逐行评论）；
   - 超了就截断，并标 `truncated`；
   - 正好取满上限时，再问一条，确认后面还有没有。
4. **评论标“针对旧版本”**：逐行评论所在的提交不是这次的 head，或者 GitHub 已经不把它放在任何一行上。
5. **拒绝时说原因，不返回空的 PR：**
   - 401：GitHub 不认这个令牌；
   - 403 且说限流：GitHub 限流了；
   - 其他 403：没有权限读这个仓库，附上 GitHub 的原话；
   - 404：找不到。没有令牌时提示私有仓库要先登录 gh；
   - 连不上：直接说连不上。

**快照**（`github::store`），存在 `<数据目录>/github/<项目>/<快照 id>.json`：

- id 是“仓库编号-PR 编号-head 提交前 12 位”。同一个 head 再取一次，返回存着的那份，固定的时间不变，所以重试不会多出一份。
- 列出时新的在前。同一个 PR 的最新快照换了 head 时，较旧的快照标 `superseded`，界面上就是“PR 已更新”。

**宿主**（`github_services.rs`）：

- `github.pullSnapshot {projectId, url}`：
  - 每次现取令牌：`gh auth token --hostname <主机>`，最多等 5 秒，取不到就不带令牌，公开仓库照样能读；
  - Aeroric 不保存令牌，也不写进快照。
- `github.snapshots {projectId}`：列出这个项目的快照。
- `github.snapshot {projectId, id}`：取一份快照。

## Alternatives considered

**用 `gh` 命令行取数据（`gh pr view --json`、`gh api`），不自己写 HTTP。** 最强的理由是登录、企业主机、代理都交给 gh。没选：

- 没装 gh 的用户就完全用不了；
- 分页和截断的规则、错误原因要从 gh 的输出里再解析一遍；
- 测试要假造 gh 的输出，不如假造 HTTP 直接，“只发 GET”也是由假服务按请求断言的。

令牌仍从 gh 取，所以已登录的用户不用再配置。

**令牌存进设置。** 最强的理由是方案提到了“设置里填的令牌”。没选：

- 存令牌要进钥匙串，还要配上界面；
- 没有 gh 的用户怎么办，留到第三步做界面时一起定。

现在没有令牌时只能读公开仓库，私有仓库的 404 写明了要先登录 gh。

**快照 id 用 “所有者/仓库/编号/head”。** 没选：仓库改名后，同一个 PR 会变成另一组快照，“PR 已更新”的比较就断了。用 GitHub 的仓库编号，改名前后是同一个。

**取满上限时不多问那一次。** 最强的理由是少一次请求。没选：恰好 200 个文件的 PR，会被误标成“不完整”，或者漏标。

## Consequences

- **收益：**
  - PR 的内容固定在一个 head 上，之后的审查读的都是这份快照；
  - 同一个 PR 推了新提交后，旧快照会如实标出“PR 已更新”；
  - 拿不到数据时写明原因。
- **代价：**
  - 一次快照要 6 种请求，文件、评论多时还要翻页；
  - 每次取都要启动一次 gh。
- **局限：**
  - 检查只读 check runs，不读旧式的 commit status；
  - 评论不分页显示，最多 200 条；
  - 没有令牌时只能读公开仓库；
  - 不跟随网关或连接的代理设置，用系统代理；
  - 第二、三步做完前，用户看不到这些快照，审查也还用不上它们。
- **验证：** 新增测试，全部通过：
  - core 4 个，测试对着 127.0.0.1 上的假 GitHub：
    - 链接解析：认的几种写法和 Enterprise 主机，以及 5 种不认的写法；
    - 取一个完整的 PR：仓库改过名，按编号记下现在的名字；300 个文件截断到 200 并标“不完整”；检查和两类评论都取到，旧提交上的和已不在某行的标“针对旧版本”；假服务收到的每个请求都是 GET，都带着令牌；
    - 403 没权限、403 限流、401、404 各返回写明原因的错误；
    - 取文件时断一次，什么都不存；重试只存一份；同一个 head 再取，返回原来那份，时间不变；强推后存成新快照，旧的标“PR 已更新”；别的项目列不到。
  - 宿主 1 个：看不懂的链接、缺项目，都在发请求前拒绝；空项目列表为空；不存在的快照返回“没有这份快照”。
- **NOT RUN：** 对真实 GitHub 的读取，包括本机 gh 登录、私有仓库、Enterprise。
