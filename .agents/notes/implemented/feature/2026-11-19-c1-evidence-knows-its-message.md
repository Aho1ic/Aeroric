# Agent Note: C1 第一步：记忆的依据记下原话在哪条消息，读取时核对原文

Status: implemented

## Problem

[批次 C 方案](../../proposed/feature/2026-11-15-adoption-c-memory-gateway-skills.md)第 C1 片要求：打开一条记忆的依据，能找到来源会话里的那条消息，原话高亮；来源被删或改过时如实说明，摘录照常显示。

动手前的现状：

- 依据（`Evidence`）只有任务 id、来源、模型、摘录、摘录的哈希和时间。
- 能知道一条记忆来自哪个会话，但不知道是哪条消息。
- 会话之后被 Agent 压缩、改写或删除了，也无从得知。

核对代码时还发现两点，影响了做法：

- 抽取时，模型给出的每条候选都带一句用户原话（quote）。core 已经用"去掉空白、全角转半角、忽略大小写"的方式，确认原话确实出现在会话里，找不到就丢掉候选。所以原话在哪条消息里，core 自己就能找，不需要模型报序号。
- 会话消息大多没有稳定的消息 id：Claude 和 Codex 的解析结果里没有，只有 OMP 有。能稳定指向一条消息的，是它在会话文本消息中的序号，再加上消息内容的哈希。

## Decision

**依据记下位置**（`aeroric-protocol` 的 `EvidenceLocation`，`core/crates/aeroric-core/src/memory/locate.rs`）：

- `Evidence` 加可选字段 `location`，包含：
  - `messageIndex`：在会话文本消息中的序号；
  - `role`：用户或 Agent；
  - `start` / `end`：原话在消息里的字符位置；
  - `messageHash`：抽取时这条消息全文的 SHA-256 前 16 位，即方案说的"来源版本"。
- 抽取写入候选时，用 `locate` 拿原话去逐条匹配消息，比较方式与抽取校验一致：
  - 先找用户的消息，再找其余的；
  - 原话跨了两条消息、或太短（少于 2 个字），就不记位置，留空。
- 模型给的序号一概不用。会话线索和经验的依据是总结，不是原话，不记位置。
- 记忆库的 `evidence` 表加一列 `location`（JSON），打开旧库时自动补列。旧依据不回填，读出来 `location` 为空。

**读取时核对**（宿主新方法 `memory.evidenceLocate {itemId, index}`）：

- 先按依据的任务 id 重新读来源：
  - 是任务就读它当前的会话记录，与抽取时同一个读取函数，压缩成 `.jsonl.zst` 的也能读；
  - 不是任务就按导入的会话读。
- 返回五种状态之一：
  - `located`：原序号上的消息还在，角色和全文哈希都没变；
  - `moved`：那条消息变了（比如 Agent 压缩了历史），但原话在别的消息里还能找到；
  - `changed`：原话已经找不到；
  - `gone`：会话或它的记录已经不在；
  - `unrecorded`：C1 之前的依据，或 `/记住` 这类没有会话来源的依据。
- 找到时附上那条消息和原话在其中的位置；超过 4000 字的消息只回原话周围 4000 字的窗口，并标明前后有截断。
- 摘录在每种状态下都返回。
- 会话记录存在但读不出（文件太大或出错），返回错误和原因，不当作"已不在"。

**App 暂未接入**：依据行上的"在会话里查看"放在第二步。

## Alternatives considered

**按方案让模型在每条候选里附上消息序号，core 再核对。** 最强的理由是模型读过整段对话，序号是它直接给出的。没选：方案的风险一节已经指出模型可能给错，core 无论如何都要拿原话去匹配；原话已经经过逐字校验，匹配本身就能给出位置，再让模型报序号只是多一项要它遵守、又不能信的输出。

**记消息 id，不记序号。** 最强的理由是 id 不随前面插入或删除消息而变。没选：Claude 和 Codex 的会话解析结果里没有消息 id。序号加上内容哈希，在消息没变时能精确命中；变了的话，再按原话重新找一遍，结果一样可靠。

**来源版本用整份会话记录的长度加末尾哈希。** 最强的理由是方案就是这么写的，算起来也便宜。没选：会话只要往后追加一句，这个版本就变了，但原来那条消息并没有变，会被误判为"原文之后改过"。按单条消息的哈希比较，只有那条消息本身变了才算。

## Consequences

- **收益**：
  - 新抽取的用户偏好和项目约定，都能定位到原话所在的消息和位置；
  - 会话被压缩、改写、删除之后，读取时能说清现在是什么情况，不会把对不上的位置当作还在。
- **代价**：
  - 每次核对都要重读一遍会话记录，大小以现有的上下文读取上限为界；
  - `evidence` 表多一列。
- **局限**：
  - 位置是"第几条文本消息"，依赖会话解析的结果；解析规则改了，序号可能对不上，这时会退回按原话重新找；
  - 原话恰好也出现在 `<private>` 段里时，可能定位到那一处。
- **验证**：
  - `locate_tests.rs` 新增 3 个测试：
    - 忽略空白、全角和大小写找到原话，位置对应消息里的原始字符；先找用户消息；跨消息或太短的不记位置；
    - 五种状态逐一出现：未变、压缩后挪到别处、改写后找不到、会话不在（含记录为空）、旧依据没记；
    - 长消息只回窗口，位置跟着平移。
  - `run.rs` 的抽取测试延伸：用户偏好和项目约定的依据带上位置，写入记忆库后能读回；会话线索的依据没有位置。
  - 旧库升级测试延伸：没有 `location` 列的旧依据表升级后照常读出，位置为空。
  - 宿主集成测试 `session_live` 延伸：
    - 对 `/记住` 的依据返回 `unrecorded` 和摘录；
    - 不存在的记忆或依据序号返回 NOT_FOUND。

    有位置的依据经宿主重读真实会话记录、再核对的整条路径，集成测试没有覆盖：它要先走一次真实模型的抽取。核对逻辑由 core 的纯函数测试覆盖。
