# Agent Note: 可选 embedding：按意思找相近的记忆，默认关闭；nomic-embed-text 对中文没有净收益，bge-m3 有

Status: implemented

## Problem

记忆的检索只看字面：

- `memory_recall` 走 FTS5（BM25）；
- [做梦](2026-11-13-memory-dream.md)分组看两条记忆共享多少字符对。

换了说法的同一件事，两边都找不到。例如记忆"Python 代码缩进用 4 个空格"，Agent 问"排版时每一级往里推几格"，召回为空；"不要自动提交代码"和"commit 之前必须征得我同意"也不会被当成重复。

路线图 J5 把向量定为"只负责找候选"的派生索引，B6 列了"可选 embedding"。[第二批做梦](2026-11-14-memory-dream-second.md)把"用 FTS 或 embedding 补召回"也归到这里。

用户 2026-11-14 说"全部按推荐"，定了 5 条：

1. 下一项做可选 embedding。
2. 只用在记忆上：`memory_recall` 补候选，做梦分组补换了说法的重复。Wiki、参考代码库、随手记不动。
3. 复用随手记的 embedding 设置（接口类型、地址、模型、钥匙串里的 key），不另开连接。整理设置里加开关"按意思找"，默认关闭。向量放在 memory.db 的派生表里，不用 sqlite-vec，在内存里算余弦；换模型整批重建。
4. 召回：FTS 和向量各取前 20，用 RRF 合并，余弦低于 0.5 的不要。做梦：字面相近或余弦 ≥ 0.85 都算相近（看过 bge-m3 的结果后，用户 2026-11-14 改为 0.75）。
5. 用 Homebrew 装 Ollama、拉 nomic-embed-text 做前后对照；没有净收益就保持默认关闭，并写明。

## Decision

**向量是派生索引**（core `memory/semantic.rs`）

- 表结构：memory.db 新增 `vectors(item_id, vec)`。`vec` 是单位化后的 f32 小端字节。一条生效中的记忆最多一个向量，表里的向量全部来自同一个模型。
- 换模型：模型名记在 kv `vectors:model`。`embed_missing` 发现模型变了，先清空整表再重建。
- 遗忘：向量和原文一起删。`store.delete`（`forget` 逐条调用它）在删除 `items_fts` 的同一个事务里删掉向量，因为向量是从原文算出来的，留着等于没忘。
- 经验的问题或解法改了（`set_experience`），旧向量随之删掉，下一次扫描重新算。
- 删掉整张表，记忆本身不受影响；权威仍然是带证据的记忆条目（J5）。
- 算什么：
  - 记忆正文；经验另外加上问题和解法（`text_of`）。
  - nomic-embed-text 训练时带任务前缀，所以文档加 `search_document: `、查询加 `search_query: `；其他模型原样送。
- 相似度：单位向量的点积。维度不同的向量相似度记为 0，不会把两个模型的向量混着比。

**core 不碰网络**

`Memory::embed_missing(model, embed, limit)` 接收一个同步函数 `embed(&[String]) -> Vec<Vec<f32>>`，由宿主构造。

- 每次最多处理 `limit` 条还没有向量的生效记忆，从新到旧。
- 失败时把原因写进 kv `vectors:error`，成功时清掉。
- `semantic_status` 报告：用的哪个模型、已算多少条、还差多少条、最近一次的错误。

**召回**（`Memory::recall_with`）

1. FTS 照旧取前 30。
2. 带了查询向量时，再取本项目和全局生效记忆里余弦 ≥ 0.5（`SEMANTIC_RECALL_MIN`）的前 20 条（`SEMANTIC_EACH`）。
3. 两个列表用 RRF 合成一个分数（`1 / (60 + 名次)` 相加），只被向量找到的条目补进候选。
4. 合成分数替代原来的 BM25 名次，排在原有排序键的最后一位。项目优先、置顶优先、用户亲口说的优先、"有用"多的优先，这些规则都不变。
5. 不带向量时，结果和改动前完全一样。

**做梦分组**（`dream::groups_with`）

- 开关打开时，两条记忆字面相近，或者向量余弦 ≥ 0.75（`SEMANTIC_DREAM_ALIKE`），都算相近，再用原有的并查集连成组。
- 组的大小和组数上限不变。分组之后照旧交给分析模型判断重复、矛盾还是无关。

**宿主**（`session_live_services/memory.rs`）

- `embedder`：开关关闭时返回 `None`。
  - 打开时用 core 新增的 `settings::notebook_embed_config()` 取随手记的 embedding 设置和全局代理；key 用随手记同一个钥匙串账户补上（`resolve_key_with_secrets` 改为 `pub(crate)`）。
  - 按接口类型分批调用 `embed::embed_batch`。
- 每 2 分钟的自动整理（`sweep`）先补向量，每次最多 256 条（`SEMANTIC_PER_SWEEP`）。这一步不受"自动整理"开关和分析模型影响。
- 召回（`context.memoryRecall`）先算查询向量，再调 `recall_with`。以下情况只用字面召回，不等待：
  - 开关关闭；
  - 最近一次算向量失败；
  - 向量表的模型和现在设置的不一致（换模型后、补完之前）。
- `memory.semanticStatus {}` 返回 `{status, model}`，其中 `model` 是随手记现在设置的模型名。

**界面**（整理设置）

- 新增一行"按意思找"，用胶囊开关。打开后显示两行说明：
  - 状态行："nomic-embed-text · 已算 12 条 · 还差 2 条"；还没算过时显示"打开后在后台用随手记的 embedding 模型（…）给记忆算向量"；失败时显示"向量没算成：…"。
  - 固定提示：用随手记设置里的 embedding 模型；nomic-embed-text 对中文分不清相关和无关，建议换 bge-m3 这类支持中文的模型。

## 前后对照（2026-11-14）

**环境**：Mac 上用 Homebrew 装了 Ollama，拉取 nomic-embed-text（274MB）。Ollama 拉取时，下载地址经本机代理的假 IP DNS 解析成了 198.18.x.x，被 Ollama 拒绝；让 `ollama serve` 走 `HTTPS_PROXY=http://127.0.0.1:7890` 之后拉取成功。

**题目**：core 里一个 `#[ignore]` 测试 `eval_with_a_real_model`，用 `AERORIC_EMBED_EVAL=<地址>` 打开，可以复跑。

- 24 条记忆，内容取自这位用户的日常：缩进、发布检查、YOLO batch、RK3588、LoRA 超参、代理端口等。每条配一个换了说法、几乎不共享字面的问题。
- 6 个与记忆无关的问题（晚饭、电影、天气……）。
- 6 对"同一条规则换个说法"的记忆，看做梦能否把它们分到一组。

用户看到 nomic 的结果后同意下载 bge-m3（1.2GB），用同一份题目重跑：

| 指标 | 只用字面（FTS） | + nomic-embed-text | + bge-m3 |
|---|---|---|---|
| 24 个换说法的问题，目标排第 1 | 0 | 3 | 17 |
| 目标在前 3 | 0 | 6 | 19 |
| 每个问题平均返回条数 | 0.0 | 7.7 | 3.9 |
| 6 个无关问题共返回 | 0 条 | 47 条 | 0 条 |
| 做梦找到的重复对（共 6 对，阈值 0.75） | 2 对，2 组 4 条 | 2 对，4 组 12 条（两组是错的） | 4 对，4 组 8 条（都对） |

**余弦分布说明了差别**：

| | nomic-embed-text | bge-m3 |
|---|---|---|
| 问题 → 它对应的记忆 | 0.44–0.72 | 0.41–0.73 |
| 无关问题 → 最像的那条记忆 | 0.56–0.67 | 0.40–0.50 |
| 6 对重复之间 | 0.74–0.98 | 0.68–0.90 |
| 不同规则之间最高 | 0.88 | 0.65 |

- nomic 的相关和无关两段完全重叠，没有阈值能分开；它主要是英文模型。
- bge-m3 的无关问题都在 0.50 以下，召回阈值 0.5 刚好把噪声挡在外面；目标没找到的 5 个，余弦都在 0.41–0.49。
- bge-m3 的重复对和不同规则之间隔开了（0.68 对 0.65）。做梦阈值原定 0.85，只靠向量认出 2 对（0.88、0.90），加上字面共 3 对。用户看过后定为 0.75：多认出 0.79、0.82 两对，共 4 对，这份题目里没有误分组。6 对样本很少，0.75 可能偏乐观；误分组的代价只是多问一次分析模型，不会自动合并用户的记忆。
- nomic 在 0.75 下更差：多出两个错误的组（0.85 时是一个）。

**结论**：

- nomic-embed-text：没有净收益。召回多找到 6 个，却给每个无关问题塞进约 8 条噪声；做梦没多找到重复，还多出一个错误的组。
- bge-m3：有净收益。前 3 命中从 0 到 19（共 24），无关问题零噪声；做梦多找到 2 对重复，没有误分组。
- 开关仍然默认关闭：随手记默认的 embedding 模型是 nomic-embed-text，直接打开反而有害。设置里的提示写明了要换 bge-m3 这类支持中文的模型。

## Alternatives considered

- **用 sqlite-vec 的 `vec0` 虚表**：随手记已经在用，记忆条数上来后检索更快。没有采用（第 3 题）：记忆是几百到几千条，全量点积不到一毫秒；虚表需要按维度建表，换模型时还要重建表结构，派生索引越简单，越容易整批丢掉重来。
- **记忆单独配一套 embedding 连接**：可以和随手记用不同的模型。没有采用（第 3 题）：多一处设置和一个钥匙串账户，而两边用的都是同一台机器上的同一个服务。代价是随手记换模型时，记忆的向量也会整批重建。
- **写入记忆时同步算向量**：新记忆能立刻按意思被找到。没有采用：写入路径会多一次网络调用，模型不可用时还得决定写入是否失败。改为每 2 分钟的扫描补算，最长延迟两分钟；召回时没有向量的条目照样能按字面找到。
- **只用向量、不用 FTS**：没有采用。路径、命令、标识符这类字面信息，向量反而容易丢；评测里 FTS 在无关问题上零噪声，是合并之后唯一能控制噪声的一路。
- **按每次查询的最高分动态取阈值**：可以去掉一部分噪声。没有采用：无关问题也总有一个"最高分"，动态阈值只是把噪声从 8 条压到 1–2 条，并没有解决模型分不清中文语义的问题。
- **把随手记的默认 embedding 模型改成 bge-m3、开关默认打开**：评测里 bge-m3 有净收益。没有采用：随手记的默认值会影响随手记自己的索引，而且 1.2GB 的模型不能假定每台机器都装了；要不要改默认，属于随手记的决定，不在这一批里改。

## Consequences

- 收益：
  - 有了按意思召回和按意思分组的完整通道：向量表、补算、RRF 合并、做梦分组、状态行；换一个支持中文的模型就能直接重新评测；
  - 开关关闭时，召回、做梦和以前逐字节相同，没有额外开销；
  - 向量随遗忘一起删除，不会让"已遗忘"的内容以向量形式留下。
- 代价：
  - 用默认的 nomic-embed-text 打开开关会让召回明显变吵，界面上写了提示，但用户仍然可能打开；要得到收益，得在随手记设置里换成 bge-m3 这类模型（约 1.2GB）；
  - 做梦阈值 0.75 是用 bge-m3 的 6 对样本定的，换模型后未必合适；用 nomic 打开时会多出错误的组，多花分析模型的钱；
  - 每 2 分钟扫描一次，新记忆最多两分钟后才能按意思找到；
  - 模型服务不可用时，在下一次扫描成功之前，召回不使用向量；
  - 随手记换 embedding 模型，记忆的向量要整批重建，期间召回只用字面；
  - 向量存的是记忆原文的派生数据，memory.db 变大：nomic 768 维每条约 3KB，bge-m3 1024 维每条约 4KB。
- 待目检（已记进路线图的待目检清单）：整理设置里"按意思找"的开关、状态行和提示文字；真实召回在开关打开时的样子。
