# Agent Note: C4 第一步：网关按每次尝试记账，没报的用量不算零

Status: implemented

## Problem

[调研落地批次 C](../../proposed/feature/2026-11-15-adoption-c-memory-gateway-skills.md) 的 C4。Aeroric 自带的网关（`local_router`）把每个请求记成 `gateway-usage.sqlite` 里的一行：

- 一次请求内部换了几次连接，只记一个 `attempt_count`。每次去了哪里、各自什么状态、花了多少，都没有。
- 上游没返回用量（流中途断开、有的服务商干脆不给）时，四项用量记成 0，和真的是 0 分不开。
- 缓存写入只有一个合计。Anthropic 的 5 分钟档和 1 小时档价格不同，它们分别报的数字被丢掉了。

动手前核对时还发现：这份记录**只有写入，没有任何地方读**。宿主没有读它的方法，App 的用量页、回合账单读的都是会话转写，不是这里。

## Decision

**每次尝试一行**（`core/crates/aeroric-core/src/local_router/usage.rs` 的 `RouterAttempt`，新表 `router_attempts`）：

- 主键是请求 id 加序号。序号按网关遇到目标的顺序编，被熔断跳过的目标也占一个序号。
- 每行记：目标、出站模型、状态码（没收到上游回应时为空）、耗时、四项用量、用量来源、错误摘要、是否被熔断跳过。
- 怎么填（`server.rs`）：
  - 失败后换下一个目标的尝试，当场记下，用量来源记"未知"；
  - 被熔断跳过的目标记为跳过，摘要写 `circuit open: skipped`；
  - 最后作答的那次，等响应收尾、用量确定后再补上，耗时从这次尝试开始算。
- 请求行保留，作为汇总，和各次尝试在同一个事务里写入。清理 90 天前的旧行时，连同它们的尝试一起删。

**用量来源**（`UsageSource`：`reported` / `estimated` / `unknown`）：

- 上游返回了 `usage` 对象，就是"上游报告"。`"usage": null`（OpenAI 流式中间的分片）不算报告。
- 没有报告就是"未知"：网关断开、被取消、全部失败、上游不给用量，都算。
- "估算"先留着，目前没有地方会写它。
- 请求行和尝试行都有来源。

**缓存写入分档**：

- 上游给了 `usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` 时，分别存进 `cache_write_5m_tokens` / `cache_write_1h_tokens`；
- 只给了合计时，两列留空，不按比例猜；
- 原来的 `cache_creation_tokens` 仍是合计。

**汇总**（`RouterUsageSummary`）：

- 四项用量的合计不计入来源为"未知"的请求，另外报出 `unknownUsageRequests`（有几次请求的用量未知）；
- 加上两档缓存写入的合计。

**读取**：新增宿主方法 `gateway.requests {limit?}`，返回汇总和最近 N 个请求（默认 50，最多 500），每个请求带上它的各次尝试。这是这份记录第一次能被读出来。

**旧数据**：用 `ALTER TABLE` 加三列，旧行的来源读作"上游报告"、没有尝试明细、没有分档。旧行无法追溯来源，这里明说，不去猜。

## Alternatives considered

**来源为"未知"时，用量列存空值（方案原文）。** 最强的理由是数据库本身就不会被误读。没选：四个用量列建表时是 `NOT NULL DEFAULT 0`，改成可空要在 SQLite 里重建整张表，迁移风险大于收益。现在的做法是：列里仍是 0，但每一行都带着来源；所有汇总都按来源排除；接口一律把来源和数字一起交出去。

**只在最后作答的那次记用量，失败的尝试不记行。** 最强的理由是简单，失败的尝试多半没有计费。没选：方案的要求就是看得见每次去了哪里、为什么失败；"第一次 429、第二次换连接成功"正是要交代清楚的情形。

## Consequences

- **收益**：
  - 一次换过连接的请求能看到每次尝试；
  - 没报的用量不再冒充 0；
  - 缓存写入的两档分开了；
  - 宿主第一次能读出网关的记录。
- **代价**：每个请求多写几行尝试记录，在同一个事务里，量级不大。
- **没做（第二步）**：
  - 回合账单和配额节奏显示"用量未知"。它们现在读的是会话转写，要先决定什么时候改读网关的记录；
  - App 用量页按请求展开、显示来源标记；
  - E6 用量上限、E7 按用途记账会建在这份记录上。
- **验证**：
  - `server.rs` 新增 2 个测试：
    - 第一个目标 429、第二个成功并报了用量：两行尝试依次是 429/未知、200/报告；各次尝试报告的用量之和等于请求行的合计；两档缓存写入存了下来；
    - 作答的响应没有 `usage`：请求和那次尝试都是"未知"，不分档。
  - `usage.rs` 新增 2 个测试，旧库升级测试补了断言：
    - `usage: null` 不算报告，只有合计时不分档；
    - 尝试明细存进去后按顺序读回；汇总不计入用量未知的请求，并报出它们的个数；
    - 旧行读作"上游报告"、没有尝试明细。
  - 宿主集成测试 `gateway_requests_answer_with_totals_and_tries`：方法返回汇总字段和带尝试的请求列表，未知参数被拒。
  - 网关共 190 个测试通过。没有界面改动。
