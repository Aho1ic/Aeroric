# Agent Note: E16 定时任务可以要求按 JSON 结构交结果

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E16：定时任务可以要求按给定的 JSON 结构交结果；结果不合格，这一次运行就记失败，不会退化成一段散文。来源是 OMB #1506。

shell 预检那一半 Aeroric 已经有了（§3.8），这一片只补结构化输出。

动手前（`main@1935fa06`）核对的事实：

- 定时任务规则存在 `<数据目录>` 的一个 JSON 文件里，运行记录也在里面。宿主每 30 秒调一次 `Schedules::tick`。
- 一次运行开了会话就记为 `Started`。会话后来怎样，运行记录不知道：
  - 只有宿主重启打断时，`note_task` 会补一行；
  - “是否还在跑”由宿主的 `busy` 判断：回合进行中，或任务状态是 pending、running、input_required。
- 四家 Harness 的会话都没有“按结构输出”的统一开关：
  - Codex 的 `outputSchema` 只在 `turn/start` 上，而且只约束模型的最终消息；
  - Claude、DSH、OMP 没有对应的东西。
- 宿主已经能读一个任务转写里 Agent 的最后一条回复：E12 第一步的 `latest_assistant`。
- core 没有 JSON Schema 库。

## Decision

**规则加 `resultSchema`（可选），一段 JSON Schema 的子集：**

- 支持的关键字：`type`（单个或列表）、`properties`、`required`、`additionalProperties: false`、`items`、`enum`，以及说明性的 `description`、`title`、`$schema`。
- 保存时整段检查：用了不支持的关键字、`type` 不认识、`additionalProperties` 不是 false、超过 4000 字，都拒绝保存，并写明是哪一处。这样用户写下的每一条都会真的被检查，不会悄悄忽略一部分。

**提示词：** 开会话时，在提示词（和前置检查的输出）后面附一段说明：在最后一条回复里，用一个 json 代码块交出结果，结构必须符合下面这段；不符合，这次运行记为失败。下面贴出那段结构。

**判定：** 运行记录在开会话时记下 `resultExpected`。之后每次 tick：

1. 先找出要了结果、还没判定、会话已经不忙的运行；
2. 取这个会话 Agent 的最后一条回复（宿主的 `latest_reply`，和 E12 读的是同一份，不截断）；
3. 取最后一个能解析的 json 代码块（没写语言的代码块也算），没有代码块时，看整条回复是不是 JSON；
4. 按规则现在的结构检查：
   - 合格，存进 `result`；
   - 不合格、没有 JSON、会话没有回复，就写进 `resultError`，这次运行算失败。错误写明第一个不符合的位置，例如“$.items[0] 缺少字段 title”。
5. 每次运行只判一次。规则的结构被删掉了，这次运行就不用交结果了。

**界面（定时任务页）：**

- 编辑器多一栏“结果结构（可选）”，等宽字体，下面写明用法和支持的关键字。
- 保存前先在 App 里解析：不是 JSON 对象的，当场提示，不发给宿主。
- 运行记录在“已开会话”后面写明结果：
  - “结果合格”，后面一行是结果的 JSON；
  - “结果不合格”，用警示色，后面一行是原因；
  - 还在等的写“等结果”。

## Alternatives considered

**用 Codex 的 `outputSchema` 让模型直接按结构输出。** 最强的理由是模型侧强约束，几乎不会不合格。没选：

- 只有 Codex 有，另外三家没有；
- 它要求严格模式的 schema，比这里支持的子集更苛刻；
- 定时任务的会话走的是新会话按钮那条路，加它要改 `task.run` 和 Codex 驱动。

以后可以在 Codex 上加用它，判定仍走这里，作为四家共同的底线。

**引入 JSON Schema 库（`jsonschema` crate）。** 最强的理由是关键字全、行为标准。没选：

- 依赖重：会拉进正则引擎、网络引用解析等；
- 定时任务的结果是几个字段的小对象，这个子集够用；
- 保存时拒绝不支持的关键字，用户不会以为写了就被检查了。

**判定不合格时自动再问一次 Agent。** 没选：

- 会多花一轮的钱，而无人值守的用量有上限（E6）；
- 方案要的是“记失败”，不是“修到合格”。

用户看到失败原因后，可以打开会话接着问。

## Consequences

- **收益：** 定时任务的结果可以被机器读、被比较，不合格的明确记为失败，不会被当成“已开会话”就算完成。
- **代价：** 每个要结果的提示词多一段说明和结构，大约几百字。
- **局限：**
  - 判定最多晚 30 秒：在下一次 tick，不是会话一结束就判；
  - 按规则现在的结构判，跑到一半改了结构，旧的那次运行按新结构判；
  - “最后一条回复”取自转写，被中断的回合里只说了一半的话也算；
  - 结果只存在运行记录里，没有导出，也没有通知；
  - 没有在真实 Agent 上跑过一次要结果的定时任务（NOT RUN），界面没有目检（UI 自动化暂停）。
- **验证：**
  - core 新增 5 个，定时任务的 41 个全部通过：
    - 结构检查只收能检查的关键字，写明哪一处、超长拒绝；
    - 结果取最后一个 json 代码块，整条回复是 JSON 也行，没有 JSON 时报错；
    - 不合格时写明路径，涵盖缺字段、枚举、整数、多余字段、顶层类型；
    - 判定的三种结论；
    - 调度：提示词带上要求，会话还在跑时不判，结束后判一次且只判一次，没有 JSON 的回复记为不合格。
  - Swift 新增 1 个，定时任务的 7 个全部通过：结构的往返、空文本表示不要、非对象和非 JSON 被拒，运行的“合格、不合格、等结果”三种说法和失败判断。
- **待目检：** 已记进路线文档 §8 待目检清单。
