# Agent Note: 统一投递队列（R1-2a）：委派结果与审查意见走持久队列，带送达证据

Status: implemented

## Problem

委派结果、返工说明、审查意见都直接调用 `driver.prompt`。这个调用只是把命令放进驱动的通道，没有回执，也不落盘，因此：

- 宿主重启、按停止、或会话没启动起来时，消息会悄悄丢失；
- 界面也说不清一条消息到底送到没有。

路线复核把这件事列为 R1 状态真实性的第二批（Q-S1），具体决定见 Q-S2～Q-S8。

## Decision

- **队列**：core `sessions/live/delivery/` 实现一个纯函数状态机（`state::step`）。
  - 状态：等待、发送中、已接收、已送达、失败、结果未知、已暂停、已撤回。
  - 数据存在数据目录下的 `delivery.db`，每条一行 JSON；已结束的条目保留 7 天。
- **位置**：`Deliveries` 放在 sink 链最靠宿主的一层。它读驱动推来的 `deliveryReceipt` 和回合边界，并为客户端追加 `delivery` 更新。
- **发送**：同一会话一次只发一条。内部消息和"这轮结束后再发"的消息要等回合结束（Q-S5）。会话没在运行时由宿主悄悄启动；启动失败只试一次，再有新消息进队时，非用户问题的失败会再试一次（Q-S8）。登录失效、程序缺失这类只有用户能解决的问题，标记后不再自动重试。
- **证据**：
  - Codex：`turn/start`、`turn/steer` 的回应，记为 Delivered(protocol)；
  - omp：`prompt`、`steer` 的回应，同上；
  - Claude：写入 stdin 后记为 Accepted；启动参数加 `--replay-user-messages`，收到 `isReplay` 回显后记为 Delivered(echo)，按文字配对；
  - 不给回执的驱动：先记 Accepted，下一个回合开始时记为 Delivered(turnStarted)。
- **停止屏障**：`session.interrupt` 会把这个会话里还在等待或发送中的条目标为已暂停（Q-S6）。
- **重启**：启动时，发送中或已接收的条目一律改为结果未知，再去 Agent 自己的会话记录里找这段文字：
  - 找到：算送达（transcript）；
  - 没找到：给"重发"；
  - 读不到记录：进入"需要我处理"（Q-S4）。

  等待中的内部消息自动补发；已暂停的保持暂停（Q-S7）。
- **接入**：宿主里委派（结果、返工说明）和审查（发给审查者、发回写代码会话）的 `prompt` 都改为入队。
- **界面**：
  - 输入框上方只在失败、结果未知、已暂停时显示一行，用户消息排队的情况留到 R1-2b（Q-S3）；
  - 右侧详情新增"投递"时间线；
  - 需要我处理新增"投递待确认"。

## Alternatives considered

- **每个驱动自己排队**：每族要各写一遍，而且重启后不知道该往哪个驱动补发。
- **结果未知时自动重发**：可能让 Agent 重复执行同一指令（Q-S4 已否定）。
- **纯内存队列**：做不到重启后补发，也给不出证据。

## Consequences

- 发给子会话的第一条委派消息仍直接发送：它和启动子会话是一起的，失败时委派本身就会失败。
- 换来源时的交接和用户自己的消息留到 R1-2b。
- 委派和审查的 `prompt` 不再同步返回错误；失败改由投递状态表达。
- Claude 回显配对目前用 fake 驱动测试；真实 Claude 版本的回显格式要用一次真实会话验证。

## CU 目检后修复（2026-11-02 23:20 报告）

- **F1**：Codex 先推 `turnEnded`，之后才清空自己的运行状态。回合结束那一刻的 pump 仍读到忙，于是什么都没发。现在会话状态结算为非运行时再 pump 一次。测试按真实顺序：回合结束时仍是忙，结算之后才发送，两条逐条发出。
- **F2**：工具栏的“停止”走 `task.cancel` 到 `StructuredExecutor::cancel`，绕过了屏障。现在 `cancel` 先暂停队列。之后在输入框再按停止，会话已关闭时直接算成功，不再报“没有打开的原生会话”。
- **F3**：退回重做后，卡片和发回的正文仍是旧结论，因为 `redo` 没有清空上一轮的回复。现在 `redo` 时会清空。
- **未解决**：工具栏停止后再续接 Codex 会话，报 `thread … already has an active writer`。这个错误来自 Codex 跨进程的写者锁（`rollout/src/writer_lock.rs`）。用户自己续接走的也是同一条路径，所以不是队列引入的问题，另立任务排查。

## CU 复测后修复（2026-11-03 10:34 报告）

- **C13**：两条结论送达只差 4 毫秒，主会话一次回复了两条。原因是 Codex 驱动收到 `turn/start` 的回应后，先发“已送达”回执，之后才记下进行中的回合。队列收到回执就 pump，读到的还是空闲，于是第二条被立刻发出，作为 steer 插进了同一轮。现在先记下回合，再发回执。omp 和 Claude 本来就是先开始回合、再发回执，不受影响。测试用探针 sink，在回执到达的那一刻读取会话快照，断言回合已在运行。

## Verification

- core `delivery::tests`（7 个）：回合结束后发送且一次一条；回显作证据；无回执时以回合开始作证据；停止后暂停、继续后发出；启动失败只试一次、用户能解决的不自动重试；重启后核对会话记录并补发；状态机拒绝不适用的转换。
- 三个驱动各一个回执测试。
- 宿主端到端测试：委派结果经队列送达，证据为 protocol。
- 宿主单元测试：标签生成、会话记录匹配。
- Swift `DeliveryTests`（4 个），以及更新后的合同夹具测试。
