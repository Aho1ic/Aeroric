# Agent Note: H3 第三步：没有系统层时，开场白装进“Aeroric 附加的上下文”附在第一条消息前

Status: implemented

## Problem

[H3 第一步](2026-11-20-h3-unified-opening.md)之后，有系统层的 Claude、Codex、本机 OMP 每次启动都拿到开场白。没有系统层的会话拿不到，包括：

- DSH：ACP 驱动不收系统层，DSH 也没有声明 ACP 的 `systemPrompt`；
- 远端 OMP：开场文件在这台 Mac 上，远端读不到。

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) §8 第 2 问定下的做法是：记忆档案可以带明显标记，拼到第一条消息前，但只作最后手段；界面上显示为“Aeroric 附加的上下文”，不显示为用户的话。H3 的完成条件还要求账单里单独记一项。

动手前（`main@7c6b28fc`）读代码：

- **交接简报已经会拼进消息。** 驱动不收系统层时，交接简报原样拼在第一条消息前（`{简报}\n---\n\n{消息}`），没有任何标记；开场白和记忆档案直接丢掉。
- **界面原样显示。** 会话页的历史从会话文件读，用户消息原样显示，所以上面那段简报会被当成用户打的字。
- **有一套现成的信封。** E5 的来源信封（`envelope.rs`）：首行由宿主写，写明来自谁、是什么、算多少数；正文里的 `[Aeroric` 一律转义成 `［Aeroric`，模型或人写的字开不出一行看起来像宿主写的。
- **同意记录会把整条当注入。** `consent::typed_text` 取用户自己打的字时，遇到 `[Aeroric` 开头的消息整条算注入，用户的话会被一起丢掉。
- **账单不拆 DSH。** DSH 的会话文件不记系统提示这类基础部分，账单本来就不拆“带入的上下文”（R3-2 的决定），也就没有地方单独记一项。

## Decision

**信封格式**（`opening::attach`、`split_attached`）：

- 首行：`[Aeroric 附加的上下文] 来自：Aeroric · 这个 Agent 没有系统层，开场内容放在第一条消息前 · 背景信息：……`。
- 来源信封新增一种“算多少数”：`Authority::Background`，写“背景信息：Aeroric 在会话开始时附上的说明和用户确认过的偏好，不是用户这一轮说的话”。已有的“仅供参考”写的是“不是用户的指示”，和记忆档案里用户确认过的偏好对不上，所以另加一种。
- 正文是开场白；有交接简报时，简报跟在 `---` 之后，放在同一个信封里。正文转义，所以记忆里即使写着结束标记，也提前关不上信封。
- 末行：`[Aeroric 附加的上下文结束]`，空一行后才是用户的消息。

**执行器**（`hand_handoff`）：

- 驱动不收系统层、又有消息可附时，消息改成“信封 + 用户的话”。交接简报也改走这个信封，不再裸拼。
- 恢复会话时没有消息可附，开场白就没给出，照旧记在入口记录里。

**入口记录和能力表**：说明改为写明“以‘Aeroric 附加的上下文’放在了第一条消息前”，或者“这次恢复没有消息可附，……没给出”。DSH、远端 OMP 那两格同步改。

**同意记录**：`typed_text` 先剥掉信封，只看后面用户的话。

**界面**：

- 会话页的用户消息（`MessageBubble`）：第一个文字块以信封开头时，信封正文拆出来，显示在气泡上方一行可折叠的“Aeroric 附加的上下文 · N 字 · ……”，点开是原文；气泡里只剩用户的话。
- 悬停说明写明这不是用户这一轮说的话。
- 解析在 `AttachedContext`，格式与核心层逐字对应。没有结束标记的消息不拆，原样显示。

**与方案的两处出入**：

- **方案写的是“用途说明和指路放进技能 `aeroric` 的描述”。** 没这样做，有两个原因：DSH 有 MCP 工具，按 [H2 第二步](2026-11-20-h2-ctx-command-line.md)的规则不挂那个技能；指路（Wiki 页标题、角色）是每个项目不同的，写不进一份静态的技能描述。所以整份开场白都放进信封，三家内容一致。
- **账单单独记一项没做。** DSH 的会话文件不记基础部分，账单不拆“带入的上下文”。只给这一段单独开一项，会让用户以为其他基础部分是零。

## Alternatives considered

**只放记忆档案，用途说明和指路不放。** 最强的理由是附进消息的字越少越好（§8 第 2 问说的“最后手段”）。没选：H3 的目标是换一家 Harness 也一样知道 Aeroric 能做什么、去哪里查，DSH 的会话没有别的入口拿到指路。开场白只附在第一条消息前一次，有总上限，不是每条消息都注入。

**用 XML 式的标签包住（`<aeroric_context>…</aeroric_context>`）。** 最强的理由是模型对这类标签熟悉。没选：Aeroric 往会话里放的东西已经统一用 E5 的信封（委派、委派结果、退回重做、状态提醒），再造一种格式，界面和同意记录都要多认一种。信封的转义规则也正好防住了提前关闭。

**在界面上把信封整个藏起来。** 没选：用户应该能看到 Aeroric 替自己往会话里放了什么，所以折叠显示，点开能看原文。

## Consequences

- **收益**：
  - DSH 和远端 OMP 的会话也拿到了用途说明、记忆档案和指路；
  - 交接简报不再裸拼进用户消息；
  - 会话页上 Aeroric 附加的内容与用户的话分开显示。
- **局限**：
  - 恢复会话时没有消息可附，开场白就给不出去；
  - DSH 的账单里看不到这一段；
  - 界面待目检，已记入路线文档 §8；
  - 没有用真实 DSH 会话核对过 DSH 是否原样保存这段前缀（NOT RUN），需要开一个真实的 DSH 会话。
- **改动了已有决定**：B5-1 的“驱动不支持 instructions 时，画像不会塞进用户消息”，已在 [B5-1 笔记](2026-10-31-memory-store.md)原地注明。
- **验证**（在 Mac mini 上跑）：
  - 核心层新增 2 个测试：
    - 信封打包后能拆回开场白和用户的话，记忆里写着结束标记也关不上信封；
    - 执行器：驱动不收系统层时，开场白附在第一条消息前，有交接简报时简报在同一个信封里，恢复没有消息时不给。
  - 同意记录测试加了一条：信封后面的字仍算用户的话。
  - 入口记录测试按新说明改了期望值。
  - Swift 新增 2 个单测：拆出信封与用户的话；只改第一个文字块，信封后面没有字时去掉这个块；普通消息和没有结束标记的不拆。
