# Agent Note: 本回合账单与工具瀑布（R3-1）

Status: implemented

## Problem

路线 R3「账单与上下文透视」要回答一回合花了多少、钱花在哪（见 [路线复核](../../proposed/architecture/2026-11-02-roadmap-recheck.md)）。改动前只有两处数字：输入框下的统计栏是整段会话的累计；每轮答复下方的"用量 N tok"只有一个总数。看不出这一轮输入里多少命中了缓存、大概花了多少钱、时间耗在哪个工具上，后面的上下文透视、额度节奏和"每个被接受改动的成本"也没有逐回合的数据可用。

R3 拆成三批：R3-1 本回合账单与工具瀑布；R3-2 本次带入的上下文与无新证据重试检测；R3-3 额度节奏与每个被接受改动的成本。本篇只覆盖 R3-1。

## Decision

- **数据来源是 Agent 自己的会话文件**：宿主读历史时本来就用 `sessions/transcript_stats.rs` 从 Codex rollout、Claude jsonl、OMP、DeepSeek Harness 的会话文件逐回合算起止时间和 token（[会话页统计栏](2026-10-28-session-page-polish.md)）。R3-1 在这条路上把每个 `TurnStat` 补齐，经 `session.history` 的 `stats.turns` 带给 App，不另建存储，以前的会话也有账单：
  - `inputTokens` / `cachedInputTokens` / `outputTokens`：这一轮每次模型调用的分项相加，输入含缓存读取；会话文件没记用量时为空。Codex 取 `token_count` 的 `last_token_usage`；Claude 按 `message.id` 去重后的 usage；OMP、DSH 在逐次调用累加处同时记到当前回合。
  - `model`：Codex 取 `turn_context.model`，Claude、OMP 取消息上的 `model`（`<synthetic>` 之类不算），DSH 取 `assistant/message` 的 `model`；某轮没写就沿用上一轮。
  - `costUsd`：只在模型列在价目表（`metrics/analytics.rs` 的 `MODEL_PRICES`）里时，按未缓存输入、缓存读取、输出分别计价（`estimate_listed_cost_usd`，DeepSeek 高峰时段照旧翻倍）；不在表里就不给，界面只显示 token。
  - `tools`：每次工具调用一条，含名称、`detail`（命令或输入的第一行，最多 80 字）、开始时间、结束时间和是否失败；每轮最多记 100 条，多出的只计数（`moreTools`），防止一轮几百次调用撑大历史答复。失败的判定：Claude 看 `tool_result.is_error`，OMP 看 `toolResult.isError`，DSH 看结果上的 `isError`，Codex 看输出是否以 `Script failed` 开头、`Process exited with code` 非 0，或含 `aborted by user` / `user rejected`；`exec` 脚本常只回传 `r.output`，退出码不在输出里，这时看夹在调用和输出之间的 `item_completed`（`CommandExecution` 的 `status: failed` 或 `exit_code` 非 0），它不带 call id，记到这一轮最近一个还没返回的调用上。
- **界面**：每轮答复下方原来的"用量 N tok"换成一个胶囊（`TurnBillChip`），写着"12.3K tok · ≈$0.012"，点开是本回合账单卡：
  - 上半部分是模型、输入、其中缓存读取和命中率、输出、用时；
  - 金额前一律加"≈"，卡里注明"按价目表估算，以服务商账单为准"；没有金额时说明原因（会话文件没记模型，或价目表里没有这个模型）；
  - 下半部分是工具瀑布：横轴是这一轮从开始到结束，每次调用一条横条；1 秒内灰、10 秒内主色、更久为警告色，失败标红，没返回结果的半透明并画到回合结束；超过 30 条先折叠，点"还有 N 条"展开；悬停显示命令。
- 正在跑的一轮没有账单：要等这一轮结束、历史刷新后才出现，和"已完成，用时 N 秒"一致。

## Alternatives considered

- **宿主在回合结束时，用前后两次累计用量相减，写进单独的回合记录**：这是本批最初的推荐，理由是结果由 Aeroric 自己保存，重启也不丢。复现时发现宿主内存里的事件日志在会话关闭 10 分钟后就清掉，回合账本（`turn_ledger`）又只记改过文件的回合；要做就得新建一份存储，还得把它和历史里的回合重新对上号，而且上线前的会话永远没有账单。会话文件里已经有逐次调用的用量和每个工具的起止时间，四家都能读，所以改为在现有解析上补字段（用户 2026-11-09 确认）。
- **把账单放进输入框下统计栏的卡片里，只显示"上一回合"**：改动更小，但看不了更早的回合，也和"改动""待验收"这些按回合的信息分开了。
- **价目表没有的模型按名字猜一个单价**：用量统计页就是这么做的（标"按同档推算"）。单轮账单数字小、看的人多，猜出来的金额容易被当真，所以不给金额。

## Consequences

- 收益：
  - 以前的会话打开就有逐回合账单；
  - 四家都有工具瀑布；
  - R3-3 算"每个被接受改动的成本"时可以直接用 `TurnStat` 的分项和金额。
- 代价：
  - 账单的准确程度取决于各家会话文件写了什么：
    - Codex 的工具多数包在 `exec` 脚本里：账单取脚本里第一个 `tools.xxx(` 当名字、第一个 `cmd` 当命令，一个脚本连调几个工具时只显示第一个；
    - OMP、DSH 的工具名和失败字段是按代码读到的格式写的，还没有用真实会话核对过；
    - 读不到的格子显示"—"。
  - `session.history` 第一页的答复变大：每轮多了分项用量和最多 100 条工具记录。
  - `TranscriptStats` 和 `TurnStat` 因为带了 `f64` 金额，不再实现 `Eq`，只实现 `PartialEq`。

## Verification

- core 单测（`transcript_stats`，13 个）：
  - Codex 一轮两次调用的分项相加、模型来自 `turn_context`、价目表内模型的金额；
  - 退出码非 0、`Script completed` 和只在 `CommandExecution` 事件里报的失败判定，命令作为 `detail`；
  - 目检（2026-11-09 第一轮）发现 `cat` 不存在的文件没标红：脚本只回传了输出，已按上一条修正。
  - 没有用量的回合沿用上一轮的模型；
  - Claude 的 `is_error`、价目表外模型不给金额；
  - 每轮 100 条的上限和计数。
- Swift（`TurnBillTests`）：解码、胶囊和卡片文字、瀑布的分色和横条位置。
- 界面目检（2026-11-09）：旧会话的胶囊和账单卡、新 Codex 会话三次调用的工具名、命令和耗时符合预期；复测确认 cat 不存在的文件那一行标红、汇总有"1 次失败"。悬停提示、约 900 像素窄窗口和价目表内模型的金额没能在界面上验到（通道限制，CPA 没有 gpt-5.4 / gpt-5.5）。
