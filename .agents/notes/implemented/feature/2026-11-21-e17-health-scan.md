# Agent Note: E17 `aeroric-cli doctor --scan`：只读健康扫描

Status: implemented

## Problem

[1118 调研](../../proposed/architecture/2026-11-19-new-addition-1118-research.md) E17：`aeroric-cli doctor --scan` 只读扫描数据目录，把失败的回合、卡住的投递、反复出现的错误按特征归组，给出一份报告。不调模型，不改数据。来源是 OMB 的哨兵。

动手前（`main@98cfeee7`）核对的事实：

- `aeroric-cli doctor` 只看数据目录本身：卷、写租约、runtime 元数据、socket 是否在。不看任务和队列。
- **失败的任务：** 在 `projects/<id>/tasks.json` 里，`status: failed`，原因在 `failureReason`，时间在 `completedAt`（毫秒）。`storage::tasks::load_tasks` 只读文件，不要求写租约。
- **投递队列：** 在 `<数据目录>/delivery.db`（SQLite）里，每行的 `body` 是一条 `Delivery` 的 JSON。宿主打开它的方式（`Store::open`）会建目录、建表，并删掉 7 天前已经了结的行，不能拿来做只读扫描。
- **定时运行：** 在 `<数据目录>/schedules.json` 里。E16 起，运行记录多了 `resultError`。
- 失败原因里常带每次都不一样的部分，例如 `exited with code 137 after 12s` 和 `after 340s`，还有各种 id。直接按原文分组，同一个问题会散成很多条。

## Decision

**core 新模块 `health`，`scan(context, since_ms, now_ms) -> Report`，读三处：**

- **任务：** 时间窗内 `failed` 的任务，按 `failureReason` 归组；没记原因的，归到“（没有记下原因）”。
- **投递：** 用 SQLite 只读模式打开 `delivery.db`，只读行，不建表，也不清理。时间窗内下面三种算有问题：
  - `failed`：发送失败；
  - `unknown`：发出后没有回音；
  - 仍在 `waiting`、`sending` 或 `accepted`，但超过 10 分钟没有变化：长时间没有进展。

  有原因的带上原因。
- **定时运行：** 时间窗内 `failed` 的运行，按 `detail` 归组；E16 结果不合格的，按 `resultError` 归组。

**特征（signature）：** 去掉每次都会变的部分，再归组：

- 连续数字换成 `N`；
- 12 位以上像十六进制的 id 换成 `…`；
- 连续空白合成一个空格；
- 最多保留 120 字。

**每组记下：**

- 类别、特征、次数、最近一次的时间；
- 最近一次的完整原文，最多 400 字；
- 最多 3 个例子：任务 id，定时运行没开出会话的用运行 id。

按次数从多到少排，所以反复出现的排在最前面。

**读不了的部分**（项目列表、某个项目的任务、投递库）写进 `unreadable`，扫描的其余部分照常进行。

**命令行：**

- `doctor --scan` 在原有体检之后打印报告：先写扫描了多少、只读、没有调用模型，再一组一组列出，出现不止一次的标“反复出现”；
- `--days N` 定时间窗，默认 7 天，只能配合 `--scan` 用；
- `--json` 时，报告放在 `scan` 字段里。

**只读的保证：**

- 任务和定时任务都只读文件；`Schedules` 加了一个只读的 `all_runs`。
- 投递库用只读模式打开。

测试会在扫描前后，逐字节比对数据目录里的每一个文件。

## Alternatives considered

**扫描放进宿主，作为一个 RPC，在 App 里显示。** 最强的理由是用户不用开终端。没选：

- 方案要的是 CLI 哨兵，宿主没在跑、甚至起不来的时候也能用，这正是最需要体检的时候；
- 宿主在跑时，`doctor` 也只读文件，不跟宿主抢写。

以后需要 App 里看，可以让宿主调同一个 `health::scan`。

**按错误类型的规则表归类，例如“登录过期”“额度”“进程被杀”。** 最强的理由是报告更好懂。没选：

- 规则表要跟着四家 Harness 的报错一起变，会漂；
- 特征归组不需要预先知道错误长什么样，新的问题也能立刻排进去。

**同时扫描会话转写里的错误。** 没选：转写在四家 Harness 各自的目录里，格式各异，而且量大。任务的 `failureReason` 已经是驱动从转写里提炼出的结论。

## Consequences

- **收益：** 一条命令看清最近哪些问题在反复出现、出现在哪些任务上，不用一个个点开。宿主起不来时也能用。
- **代价：** 没有。
- **局限：**
  - 只看任务、投递、定时运行三处；委派、审查、检查点的失败不在里面；
  - 特征归组是文本层面的：同一个问题若有两种说法，会分成两组；
  - 时间窗按任务的 `completedAt`（没有时用 `createdAt`）算，投递按最后变化的时间；
  - 投递库在宿主写入的同一时刻被读，只会读到写入之前或之后的样子。SQLite 的只读打开不会读到写了一半的行。
- **验证：**
  - core 新增 4 个，全部通过：
    - 特征去掉数字和 id；
    - 一套夹具（失败任务 4 个，其中一个在窗外；投递 4 条；定时运行 3 次）扫出 6 组，“exited with code 137” 的两次归为一组并排第一，窗外的和健康的不算；
    - 扫描前后数据目录逐字节一样，没有多出文件；
    - 空目录报告“没有发现”，不建任何文件。
  - 命令行新增 1 个、延伸 2 个，共 28 个单元测试加集成测试全部通过：
    - `--days` 不配 `--scan` 是用法错误；
    - 命令树能解析 `doctor --scan` 和 `doctor --scan --days 30 --json`；
    - 在空数据目录上跑 `doctor --scan --days 3 --json`，返回空的 `scan.groups`。
  - 没有在真实数据目录上跑（NOT RUN）。
