# Agent Note: H4 第二步：按消息在本地召回记忆和 Wiki，默认只记录

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H4 第 2 条：用户发出一条消息时，在本地检索记忆和 Wiki（不调模型），分数过线才附上，最多几条，带来源和 id；没有就什么都不加。

方案对它有三条约束：

- 默认关闭，等 H8 证明有用再开；
- 四族上同一条消息触发同样的决定；
- 开关关闭时没有任何附加。

动手前（`main@d7d09a9a`）核对的事实：

- **用户消息的去路**：所有用户消息经投递队列，最后在宿主的 `send_user` 里交给驱动的 `deliver`。四族同一条路，检查点的提醒也在这里加在消息前面。
- **H3 的“Aeroric 附加的上下文”信封**（`opening::attach`）：带“背景信息”的权威标记，会话页会折叠显示。
- **`Memory::recall` 的两个问题**：
  - 会把命中计为一次“被检索”，H7 的升降要用这个数；
  - 它的全文检索按空白拆词、每个词当一个短语。一整句中文就成了一个短语，几乎不会命中，这是给 Agent 传关键词设计的。
- **Wiki 的全文检索**不给分数。

## Decision

**判断放在宿主，只看消息本身**（`sessions/live/recall.rs`、`StructuredExecutor::recall_for`）。判断的输入里没有 Harness，所以四族的决定天然一样。

- **关键词**：
  - 三个字符以上的英文或标识符词（可带 `-_./`）；
  - 相邻两个汉字成一个词；
  - 去掉“怎么”“一下”“帮我”这类常用词。
- **记忆**：
  - 用这些关键词做全文检索拿候选（新的 `Memory::matches`，不计数）；
  - 和消息至少共有 2 个关键词才算命中，六个字符以上的标识符算 2 个；
  - 按共有多少排，最多 3 条；只在启用了记忆的项目里找。
- **Wiki**：页面标题出现在消息里才算，最多 1 页，不算首页；只在 Agent 能读 Wiki 的项目里找。
- 少于 6 个字的消息不找，记为“消息太短”。

**三种模式**（`recall.mode`，存在 `<数据目录>/recall/mode.json`）：

- `off`：什么都不做，也不记录；
- `candidate`（默认）：判断并记录，什么都不附加，就是 H8 说的“候选”档；
- `on`：有命中时，用 `opening::attach_because` 把指路装进同一个信封，放在消息前。
  - 信封上的说明是“Aeroric 按这条消息自动找到的相关记忆和 Wiki”；
  - 正文写明“不一定相关；用不上就忽略”；
  - 列出记忆的 id 和原文（截到 160 字），以及 Wiki 页的标题和 slug（让它用 `read_wiki` 读全文）。

**每条消息的决定**都记在 `<数据目录>/recall/<任务>.jsonl`：时间、模式、命中、是否附加、为什么没找。`recall.decisions {taskId}` 可读，这是 H8 判断“有没有用”的原料。

## Alternatives considered

**直接用 `memory_recall` 那套（`Memory::recall`）。** 最强的理由是和 Agent 用的检索一致。没选：

- 整句中文按短语匹配，几乎找不到；
- 它会把每次命中记成“被检索”，用户没让 Agent 查的东西也会被算成用过，H7 的升降会被带偏。

**用全文检索的 bm25 分数定门槛。** 最强的理由是现成。没选：

- bm25 的大小随记忆库的条数和词频变化，库小时一个罕见词的分也很低，同一个门槛在不同项目里含义不同；
- “共有几个关键词”的规则在哪个库里含义都一样，也好向用户解释。

**默认打开。** 方案明确默认关闭。`candidate` 只记录、不改消息，符合“开关关闭时没有任何附加”，又能在 H8 之前攒下证据。

**用 Claude 和 OMP 的 Hook 在它们自己那边注入。** 只有两家能做，四族的决定就不一样了；宿主本来就经手每条消息。

## Consequences

- **收益**：
  - 四族同一个决定，开关一处；
  - 默认什么都不附加，但每条消息“本来会附加什么”都有记录，H8 可以直接拿来评。
- **局限**：
  - 关键词规则是粗的：二字词会带出“本钉”这类无意义的组合，靠“至少共有 2 个”压住误命中；Wiki 只认标题被点名。门槛要等 H8 的数据来调；
  - 还没有界面开关，只能用 `recall.mode` 设置，界面放在 H8 的分档管理里；
  - 附加的记忆没有计入“注入后的反馈”，H7 的升降会接上；
  - 真实会话里附加内容对回答的影响，NOT RUN（H8）。
- **验证**（在 Mac mini 上跑）：
  - 关键词：标识符和汉字二字词，常用词去掉；
  - 命中：只共有一个词的记忆不算，共有多的算；单个长标识符就够；Wiki 只认被点名的标题，首页和单字标题不算；无关的消息什么都不命中；太短的消息不找；
  - 模式默认 `candidate` 并能保存，决定逐条追加；
  - 执行器：
    - `candidate` 记下命中但返回空；
    - `on` 返回带记忆 id 的指路；
    - 太短的消息记“消息太短”；
    - 没开记忆的项目没有命中；
    - `off` 什么都不记。
