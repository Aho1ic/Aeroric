# Agent Note: Codex 订阅额度节奏（R3-3b）

Status: implemented

## Problem

Codex 订阅有 5 小时和每周两个窗口，用完就只能等重置。用户此前只能看到"已用多少"，判断不了按现在的速度会不会在重置前用完。[路线复核](../../proposed/architecture/2026-11-02-roadmap-recheck.md)把额度节奏并入 R3：按窗口已用百分比和已过时间外推，近一小时至少 3 个读数才算近期速度，只提示不替用户换。

复现时发现两件事：

- 会话都走 CPA 或本机登录网关，Codex 写进会话文件的 `rate_limits` 全是空的，额度只能从订阅接口 `account/rateLimits/read` 读。
- CPA 消耗的就是本机这个 plus 账号：2026-11-10 08:39 到 10:44 只有经 CPA 的流量，5 小时窗口从 0% 涨到 16%，周窗口从 86% 涨到 89%。CPA 若在多个账号间轮换，这里只反映这一个。

## Decision

- **窗口时长**：`metrics::usage` 解析 Codex 额度时保留 `windowDurationMins`（`UsageWindow.window_minutes`），没有它就不知道窗口过了多少。
- **读数**（`metrics/quota_pace.rs`）：
  - 宿主启动后起一个线程，每 10 分钟读一次 Codex 订阅额度，把两个窗口的已用百分比、重置时间和时长追加到 `<data>/quota-readings.jsonl`，只留最近 8 天；没有 `codex` 命令就不起。只读 Codex，不读 Claude（Claude 没订阅，每次读还会碰钥匙串）。
  - `usage.quotaPace {}` 先现读一次并记下，再按读数算节奏；读不到时返回 `{status: "unavailable", reason}`。
- **怎么推算**：
  - 同一窗口（重置时间相差不超过 2 分钟：订阅接口给的重置时间偶尔差 1 秒）最近一小时有至少 3 个读数时，用最早和最晚两个读数之间的速度；否则用"已用 ÷ 窗口已过时间"的平均速度。
  - 按这个速度推到重置时刻：会超过 100% 的是"偏快"，给出预计用完的时间；不会的是"正常"，给出重置时约剩多少；已用 100% 也算偏快；窗口开始不到 1 分钟、没有近期读数时是"读数不够"。
- **界面**：Agent 配置页的"改动成本"标签改名"用量与成本"，顶部加"Codex 订阅额度"卡片，标明"本机 Codex 登录（plus）"。5 小时、每周各一行：已用、窗口过了多少、重置时间、节奏胶囊（偏快为橙色），下面一行写推算结果和依据（近一小时还是整个窗口）。读不到时写原因。
- **只提示**：不进"需要我处理"，不在会话页提醒，不切换账号或模型；委派时额度用完就拒绝这次没做。

## Alternatives considered

- **从会话文件或 `account/rateLimits/updated` 通知取额度**：不用额外调接口，会话一跑就有。没选：经 CPA 和网关的会话里额度全是空的，用户的会话全走这两条路。
- **读 CPA 自己的账号用量**：能直接对上 CPA 实际用的账号，包括轮换。没选：要用 CPA 的管理密钥，不碰凭据；从读数变化已经能确认消耗的是本机这个账号。
- **放在运维的用量面板里**：原计划。没选：运维页在侧栏里是"即将推出"，进不去；和[改动成本](2026-11-10-change-cost.md)放在一起，一页看完花费和额度。
- **只在打开页面时读，不定时采样**：少一个后台线程和一个文件。没选：没有历史读数就算不出近期速度，用户不常开这一页，近一小时凑不齐 3 个读数。

## Consequences

- **收益**：能看出 5 小时和周额度按现在的速度够不够用、大约什么时候用完，决定是否放慢或换模型。
- **代价**：
  - 宿主每 10 分钟调一次本机 Codex 的订阅接口（复用读用量的那个 `codex app-server` 进程）。
  - 接口给的已用百分比是整数，窗口刚开始时平均速度波动大；读数只来自这个宿主，App 没开的时候没有读数。
  - 只反映本机 Codex 登录的那一个账号。
- **验证**：
  - core 单测（`metrics::quota_pace`）：平均速度会用完时是偏快并给出用完时间；够用时给出重置时剩余；近一小时 3 个读数按近期速度；上一个窗口的读数不算近期，重置时间差 1 秒仍算同一窗口；已用完是偏快、刚开始是读数不够；缺重置时间或时长的窗口不记；超过 8 天的读数被删掉。
  - Swift 单测（`ChangeCostTests`）：解码 `usage.quotaPace`；窗口名、已用和重置时间、偏快的用完时间和提前多久、正常的剩余、依据、已用完。
  - 目检（2026-11-10，Codex Computer Use，审阅版）："用量与成本"标签顶部的额度卡片两行与 `usage.quotaPace` 一致，周额度为偏快、5 小时随目检消耗从正常变为偏快。首轮发现订阅接口的重置时间偶尔差 1 秒，那次依据退回了平均速度；改为 2 分钟内算同一窗口后复测，来回切换 4 次依据都保持"按最近一小时的速度推算"（复测期间没再出现 1 秒的差，这一情况由单测覆盖）。
