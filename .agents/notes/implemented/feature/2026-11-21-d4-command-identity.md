# Agent Note: D4 第一步：手机的命令带稳定编号，重发只执行一次

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D4 指出的缺口：

- 手机发出的命令没有稳定的标识，重连后可能重发；
- 宿主不知道一条命令是基于哪一次启动时的状态发出的。

做法第 1、2、5 条：

1. 命令带设备生成的 `command_id`，重发不变；宿主按它去重，保留结果一段时间，重复的命令返回第一次的结果。
2. 命令带上它所基于的状态（`host_epoch` 等），过期了就拒绝。
3. 设备被撤销后，它的在途命令全部拒绝，保存的结果清除。

完成条件之一：不存在重连后重复执行的命令。

动手前（`main@b43695d9`）核对的事实：

- **请求入口：** 手机的 RPC 经端到端加密通道进来，在 `remote/server.rs::handle_request` 解析后交给 `remote/rpc.rs::dispatch`，一个方法一个分支。会改东西的方法有：任务输入、审批、取消、完成、新建、续跑，以及置顶、写文件、Agent 配置、推送登记。
- **宿主一侧没有启动标识。** 手机的 `CompanionStore` 已经按 `hostEpoch` 判断审批是否过期，可是这个值宿主从来没给过。
- **撤销：** `remote/control.rs::revoke_device` 从设备表删掉设备，并断开它的连接。断开时如果有请求正在执行，结果只是发不回去，宿主那边照样执行完。
- **另一套协议：** Orca 协议的请求走 `orca_rpc::handle`，不经过 `dispatch`。

## Decision

**宿主启动标识：**

- `RemoteState` 每次构造时生成一个新的 `host_epoch`（随机 UUID），`hello` 回包里给出 `hostEpoch`；
- 能力表加 `commands.idempotent`，手机可以据此知道宿主支持去重。

**命令台账**（`remote/commands.rs::CommandLedger`）：

- **哪些算命令：** `COMMANDS` 里列出的 12 个会改东西的方法。读取类的方法不算，照旧执行。
- **按设备、按 `commandId` 记：**
  - 第一次来时登记一个“只执行一次”的格子（`tokio::sync::OnceCell`），真正执行并记下结果；
  - 同一个 id 再来时，拿到同一个格子：第一次已经执行完，直接返回它的结果；还在执行，就等它执行完拿同一个结果。所以两个同时到达的重发也只执行一次；
  - 判断“是同一条命令”的依据是方法加参数的指纹，不含 `commandId` 和 `hostEpoch`。同一个 id 换了参数，就拒绝：“这个 commandId 已经用在了另一条命令上”。
- **保留多久：** 结果保留 10 分钟，每台设备最多 500 条，超了先丢最旧的。
- **id 的限制：** 不能为空，不超过 128 个字。
- **按启动标识判旧：** 带了 `hostEpoch` 而不是本次启动的，拒绝，回答以 `STALE_HOST_EPOCH` 开头，说明宿主已经重启、要重新同步后再决定。手机按这个前缀认出来。
- **不带 `commandId` 的命令照旧执行。** 老版本的手机不受影响。

**入口**（`server::dispatch_once`）：`handle_request` 拿到这个连接认证过的设备 id 后，按顺序：

1. 命令来自已经不在设备表里的设备（撤销正好赢了这一刻），拒绝；
2. 交给台账，按结果执行一次、照旧执行，或者拒绝。

**撤销：** `revoke_device` 在删掉设备、断开连接的同时，清掉这台设备留在台账里的结果。

## Alternatives considered

**在宿主各个执行方法里分别去重。** 比如审批按请求 id、取消看任务状态。最强的理由是各方法本来就有一些幂等性：取消一个已取消的任务没有副作用。没选：

- `task.input`、`task.create` 没有天然的幂等键，同一段文字再输入一次，就是两次；
- 在入口统一按 `commandId` 处理，12 个方法一个规则，新加命令也只要列进表里。

**台账落盘，宿主重启后照样去重。** 最强的理由是，重启前发出、重启后重发的命令，也能认出来。没选：

- 宿主重启后 `hostEpoch` 换了。手机带着旧的启动标识重发，会被当成过期命令拒绝，不会执行，也就不需要靠台账去重；
- 结果落盘还要处理“执行到一半宿主停了”的情况，那正是要手机重新同步的时候。

**同一个 id 在执行时再来，直接回“正在执行”。** 最强的理由是不用等。没选：方案要求重复的命令返回第一次的结果。手机重连后重发，最想知道的就是那次的结果，让它等一会儿更有用。

## Consequences

- **收益：**
  - 带 `commandId` 的命令，不管重发几次、是不是同时到达，在 Mac 上只执行一次；
  - 基于上一次启动发出的命令不会执行；
  - 撤销的设备，命令不会再被执行。
- **代价：** 内存里按设备保留最近十分钟的命令结果。
- **局限：**
  - 手机端还没带上 `commandId` 和 `hostEpoch`，在它带上之前，这些规则都用不上，那是下一步；
  - 第 2 条只做了 `hostEpoch`，按任务的 `generation` 和对象修订号判旧还没做；
  - Orca 协议的请求不经过这里；
  - 宿主重启后的去重靠 `hostEpoch` 判旧，不靠台账。
- **验证：** core 新增 3 个测试，远程模块原有的测试照旧通过，共 123 个：
  - 台账：
    - 读取类方法和不带 id 的命令照旧执行；
    - 同一设备同一 id 拿到同一个格子，别的设备不同；
    - 同一个 id 换参数被拒绝；
    - 旧的启动标识被拒绝，并以 `STALE_HOST_EPOCH` 开头；
    - 超长 id 被拒绝；
    - 超过十分钟重新登记；
    - 忘掉设备后台账清空。
  - 入口：
    - 同一个取消命令，两次同时发、再发一次，Mac 上只执行一次，三次拿到同一个结果；
    - 旧的启动标识被拒绝，不执行；
    - 换一个 id 的新命令照常执行；
    - 设备撤销后命令被拒绝，台账清空。
  - `hello` 给出本次启动的标识，两次启动的标识不同；能力表里有 `commands.idempotent`。
