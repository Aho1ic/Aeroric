# Agent Note: D1 第三步：Git 侧栏的“PR 审查”

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D1 的完成条件是用户能走完一条流程，全程对 GitHub 只有读请求：

1. 选 PR；
2. 固定版本；
3. 读变更和检查；
4. 独立审查；
5. 打开每条结论的位置；
6. 保存草稿。

方案第 8 条：Git 页加 PR 入口、快照视图和审查结论视图。

动手前（`main@2affe710`）核对的事实：

- **宿主侧已经齐了。**
  - [第一步](2026-11-21-d1-pull-snapshots.md)有 `github.pullSnapshot`、`github.snapshots`；
  - [第二步](2026-11-21-d1-read-only-review.md)有 `github.reviewStart`、`github.reviews`，结论在读审查时解析并存成草稿。
- **方案说的“Git 页”现在是会话页右侧的 Git 侧栏**（`GitSidebarPanel`）。2026-10-30 起侧栏取代了 Git 页，里面是提交框、更改列表，以及可展开的“贮藏”和“历史”。
- **打开文件的入口：**
  - 侧栏打开文件走 `openPreview(ResourcePreviewTarget)`，路径相对项目，预览不能跳到指定行；
  - 打开一个会话走 `services.requestedSelection = SessionNavigation.task(id)`。

## Decision

**Git 侧栏多一个可展开的“PR 审查”段**，放在“历史”下面，标题带快照数：

- **固定：** 一个“粘贴 PR 链接”输入框和“固定”按钮。悬停说明只读取 PR，不向 GitHub 写任何东西。正在取时显示“正在取 PR…”，出错时写原因（就是宿主说的原因）。
- **每份快照一行：**
  - “#编号 标题”；
  - “快照于 某时 · 对应提交 abc1234”；
  - 被取代时多一行“PR 已更新”；
  - 有审查时，写最新一次审查的状态。

**点一行打开快照窗：**

- **顶部：** 标题、“所有者/仓库 · 分支 → 目标分支”、快照时间和对应提交。
- **被取代时：** 写“PR 已更新，这份快照针对的是旧版本”，并且不能再发起审查。
- **按钮：**
  - “让 Agent 审查”菜单，可选 Claude Code 或 Codex；
  - “刷新快照”：用这个 PR 的链接再取一次，有新提交就存成新快照；
  - “更新结论”：重读审查列表，宿主在这时从会话里解析结论。
- **每次审查一块：**
  - 状态：审查中…、N 条结论、没有发现问题，或者“没有结论：原因”；
  - 有没收的条目时写个数；快照被取代时写“针对旧版本”；
  - “打开审查会话”。
- **每条结论：**
  - 严重程度（高、中、低）；
  - 位置按钮，例如 `src/a.rs:12`，点开 PR 检出里的这个文件（`.aeroric/pr-reviews/<快照>/<路径>`）；
  - 正文和依据。
- **再下面：**
  - 变更文件：最多列 60 个，带增删行数；列表不完整时写明；
  - 检查：先汇总“1 失败 · 1 进行中 · 2 通过”，再逐项列出；
  - 已有评论：最多 30 条，写位置和作者，针对旧版本的写明。

**状态对象** `PullReviewBook`：

- 跟着侧栏当前的项目走，Git 侧栏刷新时一起读快照和审查；
- 固定、开审查成功后重读列表；
- 同一时间只做一件事；
- 出错时写“固定快照失败：…”“开始审查失败：…”，列表保持原样；
- 还没有项目时什么都不发。

文字在 `PullText`，协议模型是 `LivePullSnapshot`、`LivePullReview`，客户端是 `GitHubClient`。

## Alternatives considered

**单独做一个“PR”页面，放进侧栏的主导航。** 最强的理由是审查结论和文件列表在窄侧栏里显得挤。没选：PR 属于一个项目的仓库，和分支、提交放在同一个 Git 侧栏里，用户不用换地方。详情用弹窗展开，宽度够用。

**结论的位置直接打开 GitHub 网页上的对应行。** 最强的理由是网页能看到 PR 的完整差异。没选：

- 快照固定的是一个提交，网页显示的是 PR 现在的样子，推过新提交后行号会对不上；
- 检出里的文件，正是审查者看到的那一份。

**审查跑完后自动刷新结论。** 最强的理由是用户不用点“更新结论”。没选，这一步不做：

- 要监听审查会话的回合结束；
- 现在打开侧栏或刷新 Git 时都会重读，而“更新结论”只是一次读取。

## Consequences

- **收益：** D1 的整条流程在 App 里能走完：固定 → 读 → 审查 → 打开位置 → 草稿留存，全程只读 GitHub。
- **代价：**
  - Git 侧栏多一段；
  - 每次刷新 Git 侧栏多两次读取：快照和审查；
  - 审查没完成的话，宿主每次都会重读审查会话的记录。
- **局限：**
  - 预览不能跳到行，位置里的行号只是写出来；
  - PR 检出在 `.aeroric/` 下，文件预览能不能打开这类目录，要目检确认；
  - 不能选模型和 Agent 配置；
  - 快照和审查没有删除入口，检出也没有清理；
  - 没有 PR 列表，只能粘贴链接。
- **验证：** Swift 新增 `PullReviewTests` 2 个测试，全部通过：
  - 快照和审查按侧栏的样子读出：标题、分支、对应提交、文件汇总、检查汇总和逐项、评论位置和“针对旧版本”、审查状态的几种写法、结论位置、严重程度、检出里的路径；
  - 状态对象：没有项目时不发请求；固定和开审查发给当前项目，之后重读；出错时写明，列表不变，结束后不留在“进行中”。
- **待目检：** 已记进路线文档 §8 待目检清单。
- **NOT RUN：** 对真实 GitHub 的整条流程，包括本机 gh 登录、私有仓库、真实审查者交回结论。
