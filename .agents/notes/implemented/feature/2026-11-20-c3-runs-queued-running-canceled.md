# Agent Note: C3 第一步：整理记录看得到排队和进行中，可以取消，每条候选有去向

Status: implemented

## Problem

[批次 C 方案](../../proposed/feature/2026-11-15-adoption-c-memory-gateway-skills.md)第 C3 片要求：任意时刻整理记录都与实际进行的整理一致，每条候选的去向都能查到。动手前的情况（`main@b1800c0b`）：

- **只有结束态。** `MemoryRunState` 只有完成、部分成功、失败、跳过。一次抽取要等模型回复、写完，才在记录里出现一行。模型调用常常要几十秒，这段时间里记录看不出有整理在进行。
- **自动巡检是串行的。** 巡检一次可能找到好几个待整理的会话，一个接一个做。排在后面的那些，记录里看不出来。
- **不能取消。**
- **候选没有逐条交代。** 运行记录只有计数（几条线索、几条候选、几条写入失败）和一句原因。候选并入了已有的记忆、被遗忘签名拦下，还是写入出错，看不出来，更对不上是哪一条。
- **重启后对不上。** 宿主在整理途中退出，这次整理在记录里不留痕迹。如果在中途先写了一行，重启后那一行会永远停在中间状态。

## Decision

**三种新状态**（`aeroric-protocol` 的 `MemoryRunState`，追加在原有值之后）：

- `queued`（排队中）：自动巡检找到、还没开始的抽取；
- `running`（进行中）：正在调用模型或写入；
- `canceled`（已取消）。

**一行记录贯穿始终**（`memory/runs.rs`）：

- 抽取在通过检查（模型已选、没到每日上限、没整理过）之后，先写一行 `running`，结束时用同一个 id 改成最终状态。
- 整理（dream）在真要调用模型时才写 `running`，不用模型的过时检测不写。
- 中途出错（例如撤回检查读库失败）也会把这一行改成失败，不会停在"进行中"。

**自动巡检先排队**（宿主 `extract_due`）：

- 先把这次找到的会话都写成 `queued`，再逐个做，做的时候用排队那一行的 id。
- 用户在排队期间取消的，跳过。
- 碰到每日上限或没选模型时停下。没轮到的、或者"已经整理过"的，排队行删掉：记录里只留真实发生的事。
- 加了一个全局标记，同一时间只有一次巡检，一个会话不会被排两次。

**取消**（`memory.runCancel {runId}`，`Memory::cancel_run`）：

- **排队中的立即取消**，写明"排队时取消，没有调用模型"，并把会话标为已整理。否则下一次巡检又会把它排上，取消就没有意义了。用户仍可在会话菜单里手动整理。
- **进行中的**记下取消请求。抽取在模型回复后、每一条写入之前检查：
  - 已写入的保留，不撤回；
  - 没写的逐条记为"取消未写"；
  - 原因写"已取消：取消前写入的 N 条保留，没有撤回"，或"已取消：模型的回复没有写入"。

  整理（dream）在模型回复后检查，取消了就什么都不改。
- 取消后的运行，已经调用过模型的，照常计入每日次数和花费，因为 token 已经花了。排队时取消的不计。
- 已结束的运行不能取消，返回状态不对。

**重启恢复**（`runs::recover`，打开记忆库时）：

- 停在 `running` 的改为失败，原因写"Aeroric 退出时这次整理还没做完，没写进去的可以重试"。抽取的会话没有标为已整理，所以巡检会重新做，用户也可以点重试。
- 停在 `queued` 的删掉：它没有开始，下一次巡检会重新排队。

**逐条结果**（`MemoryRun.outcomes`）：

- 抽取产生的每一项（会话线索、经验、待确认候选）记一条：类别、去向，以及写入或并入的记忆 id，被拦下或失败时附原因。去向分六种：
  - 新写入；
  - 并入已有（同样的话已经在，只多了一份依据）；
  - 被规则拦下（已遗忘、疑似密钥、太长）；
  - 写入失败；
  - 整理期间被撤回（C2）；
  - 取消未写。
- 不带原文，只带文字的签名：用遗忘签名同一把密钥，截取前 16 位。被遗忘的话不会因为出现在运行记录里而留下原文。
- 没有原话依据被丢掉的候选（`extract::parse` 里丢的）仍然只有计数。解析阶段就丢了，不算写入的去向。

**计数规则统一**（`store::counted`）：

- 排队行和取消前没调用模型的行，都不占每日次数；
- "用量与成本"的本月次数不算排队行。

**App 的最小适配**：

- 整理记录的状态文字加上排队中、进行中、已取消。不认识的状态显示"进行中"，原来会显示成"跳过"。
- 整理历史会话的统计里，已取消的不算失败。

取消按钮、逐条结果的展示，放在第三步。

## Alternatives considered

**只在内存里记"正在进行的整理"，记录表仍只存结束态。** 最强的理由是不会有重启后停在中间状态的行，不需要恢复逻辑。没选：

- App 要看两处才能拼出完整的记录；
- 宿主崩溃时，这次整理就悄无声息地消失了，方案明确要求"恢复为失败并可重试，不是静默消失"。

写进表里，再在打开时恢复，只需要一处读、一处恢复。

**取消正在进行的模型调用（中断 HTTP 请求）。** 最强的理由是取消立即生效，不用等模型回复。没选：调用在阻塞线程里经同一个 `chat_once` 发出，中途中断要给整条调用链加取消通道。而且请求已经发出，上游照样计费。现在的做法等回复回来后不写入，结果一致，代价只是多等几十秒，记录在这期间显示"进行中"。

**排队时取消的会话不标为已整理。** 最强的理由是用户也许只是想晚点再整理。没选：自动巡检每隔几分钟就会把它重新排上，取消等于没取消。标记后，用户手动整理仍然可以，原因里也写明了。

**逐条结果存候选原文。** 最强的理由是记录里能直接看到每条是什么。没选：被规则拦下的恰恰是已遗忘或疑似密钥的话，原样存进运行记录就违背了遗忘的承诺。写入或并入的有记忆 id，App 能按 id 显示文字。失败候选为了重试需要的内容，第二步另行处理，设保留期。

## Consequences

- **收益**：
  - 整理记录在任何时刻都与实际一致：排队的、进行中的都看得到，宿主重启后不会留下假的"进行中"；
  - 用户可以取消；
  - 每条候选的去向可查。
- **代价**：
  - 每次抽取多写一行（开始时）；
  - 巡检多写排队行，没轮到的再删掉；
  - 记录表的行体积多了逐条结果，每条几十字节。
- **未完成**（第二步）：
  - 失败重试只重试失败的候选，不重新调用模型；
  - "用过几次"按（记忆、任务）去重；
  - 重建索引作为一种运行类型。

  第三步做 App 的取消按钮和逐条结果。
- **验证**：
  - 核心层新增 5 个测试，并在 C2 的撤回测试里加了逐条结果的断言：
    - 模型调用期间记录显示进行中；取消后什么都没写，逐条记为取消未写，token 照记，会话标为已整理，仍可手动整理；已结束的不能取消，不存在的报错；
    - 每一项的去向：线索和经验新写入、候选并入已有（id 指向已有那条）、被遗忘签名拦下（附原因）；签名 16 位，记录里没有原文；
    - 排队行立即显示，不占次数；取消后标为已整理；巡检用排队行的 id 做完后，那一行变成结果；没轮到的移出记录，非排队行不会被误删；
    - 重新打开记忆库：进行中的变成失败、带原因，会话没标记，可以重做；排队的移出；
    - 整理（dream）在模型调用期间显示进行中；取消后不合并、不提议，记录写明。
  - 宿主集成测试新增 1 个：排队的整理出现在 `memory.runs` 里，`memory.runCancel` 取消后变成已取消，再取消或取消不存在的会报错。
  - Swift：状态文字的断言。
