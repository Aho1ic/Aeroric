# Agent Note: 故障注入（R1-4）：会话死掉或不回应时，消息记为“未知”，不堵住后面的队列

Status: implemented

## Problem

R1-2 的投递队列只在宿主重启时，才把还在“发送中 / 已接收”的消息改成“未知”。宿主不重启的情况下，下面三种故障都会出问题：
- Agent 进程在回执到达前死掉；
- Agent 收到消息后一直不回应；
- Codex 在回应 `turn/start` 前退出。

前两种会让消息永远停在“发送中”。同一会话后面的消息也会一起卡住，因为队列规定每个会话只能有一条在发送。第三种则被说成“Codex 拒绝了这条消息”，其实 Codex 可能已经收到了。

## Decision

- 在测试用的假 Agent 上做故障注入：
  - 队列单测：会话死掉、回显没到、超时没有任何回应、回执重复或乱序、发送失败保留原因；
  - Codex 和 Claude 的端到端测试：进程在回应前或回显前死掉、一直不回应。

  omp 走同一条“会话失败”路径；它在一轮进行中退出会让这一轮失败，已有测试覆盖。
- 修复：
  - **会话失败**：会话报失败时，这个会话里还在“发送中 / 已接收”的消息改成“未知”（原因：会话中断了，没收到回执）。然后去 Agent 自己的会话记录里核对，队列继续发后面的消息。
  - **发送调用还没返回时会话就失败了**：先记下这条消息。如果发送调用最后成功返回，同样改成“未知”；如果发送本身失败，就保留它自己的失败原因，例如登录被拒，好让 R1-3a 的“等用户处理”逻辑照常工作。
  - **超时**：发出后 90 秒内没有任何回执，改成“未知”（原因：Agent 没有回应），然后核对记录、放行后面的消息。只对“发送中”计时：“已接收”可能要等当前这一轮结束才回显，不能按时间判它失败。
  - **Codex 传输关闭**：不再发“拒绝”回执，只让这一轮失败，由队列判为“未知”。
- 目检 C17 用真实故障来测：一轮进行中 `kill -9` 掉 Agent 进程。不额外加 Debug 开关。

- 目检补充：
  - Codex 进程在一轮中途被杀时，rollout 里这一轮没有结束标记。下一轮的 `task_started` 出现时，把它记为“已中断”，不再显示“已完成”。
  - 新建会话页的“登录失效”提示只匹配同一个 Agent 配置：自带登录只匹配自带登录，此前选了自带登录也会显示其他配置的失效提示。
  - Claude 会话记录里，带 `isApiErrorMessage` 的那一行表示这一轮因为接口出错而放弃。这样的一轮标题显示“失败”，不再显示“已完成”。
  - 侧栏状态 `interrupted` 显示为“已中断”，不再直接显示英文。

## Alternatives considered

- **在 Debug 版加故障注入的环境变量**：会多出一条只为测试存在的代码路径；真实故障用 `kill` 就能制造。
- **“已接收”也按时间判失败**：Claude 的插话可能要等当前这一轮结束才回显，按时间判会误报。
- **会话失败时，直接把还在途的消息判成失败**：Agent 可能已经收到了，说失败同样不真实。“未知”加核对记录，是唯一不说假话的做法。

## Consequences

- 一条消息最多 90 秒内会脱离“发送中”，后面的消息不会再被永远卡住。
- 判成“未知”的消息不会自动重发，避免重复发送；用户可以在提示条上手动重发或丢弃。

## Verification

- core 队列单测 5 个：会话死掉、回显没到、超时、回执不倒退、发送失败保留原因。
- 宿主端到端测试 3 个：Codex 回应前死掉、Codex 不回应、Claude 回显前死掉。连跑 3 遍都通过。
