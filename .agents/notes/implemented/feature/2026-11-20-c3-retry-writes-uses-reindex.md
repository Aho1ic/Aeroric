# Agent Note: C3 第二步：失败只补写那几条，"用过几次"按会话计，可以重建索引

Status: implemented

## Problem

[C3 第一步](2026-11-20-c3-runs-queued-running-canceled.md)让整理记录有了排队、进行中、取消和逐条结果。方案 C3 的第 4–6 条还没做（`main@c1d712a2`）：

- **失败重试会重新调用模型。** 写入失败时，原来的做法是不给会话打"已整理"标记，等下次触发时整次重来：再读一遍对话、再调一次模型，已写入的靠合并去重。这样多花一次 token，模型第二次的回复也可能和第一次不同。点"重试"走的也是这条路。
- **"用过几次"会被同一个会话刷高。**
  - 召回（`retrieved`）每调用一次就加一；同一个 Agent 在一次会话里查十次同一条，就算十次。
  - 画像注入（`injected`）在恢复会话时也会再加一。
  - Agent 的有用 / 不对没有去重。一个会话连说三次"有用"，经验的可信度就会升到"高"，进而被提议成技能。
- **索引坏了没有办法修。** 全文索引（`items_fts`）和条目分开存。如果两者不一致（例如写到一半出错），搜索和召回会漏掉条目，没有任何提示，也没有修复的入口。

## Decision

**写入失败的整条存下，只补写这几条**（`memory/runs.rs` 的 `PendingWrite` / `Retry`，`run.rs` 的 `retry_run`）：

- 抽取先把要写的每一项（线索、经验、候选）整理成完整的 `PendingWrite`，包括文字、细节、依据和原话位置，再逐条写入。写入失败的连同它在 `outcomes` 里的位置，以及模型调用开始时的撤回序号，存进新表 `retries`。
- 存下之后，这个会话照常标为已整理，不再调用模型。原因写"N 条没写进去，会自动重试，不再调用模型"。如果存都存不进去，退回原来的做法：不打标记，下次重来。
- **重试**有三个入口：
  - `memory.runRetry {runId}`；
  - 后台巡检每轮都试一遍，不调用模型，所以不看自动整理开没开；
  - App 的"重试"按钮，已改为调用 `memory.runRetry`。
- 重试只写存下的那几条，结果写回**原来那一行**：
  - 对应的 `outcomes` 改成新结果，计数补上；
  - 原因去掉旧的失败说明，加"重试补写了 N 条"；
  - 全部写成后变为完成，删掉存下的内容。
- 仍然失败的，留在原位置等下次。
- 重试前，同样的话被删除、归档或取代了（C2），记为"期间被撤回"，不写。
- 没有存下内容的运行（例如模型调用本身失败）重试时，抽取的会话重新整理一次，与原来一样。

**存下的内容要跟着遗忘走**：这张表存的是原文，所以它是 [C2 清单](2026-11-20-c2-withdrawal-reaches-memory-store.md)里新增的一处派生点（第 20 项）。处理是：

- 最多保留一周（`RETRY_KEPT_MS`），与撤回记录相同；
- 永久遗忘时，存下的内容里被遗忘的那几条当场删掉，不等重试时才被拦下。重试时，这几条在 `outcomes` 里改记为"被规则拦下：已遗忘"。

**"用过几次"按（记忆、任务）计**（新表 `uses`）：

- Agent 召回（`context.memoryRecall` → `recall_in_task`）：同一个会话再找到同一条，不再加一。
- 会话开始注入画像（`profile_for_session` 带上任务 id）：恢复的会话不算新的一次。
- Agent 的有用 / 不对（`context.memoryFeedback` → `feedback_in_task`）：
  - 一个会话对一条记忆只算一票，不论之后说有用还是不对；
  - 重复的回复写明"这个会话已经反馈过，不重复计数"。
  - 这样，一个会话不能单独把一条经验抬到"高"可信度、提议成技能。
- 没有任务的调用（App 里的搜索、用户自己点的有用 / 不对）照旧每次都算：前者不是使用，后者是用户明确的判断。
- 删除一条记忆时，它的 `uses` 行一起删掉。

**重建索引**（`memory.reindex`，`Memory::rebuild_index`）：

- 从条目重写整个全文索引，经验的正文照常包含问题、解法、搜索词和环境。同时删掉已不存在的条目留下的语义向量。没有向量的条目由后台按原来的方式补算，不在这里调用模型。
- 作为一行出现在整理记录里：类型新增 `reindex`，标题"重建索引"，原因写重写了几条、清掉几个向量、几条等补算。不占每日次数，不计入本月次数。
- `memory.runs` 新增 `indexHealthy`：用 FTS5 的 `integrity-check`，再加上条目数与索引行数是否一致来判断。第三步在 App 里，据此在索引不完好时给出"重建索引"。

## Alternatives considered

**重试时重新调用模型，但把第一次写成的候选传给模型，让它别重复。** 最强的理由是不用存任何原文。没选，有三个原因：

- 多花一次 token；
- 模型第二次的回复不一定包含第一次失败的那条，失败的那条就悄悄没了；
- "每条候选的去向都能查到"要求失败的那条本身有下文。

存下来最多一周，遗忘时当场清掉，已经满足了"不留原文"的承诺。

**"用过几次"改成只记不同任务的个数，不保留原来的计数方式。** 最强的理由是口径统一。没选：App 里的搜索没有任务，用户点的有用 / 不对是明确的判断，不该和 Agent 一样去重。只有带任务的调用去重，改动面最小，旧数据也不用迁移。

**索引损坏时自动重建，不经用户。** 最强的理由是用户不用操心。没选：判断"坏了"只能看到行数对不上，原因可能是正在写入。自动重建可能和写入撞在一起。先报告、由用户点，第三步给入口。重建本身很快，也是幂等的。

## Consequences

- **收益**：
  - 写入失败不再多花模型调用，失败的那条不会因为第二次回复不同而丢掉，记录一行到底；
  - 一个会话不能刷高使用次数和可信度；
  - 索引出问题时能看到，也能修。
- **代价**：
  - 记忆库多了两张表：`retries` 一周后清掉；`uses` 每个（记忆、任务、类别）一行，随记忆删除；
  - 抽取在写入前多一步，把每一项整理成完整的待写条目。
- **局限**：
  - 恢复会话时，已注入过的画像不再计数，但新会话照算；
  - App 里还看不到逐条结果、重建索引的入口，以及"重建索引"这一行的专门样式，留给第三步。目前这一行会按普通整理的格式显示。
- **验证**：
  - 核心层改写 2 个、新增 4 个测试：
    - 一部分写入失败：会话已标记，不再调用模型；仍失败时原位等待；恢复后补写了那一条，写回同一行，其他条目没有重复写；已完成的不能再重试。
    - 全部写入失败：每一条都存下，会话已标记。
    - 等待重试期间：一条被永久遗忘，存下的内容当场少了它，重试时记为"被规则拦下"；另一条被归档，重试时记为"期间被撤回"，没有写回。
    - 同一任务召回十次只算一次，另一个任务再算一次；画像注入同理；没有任务的搜索每次都算；删除后不留使用记录。
    - Agent 在一个会话里投十次只算一票，换一个会话再算一票，两票不会升到"高"。
    - 删掉全文索引后能看出不完好、搜索找不到；重建后一行"重建索引"，完好，搜索恢复，经验细节也能搜到，不占次数。
  - 宿主集成测试：
    - 延伸 1 个：同一会话再召回、再投票，不重复计数，回复写明；
    - 新增 1 个：`memory.reindex` 产生一行并出现在 `memory.runs` 里，`indexHealthy` 为真，不占次数；完成的或不存在的运行不能重试。
