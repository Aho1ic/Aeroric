# Agent Note: 后台整理（做梦）第一批：合并重复、提出冲突，一次整理可以整批撤销

Status: implemented

## Problem

B5 的记忆是按会话写入的：

- 每个会话结束后，[整理](2026-10-31-memory-extract.md)一次，产出会话线索、0–2 条[经验](2026-10-31-memory-experience.md)和待确认的候选；
- [存储](2026-10-31-memory-store.md)不原地改文字，修改就写一条新的、把旧的标为已取代。

但没有任何环节跨会话收拾：

- 同一个修法在三个会话里被记成三条经验，置信度和"有用"次数各算各的；
- 两条互相矛盾的约定（比如"缩进用 tab"和"缩进用 4 个空格"）可能同时生效，新会话两条都带上。

路线图 §6.5 的"后台整理（做梦）"就是补这个环节，Q-M1 把它留到了 B6。用户 2026-11-13 说"全部按推荐"，第一批定为：

1. 只做合并重复、发现冲突，以及整理记录与撤销；过时检测和画像压缩放第二批。
2. 在本地按字面重合度先把可能相关的条目分成小组，模型只看有 2 条以上的小组；没有这样的小组就不调用模型。
3. 能自动生效的只有模型整理出的经验之间的重复。用户自己说的、置顶的、画像，以及所有冲突，一律进待确认。不因"长期没用"删除或归档任何东西。
4. 只在开了记忆、并且打开了"自动整理"的项目上运行，默认关闭（Q-F8）。上次整理之后新增 20 条以上、所有会话都安静 10 分钟以上才自动触发；每个范围每天最多自动一次；记忆页有"现在整理"。
5. 复用"整理设置"里的分析模型，每次整理记一行整理记录，和会话整理共用每天的上限。
6. 每次做梦是一批改动，可以"撤销这次整理"。快照之后被改过的条目，这次不动。

## Decision

**做梦从不写自己的文字**（core `memory/dream.rs`）

- 做梦只会"留下现有的一条，把其余几条标为已取代、指向留下的那条"，不生成新的记忆文字。
- 这样模型编出来的内容进不了记忆；做梦也不需要另外的引用校验。代价见 Consequences。
- 第二批的画像压缩是唯一的例外：模型改写的文字只作为建议，用户采纳后才写入，见[第二批](2026-11-14-memory-dream-second.md)。

**一次做梦的步骤**（`Memory::dream`）

一次做梦只整理一个范围：一个项目，或者全局。

1. **取租约**：`Memory.dreaming` 记下正在整理的范围；同一个范围已经在整理，就返回"这里正在整理"。
2. **分组，不调模型**：
   - 取这个范围生效中的画像、项目事实和经验（`dream::KINDS`）。会话线索不参与，因为两条相近的线索是两个会话，不是同一件事说了两遍。
   - 同类条目两两比较规范化文字的字符对（经验用标题加问题）：共享的字符对至少 2 个，并且占较短一条的 40% 以上，就算"相近"（`ALIKE`、`MIN_SHARED`）。
   - 用并查集把相近的条目连成组。每组最多 6 条（`DREAM_GROUP_MAX`），一次最多 12 组（`DREAM_MAX_GROUPS`），大组和新组优先。
   - 用户已经处理过的组（采纳或"都留着"）不再提；判断依据是把组内 id 排序后拼起来作为键。
3. **没有小组**：自动触发时什么都不记，只更新这个范围的整理时间；手动"现在整理"时，记一行"跳过 · 没有字面相近的记忆，画像也没超出，不用整理"。两种都不调用模型，也不占当天次数。
4. **检查当天上限**：到上限就报错，不记录。
5. **调用分析模型**：
   - 按组列出 id、来源（用户亲口说的 / 用户确认过 / 模型整理）、是否置顶和文字，经验再带上问题和解法；
   - 要求只回一个 JSON：每组的 `relation`（duplicate / conflict / unrelated）、`ids`、`keep` 和理由；
   - 提示里写明多值偏好不算冲突，拿不准就判 unrelated。
6. **确定性校验**（`dream::parse`）：
   - 组号必须是发出去的那些；
   - `ids` 只保留属于这一组的，去重后至少 2 个；
   - `keep` 必须在 `ids` 里；
   - 一组只认第一个判断。
   - 对不上的判断丢掉并计数，写进整理记录的原因里。
7. **快照检查**：应用前重读每一条。不再生效，或者 `updated_ms` 和分组时不同（用户在模型思考时改过、置顶过），这一条这次就不动；剩下不到 2 条或者留下的那条没了，整个判断作废。
8. **应用**：
   - **自动合并**：判为重复，并且每一条都是未置顶、不是用户亲口说的经验。留下哪条由 core 决定，不用模型的 `keep`：先比置信度，再比"有用"减"不对"，再比更新时间，这样合并不会丢掉用户依赖的那条。其余标为已取代，记进 `MemoryRun.retired`，用于撤销。
   - **整理建议**：其余情况都写一条 `DreamProposal`（`dream_proposals` 表），等用户决定。
9. **记录**：记一行 `MemoryRun`，`kind = dream`，带模型、token、估算费用、合并条数和建议组数。失败或写入出错也记，计入当天上限。

**用户怎么处理建议**（`Memory::decide_dream`）

- 采纳：留下 `keep`（默认是模型建议的那条，用户可以点另一条的"保留这条"），其余标为已取代。
- "都留着"：建议记为已拒绝，这一组以后不再提。
- 只有待确认的建议能处理；留下的那条必须还生效着。

**撤销**（`Memory::undo_dream`）

- 自动合并的条目恢复成生效中，前提是它仍然是"被这次做梦标为已取代、指向同一条"；之后被别的操作改过的不动。
- 这次做梦还在待确认的建议记为已收回。用户已经采纳或拒绝的保持不变，那是用户的决定。
- 每次做梦只能撤销一次，`undone_ms` 记在整理记录里。

**触发**（宿主 `session_live_services/memory.rs`）

- 每 2 分钟的自动整理（`sweep`）先做会话整理（`extract_finished`），再看哪些范围该做梦（`dream_due_scopes`）。
- 安静的判断：
  - 本轮扫描时有会话正在跑回合（`registry().all()` 的 `turn_active`）；
  - 或者任一记录的 `completedAt` 比上次记下的更晚（原生会话每轮结束都会更新它）；
  - 这两种情况都把 `LAST_BUSY_MS` 推到最新。距它不到 10 分钟（`DREAM_IDLE_MS`）就不做梦。
- 范围：全局，加上每个开启了记忆的项目。
- `Memory::dream_due`：这个范围今天还没整理过（以 kv `dream:<范围>` 记的时间对比当天零点），并且从上次整理以来新增的画像、事实和经验达到 20 条（`DREAM_AFTER_NEW`）。
- 需要 `settings.auto` 打开并选了模型。到上限或没有模型时，这一轮停下。

**RPC**

- `memory.dream {projectId?}` → `{run}`（现在整理，强制）。整理要调分析模型，常常超过请求默认的 30 秒，App 对这一个调用等 10 分钟（2026-11-15 目检：全局整理报"宿主没有及时回应"，其实整理完成了）
- `memory.dreamProposals {projectId?}` → `{proposals}`
- `memory.dreamDecide {id, accept, keep?}` → `{proposal}`
- `memory.dreamUndo {runId}` → `{run}`

**界面**（`MemoryPage`、`MemoryStore`）

- 标签行右侧的"整理设置"左边有"现在整理"（技能提案和历史线索两个标签不显示），没选模型时置灰。整理完，页面顶部显示一行"刚才整理：合并 1 条 · 待确认 1 条建议"。
- 关于你、项目上下文、学会的经验三个标签的最上面是"整理建议"，按建议里条目的种类放进对应标签：
  - 卡片标题写"这几条说的是同一件事，只留一条？"或"这几条互相矛盾，留哪一条？"，后面跟模型的理由；
  - 每一条都有"保留这条"，模型建议的那条写"保留这条（建议）"；
  - 右上角是"都留着"。
  - 标签上的数字算上这些建议。
- 整理记录里，做梦的行标题是"整理记忆 · 项目名"，产出写"合并 N 条 · 待确认 M 条建议"。改过东西、还没撤销的行有"撤销这次整理"，撤销后显示"已撤销"。做梦的行不显示"重试"。

## Alternatives considered

- **让模型写一条合并后的新文字**：合并后的记忆更完整，比如把两条约定合成一句。没有采用：那就是模型写的新记忆，要么一律待确认（失去自动合并的意义），要么让模型编的文字直接生效，违反"模型只能提议"（§6.2）。只在现有条目里选一条留下，确定性校验也只剩 id 检查。
- **整个范围的记忆都发给模型**：不会漏掉字面不像、意思重复的条目。没有采用（用户选了第 2 题的 A）：花费随记忆数量线性增长；记忆多了以后，模型在长列表里也容易漏。代价是用词完全不同的重复找不到，第二批可以再加 FTS 召回或 embedding。
- **会话线索也参与合并**：线索最多，重复看起来也最多。没有采用：一条线索是一个会话的记录，两条相近说明同一件事做了两次，合并会丢掉历史。
- **模型的 `keep` 直接用于自动合并**：模型挑的那条往往说得更完整。没有采用：自动合并时由 core 按置信度和"有用"次数挑，免得模型挑中一条新的低置信经验，把用户标过"有用"的那条标成已取代。整理建议里仍然先选中模型的建议。
- **整理建议做成待确认的记忆条目**：复用现有的确认、拒绝和"需要我处理"。没有采用：现有的 `supersedes` 只能指向一条，冲突和多条重复要一次处理多条；拒绝一条待确认的记忆还会按遗忘处理、留下签名，对"都留着"来说太重了。
- **用每个项目最后一条会话的时间判断安静**：更准。没有采用：宿主现成能拿到的是驱动的 `turn_active` 和记录的 `completedAt`，两次扫描之间开始又结束的回合靠 `completedAt` 补上，够判断"10 分钟内有没有在干活"。

## Consequences

- 收益：
  - 重复的经验会自动收成一条，留下的是最可信的那条；矛盾的约定会摆到用户面前，不再两条都带进新会话；
  - 没有相近条目的项目一分钱不花；有的话每次最多发 12 组；
  - 做梦从不写新文字，撤销只是把状态改回去，一次做梦的影响可以完整收回。
- 代价：
  - 字面不像的重复（换了说法的同一条约定）找不到；字面相近但无关的会被送去问模型，多花一点钱，模型判 unrelated 就什么也不做；
  - "都留着"之后，这一组以后不再提；只有组成员变了（多了一条或少了一条）才会重新出现；
  - 留下的经验不继承被合并那几条的"有用"次数和证据，它们留在已取代的条目上；
  - 用户采纳的建议不随"撤销这次整理"撤回；要恢复，用第二批加的逐条"撤回"。
- 第二批（[2026-11-14](2026-11-14-memory-dream-second.md)）做了过时检测、画像压缩、整理建议进"需要我处理"和侧栏数字、逐条撤回；用 FTS 或 embedding 补召回归到路线图 B6 的"可选 embedding"。
- 待目检（已记进路线图的待目检清单）：
  - "现在整理"按钮和"刚才整理"那一行；
  - 三个标签顶部的整理建议卡、"保留这条"和"都留着"；
  - 整理记录里做梦的行、"撤销这次整理"和"已撤销"；
  - 真实分析模型下的一次做梦。

## Testing

- core `memory::dream` 6 个测试：
  - 同类相近的条目成组，无关的不成组，处理过的组不再出现；
  - 模型回复里不属于这一组的 id、没发过的组号、不足 2 条的判断都被丢掉；
  - 经验的重复自动合并，留下高置信的那条而不是模型挑的那条；用户说的事实进整理建议；撤销恢复合并并收回建议，只能撤销一次；
  - 冲突由用户选留下哪条；拒绝之后同一组不再提，也不再调用模型；
  - 模型思考时被置顶的条目这次不动，原因里写"被改过"；
  - 没有相近条目时不调用模型：自动触发不记录，手动记为跳过、不计次数；新增 19 条时不该做梦、第 20 条时该做，做过之后当天不再做。
- 宿主集成测试 `a_dream_needs_a_model_and_a_scope_with_nothing_alike_costs_nothing`：没有模型时报错；没有相近条目时记一行跳过；建议列表为空；不存在的建议返回 NOT_FOUND；同一行只能撤销一次。
- Swift `MemoryTests`：做梦行和建议的解码、标题与产出文字、能否撤销；建议按种类出现在对应标签、计入标签数字，现在整理、采纳（指定留下哪条）和撤销都发到服务。
