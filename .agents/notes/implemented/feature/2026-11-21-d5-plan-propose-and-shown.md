# Agent Note: D5 第三步：Agent 提议计划，进度页列出并确认

Status: implemented

## Problem

[批次 D](../../proposed/feature/2026-11-15-adoption-d-new-surfaces.md) D5 的最后两件事：

- 第 8 条：计划由用户创建或确认；Agent 可以通过工具**提议**一个计划，用户确认后才生效。
- “用户会看到”：拆成几个工作单元，画出谁依赖谁；任何时候都能看到每个单元为什么在等。

动手前（`main@14a28f2f`）：

- [第一步](2026-11-21-d5-work-plan-rules.md)有了规则；
- [第二步](2026-11-21-d5-plans-advance.md)有了 `delegation.plans`、`planSave`、`planConfirm`，以及确认后自动推进。

核对的事实：

- Agent 能用的工具全部来自共享工具表（C8，`aeroric_protocol::tools::AERORIC_TOOLS`）。表里每个工具都必须在触发评测集里有 3–5 条“该用”和“不该用”的题目，测试会检查。`todo_propose` 是同类先例：Agent 提议，用户在 Aeroric 里收下。
- Agent 的请求带上下文令牌，宿主用它认出是哪个任务（`context_tokens().resolve`）。被委派的子会话，任务记录上有 `delegateOf`。
- 进度页已经有“委派”一节（`DelegationPanelSection`）：
  - 列委派卡和原生子代理；
  - 点一行打开子会话；
  - 每次载入由 App 读 `delegation.list`。

## Decision

**新工具 `plan_propose`**（基础组，会改 Aeroric 自己的记录）：

- 参数是目标和单元：编号、标题、说明、依赖、工作区（只读、在当前目录写、在副本里写）、角色、验收条款。
- 工具说明写明：
  - 只存成草稿，用户在 Aeroric 里确认后才按依赖自动开委派；
  - 上限：8 个单元，同时 3 个，同一目录同时只有一个写者；不能有环；
  - 一两件事直接用 `delegate`。
- 宿主的 `context.planPropose`：
  - 用令牌认出父任务。被委派的子会话不能再拆计划，回“被委派的子会话不能再拆计划”；
  - 交给 `save_plan`：校验，存草稿，清掉提交者自己写的委派号之类字段，所以 Agent 没法自己确认；
  - 回答“已提议计划 …（N 个单元），等用户在 Aeroric 里确认后才开始”。
- 评测集加 3 条该用（多步、有依赖、要用户确认的拆分）和 3 条不该用（单件委派应该用 `delegate`、问进度应该用 `delegations`、直接改代码不用工具）。

**进度页“委派”一节：**

- 在委派卡上面，每个计划一组：
  - 标题是“计划 · 目标”，没确认的后面加“（待你确认）”；
  - 每个单元一行：“名字 · 状态 · 原因（依赖 …）”，原因就是第一步规则给的那一句；
  - 失败、停止或输入过期的单元标警示色；
  - 已经开了委派的单元，点开进入它的子会话；
  - 没确认的计划下面有“确认计划，开始”，悬停写明同时最多 3 个、同一目录同时只有一个写者。
- App 载入委派时先读计划，再读委派卡。读计划会把该开的先开，这样刚开的单元能出现在随后读到的卡里。
- 确认后刷新工作区和这一节。

**文字**在 `WorkPlanText`，模型是 `LiveWorkPlan`、`LiveWorkUnit`，客户端是 `SessionsClient.workPlans`、`confirmWorkPlan`。

## Alternatives considered

**单独做一个看板页，用图画出依赖。** 最强的理由是方案写了“在看板上拆”，依赖关系画成图更直观。没选：

- 计划最多 8 个单元，每行写出依赖，在“委派”一节里已经能看清；
- 计划的单元就是委派，放在委派一节，用户不用在两个地方之间对照；
- 画图要的是一套新的布局组件，等真有大计划时再说。

**Agent 提议的计划直接生效。** 没选：方案第 8 条明确要求用户确认后才生效。这也防止“无界的 Agent 群”：开多少子会话，由用户点头。

**在 App 里让用户自己逐个添加单元。** 最强的理由是方案说“计划由用户创建或确认”。没选，这一步不做：

- 创建计划最自然的方式，是在会话里说一句“拆成计划”，由 Agent 起草；
- 宿主的 `delegation.planSave` 已经能存用户写的计划，编辑表单留到确有需要时。

## Consequences

- **收益：** D5 能在 App 里走完：Agent 起草，用户在进度页看到每个单元和它的依赖，确认后自动按依赖开委派，每个单元一句话说明为什么在等。
- **代价：**
  - 共享工具表多一个工具，所有 Harness 的工具清单都会多一项；
  - 评测集多 6 条题目。
- **局限：**
  - App 里不能编辑、删除计划，也不能单独重开某个单元；
  - 输入过期只标颜色，没有“重做”按钮；
  - 依赖只用文字写出来，没有画成图；
  - 开场白里的工具用途没有提到 `plan_propose`，Agent 靠工具说明知道它；
  - 真实 Harness 会不会在该用时用这个工具，NOT RUN。
- **验证：**
  - 宿主：计划接口测试延伸。经上下文令牌提议计划，结果是没确认的草稿，列出时多一个计划；令牌无效时拒绝。
  - 命令行：
    - 工具清单测试加上 `plan_propose`；
    - 评测集覆盖测试照常通过（表里每个工具都有题），命令行 26 个测试全部通过。
  - core：工具目录、OMP 受管目录放行的工具数，都按共享表计算，照常通过。
  - Swift：新增 `WorkPlanTests` 1 个，测试计划按“委派”一节的样子读出：
    - 标题，没确认的带“待你确认”；
    - 单元一行的写法：状态、原因、依赖；
    - 委派号；
    - 哪些要用户处理（输入过期）；
    - 图标、状态文字；
    - 确认后的标题；
    - 缺 id 的不解码。
- **待目检：** 已记进路线文档 §8 待目检清单。
