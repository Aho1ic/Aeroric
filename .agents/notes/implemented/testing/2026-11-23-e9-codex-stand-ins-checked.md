# Agent Note: E9 补一步：测试里扮演 Codex 的消息也按快照核对

Status: implemented

## Problem

[E9 第一步](2026-11-23-e9-codex-contract-check.md)只核对了驱动发给 Codex 的消息，另一个方向没管：Codex 发给驱动的通知和审批请求。

驱动测试里，这些消息由假 Codex（`fake::Peer` 的 `notify`、`request`）按测试作者的理解写出来。驱动按测试里的写法读字段，测试就过。但如果测试写的字段名或取值不是真实 Codex 发的，那驱动在真机上就读不到，测试照样通过。

先临时加了诊断，把 Codex 驱动、执行器、映射层（`map_notification`）测试里所有模拟消息都对照两份快照核对了一遍，有两点：
- 不合快照的，全是故意构造的健壮性用例：
  - 未知的结束状态 `paused`、`cancelled`、空串、数字、`null`；
  - 未知的条目类型 `hologram`、未知的协作工具 `somethingNew`；
  - 无关通知里随手写的字段 `x`。
- 其余模拟消息用的字段和取值都是真实 Codex 发的，没查出驱动读错字段。

## Decision

**假 Codex 的 `notify` 和 `request` 发出前，按每份快照核对：**
- **可以省略：** 必填字段可以不写。测试只写这个用例需要的字段。
- **不能写错：** 写出来的字段要是 Codex 真会发的，取值要在快照的范围内，方法要是 Codex 真会发的通知或请求。
- **核对方式：**
  - 校验器加了 `Fill::Partial`，这个模式下不报“必填没发”，其余规则和驱动发出方向一样，包括快照没列的字段算错；
  - 不合就当场失败，写明快照名、字段路径和原因。
- **故意发快照里没有的东西：** 例如“以后的 Codex 可能发一个驱动不认识的结束状态”，测试要改用 `notify_unlike_any_snapshot`，并在旁边写一句为什么。现在只有一处：子代理以 `paused` 结束。
- **映射层单元测试不接：** `map_tests` 直接调纯函数，不经过假 Codex。那里不合快照的都是有意的健壮性用例，挂上去只会逼着每处写豁免。

## Alternatives considered

**核对驱动实际读了哪些字段。** 做不到：驱动用 `serde_json::Value` 的 `pointer` / `get` 按需取字段，没有地方能收集“读过哪些路径”。核对模拟消息是能做到的近似：驱动测试里驱动能读到的字段，都来自这些模拟消息。

**模拟消息也要求写全必填字段。** 没选：要给几十个测试补上与用例无关的字段，测试变得难读，抓到的问题却不会更多。

## Consequences

- **收益：** 以后写驱动测试时，模拟 Codex 的消息如果用了 Codex 不发的字段或取值，当场失败。这样“按测试的理解读字段、真机上读不到”的问题会在写测试时暴露。
- **局限：**
  - 驱动读的字段如果没有任何测试给出，这道核对管不到；
  - 映射层单元测试不在核对内。
- **验证：**
  - core 新增 1 个校验器测试：
    - 省略必填的模拟消息不报错；
    - 不认识的结束状态、改名的字段、不存在的通知、不存在的审批请求，各报一条点名的错误。
  - MacBook 上：
    - Codex 驱动、模型目录、执行器的测试共 85 个，都过；
    - 变异验证：临时把一个测试里模拟的结束状态改成 `complete`，测试当场失败，写明 0.162.1 不发这个值，之后改回；
    - `cargo fmt --check` 过。
