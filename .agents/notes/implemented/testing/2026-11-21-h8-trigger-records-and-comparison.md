# Agent Note: H8 第一步：触发评测按 Harness 记录，描述修改出前后对比表

Status: implemented

## Problem

[各 Harness 原生融合](../../proposed/architecture/2026-11-16-harness-native-capabilities.md) H8 第 1 条：

- 触发评测要按 Harness 分别记录三样：触发率、第一次成功调用的时间、无关调用数；
- 改工具描述、技能描述、开场白用途说明之前和之后，各跑一次。

完成条件里与这一步有关的两条：评测集在仓库里；一次描述修改能产出前后对比表。

动手前（`main@55a946cd`）核对的事实：

- **评测集已在仓库里。** [C8 第三步](2026-11-20-c8-tool-trigger-eval.md)放了 `aeroric-cli/evals/tool-triggers.json`：21 个工具，127 条请求。
- **运行器和假 Harness 也有。** 运行器在 `tool_eval.rs`，只在测试里编译；假 Harness 是关键词匹配。
- **运行器的四个缺口：**
  - 报告只有一份汇总，不区分 Harness；
  - 每条请求只记第一次调用，不记之后的调用，所以算不出无关调用；
  - 不计时；
  - 两次运行之间没法对比，描述改没改也看不出来。
- **想试一个新描述，只能改代码。** 描述写在 `mcp_context.rs` 的工具表里。

## Decision

**一次运行存成一份记录**（`tool_eval.rs` 的 `Record`，JSON）：

- 内容：哪个 Harness、标签（如“改描述前”）、时间。
- 每个工具一行（`Row`）：
  - 应触发命中、误触发；
  - 无关调用：这个工具的题目里，调了题目不想要的工具几次，第一次之后的调用也算；
  - 第一次调到该用工具的平均用时：只算应触发的题，从发出请求开始计时。
- 每个工具描述的指纹（FNV-1a，16 位十六进制）：只用来看两次之间描述改没改，不存原文。

**`Harness` 接口改成返回一串调用**（按顺序，空的表示不调用）：

- 第一次调用仍是“选中的工具”，命中和完全一致照旧按它算；
- 之后的每次调用也真的发给服务器，并计入无关调用和用时。
- 假 Harness 最多调一次，行为不变。

**两种表：**

- **`compare(before, after)`：同一 Harness 的前后对比表。**
  - 只列描述改了、或任一计数变了的工具，最后一行是合计；
  - “描述”一列写“改了”，标出哪个工具是这次改的，其余变化就是它带来的连锁反应；
  - 两份记录来自不同的 Harness 时拒绝对比。
- **`by_harness(records)`：几家并排的触发率表。** 每个工具一行，每个 Harness 一列，写命中和误触发；没跑的那家写“—”。

**`with_descriptions`：先替换描述再跑。** 新描述不用先写进代码，在评测里替换后跑一次，和基线对比，满意了再改代码。

**用假 Harness 跑出的一次对比**（2026-11-21，测试输出）：

- 把 `board_write` 的描述换成它三条应触发请求的原话。
- 它的命中从 0/3 升到 3/3。
- 但 `board_read` 的命中从 2/3 跌到 0/3，三条全被 `board_write` 抢走。
- 合计命中只从 44/64 升到 45/64，误触发不变。

这正是对比表要暴露的：改一个工具的描述，会抢走相邻工具的题。基线 44/64 比 C8 记的 45/64 少 1，原因是 C8 之后工具描述又改过。

## Alternatives considered

**记录里存描述原文，不存指纹。** 最强的理由是对比时能直接看到改了什么字。没选：描述的历史在 git 里已经有，记录只需要回答“这次改没改”；存原文会让记录文件随描述一起变长，对比表也挤不下。

**把运行器搬出测试，做成 `aeroric-cli eval` 子命令。** 最强的理由是真跑时不用编译测试。没选，至少这一步不做：
- 真实 Harness 的评测还没有授权之外的计划（方案 §8 第 7 问只授权了一次小规模的）；
- 假 Harness 在测试里跑就够了。
等接真实 Harness 时，再按需要决定出口。

**只算“第一次调用对不对”，不记之后的调用。** 最强的理由是简单，C8 就是这么做的。没选：
- 方案要的“无关调用数”，只看第一次是算不出来的；
- 一个模型先调错、再调对，这和“没调对”是两回事。

## Consequences

- **收益：**
  - 改任何一个工具描述前，可以先替换、跑一次、看对比表，连锁影响一目了然；
  - 每家 Harness 的记录格式相同，接上真实 Harness 后能直接并排比较。
- **代价：** `Harness` 接口从返回一个工具改成返回一串，C8 的测试跟着改了写法，数字不变。
- **局限：**
  - 评测集只覆盖 Aeroric 的工具。技能描述和开场白用途说明还没有题目，方案说的“每种能力”目前只做到工具这一类；
  - 记录只在测试里生成，没有存进数据目录，设置里也看不到，展示放在后面一步；
  - 假 Harness 的用时只是本地管道往返，没有意义；真实 Harness 的用时才说明问题。
- **验证：** 命令行的评测测试从 3 个增加到 6 个，全部通过：
  - 一次描述修改产出前后对比表：表里标出改了的工具，没变的工具不出现，合计在最后；记录经过 JSON 来回读写后不变；
  - 多次调用的运行：每次调用都发出，该用的那次计时，其余算无关调用，状态取第一次调用的；
  - 不同 Harness 的记录拒绝对比，并排表里没跑的那家写“—”；
  - 原有的报告计数测试加上了无关调用和平均用时。
- **NOT RUN：** 真实 Harness 的评测。按方案 §8 第 7 问，Claude、Codex、OMP 各一轮的小规模评测已经授权，但这次没有跑；需要的条件同 C8 笔记。
