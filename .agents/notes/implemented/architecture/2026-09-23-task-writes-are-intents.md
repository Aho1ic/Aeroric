# Agent Note: 任务写入是交给 core 的具名意图，失败即无副作用

Status: implemented

## Problem

旧桌面端的保存队列合并的是整个项目的任务数组快照，界面先乐观地当成功、落盘失败再字段级回滚。只要还有任何一处发整表快照，"一份陈旧快照抹掉别人刚写进去的行"的窗口就不会关闭；字段级回滚还会把期间迟到 hook 写进来的值一并抹掉。被拒写、崩溃截断后的续跑也需要明确规则。

## Decision

- **core 不做乐观写**：每次变更是 `load → 改 → commit`，commit 要么整份写下、要么因基线不符根本没写（见 [写入基线](2026-09-22-content-fingerprint-write-cover.md)）。`switch_config`、`start`、`resume` 的失败路径只做三件事：释放认领、把运行号还给计数器、把错误交回调用者——不写任务文件、不起进程、不推进 revision。
- **交给 core 的是意图，不是快照**：`TaskIntent`（`core/crates/aeroric-core/src/tasks/service.rs`）每一类落盘写都有自己的具名意图，不引入通用 `PatchFields` + 字段白名单。读-改-写与互斥规则在 core 的权威快照上执行。
  - 建行与删行都是意图（`Create` / `Delete`）；`Delete` 删空时保留"删空 ⇒ 删 `tasks.json`"的语义。
  - 一次复合写是一条原子意图（`SwitchConfig` / `ResumeWithSession`），不拆成按序投递的小意图。
  - 意图不重写未点名的字段，所以宿主无法再抹掉它不知道的键（如 `launchFamily`、`resumeFamily`）。
  - 客户端的乐观视图由客户端自己回滚，配合 core 返回的权威快照与 revision 对账。
- **冲突重试按 op 分两类**：元数据类（重命名、pin、star、归档）在 `REVISION_CONFLICT` 时自动重载并重放**一次**，第二次失败不再重放；状态机类（`start`、`resume`、`complete`、`cancel`、`switch_config` 等可能起进程的）不自动重放，直接报错并刷新权威快照。冲突文案表达"有别人也改了这份数据"，不是"磁盘写入失败"。
- **被截断的运行需要确认**：崩溃对账把未决 start/resume 改为 `interrupted` 并留下确认条目，不重新 spawn。确认前只挡 `resume`（`TaskError::AwaitingAcknowledgement`），`start`、`cancel`、`complete`、改配置、删除照常；`start` 本身即确认并清掉条目，删除任务一并清掉条目。
- 远程通道装不下的载荷（附件、worktree）在服务层任何副作用之前被拒，而不只在表单里挡。

## Alternatives considered

- **继续发快照，冲突时把本地未落盘编辑字段级重放到权威快照上**：兼容旧客户端。否掉是因为需要一套任务记录的三方合并，而 core 的设计目标正是让它不必要。
- **状态变迁走意图、纯元数据走快照的混合方案**：迁移成本低。否掉是因为"这个字段谁能写"会变成逐字段记账的长期负担，迁移期最容易出"一半新一半旧"的 bug。
- **一条通用 patch 意图覆盖所有元数据写**：实现量省一半。否掉是因为宿主仍在表达"我以为这行长这样"，漂移依旧，只是从整表缩到若干字段。
- **全部意图冲突时都自动重放一次**：operation key 能保证不多起进程。否掉是因为用户明确要求起进程的操作永不自动再来一次。
- **全部只报错不重放**：最简单。否掉是因为"归档"这种毫无歧义的意图会因一次无关的旁路写而丢失。
- **对账后直接允许续跑**：少一次交互。否掉是因为没有任何交互说明上一次是被截断的。

## Consequences

- **收益**："失败后能回滚"变成更强的"失败时不曾发生"；陈旧快照覆盖别人的行在结构上不可能发生。
- **代价与已知上限**：意图词汇表需要覆盖全部写点，新增一类写就要新增一个意图；失去防抖后的去重只能靠 operation key，调用方给不出能表达身份的 key 时是已知弱点。
