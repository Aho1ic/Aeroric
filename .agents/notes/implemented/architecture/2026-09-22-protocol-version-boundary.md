# Agent Note: 本地协议主版本严格相等，relay 是独立版本空间

Status: implemented

## Problem

本地每帧带 `v: 1`，握手报出 `HostCapabilities`。若照"协商版本交集"字面实现，就要在只有一个版本时为不存在的 v2 写区间协商与降级路径，这部分代码永远测不到；而远程 relay 协议与本地协议的版本关系从未定义。

## Decision

- 本地主版本必须严格相等：`handshake_allows_peer(version) == (version == PROTOCOL_VERSION)`，Rust/TS/Swift 各一份实现；`envelope.schema.json` 的 `versionPolicy` 由该函数算出。不等即在握手期拒绝并给原因，不降级成半条连接。
- v1 内部的兼容性一律由具名能力承载，绝不由版本号推断（与"客户端不拿自己的 OS 推断宿主能力"是同一条纪律）。新增可选字段 + 能力位不 bump 主版本。
- 引入 v2 是设计决定，必须先写 Note：方法名、topic 名、枚举拼法都会被冻结。
- 远程 relay（`remote-protocol/`）与本地协议是两个独立版本空间；桥接层必须显式声明它映射的版本对，未映射的组合显式拒绝。

## Alternatives considered

- **现在就实现区间协商**：未来升级更平滑。否掉是因为协商逻辑无法用真数据验证，一旦有 bug 最先受害的是唯一真实存在的 v1↔v1 路径。
- **只拒绝不等、不定义远程映射**：更省事。否掉是因为把"远程怎么对齐"留给以后偷偷决定，届时改的就是协议本身。

## Consequences

- **收益**：握手判定只有一种结果，兼容性问题都落到可检查的能力位上。
- **代价与已知上限**：任何主版本变化都要求宿主与所有客户端同时升级；若出现必须新旧客户端并存的场景，需要新 Note 重新评估。
