# Agent Note: core 是任务事件的唯一权威，迟到观察由 core 规则丢弃

Status: implemented

## Problem

任务状态与会话事件曾由宿主各处的发射点直接发出（实测 28 处，而非文档里写的 8 处）。只要存在两个发射者，就会有双事件或事件回环；core 自己决定的变更（崩溃对账、幂等重试、被基线拒绝的写）旧发射点无从得知。转录 watcher、hook、退出边带来的"迟到观察"是否该让用户看见，也只在少数几个发射点局部判断。

## Decision

- 任务状态与任务会话事件**只由 core 发射**：宿主不得在 core 之外补 `.emit`。
- 迟到观察丢弃是 core 的一条规则：来自运行时观察（转录 watcher / hook / 协议事件 / 退出边）的状态变更，若该任务在本进程已无存活代，则丢弃（`EventOutcome::Dropped`），不改记录也不发事件。判据是"任意存活代"，不是"这一代还活着吗"。
- 存活代是问出来的：core 定义 `LiveRuns` 端口（`has_live_run(task_id)`），由持有进程句柄的宿主注册表实现；core 侧默认 `NoLiveRuns`（恒 false）供无进程场景与单测。准入判据是 core 自己在飞的认领（`open_claims`）与宿主报告的存活代之并。端口实现不得回调 core，持锁期间不取别的锁。
- 观察分"决策"与"提交"两段：事件权威永远是 core；数据权威只在持有写者租约时才落盘。一条被准入的观察必须发事件，即使 `changed == false`；只有 `Dropped` 才不发。
- 禁止"先收下、等能写了再补发"的补发队列——那是第二个事件权威。
- 原始 PTY 字节流不进 core 事件通道。

## Alternatives considered

- **旧发射点保持唯一发射者，core 事件只喂新客户端**：改动最小。否掉是因为 core 自己做出的变更旧发射点不知道，要么漏事件，要么让执行器回头调命令包装层。
- **两边都发，客户端按 (generation, revision) 幂等收敛**：最省事。否掉是因为它把要防的东西变成长期机制，之后每个新事件都会先想到去重而不是找出发射者该是谁。
- **core 内镜像一份存活状态**：不需要端口。否掉是因为进程句柄在谁手里，存活事实就归谁；复制一份必然漂移。

## Consequences

- **收益**：事件归属可机械检查；所有观察来源自动受同一道迟到保护。
- **代价与已知上限**：core 决策时同步调用宿主实现的端口，锁序必须守住叶子锁约束；core 可能"知道"一个它没有写下的状态（非写者实例），这种磁盘与事件的短暂分歧不被掩盖。
