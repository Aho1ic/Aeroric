# Agent Note: 2026-11-22 四份目检报告查出的问题

Status: implemented

## Problem

2026-11-22 用四份提示词让 Codex 的 Computer Use 目检了整张待目检清单。报告在 `~/Documents/computer-use/` 下：

- `2026-11-22-1258-aeroric-review-1122-sessions`
- `-1421-…-review`
- `-1355-…-settings`
- `-1331-…-memory-dsh-omp`

查出 8 处要修。每处修之前都先找到了原因，核对用的是宿主 RPC、只读查看数据目录和会话文件，没有动鼠标。

1. **Aeroric 项目的 Wiki 打不开。** 报“读取 Wiki 失败：reply too large for one frame: encoded frame is 3711011 B, over the 1048576 B limit”。
   - 用 `aeroric-cli rpc` 逐个量回复：`wiki.pages` 57 KB，`wiki.page index` 36 KB，`wiki.revisions index` 3.78 MB。
   - 原因：每条修订都带着整页正文。这个项目有 291 页，索引页 36 KB，改了上百次。
   - App 只用修订的编号、原因和时间，回退按编号做。
2. **`@` 引用写“（无标题）”。** E12 第二步的引用块读任务记录的 `title`，但任务记录里没有这个字段。标题在 `name` 里，没有时用 prompt，`read_session` 用的 `context_title` 就是这样取的。
3. **归档的经验找不到“恢复”。** 记忆页菜单按种类分支：经验和会话线索那一支只处理“生效中”，归档后什么都不给；“恢复”只写在另一支里。
4. **能力包里的 MCP 服务器没起来，也没有 E15 的提示。** 原因有两个：
   - Codex 在 `thread/start` 期间就启动会话的 MCP 服务器，`mcpServer/startupStatus/updated` 带着新线程的 id。几个会话共用一个 Codex 进程，连接按线程 id 把通知分给各自的会话；会话要等 `thread/start` 回复后才登记它的线程，所以这些状态先到、没人认领，被丢掉了。即使送到驱动，驱动这时也还没记下线程 id，`child_of` 会把它当成子代理线程的消息。E15 第一步的测试是在线程 id 已知之后才发通知，所以没测出来。
   - 会话信息的“工具”本来就不显示能力包：宿主记了每次启动的能力包去向（`tools.packs`），App 没有读。所以“工具里没有它”不能说明它没被下发。
5. **DSH 会话重开后看不到“Aeroric 附加的上下文”。** 没找到代码上的毛病：
   - DSH 自己的会话文件第一条用户消息以信封开头；
   - 宿主 `session.history` 返回的第一条消息也以信封开头；
   - 会话页画历史用的气泡就是会拆信封的那个。

   这一处不改代码，记为待目检复核：用辅助功能找 `session.attached-context`。
6. **计划单元一律按只读委派开出。** `plan_propose` 的单元 `workspace` 默认只读，Codex 提议时没填，要写文件的单元于是什么也写不了。界面上确认前看不出哪个单元是只读的。
7. **B2 的“这一轮没有文件变化，只跑了验收里的命令检查”没出现。** 这句说明挂在会话页的检查行上，检查行只来自实时更新。没改文件的回合不会记进回合账本，所以检查跑完之后才打开的页面（这次的子会话就是）根本没有检查行。
8. **撤销一轮后，交付物要切走再回来才变成第 2 版。** 交付物只在选中任务、读进度面板时读一次，撤销后没有重读。

## Decision

1. **Wiki 修订列表不带正文。** `wiki.revisions` 只返回 `slug`、`n`、`reason`、`atMs`。宿主测试断言列表里没有 `markdown`。
2. **引用块的标题用 `context_title`。** 宿主测试断言引用块写成“- 写文档（taskId: task-2）”。
3. **“恢复”不分种类。** 只要是已归档的条目就给，判断写成 `MemoryText.restorable`。
4. **两处都改：**
   - 共用的 Codex 连接把没人认领的 MCP 启动状态按线程先留着（每个线程最多 32 条、最多 16 个线程），那个线程一登记就交过去；其他没人认领的消息照旧不留；
   - Codex 驱动在分流到子线程之前，先处理 MCP 启动状态。线程 id 还不知道时，或者状态属于本线程时，交给 E15 的计时和提示；属于已知子线程的，不算会话的；
   - App 读出 `tools.packs`，会话信息的“工具”展开后多一段“能力包”，逐项写“MCP 服务器 名字 · 已写进…”或“没有：原因”。
5. **不改代码**，复核方法记进待目检清单。
6. **单元能不能写，说清楚、看得见：**
   - `plan_propose` 的说明写明：每个单元默认只读，要建、改文件的单元必须填 `shared` 或 `copy`；
   - 计划里每个单元的行写出“只读 / 在当前目录写 / 在副本里写”，确认前就能看到。
7. **检查器记下每个任务最近一次检查。** 记的是发布出去的那条更新，记录和写日志在同一把锁里。宿主新增 `session.autoCheck.last`，会话页在打开和重新同步时，若还没有实时的检查行，就用它补上。
8. **会话的回合记录一变（撤销会变），任务页就重读交付物。**

**提示词写错、属于设计如此的**，不改：

- 新会话页没有 `@`；
- 同一轮新建的文件撤销时被归为“之后又改过”；
- 两家 Harness 重跑的技能不同；
- rust-clippy #1 不是 PR；
- DSH 的 `ls` 免审批；
- 宿主日志不在系统日志里。

这些写进了路线文档的待目检清单。

## Alternatives considered

**Wiki 修订列表分页，正文照带。** 没选：App 不用正文，带着只是浪费；分页也挡不住单条修订本身很大的页面。

**计划单元按验收条款猜要不要写，自动改成 `shared`。** 没选：

- 猜错了会让只读的调研单元能写项目；
- 同一目录同时只能有一个会写的单元，猜错还会让计划卡住。

把默认值说清楚、在确认前摆出来，由 Agent 和用户决定。

**检查结果改成在会话状态快照（`session.state`）里带回来。** 没选：`SessionState` 是契约里的类型，要重新生成契约文档。一个独立的方法就够了，改动不跨契约。

## Consequences

- **收益：**
  - 大 Wiki 能打开；
  - 引用写对标题；
  - 归档的经验能恢复；
  - Codex 会话里没起来的能力包服务器会被说出来；
  - 能看到每次启动的能力包去向，以及计划单元能不能写；
  - 只跑命令的检查结果事后也看得到；
  - 撤销后交付物立刻对。
- **代价：** 检查器在内存里为每个任务多存一条更新。
- **局限：**
  - Claude 会话里能力包服务器没起来时，为什么没有提示，没有查清：Claude 的 init 可能还报 `pending`，要真实二进制核对（NOT RUN）；
  - DSH 附加上下文那一处只能复核；
  - 宿主重启后，最近一次检查就没有了（只存在内存里）；
  - 都还没有重新目检。
- **验证：**
  - 宿主测试延伸 3 处：修订列表不带正文、引用块的标题、最近检查在没跑过时为空；
  - core 新增 1 个：Codex 在 `thread/start` 回复之前发来的失败状态，经共用连接留住、登记后交给会话，出一条提示，子线程的不算（第一次全量验证里这个测试没过，查出是连接层丢的，才补了留住这一步）；另延伸 1 处：只跑命令的检查被记为最近一次；
  - Swift 新增 3 个：归档条目可恢复、启动的能力包项、打开前跑过的检查连同说明一起恢复；改了 1 个：计划单元行带上能不能写。
  - 全量验证结果见路线文档。
