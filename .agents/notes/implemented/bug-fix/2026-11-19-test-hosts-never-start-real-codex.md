# Agent Note: 测试宿主不再启动真实 Codex 读额度

Status: implemented

## Problem

2026-11-19 跑全量验证时，工作区测试一开始就失败，报"找不到合法的编译元数据"和"删除编译产物不被允许"。排查结果：

- 当天 08:50 的一次 `cargo test --workspace` 卡在 `lsp_session_services`，已经挂了 13 个半小时。它和新一轮编译同时写同一个 `target` 目录，互相把编译产物弄坏了。
- 卡住的测试进程下面，挂着一个 19:13 启动的真实 `codex app-server`，用的是用户本人的 Codex 登录。

真实 Codex 来自[额度节奏](../feature/2026-11-10-quota-pace.md)加的额度采样线程：

- 每 10 分钟启动一次 `codex app-server`，读取订阅额度并存成读数。
- 它在 `register_usage_services` 里无条件启动，只靠 `#[cfg(not(test))]` 拦住测试。
- 但 `cfg(test)` 只在编译 crate 自己的单元测试时成立。`tests/` 下的集成测试链接的是普通编译的库，这个条件拦不住。所以每个集成测试里的宿主，只要本机装了 `codex`，都会启动采样线程。
- 平时一个测试几分钟就结束，赶不上第一次采样（启动后先等 10 分钟），所以一直没暴露；卡住的测试才每 10 分钟去读一次真实账号。

这违反了"测试只用隔离数据和假 Agent，不碰真实 Agent 的家目录和凭据"的约定。

## Decision

**由宿主的装配参数决定是否采样**：

- `HostWiring` 新增 `quota_sampler`，默认关。
- `register_usage_services` 多一个参数，只有它为真时才启动采样线程，去掉原来的 `#[cfg(not(test))]`。
- 只有正式宿主 `aeroric-cli serve` 打开它。这与 `keep_awake` 的做法一致：只有 `serve` 给真实的 `caffeinate`，测试给假的或不给。
- 新增 `quota_sampler_requested()`：本进程里有没有宿主要求过启动采样，不管本机装没装 `codex`。

**顺带复核**：

- 宿主和 core 里另外两处 `cfg(not(test))`，一处是停止会话的等待时长，一处是故障注入点，都不触发真实副作用。
- 按需读取额度的接口（`usage.quotaPace`、`usage.read_usage_snapshot`）以及会话里按额度调度的读取：前两者只在被调用时才读，测试没有调用；后者原本就只在正式宿主里才会启动 Codex。

**没有处理**：`lsp_session_services` 为什么会卡住 13 个小时，这次没有查到原因，也没能复现。卡住的是四个用例各自的假 LSP 进程。

## Alternatives considered

**照抄会话服务的做法：看当前可执行文件是不是叫 `aeroric-cli`。** 最强的理由是不用改装配参数，所有构造宿主的地方自动正确。没选：判断藏在实现里，测试无法直接控制，也说不清"为什么这个宿主会启动真实 Codex"；装配参数写在 `serve` 的组装代码里，一眼能看到，测试的默认值天然是关。

**在测试里把 `PATH` 里的 `codex` 藏起来。** 最强的理由是不改产品代码。没选：要靠每个测试自觉设置，新测试一忘就会再漏；而且改 `PATH` 是整个进程共享的，会影响同一个测试进程里的其他用例。

## Consequences

- **收益**：
  - 集成测试里的宿主不会再启动真实 Codex、读取用户的订阅额度；
  - 测试卡住时，也不会每 10 分钟碰一次真实账号。
- **代价**：多一个装配参数。以后如果新增正式宿主的组装方式，需要记得打开它；忘了的话只是额度节奏少了后台读数，不会碰到不该碰的东西。
- **验证**：
  - `maintenance_services` 集成测试新增断言：默认装配下 `quota_sampler` 为关，这个测试进程里没有任何宿主要求过启动采样线程。改动之前，集成测试宿主会无条件调用采样启动，这条断言会失败。
  - `aeroric-cli` 编译通过，`serve` 的装配里打开了采样。正式宿主实际启动了采样，需要在 App 里目检额度节奏页仍有后台读数，记在路线文档 §8。
