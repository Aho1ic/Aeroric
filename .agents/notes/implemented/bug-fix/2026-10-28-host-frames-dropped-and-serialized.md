# Agent Note: 宿主丢掉了连发的请求帧，且逐个串行处理

Status: implemented

## Problem

每次发版后侧栏的项目和任务都是空的，要等很久，或者重新添加项目才出现。实时会话页偶尔提示“连接中断”。App 日志显示：启动后第一次 `project.list` 等满 30 秒超时（`timedOut`），3 秒后的重试却立即成功。

原因有两层：

1. `codec::read_frame` 每次从 socket 读 4 KiB，找到第一个换行就解码返回。**同一块里换行之后的字节被直接丢弃。** App 启动时在同一条连接上一口气发出 `project.list`、`task.list`、导入状态、SSH 探测等多个请求，后面的请求帧经常和前一帧落在同一块里，于是整条消失，App 只能等满 30 秒超时。
2. `serve_connection` 读一帧、处理完、写回，才读下一帧。一个慢请求（联网的 Agent 版本检查、SSH 探测、导入扫描）会挡住同一连接上排在后面的所有请求。

以前没人发现，是因为测试和 CLI 都是一问一答，从不连发；而那个“帧后多写了一个换行”的旧测试，多出的空行恰好也被这个 bug 吞掉了。

## Decision

- `read_frame` 改用 `BufReader::fill_buf` / `consume`，只消耗到本帧的换行为止，其后的字节留给下一帧。1 MiB 上限与“见不到换行即断流”的规则不变。
- `serve_connection` 改为并发处理：握手仍在读循环里串行处理，认证前不分发任何别的请求；其余请求各起一个任务，每条连接最多 64 个同时在处理；响应经单一写任务按完成顺序写回，客户端本来就按 id 配对。
- 新增回归测试：一次写入三帧，三帧都能读到；同一连接上先发慢请求再发快请求，快请求先拿到回复。
- App 的项目列表读取失败时每 3 秒重试，最多 20 次，并用公开可读的 `Logger` 记录。NSLog 的内容会被系统日志脱敏，这次排查就卡在这里。

## Alternatives considered

- **只把客户端超时调长**：丢掉的帧永远不会有回复，等多久都没用。否掉。
- **客户端串行发请求**：能绕开丢帧，但慢请求照样挡住快请求，启动也会变慢。否掉。
- **每类请求单开一条连接**：连接数与握手翻倍，而根因在服务端读帧。否掉。

## Consequences

- **收益**：
  - 发版或重启后侧栏立即出现项目；
  - 会话页轮询不再排在慢请求后面；
  - 所有经 UDS 的客户端都受益。
- **代价与已知上限**：
  - 同一连接上的请求不再保证按发送顺序执行。依赖顺序的调用方必须等上一个回复再发下一个（App 现有调用都是如此）；
  - 一条连接最多 64 个并发请求，超出的会在读循环里等待。
