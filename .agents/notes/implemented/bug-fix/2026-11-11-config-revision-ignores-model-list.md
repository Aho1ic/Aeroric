# Agent Note: 配置版本号不再随 Codex 远端模型目录变化

Status: implemented

## Problem

新建会话时，App 带着当时拿到的配置版本号提交；宿主重新算一次，对不上就拒绝，提示"Agent 配置版本已变化，请明确重新选择。"（`settings/session_catalog.rs` 的 `validate`）。这样设计，是为了在设置改动后让已选的配置作废，而不是偷偷换成新的。

但版本号是对一整组输入做的哈希，所有配置共用，其中包括内置 Codex 的模型目录。这份目录缓存 10 分钟，过期后重新问 Codex 要，内容可能在用户什么都没改的情况下变化。[R4-3 评测](../testing/2026-11-10-wiki-agent-eval.md)的 W3 里，Q2 提交那一刻缓存正好过期，宿主日志里同一秒启动了 Codex app-server 去取目录，草稿随即被拒。11 分钟后再取，版本号又稳定了。

## Decision

- 版本哈希只包含用户能控制的内容：设置、连接、迁移记录、项目 id 和路径，以及内置 Claude 是否可用。不再包含内置 Codex 的模型目录。
- 目录变化仍由各自的检查兜住：
  - 选的模型已经不在列表里：报"请明确选择此配置支持的模型。"；
  - Codex 取不到模型列表：配置带着原因被标为不可用。

## Alternatives considered

- **每个配置各算一个版本号**：别的配置变化不会连累当前草稿。没选：草稿选的正是内置 Codex，它自己的模型列表变了，照样会作废；问题出在把远端列表算进版本号，与版本号算到哪个粒度无关。
- **App 在提交前自动重新拉一次目录**：用户无感。没选：这等于静默接受变化，违背了"设置变了要用户明确重选"的本意；而且对用户真正改过的设置也会失效。

## Consequences

- **收益**：模型目录短暂抖动不再让草稿作废；用户改了设置或连接，仍然要明确重选。
- **代价**：模型目录里加了新模型、调了顺序，或者改了推理强度列表，都不会再让草稿作废。选中的模型还在、推理强度也还支持时，提交照常通过。
- **验证**：
  - 单测 `a_codex_model_list_refresh_keeps_the_draft_unless_its_model_left`：列表从 `a, b` 变成 `b, c`，选了 `b` 的草稿照常通过；变成只剩 `c` 时，只报模型不在列表里。先在修复前的代码上确认它会以"Agent 配置版本已变化"失败。
  - settings 测试 181 个、tasks 测试 101 个、host 全部集成测试都通过。
  - 实测：R4-3 W3b 连续新建 7 个会话，都没再出现这个报错。
