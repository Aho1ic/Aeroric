# Agent Note: 2026-11-22 第二轮目检查出的两处问题

Status: implemented

## Problem

2026-11-22 第二轮目检有两份报告：`~/Documents/computer-use/2026-11-22-1804-aeroric-review-1122b-fixes` 和 `2026-11-22-1857-aeroric-review-1122b-configs`。逐项核对时用了截图、宿主日志、Codex 日志和宿主 RPC。其中两处是代码的问题。

1. **能力包里有坏掉的 MCP 服务器时，DSH 会话建不起来。**
   - 界面和宿主日志里只有“DSH 新建会话失败：Internal error (-32603)”，DSH 的 stderr 里没有别的内容。
   - 时间对得上：DSH 在 18:27 失败，测试能力包 cu-broken-mcp（命令不存在）那时还开着，18:47 才停用。
   - ACP 驱动在 `session/new`（以及 `session/resume`）里把 Aeroric 工具和能力包的服务器一起交给 Agent。DSH 起不来其中一个，就拒绝了整个会话。同一份能力包在 Claude 那边只是“没连上”一条提示，会话照样能用。
2. **待办页的检查输出被截断后，只在输出里写“（前面已截断）”。**
   - 会话页的检查行有 `incomplete` 标记，标题末尾写“（结果可能不完整）”。
   - 待办的检查记录（`CheckRun`）只有状态和输出，待办页的“检查没过”胶囊看不出结果只看了一部分。

其他没过的项都不是代码的问题，记进了路线文档：

- 提示词写错了：`@` 在新会话页试的；审查和计划确认要切到辅助面板的“进度”标签；缺字段的结构被 Agent 用 `null` 填上，按 JSON Schema 本来就合格。
- Codex 会话里坏掉的能力包 MCP 服务器仍然没有提示。Codex 日志显示它在每一轮开始时刷新 MCP 运行时，那个服务器的失败只在进程关闭时记了一条警告。它有没有发 `mcpServer/startupStatus/updated`，要用真实二进制核对（NOT RUN），这次不改。

## Decision

**ACP：带着能力包的服务器打开会话失败时，去掉它们再试一次，并说出来。**

- 第一次 `session/new` 或 `session/resume` 返回错误，并且这次带了能力包的服务器时，只带 Aeroric 自己的 Context 服务器再请求一次。
- 第二次成功：会话照常打开，转写里出一条红色提示。提示写明：
  - 没带上的服务器名字；
  - 是新建还是恢复会话时失败；
  - Agent 的错误原文；
  - 去“Agent 配置 → 能力包”检查这些服务器的命令。
- 第二次仍然失败，或者这次本来就没带能力包：照旧按握手失败处理，报原来的错误。超时和被停止不重试。
- 重连时会重新带上能力包的服务器，所以修好的服务器下次会话就能用上。

**待办页：截断的检查写“（结果可能不完整）”。**

- 待办的检查输出由 core 的 `schedule::check` 截取：保留开头时末尾写“…（已截断）”，保留结尾时开头写“…（前面已截断）”。
- App 看到这两个记号，就在“检查通过 / 检查没过”后面加“（结果可能不完整）”，和会话页的检查行一样。

## Alternatives considered

**去掉服务器后不重试，直接报错并写明可能是能力包的原因。** 没选：会话仍然打不开。坏掉的一个服务器不该让整个会话用不了，Claude 那边也是照常打开。

**逐个去掉能力包的服务器，找出是哪一个。** 没选：

- 每试一次就要多一次握手；
- 有的 Agent 拒绝时不说是哪个服务器；
- 一次去掉全部，再把它们全列出来，已经够用户去查。

**给 `CheckRun` 加一个 `truncated` 字段。** 没选：要动协议和 core 两处的存档格式。截断的记号本来就写在输出里，App 照着认就行。代价是记号的写法变了，App 也要一起改；记号定在 `schedule/check.rs`，测试里写着。

## Consequences

- **收益：**
  - DSH 等 ACP Agent 遇到坏掉的能力包服务器，会话照样能用，用户知道是哪几个服务器、错误是什么；
  - 待办页能看出检查结果只看了一部分输出。
- **代价：** 带能力包被拒时，握手多一次请求。
- **局限：**
  - 真实的 DSH 有没有因为这个才拒绝，只能从时间上推断，没有用真实二进制复现（NOT RUN）；
  - 如果 Agent 是因为别的原因拒绝，第二次也会失败，报的仍是第二次的错误。提示里不会说第一次带了能力包，宿主日志里有握手的每一步；
  - Codex 的启动失败提示仍待真实二进制核对；
  - 都还没重新目检。
- **验证：**
  - core 新增 2 个测试：带能力包被拒后不带它们再开、会话打开并出一条提示；没带能力包时被拒，不重试，直接失败；
  - Swift 延伸 1 处：两种截断记号都让胶囊写“（结果可能不完整）”；
  - 全量验证结果见路线文档。
