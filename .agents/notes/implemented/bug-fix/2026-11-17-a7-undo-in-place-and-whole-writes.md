# Agent Note: A7 撤销时已是目标内容的不算冲突，写回不留半截文件

Status: implemented

## Problem

[批次 A](./2026-11-15-adoption-a-truthful-state.md) 的 A7。2026-11-17 在 `main@9603b442` 加未提交的 A3–A6 等改动上复核 `core/crates/aeroric-core/src/sessions/live/turn_ledger.rs`：

- **已是目标内容也报"又改过"。** `planned` 对每个文件只问一件事：当前内容是不是这一轮留下的样子（撤回撤销时是"撤销后的样子"）。是就写回，不是一律跳过，原因写"这一轮之后又改过"。用户手动改回去的文件、上一次撤销已经写好的文件，都被当成冲突跳过。
- **撤销做到一半就卡住。** `apply` 逐个写文件，遇到第一个失败就用 `?` 返回错误：
  - 前面已经写好的文件留在新内容上；
  - 后面的文件没写；
  - 回合状态没变，Agent 也没收到提醒。
  
  用户再点一次撤销，已经写好的那些文件不再是"这一轮留下的样子"，全部被跳过。
- **写回会留下半截文件。** `write_back` 用 `std::fs::write` 原地覆盖：写到一半被打断（磁盘满、进程被杀），文件就是半截。另外，目标路径如果是符号链接，`fs::write` 会顺着链接写进它指向的文件。

## Decision

**计划分三类，写回先写临时文件再改名，中途失败时逐个文件报告，再撤销一次能接着做完。**

### 计划分三类

`planned` 对每个文件先比当前内容和目标内容：

1. 当前内容已经等于目标（包括目标是"不存在"、文件也已经不在）：记进新列表 `TurnPlan.inPlace`，不写，不算跳过；
2. 否则当前内容等于预期（这一轮留下的样子）：照旧写回或删除；
3. 都不是：照旧跳过，写"这一轮之后又改过"。

单轮撤销、多轮撤销（`undoFrom`）、撤回撤销都走同一个 `planned`，[多轮撤销](../feature/2026-11-05-batch-undo-stale-conclusions.md) 自动用上同一套分类。

一批里先改后改回、首尾内容相同的文件，原来会计划一次空写，现在归到 `inPlace`。

### 写回：临时文件加改名

`write_back` 的普通文件分支改为：

1. 在同一目录写 `.<文件名>.aeroric-undo-<uuid>`，写完 `sync_all`；
2. 设置权限：
   - 原文件是普通文件时，沿用它的权限位；
   - 原文件不在时，用新建文件的默认权限；
   - 再按快照里的模式（`100755` 与否）加上或去掉可执行位，和原来一样；
3. `rename` 到目标路径。

失败时删掉临时文件。目标是符号链接时，`rename` 换掉的是链接本身，不再写进链接指向的文件。快照里本身是符号链接的分支（`120000`）和删除分支不变。

### 中途失败

- `apply` 把计划里的文件全部试一遍，失败的不再中断后面的。写不进去的放进新列表 `TurnPlan.failed`（路径和原因）；`files` 只列真正写好的。
- 有失败时：
  - 回合状态不变（仍是待验收或已接受），`undoGroup` 等字段也不动；
  - 已经写好的文件仍然要告诉 Agent。宿主照常在下一条消息前加提醒，提醒里写明"其中这些没能恢复"。
- 用户再撤销一次：已经写好的文件归到 `inPlace`，只写剩下的，写完后回合记为已撤销。
- 计划里只有 `inPlace`、没有要写的文件时，也可以确认：不写文件，只把回合记为已撤销（或撤回）。
- 提醒 Agent 的文件名单是 `files` 加 `inPlace`。这样续做的那一次也会把上一次已经写好的文件一并说出来。

### App

- 协议 `LiveTurnPlan` 加 `inPlace`、`failed`。
- 撤销确认框加一段"已是撤销后的样子"（撤回时写"已是这一轮的结果"），图标是对勾。
- 确认按钮在 `files` 或 `inPlace` 不为空时可点。只有 `inPlace` 时，底部说明"这些文件已经是撤销后的样子，确认后只把这一轮记为已撤销"。
- `applyTurn` 收到带 `failed` 的结果时不算成功，错误条写"撤销没做完：N 个文件写不进去（<第一个路径>：<原因>）。已改好的 M 个文件保持现在的样子，再撤销一次会接着做完。"（撤回时写"撤回撤销"）。"重做"和重跑页的"先撤销原来那一轮再带回"都走 `applyTurn`，没做完时同样停下。

### 和批次笔记的出入

- 批次笔记说"回合状态记为部分撤销"。没有加新状态，有失败时回合保持原来的状态。原因有两个：
  - `TurnState` 被轮次账本、改动成本、结论过时、代码版本链、回合结果、重跑和 App 的徽标共同读取，加一个状态，每一处都要决定它算哪边；
  - 有了 `inPlace`，再撤销一次就能接着做完，不需要单独的中间状态来记住做到哪了。
  
  做到一半的情况由这次撤销的结果和错误条如实说出来，也告诉了 Agent。

## Alternatives considered

**加 `TurnState::PartlyUndone`。** 最强的理由是：状态本身就说明了做到一半，不靠一次性的错误条。没选：每一处读状态的代码都要决定它算"撤销"还是"未撤销"，而用户需要做的只有一件事，就是再撤销一次。结果里已经逐个文件写明了。

**写回失败时，把已经写好的文件回滚到原样。** 最强的理由是全有或全无，回合状态始终是真的。没选：回滚本身也会失败（同一个目录不可写、磁盘满），那时状态更乱。改名保证的是"每个文件要么旧要么新"，失败后续做比回滚更可靠。

**在 `rename` 之前先备份原文件。** 最强的理由是万一改名后发现不对，还能找回。没选：快照里本来就有这一轮前后的内容，撤回撤销就是找回；多一份备份只会在工作区里留下多余的文件。

## Consequences

- **收益**：
  - 手动改回去的文件不再被报成冲突；
  - 撤销中途失败后，再点一次就能做完；
  - 写回被打断时，文件要么是旧内容要么是新内容；
  - 符号链接不再被写穿。
- **代价**：
  - 中途失败时，回合状态不说明"做了一半"，要看错误条和 Agent 收到的提醒。
  - 临时文件在进程被杀时可能留在原目录里，文件名以 `.` 开头并带 `aeroric-undo`。
  - 改名会换掉文件的 inode：已经打开这个文件的编辑器要重新读才能看到新内容。硬链接到别处的同一个文件不再跟着变。
- **验证**：
  - core `turn_ledger_tests`（临时仓库）：
    - `files_put_back_by_hand_are_in_place_not_skipped`：手动改回的文件归到 `inPlace`、不在跳过里；全部改回后照样能确认，回合记为已撤销，提醒里有文件名。
    - `a_batch_file_changed_back_within_it_is_in_place`：多轮撤销里先改后改回的文件归到 `inPlace`。
    - `a_write_back_keeps_the_mode_and_does_not_write_through_a_symlink`：写回保留 0640；原位置是符号链接时换掉链接、链接指向的文件不变；不留临时文件。
    - `a_half_done_undo_is_reported_and_finished_by_trying_again`：目录设成只读，其中一个写不进去。另一个照常写好；结果的 `failed` 写明路径和原因；写不进去的文件仍是旧内容；回合仍是待验收；提醒写"没能改"。恢复权限后再撤销一次：写好的归 `inPlace`，剩下的写完，没有跳过项，回合记为已撤销。以 root 运行时目录权限拦不住，这个测试直接返回。
